# Fix plan — the audit findings of 2026-09-22

Written from the lawyer audit of commit `6792f0c256e81e1473908308bd73881004853be4` and the comparison
of the colleagues' business papers against the same tree. It is a **plan, not a backlog**: nothing is
filed as a ticket. The owner ruled on 2026-09-22 that the whole plan runs on **one branch with one
PR**, phases in order, one commit per item — so this document is the only index the work has.

## The rule this plan follows

**Only defects.** A finding earns a row here when the code is wrong, dead, or contradicts itself —
something a reader can check without asking anybody what the business wants. Everything that needs a
ruling is in [§ Blocked](#blocked--needs-a-ruling-before-any-code) with the decision that blocks it,
and is **not** planned, scoped or estimated. Two consequences worth stating plainly:

- The largest money finding — a crew of three paying three full pay rows against one flat price — is
  **deferred by the owner to R26** and is not in any phase. Fixing the package-pay defect (item 2.1)
  without it makes package jobs cost more, not less: the packages that were paying nothing start
  paying, per cleaner. That is the intended reading of "fix the defect, leave the model alone", and it
  is called out again in phase 2.
- The guest access key is **re-keyed, not redacted** (owner ruling). That makes phase 1 the largest
  piece of work in the plan, and the only phase that touches every tree at once.

## Phases at a glance

## Phase 1 — Guest access re-key

**Finding:** F69. An assigned cleaner is served the unredacted order detail, which carries
`DisplayOrderNumber`, `CustomerEmail` and `ConfirmationCode` — exactly the triple the anonymous
`POST /api/Order/CancelGuest` accepts. Cancelling that way charges the guest the 25 % / 50 % tier.

**Original shape (owner ruling; proposal history):** replace the triple with a one-time token the guest receives by e-mail. The
confirmation code stops being an access credential, which closes the class rather than one leak.

| # | Item | What changes |
|---|---|---|
| 1.1 | Guest access token | A token entity (order, hash, issued, expires, used), issued on order creation and on request; the anonymous endpoints take the token, not the code |
| 1.2 | Guest endpoints on both customer hosts | `LookupOrder`, `LookupOrderBatch`, `CancelGuest`, `GuestCancellationPreview` re-keyed; old parameters removed, not deprecated |
| 1.3 | E-mails | Order confirmation and cancellation e-mails carry the link; five locales; the code is no longer printed |
| 1.4 | Cleaner-facing redaction | `ConfirmationCode` leaves every cleaner-facing DTO and its redaction test asserts it |
| 1.5 | Clients | Customer web guest screens, both customer mobile apps, NSwag regeneration and the mobile spec re-dump |
| 1.6 | Schema | Migration regenerated (one `Initial`), DEV drop owed at the next DEV deploy |

**Shipped semantics:** the table above preserves the original proposal. The implemented token is a
reusable 256-bit credential, valid until expiry or revocation, expiring 30 days after the cleaning.
Each message issues an independent credential; issuance alone does not consume or revoke earlier
credentials. Only the hash is persisted; there is no used/consumed state. The short confirmation code
remains a display reference, never an access credential.

**Done:** a cleaner cannot produce a working guest cancellation from anything the API gives them; a
guest can still find and cancel their order from the e-mail; the integration suite covers both.

**Not in this phase:** expiring or re-issuing tokens from the customer app, guest order history,
attaching a guest order to an account later.

**Interaction to keep in view:** 2.1 makes package jobs pay. With R26 deferred, each assigned cleaner
gets a full pay row, so a three-cleaner package job pays three times the configured rate. That is the
existing model applied to a case that previously paid nothing — not a new defect, but it is money.

**Done:** every completed order produces exactly the pay rows the configuration describes; no Stripe
event we receive can 500; the revenue report reconciles with the refund ledger.

**Shipped (`799b2c635`):** 2.1, 2.2, 2.3, 2.4, 2.7 and the `order.confirmed` half of 2.6. **Struck with
evidence:** 2.5 — the headline and by-tender figures are gross on purpose (they reconcile against a
gateway statement; `NetRevenue`, the daily series and the service/package splits are net of both
refund legs); the `invoice.paid` half of 2.6 — renewals are already recorded by
`customer.subscription.updated`, and `invoice.paid` would be a second writer of the same fact.

**Found after phase 2, reported, not fixed:**

- **A chargeback on any web card booking is dropped.** The webhook finds the order only by its stored
  payment intent; `AssignStripePaymentIntentId` is called only by the mobile `CreatePaymentIntent`
  (`[Authorize]`) and `ConfirmRecurringOrder`, while web Checkout stores the session id alone. So a
  chargeback on a web booking, guest or account, answers 200, records no dispute and tells no
  administrator, and its `updated` / `closed` events find nothing. 2.3's fix is correct but guarded a
  state no guest can reach — `GuestChargebackWebhookTests` seeds a payment intent the guest flow never
  writes, and the `Dispute.cs` comment describes that path as live. Money; needs a go-ahead.
- `ResolveDispute` records the refund amount the administrator asked for, not the amount the refund
  seam moved (it clamps the card share and returns the credit share separately), and a retry re-drives
  the first attempt's row whatever amount it names.

## How a phase runs, when it runs

One branch (`fix/audit-findings-2026-09-22`) and one PR to `master` for this whole run, with locally
verified phase commits (owner ruling supersedes one branch per phase). Per phase:

- `dotnet test` on **all three** backend projects (`Cleansia.Tests`, `Cleansia.IntegrationTests`,
  `Cleansia.HostTests`) — one at a time, not in parallel.
- A schema change means the single `Initial` migration is regenerated and the DEV drop is owed at the
  next DEV deploy, not at regen time.
- A DTO or endpoint change means NSwag regeneration **before** the frontend work, committed in the
  same change, and a mobile spec re-dump when a mobile host is touched.
- iOS work is batched so it compiles in one sitting on the Mac.
- `docs/` is updated at the end of the phase, once it is green — not alongside the code.
- CI is **not** a gate between phases (owner, 2026-09-22): each phase is verified locally, committed, and
  the next one starts; CI is read once at the end and anything red is fixed in one pass.
