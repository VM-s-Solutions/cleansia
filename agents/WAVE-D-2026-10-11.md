# Wave D — new-jobs digest and stale-checkout sweep, 2026-10-10–11

Wave D removes two per-row database round trips the 2026-10-07 audit found in background jobs (B005, B006). No API, DTO, schema, index, migration or business rule changed. Ticket: [T-0808](backlog/tickets/T-0808-wave-d-digest-and-checkout.md).

## What changed

- **B005: the new-jobs digest** (`NewJobsDigestService`). Before, it asked the database "does this cleaner already have an overlapping commitment?" once for every candidate job that passed the radius test.
  - Now it reads each cleaner's live commitments once, over the span of all their surviving candidates (`IOrderRepository.GetOverlappedCandidateIdsIgnoringTenantAsync`). Each candidate is then judged in memory by the pure `Order.OccupiesWindow`, the shape ADR-0039 D3.3 names.
  - A cleaner with no surviving candidate costs no commitment read.
  - A real-PostgreSQL agreement test pins the batch against the single-window method on identical rows. It covers every status, touching edges, the floor edge, a malformed long row, and other cleaners' and other companies' rows.
- **B006: the stale-checkout sweep** (`CleanupStalePendingOrders`). Before, it resolved each cancelled order's recipient company with its own read. Now each tenant group notifies first through `INotificationProducer.NotifyEachAsync`: one read of all the group's distinct recipients' companies, then each notification recorded exactly as `NotifyAsync` records it.
  - The account, never an order or operator hint, decides the company.
  - An absent recipient, or one with no company, still logs and is skipped.
  - Feed collapse, push keys and outbox dedup are unchanged.

B006's second cause, bounded pages, is **not built**. Under one commit per tenant, with no per-page commit, no `Tracker.Clear` and no new transaction, paging would only add reads. T-0808 records the three options that would really bound the run.

## Measured outcome

**Method.** Each run:
1. drops and re-creates the disposable `CleansiaAuditJobs` clone;
2. restores the untouched audit fixture (100,000 orders, 500 cleaners, synthetic users);
3. applies the job's own seed: 10 cleaners and 100 future jobs for the digest, or 1,000 one-off stale card checkouts for cleanup;
4. runs one cohort's job harness (Release, providers blocked, queue recorded only).

There are five runs per cohort, interleaved in ABBA pairs. **Before** is master `5f94129`; the digest and cleanup code there is identical to `64dfed7`. **After** is the D code at `026bf52`. Median, and p90 by nearest rank; with n = 5, p90 is the largest run.

- **Digest.** The 660 per-candidate `SELECT EXISTS` probes are replaced by 10 batch reads, one per cleaner. The other 64 statements are unchanged.
- **Cleanup.** The 1,000 per-order recipient reads are replaced by 3, one per company group (800 / 150 / 50 orders).
- **Outcomes.** Order counts by status, outbox rows, feed rows and stamped cleaners are identical within and across cohorts, and there were 0 provider attempts.

### Limits

- **Environment.** One Apple M4 Mac, with PostgreSQL in Docker on loopback. The load average was about 3–4, not idle. Absolute times are local: on Azure each removed round trip costs more, so they do not predict production.
- **Peak working set.** It reads 0 on macOS, so no memory-peak claim is made.
- **Digest batch reads.** On this fixture they return no rows; nothing is committed inside any candidate window. The optimizer review separately ran `EXPLAIN (ANALYZE, BUFFERS)` of the batch statement on a wide band of the audit copy (14,746 live orders in a 67-day band) and found no plan risk.
- **Cleanup coverage.** Only the zero-credit 1,000-order sweep is measured. The unit and PostgreSQL suites cover the rest:
  - positive credit;
  - idempotency;
  - a failed recipient read before any credit returns;
  - guests;
  - outbox;
  - recurring orders.
- **Cleanup memory.** The cleanup still tracks every order of the run; allocation falls by only about 7 %. That is B006 cause 2, deliberately not built.
