# ADR-0034 — Challenge, db/schema lane (D1, D5, D7 + the index/query-filter question)

**Mode:** challenger. **Gate 0:** REFUTED-by-default — every claim below cites a file:line I opened, or
a computation I ran (script preserved at `scratchpad/verify.py` / `verify2.py`). No migration command was
run; no git operation was performed; the ADR was not edited.

**Headline:** the shape decision (D1) survives on its merits but its cost column is missing its two
largest entries, and both land on the exact gate D7 exists to protect. D5's IBAN composition — the thing
the author flagged as weakest — **verifies clean**; the thing next to it in the same table does not. D7 is
designed for a legacy population the repository says does not exist yet, and its central mitigation
("bi-weekly") is contradicted by the running code.

Nine findings. **CH-D1, CH-D2, CH-D4, CH-D8 and CH-D9 I consider blocking.**

### CH-D1 — The child entity converts an income gate from a data condition into a *query-shape* condition, and the one gate that matters loads `Employee` from a hand-maintained `.Include` list

**The hole.** D7 changes `Employee.cs:283` from `!string.IsNullOrEmpty(IBAN)` to `PayoutDetails is not
null`. A reference navigation that was not `Include`d is `null` — indistinguishable, in that expression,
from "this cleaner has no payout details". The ADR never states an `Include` obligation anywhere.

**Why it matters.** The job-board gate is `RequireCompleteProfileAttribute.cs:32-35`:

```csharp
var isRegistrationComplete =
    employee.IsProfileComplete() &&
    employee.Documents.Any(d => d.IsActive) && ...
```

and the employee it evaluates comes from `EmployeeRepository.GetByUserEmailAsync`
(`EmployeeRepository.cs:9-17`), whose include list is written out by hand:

```csharp
.Include(e => e.User).Include(e => e.Address).Include(e => e.Nationality).Include(e => e.Documents)
```

Miss `PayoutDetails` there and **every cleaner gets a 403 on every gated endpoint** —
`RequireCompleteProfileAttribute.cs:37-49`. That is precisely the migration-day outage F2 identifies and
D7 is built to prevent, re-introduced by D1's shape through a forgotten line in a repository. It fails
*silently* (no exception, no log), it fails *uniformly* (all cleaners at once), and it is invisible to
the ADR's own reviewer check #6, which "constructs an employee whose payout record has `Status =
NeedsReconfirmation`" — a hand-built aggregate has the nav set, so the test passes green while production
locks the workforce out.

The same nav-null hazard hits `EmployeeMappers.cs:89` and `:129` (`IsProfileComplete:
IsEmployeeProfileComplete(employee)`, `:143`) — the paged admin employee list and the admin detail view
would report every cleaner as incomplete. There are 5 distinct `Include` chains in `EmployeeRepository`
alone.

**A1 is structurally immune to this.** A scalar column on the loaded `Employee` row is always
materialized. This is a real point *for* the loser that the D1 vs A1 comparison does not contain — the
alternatives table lists A1's three failings and none of D1's. I am not saying A1 wins; I am saying D1's
"it protects the migration" claim is, in this one respect, backwards, and the ADR cannot be adjudicated
without that on the record.

**What I want changed.**
1. D1 states the `Include` obligation as a binding rule, and names `EmployeeRepository.GetByUserEmailAsync`
   (`:9-17`) and `GdprDeletionService.cs:44` as the two sites that must carry it (see CH-D9).
2. Better — remove the hazard rather than document it: the completeness gate reads a **non-null scalar on
   `Employee`** (`PayoutDetailsStatus`, or `HasPayoutDetails`), maintained by the same write path, so the
   gate can never depend on query shape. This keeps every D1 benefit (discriminator, read contract,
   lifecycle fields live on the child) and costs one denormalized column. It is also the only version of
   D7's "no cleaner loses job-board access" that is enforceable.
3. Reviewer check #6 is rewritten to load the employee **through `GetByUserEmailAsync`** and assert the
   gate returns 200 — a test that would catch a missing `Include`. As written it cannot.

### CH-D2 — The unique index does not enforce cardinality one in the deployment mode that is actually live. `(TenantId, EmployeeId)` is unenforced when `TenantId` is null, which today is *every row*

**The hole.** D1 makes the unique index *the* cardinality decision ("cardinality is enforced in the
schema, not in code" — reviewer check #2). `TenantId` is **nullable**:

`EntityConfiguration.cs:27-29`
```csharp
builder.Property(e => e.TenantId).HasMaxLength(26).IsRequired(false);
```

PostgreSQL treats NULLs as distinct in a unique index by default. This is not my reading — it is the
installed provider's own documentation, `Npgsql.EntityFrameworkCore.PostgreSQL 10.0.0`
(`.../lib/net10.0/Npgsql.EntityFrameworkCore.PostgreSQL.xml:11657-11661`):

> "Specifies whether for a unique index, null values should be considered distinct (not equal). **The
> default is that they are distinct, so that a unique index could contain multiple null values in a
> column.**"

So `(NULL, 'emp_1')` and `(NULL, 'emp_1')` both insert. And every row today has `TenantId = null`:
CLAUDE.md ("Backward compatible: `null` TenantId = single-tenant mode") and the code's own comment at
`PayPeriodBackgroundService.cs:74-75` — *"Today the system is single-tenant in practice (TenantId
null)"*. The single constraint the whole D1 argument leans on is a no-op in the only mode that runs.

**Corroborating: the "house archetype" does not have this shape.** D1 says "the house archetype — see
`EmployeePayConfig`". Its actual unique index carries **no** `TenantId`
(`EmployeePayConfigEntityConfiguration.cs:82-84`):

```csharp
builder.HasIndex(e => new { e.EmployeeId, e.ServiceId, e.PackageId })
    .IsUnique()
    .HasFilter("\"EmployeeId\" IS NOT NULL");
```

I checked all ~40 `.IsUnique()` sites under `src/Cleansia.Infra.Database/EntityConfigurations/`: **not one
includes `TenantId`.** S8's "unique indexes are `(TenantId, X)`" has never been exercised in this
repository. `(TenantId, EmployeeId)` would be the first — and it would be the first while being wrong.

**What I want changed.** Make the index `UNIQUE (EmployeeId)`, single-column, with one comment saying
why: an `EmployeeId` is a ULID, globally unique, and an employee belongs to exactly one tenant, so the
tenant is pinned transitively through the FK — putting the nullable `TenantId` in the key adds nothing and
actively destroys the constraint. If the panel prefers to keep `TenantId` in the key for S8 optics, then
it **must** carry `.AreNullsDistinct(false)` (the API exists on the installed provider,
`NpgsqlIndexBuilderExtensions.AreNullsDistinct(IndexBuilder, bool)`, and PG16 supports `NULLS NOT
DISTINCT`) — but that is a novel construct in this repo for zero benefit over the single-column form.
Either way, reviewer check #2 is false as currently written and must be restated.

### CH-D3 — Soft-delete and the unique index are one decision, and the ADR takes neither half

**The hole.** `EmployeePayoutDetails : Auditable` inherits `IsActive` (`BaseEntity.cs:7`) and
`Deactivated(by, on)` which sets `IsActive = false` (`Auditable.cs:35-39`). ADR-0007 D1 makes
`Deactivate` the default for anything user-facing, referenced, or history-bearing — a payout record is all
three, emphatically. ADR-0034 never says whether payout details are mutated in place or superseded.

**Why it matters — two coupled consequences, both live:**

(a) **A soft-deleted payout record still satisfies the completeness gate.** D7's rule is `PayoutDetails is
not null` with no `IsActive` predicate. There is no global `IsActive` filter — confirmed by reading
`CleansiaDbContext.ApplyTenantQueryFilters` (`:201-270`), which builds a filter over `ITenantEntity`
only; ADR-0007 D2 and S10 (`security-rules.md:215-222`) make the per-read `Where(e => e.IsActive)`
mandatory. A deactivated record also keeps `Status = Provided`, so the D7 issuance block (`Status !=
Provided`) does not catch it either. Both gates pass on a deleted record.

(b) **If the write path ever supersedes rather than mutates** — the natural, audit-preserving choice for a
financial identifier, and the one ADR-0007 D1 pushes you toward — the unique index blocks the insert of
the replacement. Add `.HasFilter("\"IsActive\"")` to fix that and you have *created* problem (a) at scale
(N deactivated rows, any of which satisfies `is not null`). They are one decision.

The repo has partial-index precedent both times (`EmployeePayConfigEntityConfiguration.cs:84`;
`EmployeeInvoiceEntityConfiguration.cs:117-119`) but **neither filters on `IsActive`** — so there is no
house answer to copy and the ADR must supply one. (`CompanyInfoEntityConfiguration.cs:38` —
`HasIndex(RegistrationNumber).IsUnique()`, no tenant, no `IsActive` filter — is a live instance of exactly
this trap sitting in the table D1 cites as the A1 precedent.)

**What I want changed.** D1 states explicitly, in one sentence, which it is:
- **Mutate in place** → say the entity is exempt from ADR-0007 D1's `Deactivate` default and why (the
  record *is* the current destination; history belongs in the audit log, not in tombstone rows). Then the
  unfiltered unique index is correct and the gate needs no `IsActive`. This is my recommendation.
- **Supersede by insert** → the unique index carries `HasFilter("\"IsActive\"")` **and** the completeness
  gate **and** the issuance block both gain `.Where(x => x.IsActive)`, in the same ticket.

Silence here ships (a).

### CH-D4 — D4's mod-11 rule is stated backwards. Implemented literally it rejects the owner's own bank account, and 91.4% of valid CZ accounts

**The hole.** D4's check table says: *"prefix and number each pass the weighted modulo-11 check (weights
6,3,7,9,10,5,8,4,2,1 **applied right-to-left**; weighted sum mod 11 must be 0)"*.

The **vector** is right. The **direction** is wrong, and the ADR's honesty note (AC15) tells T-0519 to
verify *the weights*, not the direction — so this survives the flag that was supposed to catch it.

**Computed, not read** (`scratchpad/verify.py`, `verify2.py`):

| Account | Canonical (vector left-to-right over the zero-padded field) | ADR text taken literally (right-to-left) |
|---|---|---|
| `5885638003` — **the owner's own specimen**, `5885638003/5500` | **0** (valid) | **1** → **REJECTED** |
| `2000145399` — the F1 example `19-2000145399/0800` | **0** (valid) | 7 → REJECTED |

Over 18,135 genuinely-valid 10-digit account numbers, the literal right-to-left reading rejects **16,570
— 91.4%**. The vector is `2^k mod 11` read right-to-left (`[1,2,4,8,5,10,9,7,3,6]`), i.e. the ADR's list
is that sequence *reversed*, which is a left-to-right vector. Applying a left-to-right vector
right-to-left is applying it to reversed digits, which is not the same function.

**Second defect in the same sentence.** "prefix and number **each**" pass the check — but one 10-long
vector is given, and a 6-digit prefix needs the **last** six weights (`10,5,8,4,2,1`), not the first six.
Using the first six is wrong for ~13% of prefixes (129,869 mismatches against canonical over the sampled
range). There *is* a clean uniform rule and the ADR should state it: **zero-pad the field to 10 digits and
apply the 10-vector left-to-right** — 0 mismatches against canonical for both the prefix and the account.

**Why it matters here rather than in T-0519.** This ADR text will be pasted into a validator comment as
the cited rule (reviewer check #4 requires exactly that: "the CZ/SK weight vector carries a cited primary
source in a code comment"). A wrong instruction with a citation attached is worse than no instruction. And
D4 "fails closed" — so the failure mode of this specific error is *rejecting* nine out of ten real Czech
bank accounts at the write path, on a field that gates income.

**What I want changed.** D4's wording becomes: *zero-pad each of prefix and account number to 10 digits;
apply weights 6,3,7,9,10,5,8,4,2,1 left-to-right; the weighted sum mod 11 must be 0.* AC15's test-vector
table names the owner's specimen `5885638003` as a required known-good. T-0519's verification duty stays.

### CH-D5 — The IBAN composition read **holds** (I verified it). But "leading zeros are significant" is false, contradicts the derivation, and silently defeats the duplicate-account check D6 promises

**First, the part the author flagged as weakest survives.** I composed it rather than reading about it:

| Input | Derived IBAN | Length | mod-97 |
|---|---|---|---|
| `5885638003/5500` (owner's specimen, no prefix) | `CZ3155000000005885638003` | 24 | **valid** |
| `19-2000145399/0800` (the F1 prefix case) | `CZ6508000000192000145399` | 24 | **valid** |

`CC` + 2 check + bank(4) + prefix(6, zero-padded) + account(10, zero-padded) = 24 is correct, including the
prefix case. **D5's derivation and D7's class-1 decomposition are structurally sound, the two-field CZ form
works, and the "no cleaner action needed" consequence stands.** The fallback does not need to become the
primary. That is the answer to the panel's question #2 — say so in the Defense.

**Now the hole, which is in the row above.** D5 says `AccountPrefix` — *"**Leading zeros are
significant** — store as text, never as a number"*, and the same for `AccountNumber`. That is false, and
it contradicts the very derivation I just verified:

```
compose('5500', '', '123456')      = CZ2455000000000000123456
compose('5500', '', '0000123456')  = CZ2455000000000000123456   ← identical
compose('5500', '',  '5885638003') = CZ3155000000005885638003
compose('5500', '0', '5885638003') = CZ3155000000005885638003   ← identical
```

The IBAN is *the* international identifier of the account and it cannot distinguish them, so they are not
distinguishable accounts. Leading zeros are **not** identity.

**Three consequences the ADR gets wrong as a result:**
1. D7 class 1 calls the decomposition "deterministic and **lossless**". It is deterministic and
   *canonicalizing* — it cannot recover how many leading zeros the cleaner typed. Harmless, but the word
   is wrong in a table that a migration author will implement literally.
2. **D6's fraud check breaks.** D6 argues against encryption partly because *"'two employees sharing one
   account number' is a real fraud signal we may want to check"* — a check that needs equality. Store the
   typed parts and `123456` vs `0000123456` compare unequal while naming one account. The check silently
   under-reports, which is the worst kind of fraud control.
3. Any uniqueness/duplicate constraint placed on the raw parts is wrong for the same reason.

**What I want changed.** Replace "leading zeros are significant" with the accurate rule: **store the
zero-padded canonical form (prefix `char(6)`, account `char(10)`), and make the derived IBAN the
comparison key** — every duplicate/fraud/equality check compares the IBAN, never the typed parts. Keeping
these as text rather than integers is still correct (they are digit strings, not quantities); only the
stated *reason* is wrong, and the wrong reason produces a wrong equality.

### CH-D6 — D7's entire legacy apparatus is designed for a population the repository says does not exist yet, and the ADR asks "how many in each class" without first asking "is there a class at all"

**The hole.** D7's four-class classifier, the `LegacyRawValue` column, the reconfirmation campaign, the
withheld-invoice rule and the deliberate `"profile.fields.iban"` naming mismatch are **all** justified by a
population of pre-existing `Employee.IBAN` values. The evidence that such a population exists at launch is
never presented.

**What the repository actually says:**
- The migration set contains **exactly one** migration:
  `src/Cleansia.Infra.Database/Migrations/20260723182623_Initial.cs` (plus its Designer and the snapshot).
  Nothing else. Its most recent history entry is `1685b7ae chore(db): owner-regenerated Initial migration
  + snapshot` — the project's pre-prod practice is to **regenerate** `Initial`, not stack onto it.
- `deploy/` carries `AZURE-DEV-RUNBOOK.md` and `AZURE-PROD-POSTURE.md`. Prod is authored, not deployed.
  The only live database is DEV.
- `sql-scripts/insert_seed_data.sql` seeds **no** `Employee."IBAN"` at all — the only `Iban` in the entire
  seed file is `CompanyInfo`'s (`insert_seed_data.sql:1019`). So the "legacy population" is whatever the
  owner typed by hand while testing against DEV.

The ADR's Gate-0.5 note concedes the column was never inspected and defers to T-0518's dry-run for the
class **counts**. That is the second question. The first is *does this data survive to launch* — and it is
not a dry-run question, it is an owner question, because it decides **whether a column exists in the
schema at all**.

**Why it matters.** If the launch database has no legacy `Employee.IBAN` rows (or DEV data is discarded),
the correct migration is "create the table" — no classifier, no `LegacyRawValue` shipping into the
operational schema, no campaign, no withheld invoices, and CH-D7/CH-D8 below both evaporate. The ADR
currently commits the schema to carrying a migration artifact on the strength of an unasked question.

**What I want changed.** D7 opens with an explicit precondition and branches:
- **If** the launch DB carries no legacy `Employee.IBAN` values → D7 collapses to "create the table";
  `LegacyRawValue` never ships; the classifier is not built.
- **Else** → the four-class classifier as written (with CH-D7's relocation).

And the precondition goes to `questions/open.md` for the owner *before* T-0518 starts — not to T-0518's
dry-run, which runs after the schema is designed.

### CH-D7 — `LegacyRawValue` does not belong in the operational table, and "a follow-up ticket drops it" is not a closing condition

**The hole.** D7 concedes the shape of the objection ("an unbounded escape-hatch column would be a smell;
a scheduled one is a plan") but the schedule has no trigger. The column is dropped "once the
reconfirmation campaign closes"; the campaign closes when the last class-3 cleaner reconfirms; a cleaner
who stops working never reconfirms. The drop date is unbounded in practice — which is the smell, restated.

**Why the location matters more than the schedule.** By the ADR's own words the column is *"write-once by
the backfill script, never written by application code."* A column that application code must never write
should not live on the entity application code writes. Sitting on `EmployeePayoutDetails` it is:
- in every `SELECT` EF generates for the entity (EF names all columns — there is no opting out);
- in the audit JSON that reviewer check #10 now obliges `EmployeeUserAuditCoverageTests` to police;
- in the GDPR export surface that D6 §"Out of scope" hands to T-0509;
- **the one field on the record with no scheme, no validator, and no masking rule** — while holding, per
  F1, mangled raw PII (`1920001453990800`) in a table whose entire D8 contract is "never on a list DTO,
  masked by default". D8's masking list does not mention it.

**What I want changed.** Park it **outside** the operational table: a `payout_legacy_import` staging
table, written by the owner-run backfill script, keyed by `EmployeeId`, with **no `DbSet<T>`, no entity
configuration, and no `OnModelCreating` registration** — plain SQL, read by exactly one dedicated query
that builds the reconfirmation prompt. Then dropping it is `DROP TABLE` with zero blast radius on the
entity, the DTO surface, the audit-coverage test, and the GDPR export — and the "escape hatch with a
promised drop date" becomes an import artifact with no operational reach, which is a materially different
object. If the panel keeps it on the entity, D7 must state a **hard calendar drop date** (not an event)
and add the field to D8's masking rule.

(Given CH-D6, the cheapest resolution to this finding may be that the column is never needed.)

### CH-D8 — The "bi-weekly window" mitigation is contradicted by the running code (it is monthly), nobody tells the cleaner, and the withheld invoice becomes a permanent fiscal-reconciliation candidate

Three separate defects in one paragraph of D7.

**(1) The cadence claim is false.** D7: *"Pay periods are bi-weekly, so the reconfirmation prompt has a
window measured in days, not hours."* The running cadence is **monthly**:

- `PayPeriodBackgroundService.cs:89-90` — bootstrap: `endDate = startDate.AddMonths(1).AddDays(-1)`.
- `PayPeriodBackgroundService.cs:161-162` — rollover: `newEndDate = newStartDate.AddMonths(1).AddDays(-1)`.
- The code says so itself at `:85-88`: *"Pick a **monthly** window anchored on today. Matches the cadence
  the close-and-rollover job uses."*
- `PayPeriodService.GenerateBiWeeklyPeriodsForYear` (`PayPeriodService.cs:30`) has **zero call sites**
  anywhere in `src/` — as does `GenerateSemiMonthlyPeriodsForYear` (`:52`). "Bi-weekly" is a dormant
  helper and a row in CLAUDE.md's entity table, not the system's behaviour.

So the grievance the panel asked me to test is roughly **twice** as bad as the ADR priced it: up to ~31
days without the tax document, not ~14.

**(2) Nobody tells them, and the code actively sends a misleading email.** Invoices are generated inside
`SendPeriodClosedEmailsAsync` (`PayPeriodBackgroundService.cs:196-293`). When generation yields nothing,
the period-closed email is sent **anyway**, with a null attachment (`:229-238`, `:259-269`). Under D7 a
payout-blocked cleaner receives *"your pay period closed"* with no invoice and no explanation, because
that email path has no notion of a payout block. D7's own challenge list asks "who tells them"; the answer
in the current code is *no one*, and the carrier already exists
(`_emailService.SendPeriodClosedEmailAsync`, `:259`).

**(3) Reversibility holds — but it becomes an unbounded retry loop.** Credit where due: D7's "deferring
issuance is reversible" is **true**. `GenerateInvoice.Command(EmployeeId, PayPeriodId)`
(`GenerateInvoice.cs:15-16`) stays valid indefinitely because the pays keep `EmployeeInvoiceId == null`
(`OrderEmployeePayRepository.cs:46-49`), so re-running it after reconfirmation issues the invoice
correctly. I checked this specifically and it defends the decision.

But the retry is not idle. `FiscalReconciliationService.ReconcileInvoicesAsync` (`:125-165`) re-enqueues
`GenerateInvoice` for every `(period, employee)` pair with stale pays and **no** `EmployeeInvoice` row —
the candidate predicate is at `PayPeriodRepository.cs:87-94`:

```csharp
where pay.PayPeriod!.CreatedOn <= cutoff
    && !existingInvoices.Any(inv => inv.PayPeriodId == pay.PayPeriodId && inv.EmployeeId == pay.EmployeeId)
```

A payout-blocked employee matches that **forever**. Every sweep tick re-enqueues a message the new D7 rule
refuses, logging per tick per blocked cleaner. D7 converts a business hold into a permanent backlog item
in the one sweep that exists to detect genuine fiscal loss (ADR-0002 D3.4) — and a real loss will be
buried in the noise.

**What I want changed.**
1. Correct the cadence claim to monthly; it changes the size of the grievance materially and it is the
   only quantitative support the mitigation has.
2. D7 names the notification explicitly and routes it through the existing period-closed email, which must
   learn the payout-blocked reason. "The prompt appears in the app" is not sufficient for a document the
   cleaner needs for tax.
3. The block must be **visible to the reconciliation sweep** — a payout-blocked pair is excluded from
   candidacy (or recorded as a terminal, admin-visible state) rather than re-enqueued indefinitely.
   Otherwise T-0522 ships a log flood into the fiscal reconciliation path.

### CH-D9 — `Employee.Anonymize()` cannot clear a child record, and the GDPR path does not load one. Today's guaranteed erasure becomes a silent no-op

**The hole.** D8 §5 and T-0518 AC6 assert *"`Employee.Anonymize()` clears the whole payout record"*.

`Employee.Anonymize()` (`Employee.cs:257-267`) sets `IBAN = AnonymizationMarker.Value`. That works today
**because `IBAN` is a column on the row already loaded**. Its only production caller is
`GdprDeletionService.cs:235`, and the aggregate is loaded at `GdprDeletionService.cs:44`:

```csharp
.Include(u => u.Employee).ThenInclude(e => e!.Address)
```

No payout include. Move the value to a child table and the erasure **silently no-ops** — no exception, no
log, and the cleaner's bank account survives a GDPR erasure request. Same failure class as CH-D1, on the
path where the failure is a compliance violation rather than a bug. Note the surrounding code already
knows this pattern is fragile: `Dispute.Anonymize()` (`Dispute.cs:152-162`) walks child collections and
therefore depends on them being loaded.

**Secondary, worth one line in D7.** After `Anonymize()`, `IsProfileComplete()` is currently **true** —
`RegistrationNumber`/`IBAN`/`PassportId` all hold `"[DELETED]"`, which is non-empty
(`AnonymizationMarker`). Under D7 class 0 (no payout record created) it flips to **false**. Harmless
because `GdprDeletionService.cs:237` also deactivates the employee — but it is an unstated behaviour change
in the gate D7 is otherwise so careful about, and `GetMissingProfileFields()` output changes for
anonymized rows.

**What I want changed.** The payout record is cleared by an **explicit repository call inside
`GdprDeletionService`**, not by a navigation walk inside `Employee.Anonymize()` — so it cannot silently
no-op when an `Include` is missing. If the panel prefers the nav walk, then `GdprDeletionService.cs:44`
gains the include in the same ticket, and reviewer check #10's audit-coverage test must exercise
**`GdprDeletionService`'s real query**, not a constructed aggregate — otherwise it green-lights the no-op.

## What I checked and found sound

Named explicitly, because silence is not assent (`process/deliberation.md:22-24`).

- **D5's CZ/SK IBAN composition — verified by computation, not read.** `CC` + 2 check + bank(4) +
  prefix(6, zero-padded) + account(10, zero-padded) = 24, ISO 7064 mod-97-10 check digits. Both the
  owner's no-prefix specimen and the F1 prefixed case compose to valid 24-char IBANs. **The derivation
  stands, the two-field CZ capture form stands, and D7 class-1 decomposition stands.** The author's own
  worry #2 — "should the fallback become the primary?" — is answered **no**. Only the leading-zero note
  beside it is wrong (CH-D5).
- **D1's read-contract argument (ii) is factually grounded.** `EmployeeListItem.cs:52` and
  `EmployeeItem.cs:27` both carry `string? Iban` — a payout identifier really does ride a paged list DTO
  today. Of the three legs D1 stands on, this one is real and A1 genuinely cannot fix it structurally.
- **A5's "zero owned types" claim is true.** No `OwnsOne`/`OwnsMany`/`ComplexProperty` anywhere in
  `src/Cleansia.Infra.Database`. Declining to introduce the pattern here is well-judged.
- **D1's `Auditable, ITenantEntity` archetype is correct** — `EmployeePayConfig`, `EmployeeInvoice`,
  `PayPeriod`, `OrderEmployeePay` all follow it, and `AuditableEntityConfiguration`
  (`EntityConfiguration.cs:20-51`) supplies `TenantId` + the audit columns + `HasIndex(TenantId)`
  automatically. Only the *unique index* shape is not the archetype (CH-D2).
- **The A1-vs-`CompanyInfo` dismissal is fair.** `CompanyInfo.cs:60-70` really is a singleton describing
  one company (`CompanyInfoEntityConfiguration.cs:38-43` — unique `RegistrationNumber`, `CountryId`
  lookup index), with no per-employee cardinality question and no discriminator need. It is not the
  precedent it looks like, exactly as D1 says.
- **S10 / ADR-0007's "no global `IsActive` filter" is accurate.**
  `CleansiaDbContext.ApplyTenantQueryFilters` (`:201-270`) builds a filter over `ITenantEntity` only —
  tenancy, nothing else. The ADR is right that the `IsActive` obligation is per-read; it just does not
  discharge it (CH-D3).
- **D7's "deferring issuance is reversible" is true** — verified against `GenerateInvoice.cs:15-16` and
