Role: CHALLENGER. Gate 0 discipline — every claim below is cited to code I read in the tree at
`master` (`da88b695` is HEAD-adjacent), not to the ADR's description of it. Where a claim of the
ADR's held, it is named in the final section rather than left silent.

Nine findings. Three are blocking (**CH-P2**, **CH-P5**, **CH-P6**). One is a defect in shipped code
(**CH-P3**). One is a free correction that makes the ADR's own detection query survive production

### CH-P1 — CH-2: the drain-window arithmetic is wrong on **both** sides. The rejection survives (the outbox window is ~4× larger than stated), but the "milliseconds" baseline the comparison rests on is not achieved by the in-process seam either, and the ~10s number has already been written into the catalog as a general claim about the outbox

**The outbox side: understated, so the rejection is stronger than argued.**
`OutboxDrainerFunction.cs:14` is `[TimerTrigger("*/10 * * * * *")]` — confirmed, 10s. But that is one
leg of three. The drainer does not perform the work; it puts the body on a **queue**
(`OutboxDrainerService.cs:62` → `queueClient.SendAsync`). The consumer is a queue-triggered Function,
and `src/Cleansia.Functions/host.json:19` sets `"maxPollingInterval": "00:00:30"` with
`"newBatchThreshold": 0` and `"batchSize": 1`. On an idle queue — the normal state — the listener has
backed off to that 30s ceiling. Worst-case end-to-end is therefore **~10s + ~30s + handler ≈ 40s**,
typical maybe 15–25s, not 10s. §D1.1's number is a lower bound presented as the bound.

**The in-process side: overstated, and this is the half that matters.** §D1.2 and §Consequences claim
the end state narrows the window "from the whole request to **milliseconds**". That measures
commit→effect. The window that governs the exploit is **preview-read → redemption-row-committed**,
because the per-user gate the attacker beats is the preview count at `PromoCodeService.cs:47-53`, read
at `CreateOrder.cs:280`. In the end state the redemption row commits *after* the UoW commit, i.e. at
the very end of the same request — and that request contains `OrderPaymentDispatcher.DispatchAsync`
minting a Stripe Checkout Session on the Web+Card path, an external HTTP round trip. So the in-process
window is **one request duration** (hundreds of ms to seconds), not milliseconds. Two browser tabs
submitted half a second apart both read zero priors under the end state too.

**Net:** the outbox rejection **stands** — ~40s vs ~0.5s is still ~2 orders of magnitude and still
converts "needs concurrency tooling" into "needs a stopwatch". The exploit does *not* need more than a
browser: I traced it, and it yields extra **discounts**, not extra ledger rows (the reservation
statement still refuses in the consumer at `PromoCodeRedemptionRepository`'s `HAVING`, and the global
counter stays consistent because the compensating decrement releases the slot). So CH-2's substance is
right. But §D1.1 should be corrected to "~40s worst case, against a window of one request duration",
and "~4 orders of magnitude" struck — it is ~2.

**This is not confined to the ADR.** `agents/knowledge/patterns-backend.md:550` now states, as the
catalog's description of the outbox seam generally: *"Durable, at-least-once, **~10s**."* That is
wrong for every external effect on the platform, not just promo, and it is the number a future author
will quote when deciding whether an email/push/fiscal effect is "fast enough". Fix it in the same
hunk.

### CH-P2 — **BLOCKING.** The "the interim loses nothing in the live deployment" justification is verified on the axis the ADR tabulated and **false on an axis it did not**: the interim disarms the order-level idempotency guard in NULL-tenant mode, where the failure it converts to is exactly the rolled-back-order 500 the ADR says only happens under a non-null tenant

**First, the ADR's claim is independently correct on its own terms.** I verified all three legs:

- The index is nulls-distinct. `20260723182623_Initial.cs:3059-3063` creates
  `IX_PromoCodeRedemptions_TenantId_PromoCodeId_UserId_SlotOrdinal` with `unique: true` and **no**
  `Npgsql:NullsDistinct` annotation. The two indexes that *do* carry it are at `:2653` and `:2685`
  (`.Annotation("Npgsql:NullsDistinct", false)`), matching
  `FiscalCounterEntityConfiguration.cs:28` and `LiveActivityTokenConfiguration.cs:28`. The emitted
  DDL, not the C#, confirms it.
- Single-tenant mode is `TenantId == null`: `CleansiaDbContext.cs:229-246` (the `currentTenantId ==
  null && e.TenantId == null` clause) and `:89-92` (stamping `TenantId = currentTenantId`).
- Independently corroborated by a *different* author, before this ADR:
  `LoyaltyTransactionEntityConfiguration.cs:79-88` documents the identical trade-off and names
  `PromoCodeRedemption (TenantId, …)` explicitly as one of the indexes that already makes it.

So the concurrent-double-redeem row of §D3's table is right, and A4/CH-3 are correctly disposed **for
the case tabulated**.

**Second, the table is incomplete, and the missing row is a regression in the live deployment.** The
interim's pre-read runs against the **database**: `PromoCodeRedemptionRepository.cs:43-46`
(`GetDbSet().Where(...).MaxAsync(...)`). So do the two guards upstream of it —
`GetByOrderIdAsync` (`:16-20`) and `CountForUserAndCodeAsync` (`:10-14`). A change-tracked `Added`
entity is **not** returned by an EF LINQ query; it lives only in the change tracker until
`CommitAsync`. Under the old raw statement the row was durable the instant it was reserved
(`git show da88b695^:…/PromoCodeRedemptionRepository.cs` — `SqlQueryRaw`, auto-committing). Under the
interim it is not durable until the pipeline commits, which happens **after the handler returns**
(`UnitOfWorkPipelineBehavior.cs:20-30`).

Consequence: a **second** `ApplyAsync` for the same order **within one request** now:
- misses the idempotency short-circuit at `PromoCodeService.cs:90-94` (the DB has no row yet), and
- adds a second tracked `PromoCodeRedemption` with the same `OrderId`, which at commit violates
  `IX_PromoCodeRedemptions_OrderId` — created `unique: true` at `Initial.cs:3044-3047` on a **NOT
  NULL** column, so **nulls-distinct does not save it**. That is a `DbUpdateException` inside
  `UnitOfWorkPipelineBehavior`: the whole paid order rolls back, 500.

Under the old statement the same second call hit `ON CONFLICT DO NOTHING` (no conflict target ⇒ all
unique constraints, including `OrderId`) → zero rows → a clean `null`.

**Why this is not academic.** `PromoCodeService.cs:87-89` states the guard's own threat model in
prose: *"Protects against double-fire (e.g. handler retry, race between Preview-then-Apply paths)."*
The interim silently removed that protection and the comment now overclaims — an ADR-0032 D3 coverage
failure sitting in the shipped diff. It is latent only because `CreateOrder.cs:315` happens to call
`ApplyAsync` exactly once today. §D2.2 **law 2** for the end state is stated as *"idempotent on a
natural key … backed by the UNIQUE index on `PromoCodeRedemptions.OrderId` and the `GetByOrderIdAsync`
short-circuit"* — that law is **not currently true**, and the end state must restore it, not assume
it.

**What I want changed:** §D3's table gains a fourth row (same-request double-fire: clean `null` →
rolled-back order, **in NULL-tenant mode too**), and §D3's headline sentence — *"in the deployment
that is live, the interim loses nothing on the per-user cap"* — is narrowed to the concurrent
cross-request case it actually covers. The "loses nothing" framing is the sentence that authorized
shipping; it must be accurate.

### CH-P3 — the compensating `finally` fires on every non-success of the reservation *call* (verified), but it can **replace the in-flight exception**, and it will do so in precisely the scenario §D6 leak 3 was written for

I read `PromoCodeService.cs:145-193` and enumerated every exit after the auto-committing increment at
`:151`:

| path | compensated? |
|---|---|
| `TryReserveRedemptionSlotAsync` returns `null` (cap) | yes — `finally` `:173-181` |
| it throws | yes — same `finally`; `redemption` is still `null` |
| anything between `:151` and the `try` at `:168` | nothing exists there — verified line by line |
| reservation succeeds, pipeline commit later fails | **no** — named as leak 2, accepted residual |

`CancellationToken.None` at `:179` is correct and is a real second fix (pre-fix used the caller's
token: `git show da88b695^` `:171`). Pinned by
`PromoCodeServiceRedeemTests.cs:167-183`, which asserts both `Assert.Same(transient, thrown)` and
`Times.Once` on the decrement. Good test.

**The defect:** `await` inside a `finally` while an exception is in flight. If
`DecrementGlobalRedemptionsAsync` throws, **its** exception propagates and the original is destroyed.
`DecrementGlobalRedemptionsAsync` (`PromoCodeRepository.cs:50-64`) runs `ExecuteUpdateAsync` on the
**same** `CleansiaDbContext` / connection that the reservation just failed on. §D6's own trigger for
leak 3 is *"transient DB error, timeout"* — i.e. the compensation is guaranteed to fail in the exact
case it exists for, and when it does the operator sees the decrement's exception instead of the
timeout/`23503`, and the slot leaks anyway. No test covers "the decrement itself throws".

**The tension this creates, which the ADR must resolve rather than leave to the implementer.** The
one-line fix is `try { await Decrement } catch (Exception ex) { log } ` inside the `finally` — which
puts a `catch` on the path where the ADR's reviewer check #1 says the grep must find exactly one
specific catch. Note that check is **already stale**: it says *"the only admissible catch is §D6's
compensating one, inside `PromoCodeService.ApplyAsync`"*, and the shipped code has **zero** `catch` in
that file (the commit message and `patterns-backend.md:592-596` both say `try`/`finally` was chosen
deliberately). Reviewer check #1 and §D6's "the required catch here compensates and then surfaces"
describe code that does not exist. Rewrite both to the `finally` shape, and state explicitly whether a
`catch` **around the compensation itself** (log-only, never rethrow, so the original failure survives)
is admissible. My read: it is — it is post-nothing, it hides nothing from the caller, and its absence
loses the diagnostic — but that is the author's call to record, not the implementer's to guess.

### CH-P4 — the trigger gate on `order.PromoCodeId` is **correct today** and rests on a single ternary that **no test pins**; the ADR's own reviewer check #3 asks for an assertion that does not exist at any level

I verified the iff in both directions:

- `PromoCodeId` set ⇒ promo priced the order: `OrderFactory.cs:95`
  `appliedPromoCodeId = resolution.PromoAmount > 0m ? input.PromoCodeId : null`, and `:94` gates
  `appliedPromoDiscount` on the same predicate. The promo-wins branch (`:208-215`) zeroes membership
  and tier, so the two sources cannot both be non-zero.
- Promo priced the order ⇒ `PromoCodeId` set: needs `input.PromoCodeId` non-null whenever
  `input.PromoDiscountAmount > 0`. Both come from one `OrderPromoPreview` (`CreateOrder.cs:298-299`);
  `OrderPromoPreview.None` is `(0m, null)` (`IOrderPromoApplier.cs:43`) and the success path always
  carries a non-null id (`PromoCodeService.cs:71`). The only other `CreateOrderInput` construction in
  the tree, `MaterializeRecurringBookings.cs:136-137`, passes `PromoDiscountAmount: 0m, PromoCodeId:
  null`.

So the gate at `OrderPromoApplier.cs:46-52` is right, and replacing the `preview` parameter with
`rawSubtotal` outright (rather than merely asking callers not to read it) is the strongest part of the
shipped change — the applier can no longer reach the preview.

**The gap.** That invariant lives on `OrderFactory.cs:95` and nothing asserts it.
`CombinedDiscountCapTests` (6 facts) contains **zero** occurrences of `PromoCodeId`.
`OrderPromoApplierTests.Apply_OrderPricedByMembershipNotPromo_DoesNotCallService` (`:107-120`)
hand-builds an order with `promoCodeId: null` via `OrderMockFactory` — it asserts the *applier's*
gate, not that `OrderFactory` produces such an order. ADR reviewer check #3 demands *"membership+tier
beats promo → order persisted with `PromoDiscountAmount == null` → **zero** `PromoCodeRedemptions`
rows"*; that end-to-end assertion exists nowhere.

The refactor that reopens the defect is natural and would be green: stamping `input.PromoCodeId`
unconditionally on the order because "the order should record the code the customer typed." Per
ADR-0032 D3 the enforcer must cover the sentence — add one fact pinning
`ResolveLoy003Discount(membership > promo) ⇒ order.PromoCodeId is null`, next to
`CombinedDiscountCapTests`. It is cheap and it is where the invariant actually lives.

Same shape on reviewer check #4: the express-subtotal correctness is asserted only against a **Moq'd**
`IPromoCodeService` (`OrderPromoApplierTests.cs:174-193`). The §D8(2) real-PostgreSQL evidence
(`CreateOrderPromoRedemptionPersistenceTests.cs:51-101`) is a single fact on a non-express date
(`:114`, `UtcNow.AddDays(3)`), Mobile channel (`:129-130`, so no Stripe), NULL tenant, `SlotOrdinal ==
0`. That satisfies §D8(2) as written; it does not satisfy checks #3 or #4. Narrow the checks or widen
the tests — ADR-0032 D3, and this ADR is the one that will be quoted at future reviewers.

### CH-P5 — **BLOCKING.** CH-6: yes, ADR-0032 gates the seam — and it gates **more than law 1**. "Follow-up, not claimed as done" is not an available disposition here

ADR-0032 is `accepted` (2026-08-01). Its D2: **T1-CI is required when — and only when — both hold:**
(1) the rule is mechanically expressible on that stack, and (2) its baseline is zero. Both hold for
law 1:

1. **Mechanically expressible, in an idiom that already exists.**
   `SendPushNotificationSeamTripwireTests.cs:29-54` is the exact shape: walk `Cleansia.*` production
   project dirs (`:56-66`), exclude test projects (`:21-27`), match a construction marker (`:12`),
   diff against an allow-list, and — critically — assert the allow-list entries are *present* so the
   pin cannot hollow out (`:52-53`). Substituting "a type implementing `IPostCommitEffectExecutor<>`
   whose file references `IQueueClient` / `HttpClient` / `Stripe`" is the same file-walk.
2. **The tier is T1-CI on this stack.** `Cleansia.Tests` runs in CI:
   `.github/workflows/backend-ci.yml:71`. (Contrast `check-consistency.mjs`, which I re-verified
   appears in **zero** files under `.github/` — ADR-0032 §Context item 3 found the same on
   2026-08-01.)
3. **Baseline is zero by construction** — there are no `IPostCommitEffectExecutor` implementations,
   and the first one (the promo reservation) touches no external service. There is no cleanup to land
   behind.

Because (2) of ADR-0032's test is *satisfied*, the `(gate pending: <ticket>)` escape is **unavailable**
— that tier exists precisely for a **non-zero** baseline (`enforcement.md:104-106`). So §D4's *"added
to §D4's enforcement item as a follow-up rather than claimed as done"* and
`roles/post-commit-effects.md:57-58`'s *"see ADR-0038 CH-6 (open)"* are not dispositions ADR-0032
permits. **Ruling: the tripwire lands in the PR that lands the seam.** It is one file in an existing
shape, in a project already in CI — cheaper than the paragraph arguing about it.

**Two things the author's framing of CH-6 misses, both larger than CH-6 as filed:**

- **ADR-0032 D2 binds all five laws, not just law 1**, and it binds the catalog entries themselves.
  Every entry that constrains code other people write carries, inline,
  `**Enforced by:** <named enforcer> — <tier token>`. **None** of ADR-0038's three catalog edits does:
  `patterns-backend.md:526-599` (two entries), `consistency.md:298-332` (two rules),
  `roles/post-commit-effects.md:26-36` (the five laws). Each is a finding under ADR-0032 reviewer
  check #2. The `PROPOSED` banners do not exempt them — ADR-0032 is accepted and applies to the hunk
  as written.
- **ADR-0032 D1: T3-HUMAN requires a *named standing checklist item*.** ADR-0038's own "How a reviewer
  verifies compliance" #8 and #12 are per-PR checks for *this* change. Laws 2, 3 and 5 constrain
  **every future effect**, forever, and an ADR's compliance list is not a standing gate over future
  PRs. Either they get a named `quality-gates.md` / numbered-reviewer-check item, or they are
  `(guidance — no gate)` and should say so. Law 3 in particular ("a tracked `Add` inside an effect is
  a silent no-op") is named in the ADR's own §Consequences as *the first misuse to expect* — a
  no-gate law on the predicted failure mode is the worst of both.

**Anti-vacuity (ADR-0032 D3), for whoever writes the tripwire:** a test asserting "no `IQueueClient`
in any executor" over an **empty** executor set passes forever, including after someone renames the
interface. It must assert at least one known executor is found, in the shape of
`SendPushNotificationSeamTripwireTests.cs:52-53`.

### CH-P6 — **BLOCKING.** The retirement trigger retires nothing: the check does not exist, would not be a gate if it did, its stated pattern **does not match the marker actually shipped**, and its predicate is satisfied by a ticket that is forbidden to start

Four independent failures, each fatal on its own.

1. **The check does not exist.** `grep -n INTERIM agents/tools/check-consistency.mjs` → zero hits.
   `consistency.md:330-332` says *"Filed as a small tooling ticket by ADR-0038"* — **no ticket id**.
   ADR-0032's `(gate pending: <ticket>)` tier requires a *real, resolvable* id, and its own
   §Consequences names the failure mode: *"a ticket named and never scheduled leaves a law permanently
   unenforced while reading as enforced-soon."* This one is not even named.

2. **Even written, it is not a gate.** `check-consistency` appears in **zero** files under `.github/`
   (re-verified this pass). Under ADR-0032 D1 that is **T2-ADVISORY** — reviewer-run, never sets an
   exit code. A T2-ADVISORY orphan-check on a code comment is, precisely, *a comment with a ticket
   number in it.*

3. **The stated pattern does not match the marker.** `consistency.md:331` and ADR-0038 §D4.2 both
   specify the rule as: *every `INTERIM(ADR-NNNN → T-xxxx)` marker in `src/`*. The template three
   lines above at `consistency.md:321` — and the marker actually shipped at
   `PromoCodeRedemptionRepository.cs:22` — is `INTERIM(ADR-0038 **§D3** → T-0532)`, with a `§Dn`
   segment between the ADR id and the arrow. A checker implemented from the rule's own stated pattern
   matches **zero** markers in the tree and reports OK. This is the ADR-0032 D3 vacuity failure baked
   into the spec *before* anyone implements it. Fix the pattern in both places to make `§Dn` explicit
   and optional.

4. **The predicate is satisfied by a blocked ticket.** The rule is "present and **open** in
   `INDEX.md`". `INDEX.md:31` carries T-0532 at status **draft** with
   🔴 *"AC0 — ADR-0038 is `proposed` with 3 OPEN challenges. Do NOT start until a second instance signs
   the Verdict"*. So the check goes green while the retirement work is explicitly forbidden — and it
   is forbidden by this panel. The trigger is circular: the interim is retired by a ticket blocked on
   the ADR that authorized the interim. "Present and open" must be "present, open, **and not
   blocked**", or the marker is load-bearing on nothing.

**What would actually retire it, in the shape this repo already uses:** an xUnit tripwire in
`Cleansia.Tests` — **T1-CI** via `backend-ci.yml:71` — asserting that the set of files in `src/`
containing `INTERIM(ADR-0038` is exactly `{Cleansia.Infra.Database/Repositories/PromoCodeRedemptionRepository.cs}`,
with the anti-vacuity present-assert. It fails the day a second ADR-0038 interim appears and it fails
the day the file moves, and it is deleted by the end-state PR as part of deleting the marker. That is
a gate. A `.mjs` rule in no workflow is a note.

### CH-P7 — CH-7: **no persisted marker, no migration** — but the "exact **iff**" §D6.3 rests on is *already false in production*, and the fix is free and strictly better than a column

**Answer to CH-7 as filed: refuse the column.** Three reasons, in order of weight:

1. **The populations are already separable without one.** The refusal path logs the specific error:
   `OrderPromoApplier.cs:67-70` writes `Error={applyResult.Error}`, and `PromoCodeError` distinguishes
   `PerUserLimitReached` / `GlobalLimitReached` / `Expired` / `BelowMinimumOrderAmount` /
   `CurrencyMismatch`. A lost effect produces no such line (or an Error-level executor line under the
   end state). §D6.3's concession that "they are distinguished by the log line" is not a weakness —
   the log line carries strictly *more* information than a boolean column would.
2. **The support scenario named in the challenge is answered before the ledger.** "My code didn't
   work" is overwhelmingly *the code never priced the order* — visible on the order itself as
   `PromoDiscountAmount IS NULL`, no new state required. The residual case ("it priced the order and
   the ledger row is missing") is a fail-soft the customer **benefited** from; there is nothing to
   explain to them.
3. **The column would need its own self-committing write.** It would be set on the *refusal* path,
   which under §D2.2 law 3 runs post-commit where a tracked `Add` is a silent no-op. So the marker
   would need a second self-committing statement in the same window that can lose the redemption —
   another thing that can fail, to record that something failed. On an outage fix, with an owner-only
   migration. Refuse.

**But the challenge surfaced a real defect next to it, and it is free to fix.** §D6.3 claims the query
is exact *"because of §D5.1: `Order.PromoCodeId` is non-null **iff** a promo actually priced the
order."* That iff **decays in production**: `Order.AnonymizeCustomerData()` (`Order.cs:615-628`) sets
`PromoCodeId = null` at `:621` and **leaves `PromoDiscountAmount` intact**. It is not hypothetical —
it is called live by `DataRetentionBackgroundService.cs:161` and `GdprDeletionService.cs:190`. So over
the retention horizon, orders that *were* priced by a promo drop out of the recon predicate entirely
(a false negative, not noise — the query stays clean, it just goes blind).

Two consequences, both cheap:

- **Change the predicate.** Gate on `o."PromoDiscountAmount" IS NOT NULL AND o."PromoDiscountAmount" >
  0` instead of (or in addition to) `PromoCodeId IS NOT NULL`. The amount survives anonymization, the
  redemption row survives anonymization, and the join key is `OrderId` which is untouched — so the
  amended predicate is anonymization-stable *and* still exact.
- **Invert the §Consequences line.** It currently reads *"Any future discount source must persist its
  applied amount on the order or it is undetectable."* Given the anonymizer, the correct statement is
  the opposite of what the ADR implies elsewhere: the **amount** is the durable detection key and the
  **source id** is not. Say that, or the next discount source will be gated on its id and go blind the
  same way.

### CH-P8 — §D2.1's own interface sketch hands the executor the exact input for the recompute §D5.1 forbids

```csharp
public sealed record PromoRedemptionEffect(
    string OrderId, string PromoCodeId, string UserId, decimal AppliedDiscount, decimal RawSubtotal)
```

§D5.1's end-state rule is *"record the frozen amount, stop recomputing … the ledger row must carry
`order.PromoDiscountAmount` verbatim."* `RawSubtotal` is the **only** input `ComputeDiscount`
(`PromoCodeService.cs:143`, `:217-230`) needs. Carrying it on the intent record makes the forbidden
recompute a one-liner in the executor, and the implementing ticket will copy this sketch verbatim
because the ADR told it to. Drop `RawSubtotal`; if `AppliedDiscount` is `order.PromoDiscountAmount`,
name the parameter so.

**And the ADR is silent on what that costs.** Removing `orderSubtotal` from the apply path also
removes the post-preview re-validation of `MinimumOrderAmount` (`PromoCodeService.cs:130-133`) and
`CurrencyMismatch` (`:135-141`), both of which re-run today against the subtotal. Under the end state
they either re-run against the frozen order or are dropped. §D5.1 does not say which. That is a
decision the seam ticket will otherwise make by accident.

### CH-P9 — the §D2.2 laws and the ADR's Consequences both assume `PostCommitEffectBehavior` sees only committed work; the registration slot the ADR specifies makes that true, and the ordering guarantee it depends on is presently pinned by a comment plus one test whose name I could not resolve

Verified the ordering premise: `FluentValidationExtensions.cs:33-37` registers
`AuditFailureCapture → PostCommitDispatch → Validation → UnitOfWork → AuditLog`, and `:32` states *"A
re-swap that breaks this order is caught by the pipeline-order unit test (verify #4)."* The predicate
the ADR wants reused is real: `UnitOfWorkPipelineBehavior.cs:27` gates on
`response is BusinessResult { IsSuccess: true }`. So §D2.1's registration slot (between
`PostCommitDispatchBehavior` and `ValidationPipelineBehavior`) does give effects-first / dispatch-second
with the commit already done. No objection to the placement.

The obligation the ADR states — *"the pipeline-order unit test must be extended in the same PR"* — is
correct and I flag only that it is stated in prose in §D2.1 and **not** in the "How a reviewer
verifies compliance" list as a *blocking* item (check #7 mentions it, but as an "end state only"
item alongside registration, not as the thing that keeps ADR-0002 D4 alive). Given `:28-32` calls a
re-swap "a blocking finding", make check #7 say the test **fails** if the new behavior is absent from
its expected sequence, not merely that it "asserts it". A pipeline-order test that enumerates a
prefix rather than the full ordered set silently tolerates an inserted behavior — the same vacuity
class as CH-P5's tripwire.

## What I checked and found sound

Named explicitly, per `deliberation.md` — silence is not assent.

  outlives an aborted request.
- **The `finally` covers every exit of the reservation call.** Line-by-line over
  `PromoCodeService.cs:151-186`: nothing between the increment and the `try`. My objection (CH-P3) is
  about the compensation *itself* throwing, not about a missed path.
- **A7 / the "`IPendingDispatch` cannot carry this" claim is correct.**
  `OutboxPendingDispatch.cs:42` — `public IReadOnlyList<PendingMessage> Drain() => [];`. An in-process

- **The trigger-predicate gate is correct in both directions today** (evidence in CH-P4). Replacing

- **A2's rejection is correct on the mechanism.** A `DEFERRABLE INITIALLY DEFERRED` FK is checked at

- **§D7's severity argument holds.** `CreateOrder.cs:305-310` returns on dispatch failure before
