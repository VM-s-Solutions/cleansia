# ADR-0039 — Challenger report, **query-cost lane** (read path + scan floor)

Role: challenger (optimizer). Gate 0 posture: every claim below is REFUTED-by-default and carries
`file:line` from code I read in this session. I did **not** query DEV, did not run `EXPLAIN`, did not
touch git, and did not edit the ADR. Where I am reasoning about a PostgreSQL plan rather than
measuring one, I say so in the finding itself.

Ranked by impact: CH-Q2 and CH-Q3 are the two that cost money or correctness at scale; CH-Q1 is the
ADR's headline claim and is unproven; CH-Q5 is where the real cycles actually are.

### CH-Q1 — "**No new index**" is asserted, and the predicate's own NULL-fallback disjunct is the thing that breaks it. The ADR never mentions the leading index column.

**What I verified.** The index is real and is exactly what the ADR says it is:
`builder.HasIndex(o => new { o.CurrentStatus, o.CleaningDateTime });` —
`src/Cleansia.Infra.Database/EntityConfigurations/OrderEntityConfiguration.cs:111`, emitted as
`IX_Orders_CurrentStatus_CleaningDateTime` over `new[] { "CurrentStatus", "CleaningDateTime" }` at
`src/Cleansia.Infra.Database/Migrations/20260723182623_Initial.cs:2910-2913`. Not partial, not
filtered, not covering. **Leading key column = `CurrentStatus`.**

**The hole.** D3's implementation shape does *not* contain a bare `CurrentStatus = ANY(...)`. It
contains a **disjunction** whose second arm carries a correlated subquery:

```
((o.CurrentStatus != null && SlotBlockingStatuses.Contains(o.CurrentStatus.Value))
 || (o.CurrentStatus == null && o.OrderStatusHistory.OrderByDescending(...).Take(1).Any(...)))
```

Once the status term sits inside an `OR`, it is not an unconditional index qual. The only
unconditional sargable conjunct left is a **range on `CleaningDateTime` — the *second* key column.**
PostgreSQL 16 btree cannot begin a scan on the second key column with the first unconstrained; index
skip scan did not land until PG 18. So the "status set + narrow date band lands together on the
existing index" story requires the planner to decompose the OR into a `BitmapOr` of two index paths
(`CurrentStatus = ANY(arr) AND band` ∪ `CurrentStatus IS NULL AND band`) and re-check the `EXISTS`
on the bitmap heap scan. That is *plausible*; it is not guaranteed; and it is nowhere in the ADR.
If the planner declines, the fallback is a full index scan or a seq scan on `Orders` — and the D3.1
floor buys nothing at all, because the floor only helps if the band is an index **start key**.

**This is reasoning, not measurement — and so is the ADR's.** The difference is that the ADR states
its conclusion as fact ("*which already exists and is already the board query's index: a status-set +
narrow-date-band range scan… **No new index.**" D3; repeated in Consequences and in Alternative A14)
while never naming the plan it depends on, never naming the leading column, and never noticing that
its own fail-closed NULL branch is what makes the leading column non-equality.

Two things I checked that *reduce* the risk and should be recorded rather than left as unknowns:
- The tenant global filter is a second top-level OR (`providerNull || (currentTenantId == null &&
  e.TenantId == null) || e.TenantId == currentTenantId`, `CleansiaDbContext.cs:262-264`), but all
  three of its operands except `e.TenantId` fold to compile-time constants/parameters, and EF Core
  keys its SQL cache on parameter nullability — so it collapses to a single `=` or `IS NULL`. It is
  **not** an additional planner hazard. Say so.
- The tenant filter is the **only** global query filter in the context (`CleansiaDbContext.cs:126` is
  the sole `ApplyTenantQueryFilters` call; no `HasQueryFilter` anywhere). So `IgnoreQueryFilters()`
  on the sibling method is narrow and safe.

**Required.** One of:
1. **Measure it** — see CH-Q6; the harness already exists and this is the ADR's headline cost claim; or
2. **Restructure so no planner cleverness is needed.** Emit the two arms as a `UNION` /
   `Concat` — `(CurrentStatus = ANY(arr) AND band)` ∪ `(CurrentStatus IS NULL AND band AND EXISTS(...))`.
   Both arms are then sargable on `(CurrentStatus, CleaningDateTime)` **by construction**, the second
   arm is empty on any database created from the single `Initial` migration, and "no new index" stops
   being a hope; or
3. **Delete the NULL branch at the source.** `Orders.CurrentStatus` is nullable *only* to serve "rows
   written before the backfill" (`OrderEntityConfiguration.cs:98-105`; `Order.cs:264-269` is the
   in-memory twin). This repo carries **one** migration. If the owner confirms zero NULL rows in
   DEV/PROD, `CurrentStatus` becomes `NOT NULL`, the disjunct disappears, the correlated `EXISTS`
   disappears, `HasOverlappingOrderStatusTests`' two legacy cases become dead, and the index claim
   becomes trivially true — for **every** consumer of this column, not just this feature.

Option 3 is the cheapest-by-design outcome in the whole ADR and it is not in the alternatives table.

### CH-Q2 — `MaxOrderSpanHours = 24` is **not** an invariant "by construction". With the *shipped seed catalog* and zero admin action, one booking can reach **58.25 hours** — 2.4× the floor. By the ADR's own asymmetry table, that is a double booking on the `TakeOrder` write gate.

**Verified: the constant does not exist yet.** I read `BookingPolicy.cs` in full (162 lines,
`src/Cleansia.Core.AppServices/Features/Orders/BookingPolicy.cs`). There is no `MaxOrderSpanHours`.
The ADR proposes it. Fine.

**Verified: the derivation is as the ADR says.**
`OrderFactory.cs:145-146` —
`estimatedTime = selectedServices.Sum(s => s.Service!.EstimatedTime) + selectedPackages.Sum(p => p.Package!.IncludedServices.Sum(s => s.Service!.EstimatedTime))`
— written once at `OrderFactory.cs:147` via `Order.UpdateEstimatedTime` (`Order.cs:434-437`). I
grepped every `UpdateEstimatedTime` call site: `OrderFactory.cs:147` is the **only** production
writer; the other four are tests. The ADR's single-writer claim holds.

**The hole is what bounds that sum. Nothing does.**

| Input | Upper bound in code | Evidence |
|---|---|---|
| `Service.EstimatedTime` | **none** — `GreaterThanOrEqualTo(0)` only | `CreateService.cs:56-58`, `UpdateService.cs:61` |
| services per order | **none** — existence + non-empty only | `CreateOrder.cs:113-115` (`ExistWithIdsAsync`), `:123` (`OrderMustNotBeEmpty`); same shape at `QuoteOrder.cs:74-80` |
| packages per order | **none** | `CreateOrder.cs:117-119` |
| package ∩ service overlap | **not deduplicated** — a service inside a selected package is summed *again* if also selected directly | `OrderFactory.cs:145-146` |

**And this is not theoretical, it is the shipped seed data.** From `sql-scripts/insert_seed_data.sql`
(services block from `-- 7. SERVICES`, package composition from the `PackageServices` insert), I
summed the catalog:

- 10 seeded services: `120, 180, 45, 90, 60, 90, 75, 240, 180, 135` → **1215 min = 20.25 h**
  (that is **84% of the proposed floor** from services alone, admin does nothing)
- 8 seeded packages (`Essential Clean` 165 … `Post-Renovation Clean` 420, `Luxury Full Service` 405)
  → **2280 min** more
- **All services + all packages in one booking: 3495 min = 58.25 h.** Nothing rejects it.
- A *realistic* misuse — all 10 services + the single `Post-Renovation Clean` package — is
  **1635 min = 27.25 h**, already past the floor.
- Three packages, no services (`Post-Renovation` + `Luxury Full Service` + `Moving Day Special`) =
  **1185 min = 19.75 h**. That is a plausible customer sequence and it is at 82% of the floor.

D3.1 says: "*`EstimatedTime` is the sum of the booked services' estimates (`OrderFactory.cs:145-146`)
for a single appointment on a single day; **24 h exceeds any single-day span by construction**.*"
There is no construction. That sentence is an assumption about catalog *content*, asserted about
code, and the seed catalog it ships with already gets within 16% of it and can exceed it by 2.4×.

**And the ADR itself says what happens when the floor is too tight:** "*an overlapping order is
invisible → the picker says available → **and the same predicate is the `TakeOrder` write gate, so a
cleaner is double-booked**.*" D3.2 makes that literal: `HasOverlappingOrderAsync` becomes a wrapper,
so `TakeOrder.cs:59` → `:156` inherits the floor. **A safety-asymmetric constant with nothing
enforcing its safe side is not safety-asymmetric. It is a comment.**

**The proposed mitigation does not mitigate.** Verify #6 (`SELECT MAX("EstimatedTime") FROM "Orders"`,
"*a reviewer step rather than a belief*") is a **point-in-time observation of a value an admin can
change tomorrow through a shipped UI** (`UpdateService.cs`). It samples history; it does not bound the
future. Nor is the named flip condition ("`MAX(EstimatedTime)` approaching the floor") monitored by
anything — nobody runs that query on a schedule.

**Required — and it is genuinely cheap.** Enforce the floor rather than hope for it, at one of:
- `OrderFactory.cs:147` — reject (or fail-closed clamp + log) when
  `estimatedTime > BookingPolicy.MaxOrderSpanHours * 60`. One line, at the single writer, covers every
  path including `MaterializeRecurringBookings`; **preferred**, because it makes `MaxOrderSpanHours`
  true by construction, which is what D3.1 claims it already is; and/or
- `CreateService`/`UpdateService` — `.LessThanOrEqualTo(...)` on `EstimatedTime`; necessary but not
  sufficient (it does not bound the *count*).

Without one of these, D3.1's whole argument collapses and A15 (persist the end instant, index it) is
no longer "the right long-term answer" — it is the only safe one, and the ADR should say so.

### CH-Q3 — Verify #1 ("**no call inside a loop, anywhere**") is contradicted by the ADR's own D6/D10-A0, and the specified signature is structurally incapable of fixing the two loop-shaped callers.

`HasOverlappingOrderAsync` has exactly two production call sites (grepped whole of `src/`):
`TakeOrder.cs:156` and `NewJobsDigestService.cs:137`. The ADR names the second as
"`NewJobsDigestService` (`:137`)" — one line, one row in D6's table.

**What is actually at `:137`:**

```
foreach (var cleaner in cleaners)            // :86   — every approved/active employee, platform-wide
    …
    var newOrders = await newJobsQuery.Select(...).ToListAsync(ct);   // :120-122 — no Take, no paging
    foreach (var o in newOrders)             // :135
        var overlaps = await orderRepository.HasOverlappingOrderAsync(...);   // :137
```

A **nested** loop, and neither bound is bounded: `cleaners` at `:62-74` is every employee with
`ContractStatus` Approved/Active across all tenants with no paging; `newOrders` at `:120-122` is a
bare `ToListAsync()`. Round trips per sweep = Σ over cleaners of |newOrders(cleaner)| — and today each
of those round trips is an unbounded lifetime scan (CH-Q7). **This is the largest query-cost item
anywhere in this ADR's blast radius, and it is on a shipped timer.**

D10-A0 prescribes for it: "*Add the `IgnoringTenant` sibling, switch `NewJobsDigestService.cs:137`.*"
A tenancy variant swap. After A0 + A1 the nested loop is still there, now calling a two-line wrapper.
Then verify #1 tells the reviewer: "*`rg -n "HasOverlappingOrderAsync" src/ --type cs` — **no call
inside a loop, anywhere.***" **A reviewer executing the ADR's own verification step against the ADR's
own prescribed end state gets a hard reject.** As written, the ADR is internally inconsistent on the
property it leads with.

**The structural reason it cannot just be tightened.** The specified signature is
`(IReadOnlyCollection<string> employeeIds, DateTime windowStart, DateTime windowEnd)` — **many
employees, one window**. Two of the four callers in D6's own table are **one employee, many
windows**:
- `NewJobsDigestService.cs:135` — one cleaner, M candidate order windows;
- `MaterializeRecurringBookings.cs:119` — inner loop over occurrences, inside an outer loop over every
  active template platform-wide (`:68`), each occurrence creating an order and therefore (per D9)
  invoking the resolver's new busy check. Same shape.

`GetBusyEmployeeIdsInWindowAsync` collapses the N+1 for exactly **one** of its four callers.

**Required.** Either:
1. Restate verify #1 as "no call inside a loop **on a request path**", and state plainly in D10 that
   the digest's nested N+1 survives A0/A1 and is filed separately — honest, and unblocks; **or**
2. Give A1 the shape both loops need, which is cheaper than the ADR's and needs no new SQL idiom:
   for one cleaner, fetch their live commitments **once** over
   `[min(windowStarts) − MaxOrderSpanHours, max(windowEnds))` and intersect the M windows in memory.
   One bounded query per cleaner instead of one per (cleaner × candidate order). That single change is
   worth more than everything else in this ADR combined, and it lands on the same predicate.

Option 2 also means the digest stops being the reason a second (`IgnoringTenant`) variant of the
*singular* method has to exist at all.

### CH-Q4 — The tenancy fix is real and correctly diagnosed. My objection is narrow: A1 "absorbing" A0 can absorb the pin, and the ADR misses two facts that make the fix cheaper than it thinks.

**Defect 1 re-verified independently, and the ADR's mechanism is the mechanism.**
`BaseRepository.cs:158` — `protected DbSet<TEntity> GetDbSet() => Context.Set<TEntity>();`, so the
global filter applies; `BaseRepository.cs:148-150` `GetQueryable()` returns it unmodified;
`BaseRepository.cs:153-156` `GetQueryableIgnoringTenant()` adds `IgnoreQueryFilters()`. The filter
body is `providerNull || (currentTenantId == null && e.TenantId == null) || e.TenantId ==
currentTenantId` (`CleansiaDbContext.cs:262-264`, comment at `:251-261`). `NewJobsDigestService`
reads its cleaners at `:63` and its orders at `:98` with `GetQueryableIgnoringTenant()` — because the
timer has no claim — then calls the tenant-**scoped** `HasOverlappingOrderAsync` at `:137`. Under a
tenant: `currentTenantId` is null and `o.TenantId` is not → all three arms false → zero rows → every
cleaner reports free → the digest advertises double-booked jobs. **Confirmed exactly as stated.**

**Two things the ADR does not say that make this cheaper and should be in the record:**
- `OrderEmployee` is **not** an `ITenantEntity` — `public class OrderEmployee : BaseEntity`
  (`src/Cleansia.Core.Domain/Orders/OrderEmployee.cs`), and the `OrderEmployees` table has no
  `TenantId` column (`Initial.cs`, `OrderEmployees` create block: `Id, OrderId, EmployeeId,
  IsActive`). So `.IgnoreQueryFilters()` on the `Orders` DbSet covers the whole join; there is no
  second filter on the semi-join side to reason about.
- The tenant filter is the **only** global query filter (`CleansiaDbContext.cs:126`; no `HasQueryFilter`
  anywhere in the context). So `IgnoreQueryFilters()` is not silently un-filtering soft-deletes.

**The objection.** D10 says A1 "**Absorbs A0 if A0 has not shipped — do not do both by hand**". A0 is
where the *pin* lives ("*pin with a non-null `TenantId` fixture (`NewJobsDigestTenantWatermarkTests`
is the shape)*"). Absorption that carries the fix but not the fixture ships a security-touching
tenancy correction with no test, on a push path. **Make the non-null-`TenantId` fixture an explicit AC
on A1**, not a thing inherited by absorption.

Second, smaller: the ignoring variant is created with exactly one intended caller and **no
compile-time guard**. Nothing stops a future request-path handler from reaching for
`…IgnoringTenantAsync`; D6's rule is enforced only by verify #2, a human reading call sites. Given
that the ADR's own §D6 calls this "the shape, and it generalizes", consider an analyzer/architecture
test rather than a checklist line — otherwise the generalization is a wish.

### CH-Q5 — Call-site cost. The set-vs-N argument is **sound**. The ADR's own accounting is not: "one extra query per picker render" is **three**, and the pre-existing feed it sits beside costs ~40× the new query.

**First, the part I am not disputing.** Against A2 (call the singular method 20×), the ADR is right,
and it is right for both stated reasons. Each of those 20 calls is (a) tenant-broken under a tenant
and (b) unbounded below — `OrderRepository.cs:281-291`, where the only range term is
`o.CleaningDateTime < newEnd` (`:283`) and `o.CleaningDateTime.AddMinutes(o.EstimatedTime) > newStart`
(`:284`) is a per-row computed expression. One set call replacing 20 is the correct call.
`.Take(20)` at `GetMyServingCleaners.cs:50` does genuinely bound `employeeIds` to ≤20. Verified.

**Now the accounting.** Consequences says "*One extra bounded query on the create path … and one on
each picker render*". But D4 requires the **server** to derive `estimatedMinutes` from the selection,
and to sum `Service.EstimatedTime` the handler must *load* the services and the packages. The shape
is right there at `OrderFactory.cs:131-140`:

```
serviceRepository.GetByIds(...)                                       // round trip 1
packageRepository.GetByIds(...).Include(p => p.IncludedServices)
                               .ThenInclude(s => s.Service)           // round trip 2, two-level include
```

`GetMyServingCleaners.cs:32` is `AsSplitQuery()` → **2** round trips today. The picker render becomes
**5**. Not "one".

**And D4's justification for that load is inaccurate.** D4 says the handler "*loads the selection
through `IServiceRepository`/`IPackageRepository` **exactly as `QuoteOrder.Validator` already does**
(`:61-65`)*". `QuoteOrder.cs:74-80` calls `ExistWithIdsAsync`, which is `BaseRepository.cs:25-33` — a
`CountAsync`. It materializes **nothing**. The picker's new load is a strictly heavier shape than the
precedent cited to normalise it. Either cite the real precedent (`OrderFactory.cs:131-140`) or find a
cheaper derivation (a `Sum` projection over the two id sets is one round trip each and materializes
two integers, not two entity graphs).

**And the elephant, which the ADR flags but under-prices and mis-sequences.**
`GetMyServingCleaners.cs:26-33` loads **every completed order of the customer as a tracked entity
graph** and then does `GroupBy` (`:44`) and `.Take(20)` (`:50`) **in memory**. Concretely, per row:

| Table | Columns pulled | Columns actually used |
|---|---|---|
| `Orders` | **58** (incl. three unbounded `text` cols — `Notes`, `SpecialInstructions`, `AccessInstructions`; the latter two accept 2000 chars each per `CreateOrder.cs:132-138`) | 1 (`CleaningDateTime`) |
| `OrderEmployees` | 4 | 1 (`EmployeeId`) |
| `Employees` | **33** — including `IBAN`, `PassportId`, `RegistrationNumber`, `VatNumber`, `RejectionReason`, `ApprovalNotes` | 0 |
| `Users` | **32** | 2 (`FirstName`, `LastName`) |

(Column counts read from the `Orders` / `Employees` / `Users` create blocks in
`Migrations/20260723182623_Initial.cs`.) **127 columns pulled, 4 used.** And
`BaseRepository.cs:148-150` `GetQueryable()` has **no `AsNoTracking()`**, so all of it enters the
change tracker on a pure read path. And `Order.AssignedEmployees` (`Order.cs:272`) is
`_assignedEmployees.ToList().AsReadOnly()` — a fresh `List` **plus** wrapper allocated on *every*
property access, invoked once per order at `GetMyServingCleaners.cs:36`.

Cross-lane note, not mine to rule on but I will not leave it unsaid: pulling `IBAN` and `PassportId`
into a **customer-facing** handler's memory to render a cleaner's first name is an over-fetch with a
security shape, not just a cost shape.

**The objection is sequencing, not blame.** The ADR is right that A6 is pre-existing and that this
feature "must not be blamed for the one that was there". But D10 sizes A6 **S**, parks it in the
"optimizer lane", and sequences it *after* A3/A4. That means the feature's first production
measurement is a measurement of the wrong thing — the new bounded query will be invisible noise
beside a 127-column tracked materialization on the same request. **Require A6 before or with A3.**
It is `.Select()` into the DTO + `AsNoTracking()` + `OrderByDescending`/`Take(20)` pushed into SQL —
genuinely S, and it removes ~123 of the 127 columns and the entire tracking cost from the exact
endpoint this ADR is extending.

### CH-Q6 — Asserted rather than measured **when the measurement rig already exists in this repo**. That changes what the panel should accept.

The ADR's caveat is: "*Priced by reasoning, not by measurement (no `EXPLAIN`, no row counts): the
same honest caveat ADR-0036 carries.*" I did not query DEV either, and I am not asking anyone to.
But this caveat is **avoidable here in a way it was not for ADR-0036**:

- `src/Cleansia.IntegrationTests/` runs a **real PostgreSQL** via Testcontainers
  (`PostgresContainerFixture.cs:1,7,15` — `PostgreSqlBuilder`) and **applies the real migrations**
  (`BaseIntegrationTest.cs:65-91`, `MigrateAsync()`), so `IX_Orders_CurrentStatus_CleaningDateTime`,
  `IX_OrderEmployees_EmployeeId` and `IX_OrderEmployees_OrderId` all exist in the test database
  exactly as in production. An `EXPLAIN (ANALYZE, BUFFERS)` on the emitted SQL is one
  `SqlQueryRaw` away, in CI, touching no DEV database and no production data.

Claims that are currently assertions and are cheaply convertible:

1. "**No new index**" / "*a status-set + narrow-date-band range scan*" (D3, Consequences, A14) — this
   is the ADR's headline cost claim, and CH-Q1 argues the predicate shape works against it.
2. "*Driving from `Orders`… the date band can only prune **after** the join, so each candidate's whole
   assignment history is still walked*" (D3, "Why this side and not the other"). The rejected side is
   never costed. Driving from `IX_OrderEmployees_EmployeeId` is ≤20 SAOP index scans plus PK probes
   into `Orders`; driving from `Orders` scans a ~(24 h + span) band of **platform-wide** volume,
   independent of candidate count. Which wins is a function of (orders/day) vs
   (assignments/cleaner-lifetime) — **at low volume the rejected side is cheaper**, and the ADR asserts
   the opposite with a number on neither. The chosen side probably wins at scale; say that, and say
   the crossover exists.
3. "*The floor's number is decided by failure asymmetry and verified by one SQL line*" (Consequences)
   — see CH-Q2: that SQL line verifies a sample, not a bound.

**Separately: two of the ADR's verification steps are rituals with no automated pin.** Verify #3
(`ToQueryString()` shows `"CleaningDateTime" >= @floor`) and verify #6 (`MAX(EstimatedTime)`) are
human checklist items. I grepped both test projects: **zero `ToQueryString` assertions exist anywhere
in `src/Cleansia.Tests` or `src/Cleansia.IntegrationTests`.** A property that lives only in a
reviewer checklist regresses at the next refactor, silently, and re-creates Defect 2 — which is the
precise failure D3.2 says it will not tolerate ("*the picker's method becomes the third place Defect 2
lives*"). **Make verify #3 an assertion, not a review step.**

### CH-Q7 — Defect 2 is real and the wrapper does fix it. But `HasOverlappingOrderStatusTests` **cannot** prove the floor is right — its back-reach resolution is **30 minutes** — and the convergence trades the write gate's early exit for the bound without saying so.

**Confirming the premise first, because the ADR is correct on it.** `OrderRepository.cs:281-291`: the
only range term is `o.CleaningDateTime < newEnd` (`:283`) — an **upper** bound; `o.CleaningDateTime
.AddMinutes(o.EstimatedTime) > newStart` (`:284`) is a per-row computed expression, not a bound. So
every call scans the cleaner's entire assignment history up to `newEnd`, with the interval expression
evaluated per surviving row. **Unbounded below. Confirmed.** And D3.2's wrapper genuinely fixes it —
`GetBusyEmployeeIdsInWindowAsync([employeeId], …)` applies `CleaningDateTime >= floor`, so
`TakeOrder.cs:156` inherits the bound. The convergence is not a rename.

**But the ADR leans on the pin twice** — D3.2 ("*must stay green through the convergence — if it does
not, the new predicate is not the old one*") and Consequences ("*the pin that proves the predicate did
not change while it moved*") — and it does not carry that weight:

- The probe is `HasOverlappingOrderAsync(CleanerId, SlotStart.AddMinutes(30), 60, …)`
  (`HasOverlappingOrderStatusTests.cs:207-208`) → window `[10:30, 11:30)`. Every seeded order starts
  at `SlotStart` = `2026-08-03 10:00Z` (`:26`) with `estimatedMinutes: 120` (`:195`, `:218`, `:130`).
  **Maximum back-reach exercised: 30 minutes.** The one "outside the window" case is
  `SlotStart.AddHours(5)` (`:151`) — *after* the window, not before.
- Therefore **any floor wider than 30 minutes keeps all 11 tests green.** A floor of `windowStart −
  1 h`, `− 24 h`, or `− 24 h` in a world where 58 h orders exist (CH-Q2) are all indistinguishable to
  this class. The pin proves the floor is not *absurdly* tight. It is **exactly blind** to CH-Q2's
  failure mode, which is the one the ADR calls a double booking.
- Second gap: the class runs on **SQLite** (`:8` `using Microsoft.Data.Sqlite`, `:32`
  `DataSource=:memory:`, `:169` `UseSqlite`). The `AddMinutes` interval arithmetic translates
  differently under Npgsql, and the floor's presence in the *PostgreSQL* SQL is never observed.

**Required on A1's AC:**
1. A case where the pre-existing order starts **more than `MaxOrderSpanHours` before** the window and
   still overlaps it — asserting the *accepted* miss. That writes the boundary down and makes any
   future floor change trip a test instead of a customer.
2. Re-run at least the overlap cases in `Cleansia.IntegrationTests` against real Postgres, where the
   fixture already exists (CH-Q6).

**One note, not a finding.** Today the write gate is `AnyAsync` (`:291`) → `SELECT EXISTS(...)`, which
stops at the first matching row. The wrapper is `(await GetBusy…).Count > 0` over a query ending in
`.Distinct().ToListAsync()` — full materialization of the matched set, a hash-aggregate, and a
`List<string>` + `HashSet<string>` allocated per call, on `TakeOrder`'s hot path. For a single cleaner
in one window the matched set is ~0–2 rows, so this is bounded and I am **not** raising it as a
blocker. But Consequences should say the write gate *trades* early-exit for a lower bound, rather than
"gets the floor **for free**".

## What I checked and found sound

Silence is not assent, so here is what I checked and did not find fault with.

- **Defect 2 is real, exactly as described.** `OrderRepository.cs:281-291`; no lower bound, per-row
  interval expression at `:284`. The ADR's diagnosis is accurate.
- **Defect 1 is real, exactly as described**, and I re-derived it independently through
  `BaseRepository.cs:158` → `CleansiaDbContext.cs:262-264` → `NewJobsDigestService.cs:63,98,137`. The
  "one method, two callers with opposite tenancy requirements" framing is the right framing.
- **The set-based method beats 20 singular calls.** The core D3 ruling is correct and the reasoning
  for it holds. `.Take(20)` at `GetMyServingCleaners.cs:50` does bound the input set.
- **Both indexes the ADR relies on exist**, and one more that it needs but does not cite:
  `IX_Orders_CurrentStatus_CleaningDateTime` (`OrderEntityConfiguration.cs:111`, migration `:2910`),
  `IX_OrderEmployees_EmployeeId` (`:2796`), and — unmentioned, but it is what actually makes the
  chosen drive's semi-join cheap — `IX_OrderEmployees_OrderId` (`:2801`). Cite the third one.
- **A16's refutation of the weekly-cap check is correct on evidence, not taste.**
  `GetEmployeeOrderCountThisWeekAsync` (`OrderRepository.cs:247-259`) derives its window from
  `DateTime.UtcNow.Date` at `:249`. For a booking more than a week out it answers about a week that
  does not contain the booking. ADR-0036 A6's cap half stands. I checked and I agree.
- **A12 is correct.** `QuoteOrder.Response` (`:42-57`) is pricing-only — no duration field. The client
  genuinely cannot supply `estimatedMinutes`, and should not.
- **`Order.EstimatedTime` has exactly one production writer** (`OrderFactory.cs:147` →
  `Order.cs:434`), which is what makes A15's denormalization cheap to maintain. The ADR's claim holds.
- **D6's `MaterializeRecurringBookings` row is right about tenancy.** The per-template override is
  really there (`MaterializeRecurringBookings.cs:70-74`), so the **scoped** variant is correct in that
  sweep and reaching for the ignoring one would widen a per-tenant materialization. (My objection to
  that caller is CH-Q3's *shape*, not its tenancy.)
- **A14's conclusion (add no index) is one I agree with — for a reason the ADR does not give.** An
  extra index on `Orders` is paid on the hottest insert path in the system for a scan the band already
  bounds. But as written the conclusion rests on CH-Q1's unverified premise. If CH-Q1 measures badly,
  A14 is a decision to **re-make**, not a decision to defend.
- **D8's "the check could not run ⇒ no hold, no push, booking never fails"** costs nothing and removes
  a whole class of latency-under-failure. No objection from this lane.
- **No new schema, no migration, no backfill, no new column.** Verified against the proposal: nothing
  in D1–D9 requires DDL. The "zero data risk" claim is accurate.
- **`OrderEmployee` is not tenant-scoped** and the tenant filter is the only global filter, so the
  `IgnoringTenant` sibling is narrow and safe (stated under CH-Q4 because it is unrecorded, not
  because it is wrong).

**Blocking from this lane: CH-Q2 and CH-Q3.** CH-Q2 because a safety-asymmetric constant with nothing
enforcing its safe side is not one, and the ADR names the consequence itself (a double booking on the
write gate). CH-Q3 because the ADR's own verification step hard-rejects the ADR's own prescribed end
state. CH-Q1 is blocking *unless* the author either measures it (CH-Q6 — the rig exists) or restates
the "no new index" claim as a reasoned expectation with a flip condition. CH-Q5 and CH-Q7 are fixable
by amending A1/A3/A6's ACs and the Consequences arithmetic; CH-Q4 and CH-Q6 by recording what is
currently unstated.
