## Context

Owner ruling 2026-09-14 (Q-AUD-L6): *"PDF would be a cleaner approach and would resolve a headache in
the beginning."* ADR-0062 D6 had cut the purpose-built incident file in favour of the audited JSON
export; QuestPDF is already a dependency of `Cleansia.Infra.Services` (receipts, invoices).

## Doing (backend)

- `ExportCustomerIncidentFile.Command(UserId, OrderId?)` on the admin host, `POST
  api/v1/AdminGdpr/incident-file/{userId}?orderId=`, `CanAdminExportUserData`, audited
  `gdpr.user.incident_file` (snapshot = subject id + order id + section counts), `application/pdf`,
  `incident-<userId>-<yyyyMMdd>.pdf`.
- Content (QuestPDF, the receipt/invoice conventions): (1) identity as of export incl. erased?;
  (2) orders — all or the one; (3) disputes on them — messages, evidence names, resolution, refund;
  (4) consents — type, version, effective date, granted at, IP, user agent; (5) the trail — customer
  rows, then admin and cleaner rows on those orders, newest first, payload as a two-column table;
  (6) a footer on every page (generated at, generated by) and the SHA-256 of the data section on the
  last page. No signature.
- Request-log suppression and the export's rate window.
- Tests: the section model and headings; HostTests 200/403/401; Postgres: an erased subject still
  gets a file with the trail and the identity marked erased.

## Doing (admin web)

`/customers/:userId`: an **Incident file (PDF)** button beside *Export subject data* with an optional
order picker; the order detail: an *Incident file* action with `orderId` prefilled. Five locales.
Facade spec.

## NOT

No signature; no PDF for the customer's own export; no change to the JSON export.
