## Correction — 2026-08-13, from working P2

The 84 were classified in this document by *rule*, from the checker's own output. Working them site by
site showed the checker is wrong in **both** directions, so the split above overstated the real-defect
count. Recorded here rather than silently edited above, because the original numbers are what PR #192
claimed.

| Rule | Flagged | Actually real | What the checker got wrong |
|---|---|---|---|
| `C3` | 10 | **6** | 4 false positives. `takeUntil(this.destroyed$)` was present but outside the checker's backward window — twice in the same pipe past an intervening `finalize()` (`profile.facade.ts:106,213`), twice in a shared helper the call site delegates to (`employee-documents.facade.ts:150,170` → `downloadDocumentBlob:181`). |
| `E6` | 11 | **13** | Under-counted. The rule only matches a receiver literally named `vm`, so `authVm.uiState` and `profileVm.currentUser` (`CleansiaNavHost.kt:461-462`) — the same defect in the same file — were invisible. |
| `conv` (hardcoded `Text`) | 1 | **0** | False positive: matched `Text(` inside `ClipData.newPlainText("referral_code", code)`, a clipboard label, not a UI string. |
| `B10` | 2 | **0** | Already known — matches `.Resolve(` on any receiver, firing on `TimeZoneResolution.Resolve(...)`. |

**Revised: 19 real defects · 58 convention debt · 7 checker false positives.** All 19 are fixed in P2.
The seven false positives are the checker's problem, not the codebase's — routed to **CL-024**, which
already owned the `B10` fix.

The lesson is the one this repo keeps re-learning: a rule that names a mechanism is a claim about the
tree, and it decays. A checker nobody has run site-by-site is a *hypothesis* about 84 defects, not a
count of them.
