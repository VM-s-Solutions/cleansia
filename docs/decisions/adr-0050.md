# ADR-0050 — A dormant tenant column arbitrates nothing: `IX_Users_TenantId_Email` is declared `NULLS NOT DISTINCT`, so the arbiter it already claims to be is the arbiter it actually is

- **Status:** `proposed`
- **Date:** 2026-08-11
- **Supersedes:** —
- **Superseded by:** —
- **Composes with:** ADR-0017 (tenancy is app-level, row-scoped, claim-driven — untouched here; this
  ADR changes one index option and no filter, no provider, no claim). **ADR-0028 is `DECLINED`**
  (`agents/archive/2026-08/backlog/adr/0028-multi-tenant-activation-pack.md:3`) — this ADR decides the one item on
  T-0365's list that survives that decline, and does so on the opposite premise. **Retires when:** that
  status line stops reading `DECLINED`.
- **Applies to:** `Cleansia.Infra.Database` (one entity-configuration option) + `Cleansia.Core.AppServices`
  (one exception mapping on the four `User`-creating writers) | **owner-run `ef-migration`** (pre-prod
  `Initial` regen) | **no NSwag / no client change** | no host coupling
- **Ticket:** T-0365 (`security_touching: true`) · related: the `consistency.md` §*"Tenant-scoped unique
  indexes"* rule this applies (`agents/knowledge/consistency.md:454-465`), the guard that would have
  caught it (`src/Cleansia.Tests/Infrastructure/NullsNotDistinctIndexModelTests.cs:52-68`)

> **One decision:** *what arbitrates the uniqueness of an account's email.* Today the code answers that
> question twice and the two answers disagree. `UserEntityConfiguration.cs:96-97` declares the database
> the arbiter — *"DB-level uniqueness — not just the `ExistsWithEmailAsync` app pre-check — is the real
> guarantee that closes the register/update TOCTOU race"* — while the index it declares that of,
> `builder.HasIndex(u => new { u.TenantId, u.Email }).IsUnique()` (`:106-107`), carries no
> `.AreNullsDistinct(false)`. `TenantId` is `string?`, every production row holds `NULL`, and PostgreSQL
> treats NULLs in a UNIQUE index as **DISTINCT** — so the index admits unlimited duplicate rows in the
> only mode the platform has ever run in. **The decision is to make the declaration true rather than to
> withdraw it:** the index gains `.AreNullsDistinct(false)`, the four writers that race against it map
> `23505` to `ExistingUserWithEmail` instead of a 500, and the census that must precede the migration is
> named rather than assumed.

## Context (every citation opened in the working tree, 2026-08-11)

### The contradiction, in four lines of one file

`src/Cleansia.Infra.Database/EntityConfigurations/UserEntityConfiguration.cs:92-107` carries both halves:

- `:96-97` — the claim: DB-level uniqueness *is* the guarantee that closes the register/update TOCTOU
  race, explicitly *not* the app pre-check.
- `:99-105` — the S8 scoping rationale: uniqueness is `(TenantId, Email)` and not global `Email`,
  because a global index made tenant B's registration a cross-tenant existence oracle and barred one
  person from being a customer in two tenants.
- `:106-107` — the index itself: `.IsUnique()` and nothing else.

The rationale at `:99-105` is sound *as a scoping argument*. It is silent on the arming question, and
the arming question is the one that decides whether `:96-97` is true.

### Why the index does not fire

`ITenantEntity.TenantId` is nullable and `CleansiaDbContext.CommitAsync` stamps a new entity's
`TenantId` from the ambient provider (`src/Cleansia.Infra.Database/CleansiaDbContext.cs:89-91`), which
for every request today resolves `null` (`src/Cleansia.Infra.Database/TenantProvider.cs:12-20` — the
claim, else null; there is no other source). PostgreSQL's default `NULLS DISTINCT` therefore makes
`(NULL, 'a@b.com')` non-conflicting with itself, without limit. This is not a forecast about
activation; it is the state of the running database.

The catalog already states the governing rule and states it correctly
(`agents/knowledge/consistency.md:454-465`): *sole arbiter of a concurrent claim ⇒
`.AreNullsDistinct(false)` is mandatory; backstop behind an authoritative app-level assert ⇒
nulls-distinct is fine.* `Users` appears on **neither** roster in that entry, and appears on neither
roster in the guard that enforces it
(`src/Cleansia.Tests/Infrastructure/NullsNotDistinctIndexModelTests.cs:52-57` — the four rostered
indexes — with its negative control at `:76-84`). The rule did not fail; its roster is hand-maintained
and this instance was never added to it.

### Which side of that rule `Users` falls on — the four writers

All four `User`-creating paths are **read-then-insert across a snapshot boundary**, with no lock, no
`ON CONFLICT`, and no serializable transaction. None of them is an *authoritative* app-level assert;
each is a courtesy pre-check.

| Writer | Pre-check | Insert |
|---|---|---|
| `Register` | validator `GetByEmailAsync` (`src/Cleansia.Core.AppServices/Features/Auth/Register.cs:47-51`) | handler re-reads, then `Add` (`:76-87`) |
| `RegisterEmployee` | validator `GetByEmailAsync` (`src/Cleansia.Core.AppServices/Features/Auth/RegisterEmployee.cs:45-49`) | handler re-reads, then `Add` (`:69-81`) |
| `CreateAdminUser` | validator `GetAll().AnyAsync(...)` (`src/Cleansia.Core.AppServices/Features/AdminUsers/CreateAdminUser.cs:40-43`) | handler `Add` (`:89-95`) |
| `GoogleAuth` / `AppleAuth` provisioning | resolve-by-email fallback, then provision | `src/Cleansia.Core.AppServices/Features/Auth/GoogleAuth.cs:136-139`, `src/Cleansia.Core.AppServices/Features/Auth/AppleAuth.cs:188-191` |

So the index **is** the sole arbiter — exactly as `:96-97` says — and it is disarmed.

### What a duplicate row actually costs (the reason this is not academic)

Two `(NULL, 'a@b.com')` rows are not a cosmetic defect. They are an account-loss defect, because every
downstream reader resolves the email with an unordered `FirstOrDefaultAsync`:

- **Login resolves an arbitrary row.** `UserRepository.GetByEmailIgnoringTenantAsync`
  (`src/Cleansia.Infra.Database/Repositories/UserRepository.cs:64-70`) is the resolver for all five
  login variants and both social paths; whichever row Postgres returns wins, and the other person's
  password never matches. Their orders, cart, membership and payout details hang off a row nothing can
  reach.
- **The lockout charge hits both rows.** `RecordFailedLoginAsync` (`:157-172`) is
  `Where(u => u.Email == email)` + `ExecuteUpdateAsync` — a spray against one account locks the other.
- **Erasure reaches one.** GDPR deletion is id-keyed; the shadow row survives the erasure of "the"
  account.

Frequency is concurrency-bound and therefore low. Impact is silent account loss. **And the price of the
fix is at its historical minimum right now**: pre-production, one committed `Initial` migration that the
owner regenerates, and a `Users` table whose duplicate census is plausibly empty. After go-live the same
fix requires de-duplicating live customer accounts, which is a support operation, not a migration.

### What is locked around this decision

- **CLAUDE.md law:** `null` TenantId = single-tenant mode, backward compatible. `.AreNullsDistinct(false)`
  *strengthens* that mode and changes nothing about it structurally — the filter body
  (`src/Cleansia.Infra.Database/CleansiaDbContext.cs:262-268`) is byte-untouched.
- **The owner's standing instruction (Q-VS-03, `agents/archive/2026-08/backlog/questions/open.md:2324-2337`):**
  *"No, we won't have franchises, DON'T OVERCOMPLICATE THINGS."* Recorded there as a standing
  instruction, with the lesson attached: **ask whether the hedge's premise is real before pricing the
  hedge.** This ADR is written under it, and Alternative (d) below is where it does the most work.
- **`.AreNullsDistinct(false)` is precedented, not novel** — five shipped tables use it; the
  living note records how to re-derive the list rather than copy it
  (`agents/architecture/decisions/multi-tenancy-and-region.md:66-74`).

## Decision

> **Contract principle: an index that a comment calls the arbiter must be able to fire in the mode the
> platform runs in. A tenant column that is `NULL` on every row is not a key component — it is a
> disarmed one, and the only two honest resolutions are to arm it or to stop claiming it.**

### D1 — `IX_Users_TenantId_Email` is declared `NULLS NOT DISTINCT`

`UserEntityConfiguration.cs:106-107` becomes
`builder.HasIndex(u => new { u.TenantId, u.Email }).IsUnique().AreNullsDistinct(false);`.

Semantics after the change, in full:

| Rows | Before | After |
|---|---|---|
| `(NULL, 'a@b')` × 2 | both insert | second rejected `23505` |
| `('T1', 'a@b')` × 2 | second rejected | second rejected (unchanged) |
| `(NULL, 'a@b')` + `('T1', 'a@b')` | both insert | both insert (unchanged) |

The per-tenant scoping the S8 rationale at `:99-105` bought is **entirely preserved** — the third row of
that table is the one that matters and it does not move. This is an arming change, not a scoping change.

### D2 — The `23505` on the register race is mapped to `ExistingUserWithEmail`, not left as a 500

The tightening is not free and the living note says so in advance
(`agents/architecture/decisions/multi-tenancy-and-region.md:55-60`): *check what the write path does
with that exception before assuming the tightening is free.* Today the losing racer creates a second
row; after D1 it throws at `CommitAsync`, and no handler in the four-writer table catches it. **A 500 on
the second of two simultaneous registrations is an acceptable failure and a bad one to ship
deliberately** — the correct response is the business error the pre-check would have produced. So each
of the four writers maps a unique-violation on `Users.Email` to `BusinessErrorMessage.ExistingUserWithEmail`
(`AdminUserEmailExists` for `CreateAdminUser`, matching its own pre-check's message).

**Placement is left to the implementation ticket, with one constraint:** the mapping must be keyed on
the constraint name, never on a substring of the driver's message text, and it must not swallow other
unique violations on the same commit. A single pipeline-level `DbUpdateException` translator is
acceptable *only* if it can name the constraint; otherwise it is per-writer.

### D3 — The census is VACUOUS pre-prod, and saying so is the decision

Index creation with `NULLS NOT DISTINCT` **fails on pre-existing duplicates**, so on any database that
survives a migration this ADR would owe a census first. **This project has no such database.**

Pre-prod there is exactly one `Initial` migration and it is **regenerated**, not stacked
(owner ruling 2026-08-09). Regeneration changes the migration id, `__EFMigrationsHistory` keys on the
id, and an existing database therefore reports "up to date" while silently missing every new column —
so **DEV is dropped and re-seeded on every regen**. A census over a database that is about to be
dropped measures nothing, and a gate that cannot fail is not a gate.

**The owner's step is therefore the one that already existed** — drop DEV, regenerate `Initial`,
re-seed — with no census in front of it. The arming of this index is one more column-level fact folded
into that regen, not a sequenced operation of its own.

> ⚠️ **This becomes load-bearing the day a database survives a migration** — the first production
> deploy, or the first stacked migration after pre-prod ends. At that moment the sequence is
> census → de-duplicate → migrate, and de-duplication is an **owner decision per pair**, because the
> losing row may own orders, invoices or a payout destination. The three queries, kept for that day:
>
> ```sql
> SELECT "Email", COUNT(*) FROM "Users" GROUP BY "Email" HAVING COUNT(*) > 1;
> SELECT "TenantId", "Email", COUNT(*) FROM "Users" GROUP BY "TenantId", "Email" HAVING COUNT(*) > 1;
> SELECT COUNT(*) FROM "Users" WHERE "TenantId" IS NOT NULL;
> ```
>
> `Email` is `citext`, so equality already matches the index case-insensitively. The third is not about
> duplicates: a non-zero answer means a tenant-stamped account exists in an environment whose entire
> read path assumes none does — an ADR-0051 finding, not this one's.
>
> **Retires when:** a migration other than `Initial` exists under
> `src/Cleansia.Infra.Database/Migrations/`.

### D4 — The guard's roster gains `Users`, and the roster's hand-maintenance is stated where it is claimed

`NullsNotDistinctIndexModelTests` gains `[InlineData(typeof(User), new[] { "TenantId", "Email" })]`
alongside its existing four (`src/Cleansia.Tests/Infrastructure/NullsNotDistinctIndexModelTests.cs:52-57`).
It goes red the moment it is added and green when D1 lands, which is the correct order and the reason
the tier in the catalog entry is `(gate pending: …)` and not `T1-CI` until then.

The entry that names this guard must also say that the roster is **hand-maintained** — a new
sole-arbiter index is not caught until someone adds a row. That boundary is required by
`agents/knowledge/conventions.md:391-395` (*"the named enforcer's assertion must cover the scope the
sentence claims"*) and its absence is how `Users` stayed off the list for as long as it did.

### D5 — What this decision does NOT do

- **It does not backfill `TenantId`.** The founding tenant's identity stays `NULL`, permanently. D1 is
  the reason that is now safe rather than merely traditional.
- **It does not touch `ApplyTenantQueryFilters`, `TenantProvider`, the claim mint, or any read.** Read
  tenancy is ADR-0051's subject and is deliberately not decided here.
- **It does not make `Email` globally unique** — see Alternative (d), which is the closest call in this
  ADR and is rejected on scope, not on merit.
- **It does not sweep other tenant-scoped unique indexes.** Re-deriving that list is a separate,
  recurring task and the living note already prescribes how
  (`agents/architecture/decisions/multi-tenancy-and-region.md:66-74`). Widening this ADR to "audit every
  index" would make one decision into an unbounded one.

## Alternatives considered

- **(a) Arm the index — `.AreNullsDistinct(false)` on `(TenantId, Email)`.** **CHOSEN.** One builder
  call; the shipped, precedented construct; makes the existing in-code claim true rather than deleting
  it; preserves the per-tenant scoping argument byte-for-byte; costs an owner migration that is cheapest
  today and never cheaper again.
- **(b) Downgrade the claim — delete the `:96-97` sentence and call the index a backstop.** Rejected,
  and it is the honest opposite of (a) rather than a straw man. It costs nothing and it is *coherent*:
  the catalog explicitly permits a nulls-distinct backstop. It fails on the second half of the catalog's
  own test — a backstop must sit *behind an authoritative app-level assert*, and none of the four
  writers has one (see the writers table). Choosing (b) would leave the register race genuinely
  unarbitrated and would have to say so out loud. Between "make the guarantee true" and "write down that
  there is no guarantee", the first is cheaper here because the fix is one option flag.
- **(c) Make the app-level check authoritative — a transactional pre-check, an advisory lock on
  `hashtext(email)`, or `SERIALIZABLE` on the register path.** Rejected. It is strictly more machinery
  for strictly less coverage: it would have to be added to four writers on three hosts and would still
  not cover a fifth writer added later, whereas the index covers every writer that will ever exist,
  including ones written by someone who never reads this ADR. It also puts a lock on the hottest
  anonymous path to defend against a race the database is already built to arbitrate.
- **(d) Drop the tenant term — a global `UNIQUE (Email)`.** The strongest rejected option, and the one
  ADR-0028 dismissed for reasons that have since expired. It fires unconditionally (`Email` is
  non-nullable, so `NULLS DISTINCT` is irrelevant), it makes `FirstOrDefaultAsync` deterministic
  everywhere by construction, and it would make the "email is unique across the platform" justification
  at `src/Cleansia.Core.Domain/Repositories/IEmployeeRepository.cs:14-15` true instead of false.
  ADR-0028 Alternatives (c) rejected it on two grounds — the cross-tenant existence oracle, and *"one
  person cannot be a customer of two tenants"* — **both of which are properties of a multi-tenant future
  the owner has since ruled out (Q-VS-03).** So the rejection stands on a *different* ground: (d) and (a)
  are **behaviourally identical in every environment that will ever run**, because both make one row per
  email while every `TenantId` is `NULL`. (d) additionally forecloses per-tenant email identity
  permanently, which is a business question the owner would have to answer, and it withdraws a shipped
  S8 rationale. **Paying an owner decision for zero behavioural difference is the exact shape Q-VS-03's
  second consequence names.** (a) wins on cost, not on capability.
- **(e) Do nothing — the race needs concurrency, the platform is small, and no duplicate has been
  observed.** Rejected. "No duplicate observed" is unverified (nobody has run D3's census) and the cost
  curve runs the wrong way: the same fix is one migration today and an account-merge support operation
  after launch. This is also the second time the item has been deferred — T-0365 is the first deferral
  note, and ADR-0028 deferred it again by re-framing it as an activation problem.

## Consequences

**Cheaper / safer:**
- The register/update TOCTOU race is closed for the first time, by the mechanism that has claimed to
  close it since the index was written.
- A whole class of downstream nondeterminism disappears at the root rather than being patched
  reader-by-reader: with one row per email, `FirstOrDefaultAsync` on email is deterministic in every
  auth path without a single one of them changing.
- The catalog's sole-arbiter rule gains its most important instance and its guard gains a fifth roster
  row, so the *next* tenant-scoped unique index is measured against a list that contains the `Users`
  precedent.
- The per-tenant scoping seam is preserved exactly, so nothing about ADR-0017 or a future activation
  becomes harder.

**More expensive (accepted):**
- **An owner-run migration** (pre-prod `Initial` regen), gated on a census that could come back
  non-empty and turn a one-line change into a data decision. That risk is real and is the reason D3
  sequences rather than assumes.
- **A new failure mode on the register path** — `23505` where there was silent success. D2 converts it
  to the correct business error, but until D2 lands with D1 the losing racer sees a 500. The two must
  ship together; a deploy that lands D1 alone is a regression in the user-visible direction.
- **One more hand-maintained roster row.** The guard does not discover the next index either. Stated
  in the entry rather than papered over.

## How a reviewer verifies compliance

**Mechanical:**
1. `UserEntityConfiguration.cs` carries `.AreNullsDistinct(false)` on the `(TenantId, Email)` index —
   **and the reviewer reads the emitted DDL, not the C# builder call** (`agents/knowledge/consistency.md:476`).
   The migration must show `NULLS NOT DISTINCT` on `IX_Users_TenantId_Email`.
2. `NullsNotDistinctIndexModelTests` has a fifth `[InlineData]` for `User` / `("TenantId", "Email")`,
   and its negative control at `:76-84` is untouched (without the control the theory can pass on a
   reader that answers `false` for everything).
3. Each of the four writers in the writers table maps a unique violation on `Users.Email` to a business
   error. Grep for the constraint name; a mapping keyed on driver message text fails review.
4. `ApplyTenantQueryFilters`, `TenantProvider` and `AuthExtensions` are diff-empty. This ADR touches an
   index and an exception mapping; a diff that reaches a read path belongs to ADR-0051.
5. The census output (D3) is pasted into the ticket. An unpasted census is an unrun census.

**Test contract (names for the implementation ticket):**
- **TC-EMAIL-ARB-1 — the race, red before the change.** Two concurrent `Register` commands with the same
  new email against real Postgres: before D1 both rows land (the test asserts the bug); after D1 exactly
  one lands and the loser returns `ExistingUserWithEmail`. Integration suite — SQLite cannot express
  `NULLS NOT DISTINCT` and a unit test here proves nothing.
- **TC-EMAIL-ARB-2 — the scoping is unchanged.** `(NULL, 'a@b')` and `('T1', 'a@b')` both insert. This
  is the pin that D1 armed the index without re-globalising identity, and it must seed a **non-null**
  tenant or it cannot fail.
- **TC-EMAIL-ARB-3 — the same-tenant duplicate still fails.** `('T1', 'a@b')` twice → rejected.
  Regression cover for the behaviour the index already had.
- **TC-EMAIL-ARB-4 — the four writers.** One case per writer (`Register`, `RegisterEmployee`,
  `CreateAdminUser`, social provisioning) asserting the business error rather than a 500.
- **TC-EMAIL-ARB-5 — the model guard.** `NullsNotDistinctIndexModelTests` red with the roster row and
  without the option; green with both.

## Challenge

*(Architect panel, challenger mode, 2026-08-11. Single-instance pass — see the Verdict's process note.
Every citation below was re-opened rather than taken from the draft.)*

**CH-1 — BLOCKING-CANDIDATE: the ADR asserts the race is reachable but has run nothing.** No census, no
concurrency test, no production observation. If `Users` already carries duplicates, D1's migration fails
and the ADR's own remedy is unavailable — and the ADR would then have shipped a migration that cannot
apply. Either the census runs first or the sequencing is fiction.

**CH-2 — the catalog may already decide this, in which case there is no decision and no ADR.**
`consistency.md:454-470` states the sole-arbiter rule plainly. If `Users` is a sole arbiter, the rule
already obliges the option and this is a bug ticket wearing an ADR's clothes. Justify the ADR or
downgrade it.

**CH-3 — "sole arbiter" is asserted, not demonstrated.** `UserMemberships` is on the catalog's
*backstop* list and it too is guarded by a read-then-write (`GetActiveForUserAsync`). If that counts as
an authoritative app-level assert, why doesn't `Register`'s pre-check? The distinction as drafted is
doing a lot of work with no stated test.

**CH-4 — D2 makes a 500 into a business error and calls that a fix, but it changes an anonymous
endpoint's disclosure.** `ExistingUserWithEmail` on a race that previously succeeded is a new signal on
an unauthenticated path. Is that an enumeration surface, and was it weighed?

**CH-5 — Alternative (d) is rejected on "behaviourally identical", which is an argument for either
option.** If they are identical, the tie-break should go to the *simpler* schema, and `(Email)` is
simpler than `(TenantId, Email) NULLS NOT DISTINCT`. The ADR picks the more complex one and calls it
cheaper.

**CH-6 — the ADR changes an index on the `Users` table and claims no read is affected.** Every login
path resolves by email. Show that no query plan, no `FirstOrDefaultAsync`, and no
`ExecuteUpdateAsync` predicate changes shape.

**Checked and NOT challenged (named per the protocol):** the D5 no-backfill posture — consistent with
the filter's middle clause and ADR-0017, and D1 is what makes it safe rather than merely inherited; the
`23505`-not-message-text constraint in D2 — correct, driver message text is not a contract; the
integration-not-unit placement of TC-EMAIL-ARB-1 — SQLite genuinely cannot express the option, and the
existing `NullsNotDistinctIndexModelTests` is a *model* assertion precisely because of that; the
decision not to sweep other indexes (D5) — the living note's re-derivation recipe is the right home for
a recurring task.

## Defense

- **CH-1 — CONCEDE + REVISE (folded as D3).** The challenge is right and it is the most important one.
  The draft originally asserted the census was empty; it now names the three queries, forbids any agent
  from reporting their result from reasoning, and sequences census → de-dup → migration explicitly. The
  ADR's decision does not depend on the census outcome — arming the index is right either way — but its
  *rollout* does, and that is now written down instead of assumed. **This is an owner-run step and this
  panel cannot discharge it.**
- **CH-2 — REBUT, and the rebuttal is the reason the ADR earns its place.** The catalog rule decides
  which indexes need the option; it does not decide what to do when the remedy is **owner-only and can
  fail on existing data**, nor which of two coherent resolutions to take when a shipped comment and a
  shipped index contradict each other. Alternative (b) is a real, defensible option that the catalog
  permits — a reviewer applying `consistency.md` alone could legitimately land (b) and close the
  ticket. Choosing between (a) and (b), sequencing an owner migration behind a census, and pricing the
  new `23505` path are decisions. What is *not* a decision is the rule itself, and this ADR does not
  restate it — it cites it.
- **CH-3 — CONCEDE + REVISE (the test is now stated).** The draft leaned on the phrase. The operative
  test, now in the Context, is: **is there a lock, an `ON CONFLICT`, or a serializable boundary between
  the read and the write?** For all four `User` writers there is none — read and insert cross a snapshot
  boundary with nothing in between, so the pre-check is a courtesy and the index is the only arbiter.
  The challenge's `UserMemberships` point is sharp and is conceded as a **catalog** weakness rather than
  a defect in this ADR: that entry's "authoritative app-level assert" is under-specified by the same
  test. It is recorded as such in the consistency edit rather than silently relied on, and re-examining
  `UserMemberships` is explicitly out of scope here (D5) rather than smuggled in.
- **CH-4 — REBUT with the shape of the surface.** `ExistingUserWithEmail` is already the *normal*
  response of all four writers when the pre-check finds a row — it is what a sequential duplicate
  registration returns today, on the same anonymous endpoint, bounded by the per-IP `auth` bucket. D2
  moves the racing case onto the same response as the non-racing case; it does not create a signal.
  Recorded in Consequences as unchanged-in-kind rather than as new.
- **CH-5 — REBUT, and the tie-break is not simplicity of the DDL.** The two options are identical in
  *behaviour*, not in *cost of adoption*: (a) is one builder flag inside an already-written rationale;
  (d) withdraws a shipped S8 argument (`UserEntityConfiguration.cs:99-105`), forecloses per-tenant email
  identity permanently, and — because it changes what identity *means* rather than whether a constraint
  fires — is an owner decision, not an architect one. Q-VS-03's second consequence is precisely that a
  written-down capability is not free; but neither is *removing* one whose removal buys nothing today.
  The tie-break is: **the option that changes no meaning wins.**
- **CH-6 — REBUT with the mechanics.** `NULLS NOT DISTINCT` changes what the index *rejects on write*;
  it does not change the index's columns, order, operator class, or the plans available to a reader.
  `Email` is `citext` and the index stays `(TenantId, Email)`, so every existing email lookup is
