# ADR-0051 — A read's tenancy posture is decided by the WRITE-tenant × READ-tenant asymmetry, not by the endpoint's anonymity: the filter is the default and a bypass is owed only where the two ambient tenants can differ

- **Status:** `proposed`
- **Date:** 2026-08-11
- **Supersedes:** —
- **Superseded by:** —
- **Composes with:** ADR-0017 (the filter is never modified — this ADR decides which reads *stand
  outside* it, and changes the filter's body not at all); ADR-0050 (the write-side arbiter — the two are
  independent and neither depends on the other landing). **ADR-0028 is `DECLINED`**
  (`agents/archive/2026-08/backlog/adr/0028-multi-tenant-activation-pack.md:3`); its **D3** conclusion is re-derived here
  on a premise that survives the decline, and its D1/D2 are not revived. **Retires when:** that status
  line stops reading `DECLINED`.
- **Applies to:** `Cleansia.Infra.Database/Repositories/**` + `Cleansia.Core.AppServices` auth flows |
  all four API hosts equally | **no schema migration** | **no NSwag / no client change** | **no
  behavioural change to any shipped call site** — this ADR ratifies the shape the tree already has,
  names the one it is missing, and corrects two justifications that are factually wrong
- **Ticket:** T-0365 (`security_touching: true`) · related: T-0361 (shipped —
  `src/Cleansia.Infra.Database/Repositories/EmployeeRepository.cs:19-26`; its INDEX row is stale), the
  S8 law this narrows (`docs/architecture/security-rules.md` §S8 — line numbers deliberately not cited;
  this ADR's own catalog edit moves them)

> **One decision:** *what determines whether a read may stand outside the global tenant filter.* Today
> the answer is folklore assembled from three war stories in S8, and every one of them is told from the
> *caller's* point of view — "anonymous path", "background sweep", "one method, two callers". None of
> them states the property those three share, so each new case is re-argued from scratch and the fourth
> case is not in the text at all. **The decision is that the discriminator is neither the endpoint's
> anonymity nor the predicate's key, but the answer to one question: _can the ambient tenant at the
> moment this row was WRITTEN differ from the ambient tenant at the moment it is READ?_** If it cannot,
> the read stays inside the filter — no exception, no justification comment, nothing to audit. If it
> can, the read bypasses **and re-pins on a predicate bound to the caller**, and the re-pin may never be
> an appeal to a uniqueness property the schema does not enforce.

## Context (every citation opened in the working tree, 2026-08-11)

### The machinery, in one paragraph

The filter body is
`providerNull || (currentTenantId == null && e.TenantId == null) || e.TenantId == currentTenantId`
(`src/Cleansia.Infra.Database/CleansiaDbContext.cs:262-268`). Writes are stamped from the same provider
at commit time (`:89-91`). The provider resolves the explicit override, else the `tenant_id` claim, else
null (`src/Cleansia.Infra.Database/TenantProvider.cs:12-20`) — **there is no third source**, so an
anonymous request always resolves null and an authenticated one resolves whatever its JWT carries. The
bypass is `IgnoreQueryFilters()` / `BaseRepository.GetQueryableIgnoringTenant()`.

Two consequences follow mechanically and are the whole of this ADR's subject matter:

1. A row written under ambient tenant *W* is invisible to a read under ambient tenant *R* whenever
   *W ≠ R* — including when exactly one of them is null. The middle clause rescues only the
   `null`/`null` case.
2. Therefore **the only property that decides whether a bypass is needed is whether *W* and *R* can
   differ for that row and that read.** Everything else — is the endpoint anonymous, is the key a
   secret, is the caller a sweep — is a proxy for that question, and proxies are why the same bug keeps
   arriving in a new costume.

### The four cells, each with a shipped exemplar

|  | **Read under a tenant claim** | **Read with no claim (anonymous / job)** |
|---|---|---|
| **Written under a tenant claim** | **Cell 1 — symmetric.** Same subject, same tenant. **Filtered.** `src/Cleansia.Config/Filters/RequireCompleteProfileAttribute.cs:25`, `src/Cleansia.Core.AppServices/Authentication/OrderAccessService.cs:112`, the `UpdateEmployee` family, `src/Cleansia.Infra.Database/Repositories/LiveActivityTokenRepository.cs:10-45`. | **Cell 3 — ASYMMETRIC.** **Bypass + re-pin.** `src/Cleansia.Infra.Database/Repositories/EmployeeRepository.cs:19-26` on the token-mint paths; `src/Cleansia.Infra.Database/Repositories/LiveActivityTokenRepository.cs:47-61`; `src/Cleansia.Infra.Database/Repositories/DeviceRepository.cs:46-57` and `src/Cleansia.Infra.Database/Repositories/DeviceRepository.cs:59-68`. |
| **Written with no claim (anonymous)** | **Cell 2 — ASYMMETRIC.** **Bypass + re-pin.** `src/Cleansia.Infra.Database/Repositories/RefreshTokenRepository.cs:10-23` and the whole revoke family at `src/Cleansia.Infra.Database/Repositories/RefreshTokenRepository.cs:120-150` — the tokens are issued anonymously and null-stamped, the revoke arrives with a claim. | **Cell 4 — symmetric.** Both null. **Filtered.** `src/Cleansia.Infra.Database/Repositories/UserRepository.cs:105-118`; the register/resend admission pre-checks. |

Every `IgnoreQueryFilters()` site in the repositories that this panel opened lands in cell 2 or cell 3,
and every filtered site it opened lands in cell 1 or cell 4. **The rule is not a new policy; it is the
property the shipped code already has.** What the tree is missing is the *statement* — which is why S8
files the cell-3 employee read under the mirror-sweep story (`docs/architecture/security-rules.md` §S8, "the mirror case" reference list),
where it does not belong: it is not a sweep, it has no loop, and it never writes.

## Decision

> **Contract principle: the filter is the default and needs no argument. A bypass is a permanent audit
> obligation and is owed exactly one thing — the demonstration that the write tenant and the read tenant
> can differ — and it must pay one thing: a re-pinning predicate bound to the caller.**

### D1 — The test is the write-tenant × read-tenant asymmetry, and it is asked of the ROW, not the route

For any read, name the ambient tenant at the moment rows of that kind are **written** (*W*) and at the
moment this read **runs** (*R*). If *W* and *R* are provably the same for every row this read can reach,
the read stays inside the filter. Otherwise it bypasses.

- *"The endpoint is anonymous"* is **not** the test. Cell 4 is anonymous and stays filtered.
- *"The key is an unguessable secret"* is **not** the test. `GetByConfirmationCodeAsync` (cell 4, secret,
  filtered) and `GetByTokenHashAsync` (cell 2, secret, bypassed) key on the same kind of SHA-256 hash and
  land on opposite sides — because their *cells* differ, not their keys.
- *"It's a background job"* is a **special case** of asymmetry, not a separate rule: a job holds no
  claim, so *R* is null against rows of every *W*. S8's existing sweep guidance
  (`docs/architecture/security-rules.md` §S8, "the mirror case") is the correct elaboration of that case and is not
  changed — including its two hard parts, that the sweep must be ignoring on **both** sides of the loop
  and that `SetTenantOverride` is decorative without a commit inside the iteration.

### D2 — A bypass re-pins on a predicate bound to the caller, and the pin may not be an unenforced schema property

`IgnoreQueryFilters()` alone is never acceptable — the shipped S8 remedy stands. The re-pin must be one
of: an **unguessable server-issued secret** (`TokenHash`, a 128-bit confirmation token), the **caller's
own id taken from their JWT** (`UserId`, `DeviceId`), or a **row id read out of an already-pinned row**
(`RefreshToken.ReplacedByTokenId`'s chain).

**New, and it is the part with teeth:** the re-pin may **not** be an appeal to a uniqueness property the
database does not enforce. *"Email is unique across the platform"*
(`src/Cleansia.Core.Domain/Repositories/IEmployeeRepository.cs:14-15`) is such an appeal, and it is
false twice over — the index is `(TenantId, Email)` by design, and while `TenantId` is dormant that
index arbitrates nothing at all (ADR-0050). The bypass at
`EmployeeRepository.GetByUserEmailIgnoringTenantAsync` is nevertheless **correct**, and its true pin is
narrower and stronger: **the caller has already been authenticated as the owner of that email by the
credential check that precedes the call, so the read resolves the just-authenticated subject's own
employee row.** The comment is corrected to say that; the code does not change.

### D3 — Confirm-family lookups STAY tenant-filtered — and the reason is cell 4, not ADR-0028's

The conclusion of ADR-0028 D3 survives; its argument does not, and the difference matters because the
argument was load-bearing for a reader deciding the next case.

ADR-0028 D3 kept the filtered lookup on the strength of D2: *"the ticket's dilemma dissolves … with D2's
fail-closed rule, wrong resolution is an unmapped or mis-mapped host — a 421 — not a quiet per-user dead
end."* **D2 was declined.** With no host resolution, that defence is gone: a tenant-stamped user's
legacy confirm link would silently zero-match forever and nothing anywhere would be loud.

The replacement argument does not depend on D2 and is stronger:

1. **Cell 4 is symmetric.** A confirmation code is written on the anonymous register path (*W* = null)
   and read on the anonymous confirm path (*R* = null). The filter's middle clause matches. There is no
   asymmetry, so there is nothing to bypass.
2. **The only row for which it would break is one that cannot exist.** A tenant-stamped `User` requires
   a request bearing a `tenant_id` claim to have created it, which requires a JWT minted from a
   tenant-stamped user, which requires… — the population bootstraps from nothing. There is no writer for
   it, and ADR-0028's own D1.6 needed an activation runbook to create one.
3. **The shipped guard already says so, and its roster is deliberate.**
   `UserRepositoryTokenLookupTenantTests.cs:36-79` pins the confirm lookups filtered and confines every
   bypass to eight named methods. Flipping D3 would have required editing that roster — and the panel
   that wrote it wrote out its reasoning in the roster's own comments.
4. **Q-VS-03's lesson applies directly.** Spending a permanent S8 exception to harden a dying surface
   against a population that has no writer is pricing a hedge whose premise is not real.

**So D3 costs nothing and changes nothing.** That is the correct outcome and it is worth recording as a
decision precisely because the previous ADR reached it by a route that has since collapsed.

### D4 — The scope line: what this rule does NOT sweep in

A rule of the form *"reads on anonymous paths are tenant-ignoring"* is the obvious generalisation, it is
wrong, and writing it would delete real controls. Stated explicitly so nobody re-derives it:

- **Admission pre-checks stay filtered even though their endpoint is anonymous.** `Register`
  (`src/Cleansia.Core.AppServices/Features/Auth/Register.cs:47-51`), `RegisterEmployee`
  (`src/Cleansia.Core.AppServices/Features/Auth/RegisterEmployee.cs:45-49`), `ResendConfirmationEmail`
  (`src/Cleansia.Core.AppServices/Features/Auth/ResendConfirmationEmail.cs:28`). They are cell 4. They
  ask *"may a new row exist?"*, and widening them across tenants is precisely the cross-tenant existence
  oracle the composite index was chosen to remove
  (`src/Cleansia.Infra.Database/EntityConfigurations/UserEntityConfiguration.cs:99-105`). **The
  under-inclusion here is the feature.**
- **The confirm family stays filtered** (D3), and the eight-method roster in
  `UserRepositoryTokenLookupTenantTests.cs:57-75` is **not** edited by this ADR.
- **Authenticated same-subject reads stay filtered.** `EmployeeRepository.GetByUserEmailAsync` keeps its
  filtered body and all of its authenticated callers keep calling it —
  `src/Cleansia.Config/Filters/RequireCompleteProfileAttribute.cs:25`,
  `src/Cleansia.Core.AppServices/Authentication/OrderAccessService.cs:112`, and the four
  `Update*` employee-self-service handlers. These are cell 1. A rule that swept them into "ignoring"
  would strip tenant scoping from the partner profile gate and the order-access resolver — the two
  places where tenant scoping is doing security work rather than bookkeeping. **This is the concrete
  thing the naive phrasing would have broken, and it is why the rule is stated as a matrix rather than
  as a slogan about anonymity.**
- **It does not touch the filter, the provider, the claim mint, `SetTenantOverride`, or ADR-0026/0027's
  directories.** No behavioural change ships with this ADR at all.

### D5 — The two paired-name obligations that follow

1. **A repository method reachable from two cells must be two named methods**, per the shipped pair
   precedent (`EmployeeRepository.GetByUserEmailAsync` / `…IgnoringTenantAsync`, `:9-16` / `:19-26`).
   This restates S8's third form (`docs/architecture/security-rules.md` §S8, "ONE repository method
   serving TWO callers with OPPOSITE tenancy requirements") rather than adding to
   it; what is new is that "which cell" is now a decidable question instead of a judgment call.
2. **Every bypass site names its cell in one line.** Not prose about anonymity — the literal
   *"written under W, read under R"* pair and the re-pin. Eight of the shipped sites already do this in
   substance; the requirement is that the next one cannot be written without answering the question.

## Alternatives considered

- **(a) The write-tenant × read-tenant matrix.** **CHOSEN.** One question, four cells, and every shipped
  site already sorts into it — so the rule is falsifiable against the tree today rather than aspirational.
  It subsumes S8's three war stories without contradicting any of them, and it makes the fourth case
  (write-authenticated / read-anonymous) statable for the first time.
- **(b) Keep the three war stories and add a fourth.** The status-quo-plus option, and the cheapest.
  Rejected: the failure mode being repaired is that a developer must pattern-match their case against
  narratives, and each narrative is told from the caller's viewpoint. A fourth story makes the matching
  harder, not easier — and the mis-filing at `security-rules.md:291` is direct evidence that even the
  catalog's own author matched a cell-3 read onto the cell-3-adjacent *sweep* story.
- **(c) "Anonymous-reachable reads bypass; authenticated reads do not."** Rejected, and it is the
  alternative most likely to be proposed next because it is short and nearly right. It sweeps in every
  admission pre-check (an existence oracle) and every cell-4 confirm lookup (a wasted permanent S8
  exception), and it misses cell 2 entirely — the refresh-token revoke is an *authenticated* read that
  must bypass. It is wrong in both directions at once. D4 exists because of this option.
- **(d) "Secret-keyed reads bypass; everything else stays filtered."** Rejected on a single counter-pair:
  `GetByConfirmationCodeAsync` and `GetByTokenHashAsync` are the same shape and belong on opposite
  sides. The secret makes a bypass *safe*; it never makes one *necessary*.
- **(e) Delete the bypasses entirely by giving anonymous requests a tenant** — ADR-0028's D1/D2.
  **DECLINED by the owner** and not revived. Recorded here only so the next reader sees that the
  cheap-looking root fix was considered, chosen once, and refused at the product level; the matrix is
  what remains once that door is closed, and it costs nothing to keep the door reopenable because
  nothing in this ADR would need undoing.
- **(f) Mechanise the whole rule with a static check.** Rejected as the *primary* enforcement: deciding
  a method's cell requires its call graph, which no line-scanner has. Kept as the *partial* enforcement —
  the shipped roster-confinement shape (`UserRepositoryTokenLookupTenantTests`) is mechanical, and D6 of
  the catalog entry extends it rather than inventing something new.

## Consequences

**Cheaper / safer:**
- The next bypass is decided by answering one question instead of choosing a precedent, and the answer is
  checkable by a reviewer who has never seen the feature.
- Cell 4 becomes a *positive* answer ("filtered, and here is why") instead of an absence, which is what
  lets a reviewer refuse a bypass rather than merely fail to demand one.
- Two false justifications leave the tree: the "email is unique across the platform" pin, and S8's
  mis-filing of the employee read under the sweep story.
- The rule is descriptive of the shipped code, so adopting it puts **zero** existing call sites in
  violation — which is what makes the catalog edit's routing test 1 answer cleanly.

**More expensive (accepted):**
- One more thing to state at each bypass site (the cell + the re-pin). Cheap, and eight sites already
  carry it in substance.
- **The general rule is not fully mechanisable** and the honest tier says so. A closed-roster mechanical
  guard covers two repositories today; the rest is a reviewer's job until the roster-confinement check is
  extended repository-wide.
- The matrix has to be *read*, and a matrix is a heavier artifact than a slogan. Accepted deliberately:
  the slogans are what produced cells 3 and 4 being got wrong in the first place.

## How a reviewer verifies compliance

**Mechanical:**
1. Every `IgnoreQueryFilters()` / `GetQueryableIgnoringTenant()` site carries a comment naming **W**,
   **R**, and the re-pinning predicate. A site whose comment argues from "anonymous path" alone, with no
   asymmetry named, fails.
2. No re-pin appeals to a uniqueness property the schema does not enforce. Grep the bypass comments for
   *"unique"* and check each claim against the entity configuration.
3. `UserRepositoryTokenLookupTenantTests`'s eight-method roster is **unchanged** by any diff claiming
   this ADR. A diff that edits that roster is making a decision this ADR did not.
4. `EmployeeRepository.GetByUserEmailAsync` still has a filtered body and still has its authenticated
   callers; `GetByUserEmailIgnoringTenantAsync` is still called only from the token-mint paths.
5. `ApplyTenantQueryFilters`, `TenantProvider`, `AuthExtensions` are diff-empty.

**Test contract (names for the implementation ticket):**
- **TC-CELL-1 — the corrected justification.** No new test; the change is a comment. Verified by review
  against D2. *(Named here so the ticket does not invent a test for a comment.)*
- **TC-CELL-2 — the roster-confinement guard, extended.** The shipped
  `UserRepositoryTokenLookupTenantTests` shape applied across
  `src/Cleansia.Infra.Database/Repositories/**`: every bypass call site sits in a method on a declared
  roster, and every roster entry names its cell. **Must fail loudly when its corpus is empty or its
  anchor matches nothing** (`agents/knowledge/conventions.md:396-398`).
- **TC-CELL-3 — the cell-3 pin already exists** (`EmployeeRepositoryTenantTokenLookupTests.cs:74-100`)
  and both arms must stay: the ignoring read finds the tenant-stamped employee, the scoped read does
  not. It seeds a non-null tenant, which is what makes it able to fail.
- **TC-CELL-4 — the negative pin.** A tenant-stamped `User` row is **not** reachable by
  `GetByConfirmationCodeAsync` under a null ambient tenant, and this is asserted as **intended** rather
  than as a bug — so a future developer who "fixes" it goes red and reads D3.

## Challenge

*(Architect panel, challenger mode, 2026-08-11. Single-instance pass — see the Verdict's process note.)*

**CH-1 — BLOCKING-CANDIDATE: this ADR changes no code, so what is it deciding?** If every shipped site
already sorts into the matrix, the matrix is a description, and descriptions belong in the catalog, not
in an immutable decision record. Justify the ADR or downgrade it to a `security-rules.md` edit.

**CH-2 — BLOCKING-CANDIDATE (D3): reversing ADR-0028's D3 *reasoning* while keeping its conclusion is
the shape of a rationalisation.** The conclusion was reached under a premise that has been withdrawn; the
honest move is to re-open the question, not to hunt for a replacement argument for the answer already on
the page. Show that cell 4 was the reason and not a reason found afterwards.

**CH-3 — (D1) the matrix has a fifth cell it does not name: the background job that WRITES.** S8's
mirror case is about a sweep whose write-back is scoped. A 2×2 over reads cannot express "the sweep's
children are stamped from the ambient tenant at commit time." Either the matrix covers writes or it is
sold as more general than it is.

**CH-4 — (D2) "the caller has already been authenticated as the owner of that email" is itself an
appeal the code does not enforce.** `GetByUserEmailIgnoringTenantAsync` takes a bare string. Nothing in
its signature or body knows an authentication happened. The new justification is prettier than the old
one and equally unenforced.

**CH-5 — (D4) the scope line protects six call sites by naming them, which is a roster, and the ADR
elsewhere forbids rosters-without-membership-tests.** What decides the *next* cell-1 read?

**CH-6 — (O-1) an unmeasured baseline should not ship.** `conventions.md:382-387` makes `T1-CI` turn on
a baseline being zero. Declaring a gate whose baseline is "unknown, and definitionally non-zero" is a
way of claiming enforcement without paying for it.

**Checked and NOT challenged (named per the protocol):** the cell assignments of all twelve shipped
sites in the matrix table — each was opened and each sorts as claimed; the decision not to revive
ADR-0028 D1/D2 — an owner product call, correctly treated as closed; the S8 sweep guidance left
byte-unchanged — it is right and this ADR's D1 explicitly subordinates itself to it; the refusal to edit
`UserRepositoryTokenLookupTenantTests`'s roster — correct, that roster is a decision record in test form.

## Defense

- **CH-1 — REBUT, with the counterfactual.** A description would leave the next case open; this settles
  three live disagreements. (i) ADR-0028's panel argued CH-6 (*"keeping the legacy lookup filtered is
  dogma over threat-model"*) and resolved it by appeal to a mechanism that was then declined — so the
  question is genuinely open in the record, and D3 closes it. (ii) The catalog itself mis-files a cell-3
  read under the sweep story (`security-rules.md:291`), which is what a description without a test
  produces. (iii) D2 declares an existing shipped justification **false**, which is a ruling, not a
  description. An ADR is also the only sanctioned way the catalog's S8 text gets *narrowed*, and this
  narrows it.
- **CH-2 — CONCEDE the burden, REBUT the conclusion, and the evidence is in the tree.** The test for
  "found afterwards" is whether the replacement argument was *available* before the answer, and it was:
  cell 4's symmetry is a property of the filter body and the stamping site
  (`src/Cleansia.Infra.Database/CleansiaDbContext.cs:262-268`, `:89-91`) — **both of which ADR-0028's own
  Context cites** — so that panel had every fact it needed and reached for the host-registry argument
  instead. The guard that pins the confirm family filtered carries its reasoning in its own roster
  comments (`src/Cleansia.Tests/Features/Auth/UserRepositoryTokenLookupTenantTests.cs:48-75`) and
  ADR-0028's D3 and CH-6 cite it nowhere. *(No claim is made here about which artifact was written
  first — no command was run and none is available to this panel.)* The stronger point stands anyway: if
  cell 4 had come out the other way, the honest outcome would be a code change, and D3 explicitly costs
  nothing precisely because it does not.
- **CH-3 — CONCEDE + REVISE (folded into D1).** The challenge is right that a 2×2 over reads cannot
  carry the write-back rule. D1 now subordinates rather than subsumes: the background case is named as a
  *special case of asymmetry*, and S8's existing sweep guidance —**both** sides of the loop, and the
  commit inside the iteration — is cited as the correct elaboration and left byte-unchanged. The matrix
  claims reads. It does not claim writes and no longer reads as if it did.
- **CH-4 — CONCEDE in part, REVISE, and the residue is real.** Conceded: the method signature cannot
  enforce it, and D2's pin is a *caller* obligation, not a *callee* invariant — exactly like
  `RefreshTokenRepository.GetActiveByUserIdAsync`, whose pin is "the `UserId` comes from the caller's own
  JWT" and which the method likewise cannot verify. The difference from the old justification is not
  enforceability, it is **truth**: "email is globally unique" is a false statement about the schema that a
  reader can act on and be wrong; "the caller authenticated this email first" is a true statement about
  the two call sites, and verification item 4 pins that the caller set stays those two. Recorded as a
