# ADR-0052 — A cleaner's own deletion files a request; only an admin erases, because ending a working relationship is an offline act and the records that survive it are not the subject's to delete

- **Status:** `proposed`
- **Date:** 2026-08-18
- **Supersedes:** —
- **Superseded by:** —
- **Applies to:** backend, frontend, mobile

## Context

`POST /api/v1/Gdpr/delete-account` is exposed on four hosts and ran one cascade for every caller. It
was written for a customer, and for a customer it is right: a customer's relationship with the
platform is the account, so erasing the account ends it.

A cleaner's is not. Behind an `Employee` row sits a working relationship with a contract, statutory
financial records, and — per [ADR-0041](./adr-0041) — a self-billing agreement whose facts are "the
authority for invoices that are themselves retained". None of that ends because someone taps a button
in an app, and none of it is the subject's to delete.

The endpoint did not know the difference. Its only employee-aware guard was an open-invoice check;
its blocking-order check filters `Order.UserId`, the **customer** axis, so it never saw a seat a
cleaner holds on someone else's job. A cleaner could erase themselves mid-engagement, and the same
call hard-deleted every `EmployeeDocument` row and blob — including `DocumentType.Contract` and
`DocumentType.TaxDocument`. The contract was destroyed at precisely the moment the relationship it
governs was ending.

Two store requirements make the shape urgent rather than merely wrong: Apple Guideline 5.1.1(v) and
Play's equivalent both require an in-app deletion path for any app that creates accounts. Both accept
a *request* where deletion genuinely cannot be immediate, provided the app says so and states what is
retained. So the honest design and the compliant design are the same design.

## Decision

**A subject with an `Employee` is not erased by the self path. A `Pending` `GdprRequest` of type
`Deletion` is filed and nothing else runs.** An administrator fulfils it afterwards through
`AdminDeleteUserAccount`, which runs the same cascade with an admin actor recorded.

Three things make this concrete.

**The route and its contract do not change.** `POST /Gdpr/delete-account` keeps its path, its empty
request body and its `200`. Nothing regenerates: not NSwag, not the mobile specs, not the four
generated clients. What each app *says* about the outcome differs, and that is a string, not a
contract.

**The deferral is an explicit parameter, not an inference.** `IGdprDeletionService.DeleteUserAccountAsync`
takes `bool deferEmployeeErasure` with **no default**. The self path passes `true`, the admin path
`false`.

> The first implementation forked inside the service on `user.Employee is not null` alone. Because
> `AdminDeleteUserAccount` calls the same method, that made cleaners unerasable by **anyone**,
> administrators included — a worse defect than the one being fixed. It compiled. Only the existing
> erasure suites going red caught it. A parameter with no default forces every caller to state which
> path it is, and the compiler finds them all.

**Eligibility guards run on both paths.** An admin cannot erase a cleaner out from under a live job
either — the same reading the pre-existing open-invoice guard already had. Two are added:

| Key | Refuses when |
|---|---|
| `gdpr.deletion_blocked_by_assigned_order` | the cleaner holds an `OrderEmployee` seat on an order in a non-terminal status |
| `gdpr.deletion_blocked_by_unsettled_pay` | a pay row is not attached to an invoice, or its pay period has not reached `Paid` |

The second is deliberately **one** key for two structural shapes. To a cleaner both mean "work I have
not been paid for" and both have the same remedy — settle the period — so splitting them would name a
distinction the reader cannot act on.

## Alternatives considered

- **A separate `POST /Gdpr/request-deletion` endpoint.** Honest about intent, and rejected on cost:
  it needs a mobile spec re-dump and an NSwag regeneration, both owner-run, before any of the four
  clients can call it. The existing route already reaches every client and already carries the right
  semantics for a customer.
- **Approve / reject statuses on `GdprRequest`.** `GdprRequestStatus` is `[SwaggerEnumAsInt]` on the
  wire to three generated clients, so new members are an owner-run regeneration. They also buy little:
  an admin already sees pending requests in `GET requests` and erases through
  `POST delete-account/{userId}`. Fulfilment exists; only its convenience is missing.
- **Branch on `deactivationReason`.** Zero signature change, and the reason already distinguishes self
  from admin. Rejected because it is implicit: a future caller passing a new reason gets erasure by
  falling through, and nothing makes them decide.
- **Refuse a cleaner's deletion outright.** Simplest, and it fails both stores — they require a path,
  not a refusal.

## Consequences

**Cheaper.** A cleaner cannot destroy their own contract or vanish from a staffed job. The retention
promise in [ADR-0007](./adr-0007) — financial rows are anonymised, never removed — stops being
contradicted by the erasure path itself. Both stores' deletion requirements are satisfiable without a
new endpoint.

**More expensive.** Every client that calls this route must know which audience it serves, because the
result no longer says. The partner web app already had to change: it announced "your account has been
deleted" and signed the cleaner out, which became a lie the moment the backend stopped erasing. The
two partner mobile apps have no deletion screen yet and must be built to say "requested", not
"deleted". A filed request now depends on an administrator noticing it — there is no notification, and
that is a real gap, not a hidden one.

**Unresolved, and deliberately not decided here.** How long financial records are retained is an
accounting answer, not an architectural one; no document in this repository states a period, and
`RetentionDefaults` has no invoice or pay-period key at all. Until it does, no client can state a
duration in its copy. Separately, erasure still hard-deletes `EmployeeDocument` rows including
`Contract` and `TaxDocument`; this ADR stops a *cleaner* triggering that, and does not rule on whether
an *admin* should.

## How a reviewer verifies compliance

- `DeleteUserAccountAsync` has no default for `deferEmployeeErasure`, and both production call sites
  name it.
- The deferral branch returns `BusinessResult.Success()`. `UnitOfWorkPipelineBehavior` commits only on
  a successful result, so a failure would discard the filed row.
- Nothing after the deferral branch runs for a deferred subject — not `MarkProcessing`, not the Stripe
  membership cancel, not `AnonymizeUserDataAsync`. `EmployeeDeletionRequestTests` asserts the subject
  comes back with its original email and still active.
- A client calling this route on a partner audience says "requested", never "deleted", and does not
  end the session.
- New `gdpr.*` keys exist under `api.*` in all five locales of every app that can reach the endpoint.

## Roles affected

None created. The behaviour described in `docs/flows/gdpr-and-audit.md` is updated to distinguish a
customer subject from an employee subject, which it previously did not.
