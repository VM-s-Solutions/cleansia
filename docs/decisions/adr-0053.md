# ADR-0053 — The weekly order cap becomes a per-cleaner decision an admin makes, unset by default, because a rating ladder whose lowest rung is the *default* rating throttles hardest exactly the cleaner with the least evidence (supersedes-in-part ADR-0037 Fact 3's status-blind-cap finding)

- **Status:** `accepted`
- **Date:** 2026-08-22
- **Partially supersedes:** **ADR-0037 Fact 3's** bullet *"The weekly cap is status-blind"*
  (`adr-0037.md:207-208`) — that fact was true when recorded and is now false, because
  `GetEmployeeOrderCountThisWeekAsync` now constrains `SlotBlockingStatuses`
  (`OrderRepository.cs:252-262`). Its closing sentence *"Confirmed in full, including both halves of
  the 'counts against the cap but does not block the calendar' claim"* (`adr-0037.md:212-213`) rests on
  that bullet and falls with it, in its **cap half only**. **Everything else in ADR-0037 stands**: the
  offerability predicate, the rest of Fact 3, and *"the calendar is not blocked"*
  (`adr-0037.md:209-210`), which this ADR does not touch — and which is now the *same* term the cap
  reads, which is the point of D-C2 below.
- **Does NOT supersede ADR-0036 A6, in any part** — and the earlier draft of this bullet, which claimed
  it did, was wrong. A6 (`adr-0036.md:1031`) reads in full: *"Both are genuinely dynamic
  (`TakeOrder.cs:125-161`): the limit resets weekly and the conflict depends on orders taken after
  creation. A creation-time check is wrong in both directions."* It asserts nothing about the cap being
  universal, so this ADR falsifies no premise of it, and ADR-0039's ruling on it
  (`adr-0036.md:1931-1938`, headed **"What is NOT superseded — and this half is settled on evidence,
  not judgement"**) rests on one ground this ADR leaves untouched: the window comes from
  `DateTime.UtcNow.Date` (`OrderRepository.cs:247-250`), so at creation, for a booking more than a week
  out, it answers about a week that does not contain the booking. **A6's weekly-cap half stands whole.**
  Nobody may "complete" the hold resolver by adding a cap check — and the fact that
  `TakeOrder.cs:211` now short-circuits on null, making such a check look nearly free, is a reason to
  restate the prohibition, not to weaken it.
- **Superseded by:** —
- **Applies to:** backend, frontend (admin)

## Context

`TakeOrder` has always had a weekly cap. Until this change it was a **rating ladder**: three jobs a
week below 3.5 stars, six below 4.5, ten above — a platform-wide rule nobody had chosen for anybody
in particular, and one whose reasoning is preserved in the code that replaced it
(`TakeOrder.cs:194-199`, `Employee.cs:134-138`).

Its floor caught everyone. `Employee.AverageRating` is a `decimal` that defaults to `0`
(`Employee.cs:60`) and is only ever written by `UpdateRating` (`Employee.cs:309-314`), which runs when
a review lands. `0` is below `3.5`. So **every newly approved cleaner was capped at three jobs a week
from their first day**, and the only exit was accumulating reviews — which requires taking jobs. A
platform that throttles a new cleaner hardest has the incentive backwards.

The count made it worse. `GetEmployeeOrderCountThisWeekAsync` counted every assignment row in the
Monday-to-Sunday window with **no status filter at all**, so a job the customer cancelled still
consumed one of the three. ADR-0037 recorded exactly this on 2026-08-03 and did not rule on it.

> **We saw the second half and filed it as a curiosity.** ADR-0037's Fact 3 is about a *takeable
> cancelled order*; inside that frame, *"a dead job consumes one of the cleaner's 3/6/10 slots"*
> (`adr-0037.md:207-208`) reads as trivia, and it was written down beside the observation that the
> dead assignment *"does not even reserve the time"*. Neither half is a bug alone: a rating ladder is
> a defensible policy and a counter that counts assignments is an obvious implementation. It is the
> composition that bites — the ladder's lowest rung is the default rating, and the counter counts
> rows that are not work. A new cleaner whose three jobs were all cancelled by the customer sat out
> until Monday having done nothing.

## Decision

**`Employee.WeeklyOrderLimit` is a nullable `int`. `null` means unlimited, and it is the default for
every cleaner** (`Employee.cs:146`; column `nullable: true`, `20260822150939_Initial.cs:872`). The
ladder is deleted. A cap exists only where an administrator deliberately put one on one person.

**Null is load-bearing, not missing.** There is no backfilled default, for the reason
`Employee.JobRadiusKm` (`Employee.cs:104-112`) has none — this is the same shape adopted deliberately,
not a coincidence: a number nobody chose would silently limit an existing cleaner, and work that stops
arriving produces no complaint from the person it costs. The gate short-circuits on it before doing
any work: `if (employee.WeeklyOrderLimit is not { } limit) return true;` (`TakeOrder.cs:211`), so the
overwhelmingly common path never runs the count query. That is the catalog's *"a rule that REJECTS
cheaply runs before any rule that MATERIALIZES the payload"* (`agents/knowledge/patterns-backend.md`)
applied to a rule that *admits* cheaply.

**The count is no longer status-blind.** It now filters `SlotBlockingStatuses`
(`OrderRepository.cs:252-262`) — the same set the overlap scan uses, for the same reason: an order
occupies a cleaner only while it is a live commitment.

**What the number means, stated plainly, because the status term changed it and the labels did not.**
`SlotBlockingStatuses` is `[New, Pending, Confirmed, OnTheWay, InProgress]`
(`OrderRepository.cs:270-277`) — it excludes `Completed` as well as `Cancelled`. So
`WeeklyOrderLimit = 3` does **not** mean *"three jobs this week"*. It means **"at most three
*outstanding* commitments, counted over the orders whose `CleaningDateTime` falls in the current
Monday-to-Sunday UTC week, at the instant this cleaner taps Take"**. Two consequences follow and both
are load-bearing:

- **A finished job leaves the count.** A cleaner who completes three jobs by 14:00 may take three more
  the same afternoon. The only remaining brake on weekly volume is the overlap scan, which forbids
  *simultaneous* work and says nothing about *volume*: against the bookable day of 08:00–20:00
  (`BookingPolicy.cs:42-43`) and 120-minute services, the ceiling under a cap of 3 is on the order of
  six jobs a day, or 42–49 a week. **That number is a *labour* ceiling, not a policy one** (lead
  ruling, 2026-08-23): reaching it means 84–98 hours of cleaning actually performed, each job gated by
  `IsTooEarlyToStart` (`BookingPolicy.cs:156-159`), after-photos and settled payment
  (`CompleteOrder.cs:56-75`). Within a week the cap bounds nothing except the cleaner's stamina and the
  overlap scan. **And the "against the deleted ladder's ten" comparison overstates the delta**: the
  ladder's counter was status-blind but *equally* bounded to `DateTime.UtcNow.Date`
  (`OrderRepository.cs:247-250`, byte-identical before and after this change), so a laddered cleaner
  could already take any number of jobs dated in a later week. The honest statement of the change is
  **ten rows in the current week → unbounded outstanding in the current week**, against an allowance
  that was already unbounded outside it. What is unchanged by both corrections is the operational
  point: an admin who sets 3 believing they capped the week has been misled in the **permissive**
  direction, silently.
- **The window is derived from `DateTime.UtcNow.Date` (`OrderRepository.cs:247-250`), not from the
  order being taken.** The count is asked exactly once, at take time (`TakeOrder.cs:213`). A cleaner
  capped at 3 who opens the board on Monday and takes fifteen jobs scheduled for *next* Tuesday
  evaluates every one of them against *this* week's window, finds zero, and is admitted every time.
  Next Monday they hold fifteen live jobs under a cap of three and no refusal ever fired. **The cap
  bounds the week you tap in, not the week the work is in.** This is the same `UtcNow.Date` property
  ADR-0036 A6 was upheld on, applied to the shipped call site rather than to a hypothetical
  creation-time one — and it is what an admin is actually buying.

Both are recorded here rather than fixed here — but the earlier draft of this paragraph offered a
**false dichotomy** and the lead corrected it (2026-08-23). There are three ways to make the label
true, not two:

1. **Count every status except `Cancelled`** — one predicate, `o.CurrentStatus != OrderStatus.Cancelled`
   (`CurrentStatus` is non-nullable). It makes the *outstanding* half of the label true without
   re-opening the cancellation defect this ADR closes, because a cancelled order still does not count.
   It is the cheapest honest fix and it is **deferred, not rejected**, to the ticket that builds the
   admin read surface. If it is taken, the status set must be declared **locally** (a
   `WeekConsumingStatuses` array beside the query) rather than by borrowing `SlotBlockingStatuses`:
   *does this occupy the calendar* and *does this consume the week* are two questions, and one array
   answering both is how the next change breaks a rule it was not aiming at. The comment at
   `OrderRepository.cs:256-260` already names the borrow (*"the same reasoning applied to a different
   question"*) and that is the tell.
2. **Count terminal statuses again** — re-opens the cancellation defect. Rejected.
3. **Derive the window from the order's own `CleaningDateTime`** — closes the second bullet rather
   than the first, and is a different query with its own decision (see the last *Alternative*; it also
   touches ground ADR-0036 A6 and ADR-0039 A16 rest on, so it needs its own ADR).

Neither 1 nor 3 is in scope here; what is in scope is that the record and the field's own summary stop
asserting a weekly total. `Employee.WeeklyOrderLimit`'s doc-comment (`Employee.cs:130-146`) still reads *"How many orders
this cleaner may hold in one Monday-to-Sunday week"* and must be corrected to say *outstanding at
once, within the current week's bookings*.

**One is the floor, not zero**, in both the validator (`AdminSetEmployeeWeeklyOrderLimit.cs:54-57`)
and the entity (`Employee.cs:155-165`). A cleaner who may take nothing is a `ContractStatus`
decision; a suspension expressed as a quiet number is hidden from every screen that reads the
contract.

**Setting it is a narrow command, not a field on `AdminUpdateEmployee`.** That command treats every
field as nullable and merges with `?? existing` (`AdminUpdateEmployee.cs:118-161`), so `null` there
means *"not supplied"* — it structurally cannot express *clear this cleaner's cap back to unlimited*,
which is half of what the feature is for. `AdminSetEmployeeWeeklyOrderLimit` is the in-repo shape
`AdminUpdateEmployeeAvailability` already established: its own endpoint
(`AdminEmployeeController.cs:116-130`), its own audit label, and a snapshot that carries the **values**
rather than only ids (`AdminSetEmployeeWeeklyOrderLimit.cs:38`) — a weekly limit is a number the
platform chose, not personal data belonging to the subject.

| Key | Refuses when |
|---|---|
| `order.weekly_limit_reached` | a capped cleaner's live assignments this week have reached their limit (`BusinessErrorMessage.cs:98`) |
| `employee.weekly_limit_invalid` | an admin supplies a cap below 1 (`BusinessErrorMessage.cs:99`) |

## Alternatives considered

- **Keep the ladder, raise its floor.** Cheapest edit, and it is still a number nobody chose applied
  to everybody — and still makes a rating computed from a handful of reviews a throttle on earning.
- **Seed `AverageRating` at a neutral 4.0 for new cleaners.** One line, and it does fix the floor.
  Rejected because the rating is customer-facing: it would put a score on a screen that no customer
  produced. A display value must not be repurposed as a policy input's default.
- **Delete the cap entirely.** Tempting, and the reason it is rejected is **not** the one an earlier
  draft of this ADR gave. That draft said the platform needs an answer for *"a cleaner who serially
  over-commits and cancels"* — which this decision's own status term makes the cap unable to see
  (`Cancelled` is not in `SlotBlockingStatuses`, `OrderRepository.cs:270-277`), and which the platform
  has **no verb for** in any case: `Order.UnassignEmployee` (`Order.cs:662`) has exactly one production
  caller, `AdminReassignOrder.cs:93`, and ADR-0036 A14 records the absence of a cleaner-side
  decline/withdraw path as a design fact. A cleaner cannot cancel their own assignment at all.
  The cap is kept on a **different** reason: it is the only per-person brake on **how much live work
  one cleaner may be holding at once**, and the failure it bounds is the no-show and the
  quality-collapse — a cleaner an admin has reason to distrust, holding six live jobs in a city where
  six customers are waiting. That is a real answer to a real problem, it is expressible today, and it
  is what the count actually measures. **Catching churn would need a second, status-blind counter of
  assignments taken and released per week; this ADR does not build one and does not claim the cap is
  one.**
- **A nullable field on `AdminUpdateEmployee`.** No new endpoint, no new audit label — and no way to
  clear the cap, per the `?? existing` merge above. The absence would be discovered by an admin, in
  production, trying to undo their own restriction.
- **Zero as the floor, meaning "suspended".** Two mechanisms for one state, and the quieter one wins
  by accident: every screen that reads `ContractStatus` would show an approved cleaner who cannot
  work.
- **Check the cap at booking creation / in the preferred-hold resolver.** This is A6's own rejection
  and it survives this ADR intact, on its own evidence — the window is derived from `UtcNow.Date`, so
  for a booking more than a week out it answers about a different week.

## Consequences

**Cheaper.** A newly approved cleaner is no longer throttled hardest at the moment they most need
work, and a customer cancellation no longer spends a capped cleaner's week. The common path costs one
already-loaded column read and no query. Restricting one cleaner is now possible *without* a policy
change that touches everybody — which is the shape that scales when a country or a tenant needs a
different answer.

**More expensive.** There is **no admin UI for this yet** — the endpoint exists and nothing calls it.
The admin client cannot until NSwag is regenerated, which is owner-run: any ticket that builds the
screen must carry `manual_step: nswag-regen`. `employee.weekly_limit_invalid` is present in all five
`cleansia-admin.app` locales (`assets/i18n/{en,cs,sk,ru,uk}.json:2341`) and listed in
`ADMIN_SURFACE_ERROR_KEYS` (`apps/cleansia-admin.app/src/app/i18n/error-contract-parity.spec.ts:377`),
so the parity guard covers it. And **nothing tells a capped cleaner they are capped**: the refusal at
the moment they try to take a job is the first they hear of it, and `order.weekly_limit_reached` is an
argless key (`BusinessErrorMessage.cs:98`) so the copy cannot say what the cap is, who set it, or when
it resets. That is a real gap, named here rather than hidden.

**Sequencing is part of this decision, not a follow-up.** A restriction that is **writable and
invisible** is worse than one that does not exist yet: an admin caps a cleaner on Tuesday, the cleaner
is refused on Thursday, support opens the admin employee detail and there is no cap field and no
reading of the `employee.weekly_limit.update` audit row on any screen. **The endpoint must not be
exercised in production until the admin read surface ships** — the cap on the employee detail, and the
audit row legible somewhere. Until then the correct state of this feature in production is *"present,
unused"*.

**The platform is deliberately blind to the failure the ladder used to catch, and the first detection
is a customer complaint.** This decision trades an automatic brake for an operator's judgement, and it
does not ship the operator an instrument. There is no take-rate counter, no per-cleaner workload gauge
and no job-concentration metric: the only custom meters subscribed anywhere are `Cleansia.Integration`
and `Cleansia.RateLimiting` (`src/Cleansia.ServiceDefaults/Extensions.cs:59-60`). There is no
"orders taken this week, by cleaner, by city" report. So *"one cleaner has taken every job in Brno for
three weeks and the reviews are sliding"* surfaces as a complaint, is correlated by hand, and is acted
on through owner-run SQL. **The named instrument is a live-commitment count column on the admin
employee grid** — the same number the gate reads, on the screen where the cap is set — and it belongs
in the same ticket as the read surface above.

**Cheap to reverse in code, expensive to reverse in practice, and the two directions are not
symmetric.** Reinstating a default cap is a one-line predicate. Removing a limit is a gift and is
absorbed instantly; re-imposing one a quarter later is an income cut delivered to cleaners who have
arranged their schedules around uncapped volume, and the platform's only channel for delivering it is
a refusal at the moment they try to earn. "Unlimited by default" is the state everyone adapts to,
which makes the expensive direction the likelier one.

**Unresolved.** Whether a cap should expire or decay has no current owner ruling; the audit row
(`employee.weekly_limit.update`) records who set what and when, so it remains answerable later without
a migration. Whether an admin setting a cap should **notify the cleaner** is *not* filed here as
deferrable — the moment a cap can be set silently and its only feedback is a refusal, that is an owner
ruling, escalated as **`Q-CAP-01`** (`agents/backlog/questions/open.md`).

## How a reviewer verifies compliance

- No rating is read in any **executable expression** of a cap decision. `AverageRating` has exactly
  one permitted occurrence under `Features/Orders/` — the doc-comment at `TakeOrder.cs:195` that
  preserves the deleted ladder's reasoning. A second hit, or that one moving out of a comment, is the
  regression. `NotExceedWeeklyOrderLimitAsync` (`TakeOrder.cs:201-216`) reads only the column.
- The null case returns before the count query — a change that runs the count unconditionally is a
  regression even though it is behaviourally identical.
- `GetEmployeeOrderCountThisWeekAsync` still constrains `SlotBlockingStatuses`. Deleting that term is
  the outage, per `patterns-backend.md §"Moving a gate onto a new column: the term you delete is the
  outage"`.
- The validator answers `employee.weekly_limit_invalid` for anything below 1
  (`AdminSetEmployeeWeeklyOrderLimitTests.cs:106-137` — `A_Cap_Below_One_Is_Refused` and
  `Clearing_The_Cap_Is_Valid_But_Zero_Is_Not`, both of which exercise the **Validator**). The
  `ArgumentOutOfRangeException` in `Employee.SetWeeklyOrderLimit` (`Employee.cs:157-161`) is
  **deliberately unpinned**: it is an unreachable guard kept for symmetry with `SetJobRadius`
  (`Employee.cs:118-128`), no test asserts it, and per CLAUDE.md §4 it does not earn one — an
  unreachable throw is paid once by support, a test for it is paid by every future reader. A reviewer
  must not read this bullet as claiming coverage it does not have.
- The handler guards its own load rather than null-forgiving the validator's existence check
  (`AdminSetEmployeeWeeklyOrderLimit.cs:71-75`).
- The audit attribute is present and pinned (`EmployeeUserAuditCoverageTests.cs:47`).
- No creation-time or hold-resolver path calls `GetEmployeeOrderCountThisWeekAsync`.

## Roles affected

None created. `docs/product/business-rules.md` must gain the row it never had — the cap is unset by
default, is a per-cleaner administrative act, and counts **outstanding** commitments in the current
week rather than jobs done — and lose any statement of the 3/6/10 ladder.
`docs/flows/offerability-and-take.md` describes the take chain and must show the cap rule
short-circuiting on null.

Three in-tree strings now assert something this decision made false, and each is a **required change**
carried by whichever ticket lands next in its file:

- **`ReservationSpendsNoCapacityTests.cs:24`** still states, in the present tense, that
  `GetEmployeeOrderCountThisWeekAsync` *"has no status term and no confirmation term"*. **Resized by
  the lead (2026-08-23): that sentence is a two-conjunct claim and only the first conjunct died.** The
  status term now exists (`OrderRepository.cs:261`); *"no confirmation term"* is **still true** —
  nothing in `:252-262` distinguishes an accepted assignment from a reserved one — and the ADR-0045 D2
  argument the file exists to pin is **completely unharmed**, because `SlotBlockingStatuses` contains
  `New`/`Pending`/`Confirmed` (`:270-277`), so a reservation row would still spend a capped cleaner's
  week exactly as the item argues. The correction must therefore **preserve** the item, not weaken it:
  replace only the first conjunct with *"filters to live statuses (`SlotBlockingStatuses`) but has no
  CONFIRMATION term"*. Lines `:26-28` of the same doc-comment **were** updated for the opt-in cap, so
  the staleness is selective — in the one file whose entire purpose is to pin ADR-0045 D2 against the
  shipped queries.
- **`Employee.cs:130-146`** — the `WeeklyOrderLimit` summary's *"How many orders this cleaner may hold
  in one Monday-to-Sunday week"*, per the Decision above. `:132`'s *"Read by `TakeOrder`, and by
  nothing else"* is false at the letter and is part of the same required change:
  `AdminSetEmployeeWeeklyOrderLimit.cs:77,81,84` reads it too, for its audit snapshot. The true
  sentence is *"the only **decision** that reads it is `TakeOrder`"*.
- **`cleansia.app/src/assets/i18n/{en,cs,sk,ru,uk}.json:1488`** carries `order.weekly_limit_reached`
  (*"You've reached the booking limit for this week."*) in the **customer** app, and
  `apps/cleansia.app/src/app/i18n/error-contract-parity.spec.ts:363` pins it there. The key's only
  writer is `TakeOrder.cs:68`, a **partner** endpoint (`BusinessErrorMessage.cs:98` has exactly two
  references, `TakeOrder.cs:68` and its test). No customer-host endpoint can raise it, so the string is
  dead copy in five locales asserting a customer-side weekly booking limit that has never existed —
  and this ADR makes that sentence less true, not more.

## Challenge

*(Architect panel, challenger mode, 2026-08-22. Angle: operations, cost and the human consequence —
not code-vs-record, which is the other challenger's pass.)*

### C1 — The cap the ADR keeps cannot do the job the ADR keeps it for
**Angle:** operations
**Why it matters:** *Alternatives considered* rejects "delete the cap entirely" on one reason: *"the
platform still needs an answer for a cleaner who serially over-commits and cancels. The cap is that
answer"* (`adr-0053.md:96-97`). The Decision, two paragraphs earlier, removes that answer. The count
now filters `SlotBlockingStatuses` (`OrderRepository.cs:252-262`), and that set is
`[New, Pending, Confirmed, OnTheWay, InProgress]` (`OrderRepository.cs:270-277`) — `Cancelled` is
**not** in it. So a cleaner who takes twenty jobs and cancels eighteen carries a live count of two and
the cap never fires. The serial over-committer is by definition the cleaner whose assignments end up
`Cancelled`; they are exactly the population the new status term exempts. The two halves of this
decision cancel each other, and the rejection of the cheapest alternative rests on a capability the
decision itself deleted. Either the record answers "delete it entirely" on a *different* reason, or it
names the second, churn-shaped counter (assignments taken and released per week, status-blind) that
would actually catch the behaviour — which is a new mechanism and belongs in this ADR or a follow-on,
not in folklore.

### C2 — It is not a weekly cap; it is a concurrent-open-commitment cap, and every label says otherwise
**Angle:** operations
**Why it matters:** `SlotBlockingStatuses` excludes `Completed` as well as `Cancelled`
(`OrderRepository.cs:270-277`). A job finished on Monday morning leaves the count on Monday afternoon.
So `WeeklyOrderLimit = 3` does not mean "three jobs this week" — it means "three *outstanding* at any
instant". Worked: 08:00–20:00 is the bookable day (`BookingPolicy.cs:42-43`), the seeded catalogue has
120-minute services, so a cleaner under a cap of 3 can complete three jobs by 14:00 and take three more
the same afternoon; over a week the only remaining brake is the overlap scan, which forbids
*simultaneous* work and says nothing about *volume*. Rough ceiling: ~6 jobs/day × 7 = **~42 a week**
against the old ladder's top rung of 10. The old status-blind counter genuinely bounded weekly
throughput (10 rows = 10 jobs, whatever became of them); the new one bounds nothing of the sort. The
ADR presents this purely as a cancellation fix — *"The count is no longer status-blind … an order
occupies a cleaner only while it is a live commitment"* (`:66-69`) — and never states that the number's
**meaning** changed. `Employee.WeeklyOrderLimit`'s own summary still says *"How many orders this
cleaner may hold in one Monday-to-Sunday week"* (`Employee.cs:131-132`), and the error key is
`order.weekly_limit_reached` (`BusinessErrorMessage.cs:98`). An admin reading either will set 3
believing they capped the week. This is the shape of a control an operator misuses in its first week —
and misuses in the *permissive* direction, silently. Say what the number means, in the ADR and in the
field's summary, or filter on the statuses that make the label true.

### C3 — The failure the ladder guarded now has no observable signal, and the record does not name one
**Angle:** operations
**Why it matters:** The decision replaces an automatic brake with a human one ("an admin deliberately
put one on one person"). The human needs a signal, and there is none in the tree. The only custom
meters subscribed anywhere are `Cleansia.Integration` and `Cleansia.RateLimiting`
(`src/Cleansia.ServiceDefaults/Extensions.cs:59-60`) — no take-rate counter, no per-cleaner workload
gauge, no job-concentration metric. There is no admin screen: `weeklyOrderLimit` matches **zero files**
under `src/Cleansia.App`, which the ADR concedes for the write path (`:116`) but not for the read.
There is no report of "orders taken this week, by cleaner, by city" anywhere. So the escalation path
for *"one cleaner has taken every job in Brno for three weeks and the reviews are sliding"* is: a
customer complains → someone correlates by hand → someone asks the owner to run SQL → someone
regenerates NSwag and builds a screen. The *How a reviewer verifies compliance* list has seven items,
none of which is "the platform can tell you this went wrong." A decision that trades an automatic rule
for an operator's judgement owes that operator the instrument; name it (a live-commitment count column
on the admin employee grid, or a metric with a threshold) or state explicitly that the platform is
deliberately blind here and that the first detection is a customer complaint.

### C4 — The write endpoint ships ahead of any read, which is the configuration that produces an unexplainable incident
**Angle:** operations
**Why it matters:** Today the cap is settable by API and visible on no screen. Concretely: an admin
caps a cleaner at 3 on Tuesday. Thursday the cleaner taps Take and gets `order.weekly_limit_reached` —
a bare key constant (`BusinessErrorMessage.cs:98`, no args), so the copy cannot say what the cap is,
who set it, or when it resets. The ADR already records that *"nothing tells a capped cleaner they are
capped"* (`:118-121`). The cleaner calls support. Support opens the admin employee detail: there is no
cap field. Support cannot read the `employee.weekly_limit.update` audit row from any screen either. So
the first production use of this feature is a support case that no screen in the platform can answer,
and the resolution path runs through `manual_step: nswag-regen`. The ADR files "no admin UI yet" under
*More expensive* as a build-later item; operationally, **sequencing** is the decision: a restriction
that is writable and invisible is worse than one that does not exist yet. Either the ADR says the write
endpoint must not be exercised in production until the read surface ships, or it accepts the incident
in writing.

### C5 — Reversibility is asymmetric, and the record treats it as neutral
**Angle:** operations
**Why it matters:** Reinstating a default cap is a one-line predicate — cheap in code. It is not cheap
in people, and the two directions are not symmetric. Removing a limit is a gift, absorbed instantly.
Re-imposing one, a quarter later, is an income cut delivered to cleaners who have arranged their
schedules and their earnings around uncapped volume — and the platform has **no channel to deliver
it**: the ADR leaves *"whether an admin setting one should notify the cleaner"* undecided (`:123-126`)
while the field's only feedback path is a refusal at the moment the cleaner tries to earn. This ADR
makes the expensive direction more likely, because "unlimited by default" is the state everyone adapts
to. Two things follow. (a) *Consequences* should say the decision is cheap to reverse in code and
expensive to reverse in practice, rather than leaving reversibility unstated. (b) The notification
question stops being deferrable the moment a cap can be set silently: it is an owner ruling
(`questions/open.md`), not an "unresolved, and deliberately not decided here."

### C6 — The supersession of ADR-0036 A6 is vacuous, and it is over-broad against a ruling explicitly headed "What is NOT superseded"

**Angle:** correctness

**Why it matters:** A6 (`adr-0036.md:1031`) reads, in full: *"Both are genuinely dynamic
(`TakeOrder.cs:125-161`): the limit resets weekly and the conflict depends on orders taken after
creation. A creation-time check is wrong in both directions."* It asserts nothing about a weekly limit
being "a live universal gate every cleaner is under" — that premise, which this ADR says falls, is not
in A6, and it is not in ADR-0039's ruling either. That ruling, recorded at `adr-0036.md:1931-1938`
under the heading **"What is NOT superseded — and this half is settled on evidence, not judgement"**,
gives exactly one ground: the `UtcNow.Date` window. This ADR concedes that ground is unchanged
("`GetEmployeeOrderCountThisWeekAsync` **still** derives its window from `DateTime.UtcNow.Date`") and
that A6's conclusion stands. Nothing falls, so nothing should be marked superseded. This is not
bookkeeping: ADR-0036 is `accepted` and immutable, and a `supersedes-in-part` marker on A6 tells every
future reader that a settled, evidence-backed prohibition is now *partly* void — at precisely the
moment reintroducing it looks cheapest, because `TakeOrder.cs:211` short-circuits on null and a
hold-resolver cap check now appears free for ~100% of cleaners. The ADR's own last Alternative
anticipates exactly this temptation; the supersession header undercuts it. Either quote the
universality premise from A6 verbatim, or drop the A6 limb and keep only the ADR-0037 limb (which is
accurate and correctly scoped to the bullet). One scoping miss on the limb that *is* right:
`adr-0037.md:212-213` — *"Confirmed in full, including both halves of the 'counts against the cap but
does not block the calendar' claim"* — also rests on the falsified bullet and is not named.

### C7 — The cap cannot bound the week the booking is in. The ADR quotes the evidence for that and does not draw the conclusion

**Angle:** correctness

**Why it matters:** `GetEmployeeOrderCountThisWeekAsync` derives its window from
`DateTime.UtcNow.Date` (`OrderRepository.cs:247-250`) and is asked exactly once, at take time
(`TakeOrder.cs:213`). Scenario: it is Monday. A cleaner with `WeeklyOrderLimit = 3` opens the board
and takes fifteen jobs, every one of them scheduled for **next** Tuesday. Each take evaluates the
count against *this* week's Monday–Sunday window, finds zero, and admits. Next Monday that cleaner is
holding fifteen live jobs under a cap of three, and no refusal ever fired — the cap was never violated
because it was never asked about that week. This is orthogonal to C2 above (which is about `Completed`
leaving the count *within* a week); it is the same `UtcNow.Date` property A6 was rejected on, applied
to the shipped call site rather than to a hypothetical creation-time one. The ADR uses that property
as a shield for A6 and never turns it around. It belongs in the Decision, because it is what an admin
is actually buying: not "no more than N jobs a week" but "no more than N live jobs during whichever
week you happen to tap in".
