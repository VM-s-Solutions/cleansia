# ADR-0056 — Property size is two integers; the label is per-country catalogue data

- **Status:** `proposed`
- **Date:** 2026-08-30
- **Supersedes:** —
- **Superseded by:** —
- **Composes with:** ADR-0017 (multi-region seam), and the `CountryConfiguration` precedent for
  per-country presentation data (`TaxIdLabel`, `RegistrationNumberFormat`, `LegalRequirementsJson`).
- **Applies to:** `Cleansia.Core.Domain`, `Cleansia.Infra.Database`, `sql-scripts`,
  `Cleansia.App` (booking wizard and the home-page calculator)

## Context

The booking flow offers `1+kk`, `2+kk`, `3+kk`, `4+kk`, `Dům`. That vocabulary is Czech: `kk`
(*kuchyňský kout*) counts a kitchenette, and the number counts rooms *excluding* it. It does not
translate. A German listing says `3-Zimmer-Wohnung`, a British one `2-bed flat`, an American one
`2BR`, and each counts something slightly different. Hardcoding the Czech ladder blocks the first
market that does not use it.

The important thing is what the platform already does with the answer:

- `Order.Rooms` and `Order.Bathrooms` are plain `int` (`Cleansia.Core.Domain/Orders/Order.cs:35,37`).
- `OrderPricingCalculator` computes
  `BasePrice + PerRoomPrice * (rooms + bathrooms)` (`OrderPricingCalculator.cs:33`).
- `QuoteOrderCommand` carries `rooms` and `bathrooms` as integers.

**Nothing anywhere persists the string `3+kk`.** It exists only as a label on a control. The domain is
already country-neutral; only the presentation is not.

## Decision

**The domain does not change.** Orders keep storing two integers, and pricing keeps consuming them.

Add a catalogue, `PropertySizePreset`, that maps a localised label to those two integers per country:

| Field | Why |
|---|---|
| `CountryId` | The market the preset belongs to |
| `Code` | Stable identifier (`CZ_3KK`), never shown to a user |
| `SortOrder` | Display order — `1+kk` before `2+kk` is not alphabetical |
| `Rooms`, `Bathrooms` | What pricing actually consumes |
| `Translation` (owned dictionary) | The visible label per language — the same owned-dictionary shape `Service`, `Package` and `Extra` already use |
| `IsActive` | Retire a preset without touching orders that referenced it |

Czech and Slovak seed the current ladder. A new market seeds its own set over the same two integers.

## Consequences

**Retiring a preset cannot break an order.** Because the order stored `rooms = 3, bathrooms = 1` and
not `CZ_3KK`, historic pricing stays reproducible after a preset is deactivated or relabelled. This is
the property that makes the catalogue safe to edit, and it is a consequence of the existing design
rather than something this ADR adds.

**One more seeded catalogue to keep in five languages.** It joins `Service`, `Package`, `Extra`,
`ServiceCity` and `Country`, all of which already carry a `Translation` dictionary, so the cost is
familiar rather than new.

**The frontend seam already exists.** `PROPERTY_SIZE_PRESETS` is an injection token with a Czech
default (`quick-quote/property-size-presets.ts`). When the endpoint lands, only that provider changes.

**A migration is required**, and regenerating `Initial` moves its id — which means the DEV database
must be dropped before the next deploy. That obligation is already open as **MS-2**; this folds into
it rather than creating a second one.

**An endpoint and an NSwag regeneration are required** before the web and mobile clients can read the
catalogue. The regeneration is owner-only (`manual_step: nswag-regen`).

## Alternatives considered

**Leave it hardcoded and branch per country in the client.** Rejected: it puts market data in three
codebases (web, Android, iOS) and guarantees they drift. The i18n bundles already demonstrate how
expensive five-way parity is when the data lives in the client.

**Store the label on the order.** Rejected: it makes historic orders unpriceable if a label is ever
corrected, and duplicates in every order row what is catalogue data.

**Free-numeric input instead of presets.** Rejected for the calculator specifically — asking a visitor
above the fold to type a room count is more friction than tapping a familiar label, and the estimate
exists to remove friction. The wizard may still expose the raw numbers for unusual properties.
