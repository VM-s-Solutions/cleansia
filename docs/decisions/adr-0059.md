# ADR-0059 — Cleansia Plus is priced per market: a `MembershipPlanPrice` row per (plan, currency), the subscription created in the chosen market's currency and keeping it for life

- **Status:** `accepted` — **2026-09-13**, after the architect panel's challenge round and the
  implementation lanes (T-0710 backend, T-0713 admin web, T-0714/T-0716/T-0718 customer clients).
  Where the tree departs from the draft, §Consequences says so.
- **Date:** 2026-09-13
- **Supersedes:** — (ADR-0035 is untouched: benefits, quotas, the ledger. This ADR moves only the
  *price* and the Stripe Price id.)
- **Superseded by:** —
- **Builds on:** the `ServicePrice` / `PackagePrice` / `ExtraPrice` archetype ("authored per currency,
  never converted, a missing row = not offerable"), the admin write shape `Dictionary<code, …>`, and
  **ADR-0058** (the market the customer is browsing in).
- **Applies to:** `Cleansia.Core.Domain/Memberships`, `Cleansia.Infra.Database`,
  `Features/Memberships/**` on Admin, Customer and Mobile.Customer hosts, `StripeSubscriptionWebhookHandler`,
  the admin membership-plan feature, the customer Plus / membership surfaces on three clients
- **Owner ruling (2026-09-12):** R1 — *"Cleansia Plus should be per currency and per region. I mean
  for CZ it's CZK, for SK it's EUR and so on."*

> **One decision:** where a plan's price lives, which currency a subscription is created in, and how
> a customer surface learns "the price for my market". One and not three because the row *is* the
> price, the row's Stripe id *is* what Stripe charges, and the surface must show exactly the row the
> subscribe command will use — split them and a customer can be shown one figure and billed another.

---

## Context (the tree before T-0710, verified by reading)

- `MembershipPlan` carried `MonthlyPriceCzk` (a display mirror), a computed `MonthlyEquivalentPriceCzk`,
  and **one** `StripePriceId`. Stripe Prices are single-currency, so a plan could be sold in exactly
  one currency, and its name said which.
- Neither subscribe path named a currency: `CreateMembershipCheckoutSession.Command(PlanCode)` and
  `CreateMembershipSubscription.Command(PlanCode, PaymentMethodConfirmed, IdempotencyToken)` handed the
  plan's single price id to Stripe; the charge currency was whatever that Price was created in.
- `UserMembership` recorded **no currency**. `SwapMembershipPlan` replaces the subscription item's Price;
  Stripe refuses a currency change on a live subscription, so a swap must pick the target plan's price
  *in the subscription's currency* — which nothing local knew.
- `GetMembershipPlans` was anonymous and parameterless; its `Response` carried `Price` with **no
  currency field**, and every client labelled it with the platform default code.
- Plans are split by interval: `PLUS_MONTHLY` and `PLUS_YEARLY` are two rows with `BillingInterval`;
  the yearly row stores the full annual charge. `SavingsPercentVsMonthly` compares rows. Swap is
  between rows.
- Seeds: two CZK Stripe ids; EUR is seeded inactive with no Stripe objects. **Creating Stripe Price
  objects is the owner's, out of programme; the admin enters ids.**

---

## Decision

### D1 — `MembershipPlanPrice`: one row per (plan, currency), shaped like `ServicePrice` plus the Stripe id

```
MembershipPlanPrice : Auditable
  MembershipPlanId  string(26)  required   FK → MembershipPlans  ON DELETE CASCADE
  CurrencyId        string(26)  required   FK → Currencies       ON DELETE RESTRICT
  Price             decimal(18,2)          the charge for ONE billing period of the plan (annual for a yearly plan)
  StripePriceId     string(64)  required   the Stripe Price in THIS currency for THIS plan
  unique (MembershipPlanId, CurrencyId)    IX_MembershipPlanPrices_MembershipPlanId_CurrencyId — no TenantId term (the plan is platform config; structural test)
  unique (StripePriceId)                   IX_MembershipPlanPrices_StripePriceId — a Stripe Price is single-currency and single-product; two rows sharing one is an admin typo, refused
  Create(planId, currencyId, price, stripePriceId) / Update(price, stripePriceId)
```

- **`MembershipPlan` lost `MonthlyPriceCzk`, `MonthlyEquivalentPriceCzk`, `StripePriceId`,
  `UpdatePricing`**, and `Create(...)` lost its two price parameters; it gained
  `MonthlyEquivalentOf(price)` (the cadence is the plan's; the row only supplies the number). The ~40
  test call sites were a mechanical edit in the same ticket. **Rejected — keep the parameters and
  ignore them** to spare the tests: a factory that accepts a price it does not store is the kind of
  lie the next reader trusts.
- **No collection navigation on the plan.** `.WithMany()` with no inverse, exactly as `PackagePrice`.
  Lookups go through `IMembershipPlanPriceRepository` (`GetForPlansAsync(planIds, currencyId)`,
  `GetForPlanAsync(planId, currencyId)`, `GetAllForPlanAsync(planId)`, `IsStripePriceIdUsedAsync`).
- **`MonthlyEquivalent` and `SavingsPercentVsMonthly` are computed in the query, per currency row**
  (yearly row's `Price / 12` against the cheapest *monthly* row **in the same currency**). There is
  no currency-free equivalent to keep on the entity.
- **Rejected — a `(planId, currencyId, monthlyPrice, yearlyPrice, stripeMonthly, stripeYearly)` row.**
  The interval axis already lives on the plan (two rows, `BillingInterval`, swap between them,
  ADR-0035's per-plan benefits). A price row carrying both intervals duplicates that axis and departs
  from the `ServicePrice` shape for no gain.
- **Rejected — `Prices` as JSON on the plan.** Not queryable per currency, no FK to `Currencies`, and
  `DeleteCurrency`'s in-use guard could not see it.

### D2 — The subscription is created in the chosen market's currency and keeps it for life

- **`UserMembership.CurrencyId`** — `string(26)` required, FK → `Currencies` ON DELETE RESTRICT, nav
  `Currency`. Written once at creation, never updated. `CurrencyRepository.IsInUseAsync` gained
  `MembershipPlanPrices` and `UserMemberships` (the latter under `IgnoreQueryFilters`, a tenant-scoped
  table behind a platform-wide FK), so `DeleteCurrency` answers `currency.in_use` for both — otherwise
  the Restrict FK is a raw 500.
- **Both subscribe commands gained `string? CountryId`** (the market, ADR-0058 D4; null = default):
  `CreateMembershipCheckoutSession.Command(PlanCode, CountryId)` and
  `CreateMembershipSubscription.Command(PlanCode, PaymentMethodConfirmed, CountryId)` (+ the existing
  `IdempotencyToken` init property). The currency is `ResolveCurrencyForCountryAsync(CountryId)` — the
  same resolver the quote uses — and a named country must be serviced (`country.not_serviced`,
  validator, as `QuoteOrder`). **Rejected — `CurrencyId` on the command.** Clients speak in markets;
  the catalogue and the quote already take a country; a currency on the wire would be a second way to
  say the same thing that the server has to check against the first.
- The handler loads `MembershipPlanPrice(plan, currency)`; **absent →
  `membership.plan.not_priced_in_currency`** (`BusinessErrorMessage.MembershipPlanNotPricedInCurrency`),
  refused before any Stripe object is created. This sits beside the existing in-handler
  `MembershipPlanNotFound` / `MembershipAlreadyActive` checks — the file's existing shape; the
  handlers-hold-happy-path-only rule was already deviated from here and this ADR does not widen or
  repair that.
- Stripe gets **that row's** `StripePriceId`. The webhook's `ProvisionFromCreatedEventAsync` reads the
  currency off **the Stripe `Subscription` object itself** — `Subscription.Currency`, upper-cased, then
  `ICurrencyRepository.GetByCodeAsync` — and **refuses to provision when the code names no platform
  currency** (log error, the existing "cannot provision" branch). That is the *actual charge currency*,
  which is stronger than metadata we wrote ourselves and cannot drift from it. **Rejected — a
  `CurrencyCode` entry in `SubscriptionData.Metadata`:** a second copy of a fact Stripe already states
  on the object, an `IStripeClient` signature change to carry it, and a value that *can* be missing
  where the object's own field cannot. `IStripeClient` is unchanged. The mobile path writes
  `UserMembership.Create(…, currencyId, …)` directly from the resolved row.
- **Plus's benefits are currency-free, so a subscription in one currency serves orders in every
  currency.** `DiscountPercentage` is applied as `rawSubtotal × pct / 100` in the order's own currency;
  `FreeCancellationWindowHours`, `AllowsExpressUpgrade` and `ExpressUpgradesPerMonth` are hours, a
  waiver and a count. A customer subscribed in CZK who books an SK address gets the EUR discount on the
  EUR order; nothing converts, and nothing needs to (`QuoteOrderMembershipDiscountIsCurrencyFreeTests`).
  The subscription's currency decides **only what Stripe charges for the subscription**. Stated so that
  no one adds a "membership currency must match order currency" guard by analogy with promo codes
  (`promo.currency_mismatch` exists because a promo's *minimum* is a money figure; Plus has none).
- **`SwapMembershipPlan`** loads the target plan's row **in `membership.CurrencyId`**; absent →
  `membership.plan.not_priced_in_currency`. A currency change on a live subscription is not offered
  anywhere; Stripe would refuse it and we refuse first. **The clients offer only a swap the server will
  accept:** the web management page lists `switchablePlans` = plans priced in the membership's
  currency; the Android card and the iOS view model offer the annual switch only when the listed yearly
  plan's `currencyCode` equals `GetMine.currencyCode` — the plans list is the *market's*, the swap is
  charged in the *membership's*, and quoting a price Stripe will not charge is the defect this closes.
  A customer who wants Plus in another currency cancels and re-subscribes in the new market (no
  migration of existing subscriptions). **A customer with an active membership who switches market**
  sees their membership in its own currency on the management screens (D3) and is **not** offered a
  second subscription — the existing `MembershipAlreadyActive` guard on both subscribe paths refuses it.

### D2a — Stripe's per-Customer currency: the re-subscribe path must not be a 500

Stripe documents a **`currency` on the Customer**, set when its first invoice is created, and a rule
that refuses a later subscription or invoice in a different currency on the same Customer ("You
cannot combine currencies on a single customer"). The platform holds **one Stripe Customer per user**
(`User.StripeCustomerId`). One-off order PaymentIntents do not set it (they are not invoices); a
subscription does. So "cancel and re-subscribe in the new market" could hit this rule for a customer
who ever held Plus in another currency — a rare case (a customer who moved country) that would surface
as an unclassified Stripe error.

**Decided:** both subscribe handlers classify that refusal into
`membership.stripe_customer_currency_locked` (`BusinessErrorMessage.MembershipStripeCustomerCurrencyLocked`)
instead of a 500. **Where the classification lives:** a static predicate,
`StripeRefusals.IsCustomerCurrencyLocked(StripeException)` in `Cleansia.Core.Clients.Abstractions`,
used by the handlers' `catch … when` — not inside `StripeClient.ClassifyAsync`, which only logs and
rethrows, because the business key has to be chosen in AppServices. It matches Stripe's documented
wording ("combine currencies", case-insensitive) on `StripeError.Message`, else the exception message:
Stripe gives the refusal no dedicated `StripeError.Code`.

**The sandbox probe (T-0710, DEV test key):** a Customer with a *cancelled* CZK subscription was
**allowed** both a EUR Checkout Session and a EUR subscription — Stripe did **not** enforce the rule
for that shape on 2026-09-13. The classification is kept for the documented rule; it costs one branch.

**Panel item, settled: classify only — no local pre-check.** A validator refusing when any
`UserMembership` row for the user carries another `CurrencyId` would encode Stripe's rule locally, be
stricter than Stripe now demonstrably is, and block a re-subscribe forever on a cancelled row. Stripe
is the authority on Stripe's rule. **Rejected — a Stripe Customer per (user, currency):** a schema
change on `User` for a case with no occurrence. The copy is *"Your Plus billing is already set up in
another currency. Contact support to change it."* — on the web and Android with no currency clause
(the error interceptor and `ApiErrorParser` render `api.*` / `error_*` keys without arguments); iOS
substitutes `membership_currency_locked_in` with `GetMine.currencyCode` when it knows one.
- The Stripe idempotency key already embeds the price id, so the same plan in two currencies is two
  keys. `DeriveStripeAttemptId`'s fallback became `u-{userId}-p-{planCode}-c-{currencyCode}` so a CZK
  attempt cannot replay as a EUR one.

### D3 — Customer surfaces ask for the price in their market; the server picks the row; one currency per response

`GET api/Membership/GetPlans?countryId=` on both customer hosts (`GetMembershipPlans.Query(string? CountryId)`):
resolve the currency as in D2, load every active plan's row in it, **return only plans that have one**,
and add **`CurrencyCode`** to `Response`. A market with no rows returns an empty list, which the
surfaces render as *"Plus is not available in your market yet"* (`pages.plus.not_available_in_market`
on the web, `plus_not_available_in_market` on both mobile apps: hero kept, no price, no button).
**An unserviced or unknown `countryId` also answers an empty list** — never the default market's
prices under a foreign address, and never the resolver's throw as a 500 on an anonymous route (added
beyond the draft, mirroring `GetServiceOverview`).

- **Rejected — `Prices[]` on the plan DTO with the client picking by currency.** Every other catalogue
  DTO answers in one currency with a `CurrencyCode`; a client-side pick is a second implementation of
  the offerability rule on three clients, exposes every market's price list to every visitor, and — the
  deciding point — a Plus page and the subscribe command would resolve the currency in two places that
  can disagree. One resolver, server-side.
- **What a failed read is not:** the web `MembershipPlanFactsService` treats *loaded and empty* as
  "unavailable" and a failed or null read as neither — the home teaser is omitted on both (no numeric
  claim, no CTA to a refused checkout); the iOS Subscribe screen shows a `membership_plans_load_failed`
  state with a retry rather than the "not available" claim over a network error.
- **Mobile:** `MembershipRepository` / `MembershipManagementClient` re-read the plans when the market
  changes (the `CatalogRepository` idiom; iOS only once they were ever requested).
- **`GetMyMembership.Response`:** `MonthlyPriceCzk` → **`Price`**, `MonthlyEquivalentPriceCzk` →
  **`MonthlyEquivalentPrice`**, plus **`CurrencyCode`** (last, `string?`) — all from the membership's own
  `MembershipPlanPrice(plan, membership.CurrencyId)`; a membership whose plan row in that currency no
  longer exists renders `price: null` and logs a warning. Renamed, not aliased: a field called `…Czk`
  carrying EUR is the lie the programme exists to remove, and there is no production client to keep
  compatible. The membership management screens label with **this** code, not the market's — a
  subscription keeps its currency. `MembershipViewModel.currencyCode` was removed on both mobile apps
  rather than re-pointed: every figure is labelled from its own payload's code, so no guessed unit
  exists to expose.
- `QuotePlusSavings` is unchanged (it never prints the plan's price; its `CurrencyCode` is the basket's).

### D4 — What an admin must author before a market can sell Plus (the activation gate)

- **Admin commands take the package shape, with one deliberate difference:**
  `CreateMembershipPlan.Command(… Dictionary<string, MembershipPlanPriceInput>? Prices …)` and
  `UpdateMembershipPlan` likewise, `MembershipPlanPriceInput(decimal Price, string StripePriceId)`
  keyed by currency **code**. Validators: every key names a known currency (`currency.not_found`);
  no two entries in one payload name the same Stripe Price (`MustNotRepeatAStripePriceId`); each entry
  is complete (`Price >= 0`, `StripePriceId` non-empty ≤ 64 and **not used by another row** —
  `membership.plan.stripe_price_already_used`, a validator read with the plan's own row in that
  currency excepted on update; the unique index is the backstop). **`MustCoverAllActiveCurrencies` is
  NOT applied, and `Prices` may be null, empty or partial.** The handler upserts one row per code sent;
  codes not sent keep their rows (the package idiom). Deleting a row is not offered — deactivate the
  plan instead.
- **Why plans do not require every active currency when packages do.** A package with no price in
  an active currency is a **hole in that market's catalogue** — the rule exists so an admin cannot
  open a market with an incomplete catalogue. A plan with no price in a currency is **"Plus is not on
  sale in that market"**, which this ADR declares a valid product state. Requiring it would mean: the
  day EUR is activated, an admin cannot change a *benefit* on any plan without inventing a EUR Stripe
  Price id — and the owner creates Stripe Prices out of band, on his own schedule.
- **`ActivateCurrency` does not check plans** — Plus is not a catalogue line, a market may open
  without it, and `IsOfferableAsync` is **not** extended. The gate is the row: no row → not listed
  (D3) → not subscribable (D2). That is the same fail-closed posture as
  `currency.loyalty_divisor_missing`, expressed as absence rather than a flag.
- **Admin read:** `MembershipPlanDetailDto.Prices : Dictionary<code, MembershipPlanPriceDto(Price, MonthlyEquivalentPrice, StripePriceId)>`
  (absent ≠ zero); `MembershipPlanListItem` shows the **platform-default-currency** row's
  **`decimal? Price` / `decimal? MonthlyEquivalentPrice`** + `CurrencyCode`, **null when absent** —
  rendered as "—", not 0. **Departs from the `GetPagedPackages` "0 when absent" idiom on purpose:**
  there, 0 can only appear for an inactive currency (the validator guarantees every active one);
  here absence is a real state in the default currency, and "0 CZK" would read as *free*.
- **No price sort on the admin list.** `MembershipPlanSort` dropped its price key and falls through
  to the default order (`BillingInterval`, then `Code`), exactly as `PackageSort` documents. The draft
  asked for a sort on the joined default-currency row with nulls last; the shipped list sends no sort
  and holds two rows — a second paging path for that was not proportionate.
- **Admin form:** one price block **per currency the platform knows** — active currencies badged
  *Active*, inactive ones *Optional* — each with a price and a Stripe Price id. **Every block is
  optional:** a block is sent only when both fields are filled, a half-filled block is a per-block
  form error and nothing is sent, and populating from a detail leaves an absent currency's block
  blank (never `0`). The list prints "—" for a null price and still names the default code in its
  Currency column.

### D5 — Seed, migration, existing subscriptions

- **Seed:** `MembershipPlanPrices` two rows — `PLUS_MONTHLY` × CZK 199.00 / `price_1TSiJ83KjMqxM0RBVaiKAF6r`,
  `PLUS_YEARLY` × CZK 2030.00 / `price_1TSiJ83KjMqxM0RBrfMWdjrF` (the `PackagePrices` idiom). No EUR
  rows (no Stripe objects exist; the owner creates them). `MembershipPlans` seed dropped the two columns.
- **Test seeds share one Postgres, so the unique `StripePriceId` must not be a constant.** The host
  seed derives it from the plan code (`DomainSeed.MembershipPlanPrice(planId, code)`), and the three
  host-test classes that seed plans pass in one collection run. `UserMembershipMockFactory.Paid`
  (in-memory) builds no price row and sets the `Currency` navigation so `GetMine`-style readers work.
- **Migration:** `Initial` regenerated (single-migration rule); the DEV drop is owed at deploy, not on
  the branch. Emitted DDL: `+MembershipPlanPrices` (two uniques, plan FK Cascade, currency FK
  Restrict), `MembershipPlans −MonthlyPriceCzk −StripePriceId`, `UserMemberships +CurrencyId NOT NULL`
  FK Restrict.
- **Existing subscriptions:** `UserMembership.CurrencyId` is `NOT NULL`. There is no production; DEV rows
  go with the drop. Stripe **sandbox** subscriptions created before this change provision normally —
  the webhook reads `Subscription.Currency` off the object (D2), which every subscription carries.
  **Migrating a subscription to another currency is not built.**

## Alternatives considered

| # | Alternative | Why not |
|---|---|---|
| A1 | Keep one Stripe id per plan and one plan per currency (`PLUS_MONTHLY_EUR`) | Multiplies plans per market; benefits (ADR-0035 quotas, discount) duplicated per currency and free to drift; swap and "same plan" checks break. The price varies per currency, the plan does not. |
| A2 | Price rows without a Stripe id; look the Stripe Price up by (product, currency) at subscribe time | A Stripe round-trip on every subscribe and on every listing; the admin already enters the id; and the id is what makes the row *the* price rather than a mirror. |
| A3 | `Prices[]` on the customer DTO (client picks) | D3. |
| A4 | Currency on `UserMembership` derived from Stripe on each webhook rather than stored | The swap path needs it synchronously and Stripe's object is not the platform's record of what it sold. Stored once at creation; Stripe can only confirm it. |
| A5 | Let `ActivateCurrency` refuse until every plan is priced | Couples opening a market to selling Plus; a market without Plus is valid. |
| A6 | Keep `MonthlyPriceCzk` on the wire as an alias for the default-currency price | A `…Czk` field carrying EUR; no production client to protect. |
| A7 | `MustCoverAllActiveCurrencies` on plan prices (the package validator) | Contradicts "a market may open without Plus"; blocks benefit edits until the owner has minted a Stripe Price (D4). |
| A8 | `CurrencyCode` in Stripe subscription metadata as the webhook's source | Stripe's `Subscription.Currency` is the actual charge currency and cannot be absent; metadata is a second copy that can (D2). |
| A9 | A Stripe Customer per (user, currency) to dodge the Customer-currency lock | Schema change on `User` for a case with no occurrence; classify the refusal instead (D2a). |
| A10 | Admin list shows 0 for an unpriced plan (the package-list idiom) | Absence is a real state for plans; "0 CZK" reads as free (D4). |
| A11 | A local "ever subscribed in another currency" pre-check | Stricter than Stripe, which the probe showed not enforcing the rule for a cancelled subscription; a cancelled row would block a re-subscribe forever (D2a). |

## Consequences

- **Wire changes (breaking, pre-production):** customer `GetMembershipPlansResponse` +`currencyCode`;
  `GetMyMembershipResponse` renamed two fields + `currencyCode`; both subscribe commands +`countryId`;
  admin plan DTOs/commands replaced two scalars with a per-currency dictionary; the admin list item's
  two price fields became nullable. Three NSwag clients and the shared mobile spec regenerated once
  after T-0710 and T-0711 both landed; Android `MembershipWireTest` rosters and iOS `MembershipFakes`
  / `CustomerWireContractTests` moved in the mobile tickets. `IStripeClient` signatures are
  **unchanged**.
- **Error keys:** `membership.plan.not_priced_in_currency`, `membership.stripe_customer_currency_locked`
  (customer web + both mobiles ×5); `membership.plan.stripe_price_already_used` (admin web ×5).
- **Role card:** `/domain/roles/membership-plan-price`.
- **Deviations from the draft, recorded:** the classification predicate lives in `StripeRefusals`,
  not `StripeClient.ClassifyAsync` (D2a); the currency-lock copy carries no `{{currency}}` clause on
  the web and Android (D2a); `GetPlans` answers an empty list for an unserviced country (D3); no price
  sort on the admin list (D4); the admin form renders a block per *every* currency, inactive ones
  badged optional (D4); the clients gate the annual switch on the membership's currency (D2); iOS maps
  `MyMembership.price / monthlyEquivalentPrice / currencyCode` as optional and never refuses the row,
  while `MembershipPlan.currencyCode` is required (D3).
- **Cost accepted:** the yearly-vs-monthly savings badge is per currency and may differ across
  markets — it is computed from the rows, which is the point.

## How a reviewer verifies compliance

1. `MembershipPlan` has no price or Stripe id member (grep `MonthlyPriceCzk|StripePriceId` under
   `Cleansia.Core.Domain/Memberships` → only `MembershipPlanPrice.cs`).
2. Emitted DDL: unique `(MembershipPlanId, CurrencyId)`, unique `(StripePriceId)`, plan FK Cascade,
   currency FK Restrict; `UserMemberships.CurrencyId NOT NULL` FK Restrict
   (`MembershipPlanPerMarketTests`, real Postgres, both uniques by constraint name).
3. `CreateMembershipCheckoutSession`, `CreateMembershipSubscription`, `SwapMembershipPlan` each have a
   test asserting the **exact** `StripePriceId` handed to `IStripeClient` is the row for the resolved
   currency (the contract-lock tests, re-pointed), and one asserting
   `membership.plan.not_priced_in_currency` when the row is absent
   (`…ContractLockTests.PlanUnpricedInTheResolvedCurrency_Refuses_AndNeverReachesStripe`,
   `SwapMembershipPlanCurrencyTests`).
4. Webhook: `subscription.created` whose `Subscription.Currency` is `"czk"` provisions with the CZK
   `CurrencyId`; `"xxx"` provisions nothing and logs an error
   (`WebhookProvisionActiveMembershipIdempotencyTests`, `SubscriptionWebhookIntegrationTests`). No
   test reads a `CurrencyCode` metadata entry.
5. `GetPlans?countryId=` on real Postgres: a plan priced only in CZK is absent from a EUR market's
   list; `currencyCode` matches the country's configured currency; an unserviced country lists nothing
   (`GetMembershipPlansHandlerTests`, `MembershipPlanPerMarketRouteTests`).
6. Admin validator tests: an **empty** `Prices` passes; a key naming an unknown code fails
   `currency.not_found`; an entry with a blank Stripe id fails; a duplicate Stripe id fails
   `membership.plan.stripe_price_already_used`. There is **no** `MustCoverAllActiveCurrencies` call in
   `Features/Memberships/Admin`.
7. `DeleteCurrency` on a currency with a plan price row or a membership answers `currency.in_use`
   (`MembershipPlanPerMarketTests`).
8. No client labels a plan or membership price with the platform default code (grep
   `defaultCurrencyCode` in the membership features of the three clients → none;
   `MembershipCurrencyBindingTest`, `MembershipViewModelTests`, `membership.facade.spec.ts`).
9. Both subscribe handlers' Stripe-failure tests include the Customer-currency refusal →
   `membership.stripe_customer_currency_locked`, not a 500 (`MembershipCommandsStripeFailureTests`,
   `StripeRefusalsTests`); the T-0710 report names the sandbox probe's outcome in one sentence.
10. `DomainSeed.MembershipPlanPrice` emits a Stripe id derived from the code; the three host-test
    classes that seed plans pass in one collection run.

## Challenge / Defense / Verdict

### Challenge (Architect, challenger mode, 2026-09-13)

1. **The Stripe Customer-currency lock was unaddressed.** "Cancel and re-subscribe in the new
   market" runs into Stripe's one-currency-per-Customer rule on the platform's one Customer per user;
   the draft would have shipped that as an unclassified 500. *Conceded:* D2a — classified into a
   named key on both paths, sandbox-verified in T-0710; the local pre-check is left to the panel.
2. **D4 contradicted itself:** `MustCoverAllActiveCurrencies` on plan prices *and* "a market may
   open without Plus". With EUR active and no EUR Stripe Price minted, no plan benefit could be
   edited. *Conceded:* the requirement goes; empty `Prices` is legal; reason recorded.
3. **The webhook's currency source was our own metadata when Stripe's object carries the charge
   currency.** Metadata can be absent; `Subscription.Currency` cannot. *Conceded:* the object's field
   is the source; no `IStripeClient` change; the "pre-change sandbox subscriptions are refused"
   consequence disappears.
4. **"Plus benefits apply to orders in any currency" was implied, not stated;** the promo-code
   precedent invites a currency-match guard by analogy. *Conceded:* stated in D2 with the code line.
5. **`DomainSeed.MembershipPlan`'s constant Stripe id collides on the new unique index** in the
   shared host-test database. *Conceded:* derived from the code (D5).
