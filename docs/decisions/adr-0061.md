> **One decision:** *what a tenant IS, and how every row gets one before the first production deploy.*
> A tenant is an **operating company** under the holding — the legal entity that contracts the customer,
> employs the cleaner, issues the receipt and pays the payout. The Czech s.r.o. is the first. A country
> is served by **at most one** operator; an operator serves **one or more** countries. Every business
> row is stamped with the operator that owns it, at the moment it is written, from the **country** the
> transaction is legally in — the same country the multicurrency programme already resolves the currency
> from — so a row's tenant and its currency can never disagree because they are two reads of one fact.
> Reference and catalogue rows carry no tenant. `NULL` stops being a tenant.

## Context (every citation opened in the working tree, 2026-09-13, before the code landed)

### What tenancy was, in five facts

1. The mechanism was complete and correct for N tenants **provided rows are stamped**: filter
   `providerNull ‖ (current==null && e.TenantId==null) ‖ e.TenantId==current`
   (`CleansiaDbContext.ApplyTenantQueryFilters`), commit-time stamp of every `Added` `ITenantEntity` with
   an empty `TenantId` (`CleansiaDbContext.CommitAsync`), claim `tenant_id` minted from `User.TenantId`
   (`AuthExtensions.SetClaims`), override for jobs/webhooks (`TenantProvider.SetTenantOverride`). Every
   one of the ~25 sweep/webhook callers derives its tenant **from the row it acts on** and commits inside
   the loop.
2. **Nothing had ever written a tenant.** No `Tenant` table, no constant, no resolver; the only source was
   the claim, and the claim was minted from a column nothing set. Registration is anonymous on every host
   and carried no country, so every `User` was stamped `NULL`, so no claim was ever minted. **Activation
   had no bootstrap.**
3. **Guest orders are anonymous writes** (`OrderController.CreateOrder` on both customer hosts). Under a
   non-null world they would land `NULL` and be invisible to every admin and partner — silently.
4. **Five seeded `ITenantEntity` tables carried `TenantId NULL` on purpose** — `CompanyInfo`,
   `EmployeePayConfigs` (platform defaults), `LoyaltyTierConfigs`, `PromoCodes`, the dev admin `Users` row.
   The first tenanted caller would read them **empty** — the ADR-0041 CH-S4 / RB-9 shape, landing on
   receipts (no issuer), pay calculation (no default), employee approval (pay config read through the
   filter) and loyalty.
5. **Ten of eleven `(TenantId, …)` unique indexes were already `NULLS NOT DISTINCT` in the emitted DDL** —
   the living note's and S8's *"the DDL has not"* were stale. Two unique indexes on tenanted tables
   carried **no** tenant term and would have become cross-tenant constraints on activation:
   `OrderReceipts.ReceiptNumber` (the number comes from a **per-tenant** `FiscalCounter`, so tenant 2's
   first receipt of the year collides with tenant 1's — a `23505` on the receipt path) and
   `EmployeePayConfigs (EmployeeId, ServiceId, PackageId, CurrencyId)` (two operators could not both hold a
   platform default for the same service and currency).

### What the ruling fixes as fact

- Tenant = operating company under the holding. **Coarser than a country.** ADR-0017 D3 modelled tenant ⊆
  country (*"two markets ⇒ two tenants"*); the ruling models country ⊆ tenant. Both are satisfied by a
  **country → operator** many-to-one map, which is what this ADR lays.
- The Czech s.r.o. is the first tenant. There is no second company today and no date for one. So the
  second operator is a **seam to lay**, not a feature to build — Q-VS-03's *"ask whether the hedge's
  premise is real before pricing the hedge"* still governs how much machinery this costs.
- Region (ADR-0017) is orthogonal and unchanged. The `CountryConfiguration.HomeRegion` seam sits beside
  the operator column on the same row; ADR-0017's *"a tenant never spans regions"* becomes *"every
  country of one operator shares a `HomeRegion`"* — a check for the day that column lands, not now.

## Decision

> **Contract principle.** *The tenant of a row is the operating company legally responsible for the
> transaction the row records, resolved from the transaction's country at write time by the same read that
> resolves its currency. Rows the brand defines identically for every operator carry no tenant. No
> business row is ever written without one.*

### D1 — A `Tenants` registry: three columns, seeded, no admin surface

```
Tenant : BaseEntity                     // tenantless by construction — it is the thing rows point at
  Id      string, [MaxLength(26)]       // assigned, not generated: "cleansia-cz". Lower-case kebab; ≤ 26
                                        // because every TenantId column is varchar(26)
  Name    string, [MaxLength(200)]      // "Cleansia CZ s.r.o." — display, nothing keys on it
  IsActive bool                         // BaseEntity's. No reader consults it in this ADR (see O-3)
```

- **Seeded** with one row, `('cleansia-cz', 'Cleansia CZ s.r.o.')`, first in `insert_seed_data.sql`
  (everything else references it). HostTests seed the same id as their default.
- **No admin CRUD, no DTO, no endpoint.** The only writer is the seed. A second operator is a second seed
  row (see D12). Why: proportionality — a screen is paid by every future reader, and a screen with one
  row in it and no caller that needs to add a second is the `DbConstraintNames` shape CLAUDE.md §4 names.
  It is built the day a second company exists, by the ticket that onboards it, with a real caller.
- **No foreign key from the stamped tables to `Tenants`.** The closure is by construction: a tenant id
  enters the system at exactly two points — the resolver (D3, reads a column that **is** FK'd to `Tenants`)
  and the claim (minted from a `User` row that was itself stamped by the resolver or by an admin's
  claim). Forty-odd FKs would buy a typo guard on a value nothing types. The isolation test (D11)
  proves the closure instead.
- **No `ITenantRepository`, no id-grammar rule, no grammar test** (challenger round, CLAUDE.md §4). No
  production code reads `Tenants` — the resolver reads `CountryConfiguration`, the closure scan and the
  HostTests harness read `ctx.Set<Tenant>()` directly. A repository with zero members and zero callers is
  the `DbConstraintNames` shape; a regex on a value only the seed writes is the same shape one size
  smaller. `MaxLength(26)` is the only rule the id needs, and the first stamped insert enforces it.

> **As amended 2026-09-15 (owner ruling Q-TENANCY-04, T-0758 / T-0759) — the foreign key is real, and
> the registry has one production reader.** Two bullets above are reversed; the rest of D1 stands.
>
> - **Every stamped table now carries `FK_<T>_Tenants_TenantId`** (`HasOne<Tenant>().WithMany()
>   .HasForeignKey(e => e.TenantId).OnDelete(DeleteBehavior.Restrict)`, no navigation property) —
>   46 from the shared `TenantAuditableEntityConfiguration` and two by hand on the `BaseEntity +
>   ITenantEntity` audits, **48 in the emitted DDL** (47 when T-0758 landed; T-0757 made
>   `PayoutReferenceCounter` the 48th the same day). `Restrict`, so a company is never deleted out from
>   under its rows; the two envelope tables keep a nullable column, and Postgres lets a `NULL` pass an FK.
>   **Why the 2026-09-13 reasoning changed.** The closure argument ("a tenant id enters at two points,
>   both bound to the registry") was true of production and false of the tests: eleven Postgres tests
>   stamped rows with ad-hoc ids (`tenant-A`, `some-tenant`, `tenant-payroll-A`, …) that no registry
>   held, so the suites were proving tenancy against a world the seed forbids — and "nothing types the
>   value" is a claim about today's writers, not about the next one. A constraint the database enforces
>   costs one line in the shared mapping, and the owner took the recommended step; the closure scan
>   stays, now redundant on purpose (it is the seed's contract, D11). Alternative (j) is therefore
>   taken, not rejected, and the
>   eleven tests now stamp with registered ids — the fixtures' `TestTenants` / `HostTestTenants`
>   constants, or ids they insert into `Tenants` in their own arrange. `TenantForeignKeyEnforcedTests`
>   pins a stamped row under an unknown company to a `23503` naming `FK_Users_Tenants_TenantId`.
> - **`ITenantRepository` exists, with one member and one production caller.** `GetAllIdsAsync`
>   (every company in the registry, deactivated ones included) is what the retention job loops over
>   (D10 as amended, O-3/O-4). It was cut on 2026-09-13 because nothing read the registry; the first
>   reader is what justified it, which is the order CLAUDE.md §4 asks for.

### D2 — The country → operator map is `CountryConfiguration.OperatorTenantId`, nullable, FK to `Tenants`

```
CountryConfiguration                    // stays Auditable, NOT ITenantEntity (a per-country fact — RB-9 sibling)
  + OperatorTenantId  string?, [MaxLength(26)], FK → Tenants.Id (Restrict), indexed
```

- **Why this row and not `Country`:** a country is a market only when it has a `CountryConfiguration`
  (ADR-0058 D1 — serviced ∧ configured ∧ active currency). Who operates it is a market fact, and the row
  already carries every other market fact (currency, VAT, fiscal mode, payout scheme, `IsDefaultMarket`).
  ADR-0017 reserved the same row for `HomeRegion`; the two seams sit together.
- **Why not a `TenantCountries` join table:** the ruling is one operator per country. A join table
  models a many-to-many the business does not have and would need its own uniqueness rule to forbid it.
  If the business ever changes (two companies in one country), that is a superseding ADR, not a column.
- **Why a new column and not `Auditable.TenantId` which the row already physically carries:** that column
  is a dead, unfiltered, unstamped inheritance on every tenantless `Auditable` table; reusing it on one
  row gives it a meaning it has nowhere else. `OperatorTenantId` says what it is.
- **Null means: no operating company serves this country.** Consequences: `GetMarkets` gains a fourth
  predicate and does **not list** such a country (logged as an error — a configuration defect, the same
  treatment ADR-0058 D1 gives a serviced country whose currency lookup fails); any anonymous write that
  names it fails `tenant.not_found` (D3); `SetDefaultMarket` refuses to flag it (`country.market_not_ready`
  — a default nobody operates would fail every registration that names no market). A country that is not
  serviced at all keeps its existing refusals (`country.not_serviced`) — the operator check runs only on
  markets.
- **Seed:** the CZE configuration row gets `OperatorTenantId = 'cleansia-cz'`. No admin writer in this
  ADR (same reasoning as D1); the country-configuration admin edit gains the field when a second operator
  exists.

### D3 — Anonymous writers resolve their operator from the market, through one behaviour

**The rule:** *every anonymous request that writes a tenanted row, or reads one through the filter,
names a market (a `CountryId`); the pipeline resolves the market's operator and sets it as the ambient
tenant before validation runs.* Authenticated requests are untouched — their tenant is the claim.

```
IOperatorScopedRequest { string? CountryId { get; } }        // marker on the request record

OperatorTenantScopeBehavior<TRequest,TResponse>              // registered BEFORE ValidationPipelineBehavior
  if request is not IOperatorScopedRequest            → next()
  if tenantProvider.GetCurrentTenantId() is not null  → next()          // a claim wins; S1: never from the request
  (isMarket, tenantId) = operatorTenantResolver.ResolveAsync(request.CountryId)
  if !isMarket                                        → BusinessResult failure `country.not_serviced`  (user input)
  if tenantId is null                                 → BusinessResult failure `tenant.not_found`      (config defect)
  tenantProvider.SetTenantOverride(tenantId); → next()

IOperatorTenantResolver.ResolveAsync(string? countryId) → OperatorResolution(bool IsMarket, string? OperatorTenantId)
  countryId null  → the default market's country — the SAME choice GetMarkets makes (the directory
                    handler is invoked directly; a platform with no listed default answers "market, no
                    operator" and is refused tenant.not_found)
  countryId given → that country's configuration
  IsMarket = the country is serviced and active and satisfies GetMarkets.ResolveMarketAsync (a configuration
             naming a currency, and that currency switched on) — the same predicates the directory applies,
             minus the operator one; OperatorTenantId = the column, null when IsMarket is false or the
             column is null
```

- **Why the behaviour, not a validator, refuses a non-market country** (challenger round): the behaviour
  runs *before* validation, so a validator rule `CountryId.MustAsync(IsMarket)` can never be reached for a
  bogus country — the behaviour would already have returned `tenant.not_found` for it, which mislabels user
  input as a configuration defect. The resolver therefore answers two questions, and the behaviour maps
  them to the two keys that already exist for them. **No validator rule on the six requests**; the
  existing `country.not_serviced` key is reused, so this ADR adds no fourth key.
- **Why a behaviour and not per-handler code:** the pre-checks that must run in the right tenant are in
  the **validators** (`Register.Validator.UserWithEmailNotExistsAsync`); anything set in a handler is too
  late. The behaviour is the shipped shape for "before validation" and the override is the shipped shape
  for "ambient tenant not from a claim".
- **Why this is not S1's *"never trust `tenantId` from the request"*:** the request names a **market**
  (a country id it could equally pass to `Order/Quote` today, ADR-0058 D5); the tenant is looked up
  server-side from a column only the seed writes. An anonymous visitor choosing which operator to
  register with is the public site working as intended.
- **Callers today (the abstraction's second-caller test, passed nine times):**

  | Request | `CountryId` source | Rows it writes / filtered rows it reads |
  |---|---|---|
  | `Register` | **new optional field** → default market | `User`, `Cart`; pre-check on `Users`. *Since 2026-09-15 routed on the two **customer** hosts only (T-0754)* |
  | `RegisterEmployee` | **new optional field** → default market | `User`, `Cart`, `Employee`; pre-check |
  | `GoogleAuth`, `AppleAuth` (provisioning branch) | **new optional field** → default market | `User`, `Cart`. *Since 2026-09-15 the provisioning branch runs on a **customer** host only; off one, `GoogleAuth` signs in an existing Employee or Administrator and provisions nothing (T-0754)* |
  | `RequestPromoCode` | **new optional field** → default market | `PromoCode`; `GetByCodeAsync` pre-check. **The outbox envelope passed `null` as the tenant before; it passes `tenantProvider.GetCurrentTenantId()`** — `SendEmailHandler` sets its override from the envelope, and an email consumer with no tenant reads every stamped table empty once D8 lands |
  | `ValidateReferral` | **new optional field** → default market | reads `ReferralCode` `(TenantId, Code)` |
  | `QuoteOrder`, `QuotePlusSavings` | **existing** `CountryId` (ADR-0058 D5) | reads `EmployeePayConfig` defaults (offerability) |
  | `CreateOrder` (guest) | **existing** `CustomerAddress.CountryId`, exposed by explicit interface implementation | `Order` and children, `Address`, `OrderReceipt` later |

- **The optional `CountryId` is the seam, not a client obligation today.** Absent ⇒ default market ⇒
  `cleansia-cz`, which is every registration until a second market opens. The regenerated NSwag clients
  carry the field; the clients *send* it in a ticket sequenced before the second market, not before
  go-live (T-0728).
- **Not a caller: `LookupOrder` / `LookupOrderBatch`.** An anonymous read keyed on a **secret**
  (`ConfirmationCode` + `CustomerEmail`) is ADR-0051's bypass-and-re-pin cell, not a market-scoped read:
  `GetQueryableIgnoringTenant()` + the existing predicate is the pin. A guest who booked under operator A
  must find the order without knowing which operator that was.
  *(**Dated correction, 2026-09-22.** The cell classification is unchanged and so is the reason; the
  **key** is not. `ConfirmationCode` + `CustomerEmail` was never a secret — the code was served on the
  order detail to every assigned cleaner — and the family is now keyed on a per-order access token,
  256 bits, resolved by its SHA-256 digest through the one seam `GuestOrderAccess`, which bypasses on
  the token table as well as the order. `GuestCancellationPreview` and `CancelGuest` joined the family.
  → [Guest order lookup](/flows/booking-and-pricing#guest-order-lookup))*

> **As amended 2026-09-14 (ADR-0062 D3 as amended, T-0744) — a new law and five more callers.**
> **An anonymous *marked* command that names no market implements `IOperatorScopedRequest` with an
> explicit `CountryId => null`** — off the wire, never a client field — so that its out-of-band audit
> refusal row has an operator to be stamped with (the default market's); without the marker the row
> would be skipped with one warning, and every refused sign-in would vanish from the trail. The five
> session commands that gained a customer audit marker join the roster this way: `Login`,
> `MobileLogin`, `ConfirmUserEmail`, `RequestPasswordChange`, `ChangePassword` (fourteen records now
> implement the interface; `GoogleAuth`/`AppleAuth` were already on it). They write no market-scoped
> row of their own — D4 governs what they *do* write — and the scope behaviour still refuses nothing
> for them (a null market is the default one). `CustomerAuditActionRosterTests` guards that every
> `AllowsAnonymousActor` marker in the assembly sits on an `IOperatorScopedRequest`; the two
> error-contract parity rosters carry the new operator-scoped commands.

### D4 — A request that authenticates a user adopts that user's tenant before it writes

Login on every host is anonymous and writes a `RefreshToken` (`TokenService.GenerateTokenAsync` →
`RefreshTokenService.Issue`); token rotation writes another (`RefreshToken.Handler`). Both used to land
`NULL` and were read back through an already-shipped bypass. After D8 (NOT NULL) they would fail.

**Rule:** `TokenService.GenerateTokenAsync(user, …)` and `RefreshToken.Handler` call
`tenantProvider.SetTenantOverride(user.TenantId)` after resolving the user and before issuing. Two sites,
one sentence, no new type. Every row written on an authenticating request belongs to the user being
authenticated — which is also what the JWT it returns will say.

**The roster the two sites cover (challenger round — walked, not assumed).** Every anonymous request that
mints a token goes through `TokenService.GenerateTokenAsync`: `Login`, `PartnerLogin`, `AdminLogin`,
`MobileLogin`, `MobilePartnerLogin`, `GoogleAuth`, `AppleAuth`, `ConfirmUserEmail`. The remaining
anonymous identity writers add no stamped row: `ResendConfirmationEmail` and `RequestPasswordChange`
enqueue only an `OutboxMessage` (D8-exempt) whose envelope already carries `user.TenantId`;
`ChangePassword` mutates a tracked row (`Modified` is never re-stamped); the lockout counters are
`ExecuteUpdateAsync`. So the two sites are the roster, and a reviewer re-derives it with
`grep -rn "GenerateTokenAsync\|\.Add(" src/Cleansia.Core.AppServices/Features/Auth`.

**Override replaces override — stated because two of them now meet.** `TenantProvider.SetTenantOverride`
assigns; the last writer wins. On `GoogleAuth`/`AppleAuth` the D3 behaviour sets the *market's* operator
first; when the sign-in resolves an **existing** user (by verified email, tenant-ignoring) that user may
belong to another operator, and `TokenService` then re-sets the override to `user.TenantId` before the
`RefreshToken` is added. The sequence is correct by construction (nothing stamped is added between the
two), and `AnonymousWriterLandsInMarketOperatorTests` carries the case: an SK-tenant Google user signing
in with no `countryId` gets a `RefreshToken` stamped `cleansia-sk`, not `cleansia-cz`.

**Corollary — the confirm family.** `ConfirmUserEmail`'s legacy 128-bit path
(`UserRepository.GetByConfirmationCodeAsync`, filtered) was kept filtered by ADR-0051 D3 as a *symmetric*
cell (written null, read null). It is asymmetric the moment `Register` stamps a tenant and the confirm
link is clicked anonymously: it joins the bypass roster as `GetByConfirmationCodeIgnoringTenantAsync`,
pinned by the confirmation-code hash (an unguessable server-issued secret — a permitted pin under S8).
The OTP path already bypasses. `UserRepositoryTokenLookupTenantTests`' roster gains the row.

> **As amended 2026-09-14 (ADR-0062 D3/D7 as amended, T-0744) — the rule covers the audit row too,
> and the caller table grows.** The session acts now write a **customer audit row** (a stamped row
> this ADR did not know about), and "every row written on an authenticating request belongs to the
> user being authenticated" has to hold for it. Two of the callers mint no token and one minted it too
> late:
>
> | Caller | Adopts the account's tenant … | Why it was not enough before |
> |---|---|---|
> | `Login`, `MobileLogin`, `GoogleAuth`, `AppleAuth`, `ConfirmUserEmail` | in `TokenService.GenerateTokenAsync`, now **before the confirmation check** | the unconfirmed-address early return skipped the adoption, so a correct password on an unconfirmed address wrote its `customer.session.login` row (a success that opens no session) under the default market's operator |
> | `RequestPasswordChange` | in the handler itself — `tenantProvider.SetTenantOverride(user.TenantId)` after resolving the user | mints no token; its `customer.password.reset_requested` row was stamped with the market's operator set by D3 |
> | `ChangePassword` (the reset completion) | in the handler itself, the same idiom | mints no token; same for `customer.password.reset_completed` |
>
> The adoption is the **authentication's**, not the mint's: a second operator's customer signing in,
> confirming or resetting gets a row under their own company whether a token was issued or not
> (`SessionAuditTests`, four Postgres cases seeded under the second operator; the two ADR-0061 tests
> that sign in with no market now seed the default market's operator). The D3 marker on these five
> (`CountryId => null`) is what stamps their *refusal* rows; this D4 rule is what stamps their
> *success* rows. The `grep` in the paragraph above is no longer the whole roster — add
> `SetTenantOverride` in `Features/Users` to it.

### D5 — Every user carries a tenant; every JWT carries the claim; admins are stamped with the default operator

- `Users.TenantId` is **NOT NULL** (D8). Customers get the market's operator (D3); partners get the market
  they registered against (D3) and are held to it at approval (D6); admins get the creating admin's
  tenant (`CreateAdminUser` already inherits the ambient claim at commit); the seeded dev admin gets
  `'cleansia-cz'`.
- **Admins are stamped with the default operator for now.** An admin sees, edits and audits one
  operator's rows — exactly what the filter and ADR-0012's per-tenant audit feed already do. **The
  holding-level cross-tenant view is a named future ticket** (filed when the second company exists, not
  before): a `Holding` role or a switchable tenant claim, decided when the second company exists and the
  owner says what the holding is allowed to see. Nothing in this ADR forecloses either shape; nothing in it builds
  one.
- `AuthExtensions.SetClaims` keeps its `if non-empty` guard — it is now always true for a persisted user,
  and a HostTest asserts every minted token carries `tenant_id` (D11).

**D5.1 — One identity per email across the holding: `Users (Email)` is globally unique** (challenger
round; supersedes ADR-0050 D1/D4 and re-opens its Alternative (d) on the ruling's own terms).

- **The defect the draft carried.** The draft's D6 said *"the `(TenantId, Email)` index was designed so one
  person can hold an account per operator; this ADR makes that the model."* The shipped auth path cannot
  serve that model: **every** anonymous identity read resolves by email **ignoring the tenant** with
  `FirstOrDefaultAsync` — login on all five hosts (`UserRepository.GetByEmailIgnoringTenantAsync`), the
  lockout counter (`RecordFailedLoginAsync`, which charges *every* row with that email), forgot/reset
  password, OTP confirm, and the Google/Apple link-by-email branch. With two operators and one email in
  both, login picks an arbitrary account, a password reset lands on whichever row Postgres returns first,
  and a lockout on one account locks the other. That is a live security defect the day the second operator
  opens, silent until then.
- **The choice.** Either the identity paths become market-scoped too (login, reset, OTP, social — every
  one gains `countryId`, every client sends it, and a user must remember *which company* they registered
  with), or an email names **one** person across the holding. The second is what the auth path already
  assumes, costs one index change, and is reversible (drop an index) if the owner ever wants the first.
  The first is a client programme and a UX the owner has not asked for. **Chosen: one identity per email.**
- **Mechanics.** `IX_Users_TenantId_Email` → `IX_Users_Email` unique (citext, so case-insensitive as
  today), no tenant term, no `NULLS NOT DISTINCT` needed (the column is NOT NULL). The register / social /
  admin-create writers keep their flush-and-map (ADR-0050 D2) — the 23505 they already own is now the
  cross-operator collision too, mapped to `ExistingUserWithEmail`. Pre-checks: `Register.Validator`
  `UserWithEmailNotExistsAsync`, `RegisterEmployee`'s twin, `CreateAdminUser.AdminUserEmailExists` — and

- **Escalated as O-5** (below) because it is a business fact about the holding, with this default applied.

### D6 — Tenant, country and currency agree by construction, and two validators refuse the cases that could break it

> **Historical decision, 2026-09-13.** The table and refusal below record the original implementation.
> The dated T-0765 amendment at the end of this section supersedes the signed-in booking and recurring
> rows; the guest and employee checks remain.

The order's currency is the service address's country's (ADR-0058); the cleaner's pay currency is the
work country's. This ADR reads the **same country** for the tenant:

| Row | Country it is read from | Currency (shipped) | Tenant (this ADR) |
|---|---|---|---|
| `Order` (guest) | address (`OrderAddressResolver.ResolveCountryIdAsync`) | that country's `DefaultCurrencyCode` | the ambient tenant the D3 behaviour set from `CustomerAddress.CountryId` — **and the same rule as the customer row checks it against the resolver's country** (next row) |
| `Order` (customer) | address | same | **the ambient tenant** (the claim; for a guest, the D3 override) must equal the address country's operator, else refused `order.country_operator_mismatch` — one validator rule on `CreateOrder`, **unconditional**, evaluated on the cached country id the currency rule resolved |
| `Employee` at approval | `WorkCountryId` | pay currency | **the ambient tenant** (the admin's claim — the employee is loaded through the filter, so its tenant *is* the claim) must equal the work country's operator, else refused `employee.work_country_operator_mismatch` (a rule on the `WorkCountryId` chain; needs the resolver and the provider, not the employee) |
| `RecurringBookingTemplate` → materialised `Order` | template row | address | carried forward from the template row (`MaterializeRecurringBookingTemplate`) — already the right shape |
| `OrderReceipt`, `Refund`, `Dispute`, `OrderEmployeePay`, … | — | order's | order's, via override-from-row (unchanged) |

**Why the `CreateOrder` rule is unconditional, not authenticated-only** (challenger round). The draft
scoped it to authenticated callers on the reasoning that a guest's tenant *is* the address country's
operator. It is not, in two cases: (1) `ResolveCountryIdAsync` honoured a `SavedAddressId` even when
`userId` was empty, so a guest's *currency* country could come from a saved address while the D3 marker
read `CustomerAddress?.CountryId` (null ⇒ default operator); (2) a guest with no country at all gets the
default operator from D3 and the single serviced country from the resolver, which coincide only while
there is one market. The unconditional rule makes "tenant and currency are two reads of one country" a
checked invariant rather than an argument, at the cost of one comparison the authenticated path pays
anyway. *(Case (1) was also closed at the root while the ticket was in the file: a guest has no saved
addresses, so naming one is naming somebody else's, and it is now refused `general.not_found` — see
Findings.)*

**The refusal on a customer booking another operator's country is a decision, and the alternative is
named.** A CZ-tenant customer booking an SK address (operated by `cleansia-sk`) is refused rather than
given an order their own account cannot list (the filter would hide it). A person has **one** account
across the holding (D5.1), so the alternative is not a second account — it is cross-operator booking on
one account with a cross-tenant "my orders", which is O-1 for the day two operators exist.

> **Amended 2026-09-16 — cross-market booking on one account (T-0765).** The owner’s 2026-09-15
> Q-TENANCY-01/05 rulings allow a customer to book in any market the holding serves, using one holding
> Stripe account. A signed-in booking resolves the active operator from the service address and sets
> that operator before creating the order and its children. The account claim is not a booking-market
> restriction. A guest keeps the ambient-operator consistency check and
> `order.country_operator_mismatch`; an unserviced country or inactive operator still refuses booking.
>
> **What follows the order:** its address snapshot, status history, pay rows, receipt and refund, and
> dispute retain the address operator. A saved address belonging to another company is copied into an

>
> **What follows the account:** loyalty and currency-specific credit use owner-pinned reads and are

> reads; benefit usage remains with the account’s membership. Promo and referral account records

>
> **Who can read it:** the signed-in customer’s order, receipt, photo, dispute and recurring reads
> cross the tenant filter only when pinned by the caller’s user id; by-id actions still check ownership.
> “My orders” therefore includes the customer’s bookings across operators. Ordinary admin and cleaner
> reads remain company-filtered. An operator’s dispute view uses that operator’s orders; for a customer
> of another company it displays the booking’s identity snapshot, including message identity, rather
> than exposing the customer’s current account profile.
>
> **The admin customer panel:** `GET api/AdminOrder/{orderId}/customer` requires
> `CanViewOrderCustomer` (AdminOnly) and first proves access to the filtered order. The response is the
> existing full `UserItem` for a same-company customer, or a read-only
> `CustomerOfAnotherCompanyDto` (id, first name, masked e-mail, company name) for a foreign customer.
> The shared order detail exposes `CustomerCompany`, not a new account id. A guest order has no account
> panel (`400 order.not_found`), which the admin web renders as an empty account state; booking contact
> details remain their own section. Cross-company customer listing and profile navigation stay closed.
> Successful order/dispute audit acts follow the operator; unproven probes retain the account company
> ([ADR-0062 D7](./adr-0062#d7-tenant-scoping-adr-0061)).

### D7 — Classification: which `ITenantEntity` tables change class

**The rule, stated so the next table can be sorted without a panel:**

> A table is **stamped** (`ITenantEntity`) when its rows are created by or for one operator's customers,
> cleaners or money — or when the row *is* the operator's own legal or financial configuration (its
> issuer identity, its pay rates, its fiscal counter, its campaigns). A table is **tenantless** (drop the
> interface; keep `Auditable` if it is admin-edited, `BaseEntity` if it is seed-only) when it is the
> brand's catalogue or programme definition that every operator sells identically, or a per-country fact.
> The two-question test from the living note still applies: *who writes the rows, with what tenant?* —
> if the answer is "seed, and the readers are tenanted", the table is config and it is tenantless.

### D10 — Jobs and webhooks: the invariant, restated, and the test that pins it

**Invariant:** *a job or webhook has no claim; it derives the tenant of every row it writes from the row
it read, sets the override per row or per tenant group, and commits inside that scope.* Nothing derives a
tenant from configuration, the host, or "the default". Every shipped caller already satisfies it; this
ADR changes none of them — the only thing that changes is that their rows now carry a real tenant, so the
invariant starts doing work.

**Pinned by:** `PreCleaningReminderTenantStampTests` (Postgres, two different non-null tenants, asserts on
child rows) is the reference; S8's rule that *"the pinning test must seed non-null and DIFFERENT
`TenantId`s on at least two iterations"* is already law. D11 adds one test, not a pattern: the sweep
smoke test seeds two operators and runs `CleanupStalePendingOrders`, asserting neither tenant's children
carry the other's id.

**The filter body is byte-untouched.** Its middle clause `(current==null && e.TenantId==null)` now matches
nothing on a NOT NULL table, which is the correct result: a job that forgot its override reads nothing
rather than someone's rows. No clause is removed — ADR-0017 and ADR-0050 both pin the filter diff-empty
and this ADR keeps that promise. *(The comment above the clause still calls it "single-tenant mode"; the
words are wrong and the code is right — Findings.)*

> **As amended 2026-09-15 (T-0759) — a second shape for a job, and it is the invariant's, not an
> exception to it.** A job whose work is *"for each company, do X under that company's own settings"*
> has no row to derive the tenant from — the settings are the row. The retention sweep is the first:
> it reads `ITenantRepository.GetAllIdsAsync` (every company in the registry, deactivated ones
> included — O-3), sets the override **per company**, runs its nine tasks under it (every filtered
> read and every `TenantSettingCatalog` read is that company's) and commits inside each task, then
> clears. "Nothing derives a tenant from configuration, the host, or the default" still holds — the
> registry is not a default, it is the list. The row-derived shape (`CleanupStalePendingOrders`) and
> the registry-driven shape (`DataRetentionBackgroundService`) are the two idioms; a job picks by
> asking whether its input is rows or companies. `CustomerActionAuditRetentionTests` (Postgres) pins
> it: a one-year window set on company B deletes B's two-year-old audit rows and keeps A's.

### D12 — What a second operator costs

A second operating company (say SK) is:

1. one `Tenants` seed row — `('cleansia-sk', 'Cleansia SK s.r.o.')`;
2. `OperatorTenantId = 'cleansia-sk'` on the SVK `CountryConfiguration` row (SVK must already be a market
   — serviced, configured, EUR active — the ADR-0058 story, unchanged);
3. **one `CompanyInfo` row** stamped `cleansia-sk` — the legal issuer; without it receipts and invoices in
   SK have no issuer (`ReceiptService`, `PayPeriodBackgroundService`). This is genuinely per operator and
   is not "nothing else";
4. **the first SK admin** — by SQL, because `CreateAdminUser` stamps the *creating* admin's tenant and no
   holding-level admin exists (D5). Named as the reason the holding view is the next tenancy ticket;
5. pay defaults for SK — entered by that admin through the existing pay-config screen, in EUR, in their
   tenant (D9 makes the rows insertable);
6. clients sending `countryId` on register/social/promo/referral (T-0728) — required *before* the second
   market opens, or SK visitors register into `cleansia-cz`. **The partner picker reads markets, not
   serviced countries** (challenger round): `Country/GetServiced` still lists a serviced country whose
   `OperatorTenantId` is null, `Market/GetOverview` does not (D2); a picker on the former offers a country
   that then fails `tenant.not_found`. `MarketController` exists on the two customer hosts only
   (`Web.Customer`, `Web.Mobile.Customer`); T-0728 adds it to `Web.Partner` and `Web.Mobile.Partner` —
   the same `GetMarkets` query, one controller file each, no Core change.

Nothing else: no schema, no host, no filter, no job, no webhook change. If a future onboarding needs a
seventh step, this list is where it is added and the ADR that adds it says why.

- Does not build a host → tenant registry, a tenant chooser, per-tenant DNS, or per-tenant config
  overrides on catalogue tables (ADR-0041 RB-9's routed question stays routed).

## Alternatives considered

- **(a) Country → operator column on `CountryConfiguration` + a `Tenants` registry + a market-scoped
  pipeline behaviour.** **CHOSEN.** Lays the seam where market facts already live, reuses the shipped
  override and pipeline shapes, changes no filter, and prices the second operator at six listed steps.
- **(b) Stay dormant: `NULL` is the founding tenant, activate on the second company.** The ADR-0050 D5
  / living-note posture. Rejected by the ruling — and on its merits it was never free: every row written
  between now and activation would need a backfill `UPDATE … SET "TenantId"` across ~46 tables on a live
  production database, plus the census-and-dedupe ADR-0050 D3 describes, on a day with data to lose.
  The same work costs one seed value each today. This is the cheapest day this will ever be.
- **(c) Host → tenant registry (`Tenancy:Hosts`, ADR-0028 D2).** Rejected again, on the same ground plus
  a new one: the unit of tenancy is a *company*, which serves *countries*, which a visitor already names
  as a market. Keying on the host would tie operators to deployments — exactly the tenancy/infra
  conflation ADR-0017 D2 forbids — and would need a per-operator host before a second operator could
  exist.
- **(d) A `TenantCountries` join table.** Rejected (D2): models a many-to-many the ruling excludes and
  needs its own rule to forbid it.
- **(e) Reuse `Auditable.TenantId` on `CountryConfiguration` as the operator column.** Rejected (D2):
  gives a dead inherited column a meaning on one table that it has on none of the other tenantless ones.
- **(f) Resolve the market from the `preferred_market` cookie server-side.** Rejected: ADR-0058 D5
  chose explicit `countryId` parameters over the cookie for every API read, and the API hosts are not
  the SSR origin. Same precedent, same answer.
- **(g) Stamp anonymous writers in the handler after resolving the country.** Rejected (D3): the
  validators' filtered pre-checks run first and would run in the wrong tenant; the unconfirmed
  re-registration path becomes a `23505`.
- **(h) Make every seeded config table tenantless (RB-9 everywhere: `CompanyInfo`, `EmployeePayConfig`
  defaults, `PromoCode`).** Rejected (D7): `CompanyInfo` *is* the operator; pay rates and promo money are
  the operator's; making them platform-wide would force a per-tenant override mechanism the day two
  operators disagree — the exact "override on platform config" problem ADR-0041 routed and did not
  solve. Only `LoyaltyTierConfig` passes the brand-programme test.
- **(i) Keep `TenantId` nullable and rely on the seeded-DB scan.** Rejected (D8): the scan cannot see
  the next writer; the constraint can. The fixture churn is mechanical and converts tests that prove
  nothing into tests that run in production's world.
- **(j) FK every stamped table to `Tenants`.** Rejected (D1): forty-odd constraints guarding a value
  that enters at two points, both already bound to the registry. *(Taken 2026-09-15 on the owner's
  ruling — D1 as amended says why the two-points premise did not hold.)*
- **(k) Let a customer book in another operator's country (order stamped with the address's
  operator).** Rejected (D6) with the alternative named as O-1: the order would be invisible to the
  account that placed it. Refusal is the safe direction; linking is a feature for two operators.

## Consequences

**Cheaper / safer:**
- Tenancy stops being a promise and becomes the thing production runs on from its first row, with no
  backfill ever owed.
- A second operating company is six listed steps and no code (D12).
- Every silent-empty-read failure the living note catalogued (§"filter half") is closed at the root:
  there are no `NULL` business rows to hide, and the tables that had them are either tenantless or seeded
  with the operator.
- The order/cleaner/currency/tenant agreement is one country read, so the multicurrency programme's
  guarantees extend to tenancy without a second rule.
- The next anonymous writer that forgets its market fails loudly in DEV (D8) instead of orphaning rows.

**More expensive (accepted):**
- One regenerated `Initial` + one DEV drop at deploy time (D13).
- Fixture churn: every null-tenant fixture names the operator (D8).
- Six anonymous requests gain an optional `countryId`; NSwag clients regenerate (no client *behaviour*
  change until the second market).
- Two new refusals (`order.country_operator_mismatch`, `employee.work_country_operator_mismatch`) and one
  configuration error (`tenant.not_found`) — three keys × five locales × every app that can reach them
  (CLAUDE.md landmine 3). `country.not_serviced` is reused, not added, but it becomes reachable from
  six requests it was not reachable from before — the parity specs say which apps owe it.
- One email, one account, across the holding (D5.1). A person who wants a second company's service
  books from the same account or is refused (O-1) — never registers twice.
- The living docs carried a lot of "single-tenant mode is `TenantId = null`". All of it is rewritten in
  the docs ticket (T-0729), including CLAUDE.md landmine 1, which stopped being true the day D8 landed.

**As shipped — where the tree differs from the draft above, and why each is fine (lead, 2026-09-13):**
- `IOperatorTenantResolver.ResolveAsync` returns a named `OperatorResolution(IsMarket, OperatorTenantId)`
  record struct with a `NotAMarket` constant, not an anonymous tuple. Same two answers; a name a test can
  read.
- The resolver reuses the directory by calling `GetMarkets.Handler.Handle` directly (not through the
  mediator — re-entering the pipeline from inside a behaviour buys nothing) and the static
  `GetMarkets.ResolveMarketAsync` for the three market predicates. A platform with no listed default
  market answers *"market, no operator"* and is refused `tenant.not_found` — a configuration defect of the
  same class as a market nobody operates.
- `SetDefaultMarket` gained a fourth gate: a country whose configuration has no `OperatorTenantId` cannot
  be flagged the default (`country.market_not_ready`), so the seed defect D11(d) guards cannot be
  re-introduced from the admin app.
- `TokenService` sets the override only when `user.TenantId` is non-empty — a guard the persisted
  world never takes but a unit fixture can.
- Nine records implement `IOperatorScopedRequest` (the table in D3 counts `GoogleAuth`/`AppleAuth` and
  `QuoteOrder`/`QuotePlusSavings` as one row each); six of them gained the optional field.
- `OrderStatusTrack` had a convention-only mapping that left its column `text NULL`; it moved onto the
  shared `Auditable` mapping, which the roster-free `TenantIdRequiredModelTests` caught.
- Two absorbed fixes the panel did not predict, both inside the ticket's files: `ResendConfirmationEmail`
  read the user through the filter on an anonymous request (every resend would have been "user not
  found" under NOT NULL — now tenant-ignoring like its siblings); `CreditAccountRepository.TryReturnAsync`
  flushed a new `CreditAccount` with a bare `SaveChangesAsync`, bypassing the commit-time stamp (a 23502
  the day the column is NOT NULL — now commits through `CommitAsync`).
- The dead `ExistsWithConfirmationCodeAsync` (ADR-0051 O-2) was deleted with the confirm-family change.
