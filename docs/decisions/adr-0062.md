# ADR-0062 — A customer's actions are recorded for incident defence, and support reads them in the admin panel

- **Status:** `accepted` — **2026-09-13**, after the architect and security challenge round and the
  seven implementation lanes (T-0730 … T-0736, filed under their working ids T-AUD-1 … T-AUD-7).
  Where the tree departs from the draft, §Consequences *"As shipped"* says so.
- **Date:** 2026-09-13
- **Supersedes:** — . **Amends by extension, not by contradiction:** ADR-0012 D3 (the gate) gains a
  second, opt-in arm; every sentence of ADR-0012 about the *admin* table stays true. T-0686 (terms
  acceptance never recorded) is **absorbed** by D4 and closed with this ADR's tickets.
- **Superseded by:** —
- **Builds on:** ADR-0012 (the capture pipeline: inner-to-UoW success row, out-of-band failure row,
  handler-emitted pre-redacted snapshot, `[AuditAction]` descriptor, append-only + PII-minimised
  retention); the `EmployeeActionAudit` precedent (own table per actor kind — owner ruling 2026-09-06);
  ADR-0041 D10 (versioned agreement text is *platform config*, tenantless — the upgrade path for D4);
  ADR-0045 D13 (refuse collection "just in case"); ADR-0061 (a new tenant-scoped table is stamped with
  the ambient tenant and its column is NOT NULL).
- **Applies to:** `Cleansia.Core.Domain/Auditing` + `/Legal`, `Cleansia.Core.AppServices/Auditing` +
  `Behaviors`, the sixteen customer-issued commands named in D3, `Features/Auth/{Register,GoogleAuth,
  AppleAuth}`, `Features/Gdpr`, `Features/DataRetention`, `Cleansia.Web.Admin` (`CustomerAuditController`
  + a request-log path suppression), `Cleansia.App/libs/cleansia-admin-features/{audit-log,
  loyalty-user-detail}`, the customer web register form, `agents/tools/check-booking-policy-parity.mjs`
  (two more pinned keys).
- **Owner ask (2026-09-13):** *"what's needed to be done for a customer proper audit log with a view of
  it in the admin panel, so that we can provide support and handle issues if something happens"* —
  earlier: *"if there is an incident and we need to resolve it then we have to have proofs of customer
  actions that he performed and how they align with our terms and conditions, so that we don't give
  money every time."*

> **One decision:** *what the platform writes down when a customer acts, so that a money dispute can
> be answered from the record.* The store, the list of recorded acts, the payload each carries, its
> survival of erasure and time, and the screen support reads it on are one contract — a row nobody
> can find, a row that dies with the account, or a row without the figure the customer was shown is
> the same failure: no proof. The terms-version piece (T-0686) is in this decision because an
> acceptance is a customer act like any other and the same row records it.

> **Standing assumption, stated for the owner's lawyer.** The legal documents have not been reviewed.
> Every "what must be provable" claim below is an **assumption** (marked *A-n*), chosen so that the
> lawyer's list can *narrow or extend* what is recorded by adding or removing a descriptor and a
> payload record — never by re-shaping the table or the pipeline. The nine questions only the owner or
> his lawyer can answer are in §Open questions, each with the default now in force.

### What could not be proven about a customer (the gap this ADR closes)

1. That they accepted the terms, when, from where, and **which text** (T-0686).
2. The fee tier, free window, "cleaner had accepted" flag and refund figure **at the moment they
   cancelled** — and any cancel attempt that was **refused**.
3. The price, discounts and policy figures **they were shown** when they booked.
4. Any refused or validation-rejected attempt at all (the gate dropped them before the failure sink).
5. Membership subscribe / swap / cancel, recurring template edits, notification-preference flips
   ("I was never told it was cancelled") — all in-place, no history.
6. A per-customer timeline: admin rows, cleaner rows and customer rows were three tables with no
   screen that interleaves them, and the order/dispute screens linked to only one of them.

## Decision

### D0 — The rule

**A money-relevant customer act is recorded as an append-only row the moment it commits, with the
figures and versions the customer was shown, the request context it came from, and its outcome —
and support can read the customer's whole trail on one screen and hand it over as one file.**

Data-minimised by construction: a row holds **identifiers, money, enums, versions and request
context** — never a name, contact detail, address text, free text the customer typed, card data or a
token. The domain row (`Order`, `Dispute`, `UserConsent`) stays the home of the customer's text; the
audit row *references* it by id and records that it was submitted, when, from where and how long it
was.

### D1 — The store: a third table, written by the shipped pipeline through an audience-aware gate

**`CustomerActionAudit : BaseEntity, ITenantEntity`** beside `AdminActionAudit` and
`EmployeeActionAudit` — its own table (owner ruling 2026-09-06: actor kinds apart; the roster's
"ActorEmail is the ADMIN who acted" sentence must stay true), written by the **same two behaviors**,
the **same factory**, the **same writer/sink seams** and the **same snapshot buffer** as the admin
table. Nothing about the pipeline's shape changes; the gate learns to answer *which* table.

```
CustomerActionAudit : BaseEntity, ITenantEntity            -- NOT Auditable (ADR-0012 D6 reasoning)
    TenantId        varchar(26)    NOT NULL                -- stamped by the writer/sink from the ambient tenant (D7; ADR-0061 D8)
    UserId          varchar(26)?                           -- the customer; NULL for a guest act
    ClientAudience  varchar(40)    NOT NULL                -- IHostAudienceProvider.Audience: the JWT audience of the host that SERVED the request
                                                           --   (filled for anonymous acts; never read off the token). The customer web and the
                                                           --   customer app share one audience, so it names the client FAMILY; DeviceLabel tells them apart
    IpAddress       varchar(45)?                           -- IRequestMetadataProvider.IpAddress
    DeviceLabel     varchar(120)?                          -- UA or X-Device-Label (already truncated by the provider)
    DeviceId        varchar(64)?                           -- a signed-in row: the session's signed device_id claim; an anonymous row: the X-Device-Id header
    Action          varchar(100)   NOT NULL                -- frozen [AuditAction] label, e.g. customer.order.cancel
    ResourceType    varchar(50)?                           -- Order | Dispute | User | UserMembership | RecurringBookingTemplate
    ResourceId      varchar(26)?                           -- clamped to the column on a failure row (a malformed-id probe is recorded, not lost)
    Success         bool           NOT NULL
    ErrorCode       varchar(100)?                          -- the BusinessErrorMessage KEY (AuditErrorCode.Resolve) or the exception type name; clamped
    OccurredOn      timestamptz    NOT NULL
    PayloadJson     jsonb?                                 -- the typed evidence record (D3), success rows only
    CorrelationId   varchar(64)?                           -- Activity.Current.TraceId
  IX (TenantId, OccurredOn DESC) · (UserId, OccurredOn DESC) · (ResourceType, ResourceId) · (OccurredOn)
     -- the last serves the tenant-agnostic retention scan (D5); no (Action, ...) index — the action filter runs inside the tenant-scoped list
```

- **Private setters, one static `Create(...)` factory, no public mutator but `Pseudonymise()`.** The
  draft said `init`; the shipped entity is stricter — a row can only be made whole, by the factory
  the two behaviors call through `AuditEntryFactory`.
- **No `Reason`, no `BeforeJson/AfterJson`.** A customer's act is a statement, not a diff; the diff-shaped
  actions (D3: notification preferences, plan swap, the recurring-template acts) put `{ before, after }`
  *inside* the payload. The customer's free text is never copied (D0).
- **No `ActorEmail`.** The admin table carries it because the actor is the accountable party whose
  identity must outlive the subject; here the actor *is* the subject and the erasure blanks their
  email on the `User` row — a copy would be the "second uncontrolled copy" ADR-0012 D4.1 forbids.
- **`UserId` is a bare scalar, no navigation, no FK** (the `EmployeeActionAudit.EmployeeId` shape):
  the row must outlive everything it names.
- **`DeviceId` on a signed-in row is the claim, not the header.** The `X-Device-Id` header is the
  client's word alone and re-sendable per request; the signed `device_id` claim is the device the
  token was minted for — the one device revocation acts on (ADR-0026). A signed-in row records the
  claim or nothing; only an anonymous act falls back to the header.

**The gate.** `AdminMutationGate` became `AuditGate.Resolve(request, descriptor, session) →
AuditAudience?` with two arms:

```csharp
if (!descriptor.Audited || !name.EndsWith("Command")) return null;
var role = session.GetTypedUserClaim(ClaimTypes.Role)?.Value;
if (role == Administrator)                                                  return AuditAudience.Admin;    // ADR-0012 D3, byte-for-byte
if (descriptor.Audience == AuditAudience.Customer
    && (role == Customer
        || (role is null && descriptor.AllowsAnonymousActor)))              return AuditAudience.Customer; // opt-in; anonymous only where the marker says so
return null;                                                                                               // Employee role, unmarked customer commands, system jobs: unchanged
```

- **Admin is opt-out, customer is opt-in.** ADR-0012 D3 audits *every* admin mutation because the
  owner asked for "all admin mutations"; here the owner asked for *proof for incidents*, and ADR-0045
  D13 refuses collection just in case. A customer command is recorded **only** when it carries
  `[AuditAction("customer.…", Audience = AuditAudience.Customer, ResourceType = …)]`. Of the 44
  customer commands, D3 marks **sixteen** (fifteen labels). `QuoteOrder`, `ValidatePromoCode` and
  `GetMyNotificationPreferences` are reads named `Command` — opt-in is what keeps them out.
- **The admin arm wins.** An Administrator running a customer-marked command lands in the admin
  table (accountability of the privileged actor first). An Employee running one lands nowhere, as
  before. **`EmployeeActionAudit` is untouched** — it is not wired into the pipeline by this ADR; its
  doc comment now cites this ADR for why.
- **Anonymous is a customer only where the marker says so.** `Register` and guest `CreateOrder` have
  no role claim and are the acts the owner most needs proof of, so their markers carry
  `AllowsAnonymousActor = true`. Every other customer-marked command requires the `Customer` role: a
  system job (no session at all) that one day dispatches `CancelOrder.Command` or
  `ConfirmRecurringOrder.Command` must produce **no row**, not a row that reads as a guest act.
  (`role is null` alone cannot tell an anonymous HTTP request from a Functions-host dispatch; the
  marker can.)
- **An anonymous refusal is a row too, and it carries the caller's IP.** A refused `Register` or a
  refused guest `CreateOrder` (validation reject, handler failure, exception) writes an out-of-band
  failure row with `UserId = null` and the request's IP and device label — the "they tried to book at
  09:41 with a wrong price and were refused" proof. The volume is bounded by the same window that
  bounds the request: both routes are `[EnableRateLimiting("auth")]`, 10 requests per minute per real
  client IP, so an unauthenticated caller cannot write more failure rows than that. Two things a row
  still needs: an ambient tenant and a resolved operator. A refusal raised **before** the operator is
  resolved (`country.not_serviced`, `tenant.not_found` — the `OperatorTenantScopeBehavior` refusals,
  ADR-0061 D3) has no tenant to be stamped with and is **skipped with one warning**, not written and
  not raised as an error; a refusal raised after it is stamped with that operator.
- **The error code is the refusal KEY, not the field — on both arms.** `AuditEntryFactory.CreateFailure`
  used to store `result.Error?.Code`, and `Error(code, message)` puts the **field name** in `Code`
  (`new Error(nameof(command.OrderId), BusinessErrorMessage.OrderNotFound)` gives `Code = "OrderId"`,
  `Message = "order.not_found"`); a validation reject's top-level `Error` is the generic
  `ValidationError` sentinel. A failure row whose `ErrorCode` reads `OrderId` proves nothing. One static
  `AuditErrorCode.Resolve(BusinessResult)` records `Error.Message` for a handler-returned failure and
  the first `IValidationResult.Errors[i].Message` for a validation reject (falling back to `Code` only
  when the message is blank); the exception path keeps the exception type name. **Owner ruling
  (Q-AUD-O2): the admin arm adopts the same helper**, so admin failure rows carry the key from T-AUD-1
  on; rows written before it are not rewritten (there are none in production).
- **`ResourceId` on a customer row comes from the snapshot or an exact property — never the `Id` /
  single-`*Id` fallbacks.** `AuditResourceResolver` falls back to "the one string property ending in
  `Id`", which on `CreateMembershipCheckoutSession.Command(PlanCode, CountryId)` returns the **country
  id** labelled as a `UserMembership`, and on `CreateDispute.Command(OrderId, …)` the order id labelled
  as a `Dispute`. The customer arm uses `AuditResourceResolver.ResolveExact(request, resourceType,
  resourceIdProperty)`: the `{ResourceType}Id` property, or the property the marker names in
  `ResourceIdProperty` — added so the three recurring-schedule acts, whose command carries
  `TemplateId` and whose resource is `RecurringBookingTemplate`, record the probed template id on a
  refusal instead of nothing. The admin arm keeps its fallbacks (unchanged, ADR-0012).
  `CreateDispute` therefore marks `ResourceType = "Order"` (the act is against the order; a refused
  filing is evidence about that order) and its success snapshot re-labels the row `("Dispute",
  disputeId)` — the snapshot wins, as before.

**Factory / writer / sink.** `AuditEntryFactory` gained `CreateCustomerSuccess` / `CreateCustomerFailure`
returning `CustomerActionAudit` and takes `IRequestMetadataProvider` and `IHostAudienceProvider`;
`IAuditWriter.Add` and `IAuditFailureSink.RecordFailureAsync` gained a `CustomerActionAudit` overload;
each behavior branches once on the resolved audience. The latch, the out-of-band scope, the "success
rides the single commit" placement and the "failure is best-effort and swallowed" rule are inherited
unchanged. `IAuditContext` gained **`RecordEvidence(resourceType, resourceId, object payload, string?
actorUserId = null)`** — the customer-side twin of `RecordChange`: one payload, no diff; `actorUserId`
exists for `Register`, whose actor does not exist until the handler creates them (the session has no
user id; the row must carry the new one — the session still wins when it has one, S1).

**Enums are serialised by name, camelCase, on all three tables.** `AuditContext`'s JSON options gained
`JsonStringEnumConverter(JsonNamingPolicy.CamelCase)`, so a payload reads `"tier":"plus"`,
`"consentType":"termsOfService"`, `"status":"onTheWay"` — a row a support agent can read without the
enum source. The admin snapshots changed shape with it (they used to carry integers); there is no
production data, and the admin int-pinning tests moved to names.

### D2 — Reuse over invention (why not the two cheaper-looking shapes)

- **Rejected — widen `AdminActionAudit` with an `ActorKind`.** It breaks the 2026-09-06 ruling, makes
  the roster sentence false, puts customer rows in the admin feed, and the customer row needs four
  columns (audience, IP, device label, device id) the admin row must *not* grow (ADR-0012 D4.1 keeps
  the admin row minimal; adding actor-IP to an admin accountability row is a new question nobody
  asked).
- **Rejected — handler-explicit writes, the `EmployeeActionAudit` shape.** It cannot see a refusal: a
  handler-returned business failure does not commit, and a validation reject never reaches the
  handler — yet *"the customer tried to cancel at 09:41 and was refused because the job was in
  progress"* is exactly the proof a dispute turns on (gaps 2 and 4). Only the two behaviors see both
  shapes, and they already do it right (ADR-0012 D2.1/D2.2). The employee table stays handler-written
  because its two acts have no refusal branch worth a row.
- **Rejected — the request log as the trail.** Information-level, `Warning` floor on every deployed
  host, no query surface, S6 forbids the body anyway.

### D3 — What is recorded, and what each row carries (*A-1 … A-5*)

Ranked by what money disputes turn on. Each command carries a frozen label; each success row carries
a **typed, pre-redacted evidence record** the handler emits. Every record implements
`ICustomerAuditPayload` (a marker) so one reflection test can walk them all (Verification #5).

`MarkNotificationRead`, live-activity tokens, `RequestPromoCode`, password reset (account-takeover
evidence — Q-AUD-L5 with logins); `DeleteUserAccount` (`GdprRequest` *is* the erasure's own record per
the roster, and a row written by the act that pseudonymises the table would, by construction, be the
one row the pseudonymisation missed).

**No client-asserted money figure is ever recorded.** The cancel preview a customer saw
(`GetCancellationFeePreview`) is not sent back with `CancelOrder` and would not be stored if it were: a
row holding "the customer says they were shown 0 %" is the customer's own claim, worthless as our
evidence and weaponisable against us. The server's `hoursBeforeCleaning` and `policyFigures` at the
click, plus the deterministic preview, are the proof. The one client-asserted member on any row is
`termsAccepted` (a tick is not a fact the server can observe), and it is the customer's assertion
*against* themselves.

**Assumptions to confirm with the lawyer.** *A-1/A-2* above; *A-3* (nothing else is needed);
*A-4* — the customer's free text (dispute description, cancellation reason) is **referenced, not
copied**: it lives on the domain row under that row's own erasure verdict (`Dispute.Description`
blanked, `Order.CancellationReason` retained); after erasure the description is gone by the
platform's existing design (Q-AUD-L3 — ruling: no). *A-5* — recording that a customer *saw* a figure
means recording the figure the server rendered the screen from at that instant; the platform does not
screenshot.

### D4 — Terms and consent get a version, and the acceptance is recorded server-side (absorbs T-0686)

- **The version is a code constant, pinned to the copy by the parity checker.**
  `Cleansia.Core.Domain/Legal/LegalDocumentVersions.cs`: `CustomerTerms = "2026-09-draft"`,
  `CustomerPrivacy = "2026-09-draft"`, `For(ConsentType)` (null for the marketing and data-processing
  consents, which have no document). The locale keys `terms_page.version` / `privacy_page.version`
  render it on the customer web legal pages in all five locales; `check-booking-policy-parity.mjs` pins
  the five locale values to the C# constant (§4 of the checker, with its own self-test). **The rule for
  a legal-text edit: bump the constant *and* the key in the same change** — the same "figure comes from
  one place" discipline ADR-0060 D4 built. (Q-AUD-L2 — ruling: a dated string is what identifies a
  version; the draft handle stands.)
- **Why not ADR-0041's `AgreementVersion` tables now.** They are accepted and unbuilt; they carry text
  bodies, per-language rows, review status and a content hash — the right shape for *final* legal
  texts. Today's texts are drafts with a blank date and a draft banner; a version string is what a
  draft can honestly carry. **The upgrade path is preserved:** `AgreementVersion.Version` is a
  `varchar(32)` external handle — the constant becomes that row's handle the day the lawyer's texts
  land, and every recorded `"2026-09-draft"` still identifies its text. Nothing recorded now has to be
  re-keyed.
- **`UserConsent.DocumentVersion` `varchar(32)?`** — the version in force when the row was granted or
  re-granted (`UserConsent.Grant/Regrant` take it; `ConsentService.TryGrantAsync(userId, type,
  documentVersion)`). Existing rows stay `null` = "accepted before versioning" — **no backfill, no
  re-prompt** (Q-AUD-L2 ruling). **Stamped only for a `Customer` subject**: `GrantConsent.Command` is
  also routed on both Partner hosts and an employee accepts a *different* document (ADR-0041), so the
  handler passes `LegalDocumentVersions.For(type)` only when the caller's role claim is `Customer`;
  an employee's `TermsOfService` row keeps `null` until `AgreementVersion` lands. **A re-acceptance
  under a *different* version updates the row**: `TryGrantAsync` returns `false` on an already-granted
  row with the same version (or no version), and calls `AcceptVersion(version, ip, ua)` when the
  version differs — *different*, not *newer*, because versions are opaque strings and "different" is
  all the row can tell. The `customer.consent.grant` audit row is still written either way and is the
  history; the `UserConsent` row is the truth about *now*, which is why `UserConsent` is **not** made
  append-only (T-0686 open decision 2 — answered without changing the consent model).
- **Registration writes the consent, server-side, in the same commit.** `Register.Command` gained
  `bool? TermsAccepted`; Google/Apple already carried it. When `true`, the handler grants
  `TermsOfService` and `PrivacyPolicy` with the current versions and IP/UA (the `ConsentService`
  shape) and `Register` records `RegistrationEvidence`; the Google/Apple provisioning branches grant
  the same two rows with the version and record no audit row (D3). The customer web register form
  and the two social sign-ups send the tick; the customer-side `signup-consent.service.ts` and its
  localStorage flush are **deleted**. A client that sends nothing — every shipped mobile build —
  lands `null`, recorded as "not asserted", **not refused** (Q-AUD-L4 ruling: record only, refuse
  nothing until the legal texts are final).
- **The order wizard's terms tick reaches the server.** `CreateOrder.Command` gained `bool?
  TermsAccepted`; the booking row records it with `termsVersionAccepted`. Guest checkout is the case
  this exists for. This ADR records, it does not gate. *(As shipped: the server side is complete; the
  regenerated customer client does not yet carry the field on `CreateOrderCommand`, so the web wizard
  collects the tick and sends nothing — see §Consequences.)*

### D5 — Immutability, retention, erasure and export

**Append-only.** Private setters, one factory, one sanctioned mutator — `Pseudonymise()`, which nulls
`IpAddress`, `DeviceLabel`, `DeviceId` and nothing else. `ICustomerActionAuditRepository` exposes
`Add`, reads, `PseudonymiseForSubjectAsync` and `DeleteExpiredAsync`. The two holes the base types
leave open are closed by a test, not a type: `BaseEntity.IsActive` is a **public setter** and
`IRepository<T>` exposes `Remove`, `RemoveRange`, `Deactivate`, `DeactivateRange` on every repository
including this one — `CustomerActionAuditImmutabilityTests` walks `Cleansia.Core.AppServices` and
`Cleansia.Infra.Database` by reflection and fails on any call site that invokes one of the four on the
type or sets/reads `IsActive` on it.

- **Rejected — a hash chain / signed rows.** The threat model that could alter a row is a human with
  `psql` (ADR-0041 D3.3's threat model); a chain kept in the same database is re-chained by the same
  human, and a key-signed chain needs key management this platform does not have. The proportional
  integrity guarantee is the append-only code discipline plus the fact that the export (below) is
  re-generatable from the database. Revisit if a court asks for it.
- **Rejected — `REVOKE UPDATE, DELETE` at the database.** Erasure must pseudonymise and the retention
  sweep must delete; both are application writes.

**Retention (*A-6*, legal basis — Q-AUD-L1 ruling).** The rows are kept under **legitimate interest
— establishment, exercise or defence of legal claims** (GDPR Art. 6(1)(f), with Art. 17(3)(e) as the
erasure exemption). **Window: three years from the act, per row** — the general subjective limitation
period of the Czech Civil Code (§ 629) runs per claim, i.e. per act, and three years also comfortably
covers card-scheme chargeback windows. Implementation: tenant setting `retention.customer_audit.years`
(`RetentionDefaults.CustomerAuditRetentionYearsKey`, default `DefaultCustomerAuditRetentionYears = 3`),
one `RunSafeAsync("CustomerActionAudits", …)` task on the Functions timer under the `DataRetention:Enabled`
master switch, calling `DeleteExpiredAsync(cutoff)` — tenant-agnostic, per row by its own `OccurredOn`,
in `RetentionDefaults.BatchSize` batches until a batch is empty; the `(OccurredOn)` index serves it.
**A window at or below zero is a misconfiguration, not an instruction**: this is the one delete the
append-only discipline sanctions, and a cutoff of "now" would empty the evidence table on the next tick,
so the task logs a warning and keeps the default. **Why per row and not "three years after the last
act"** (the author's first draft): the anchor form kept an active customer's IP addresses and device
labels for the life of the account — a ten-year customer's row from year one still carried their IP —
which is the data-minimisation failure ADR-0045 D13 names, and it needed a `GROUP BY` sweep that no
other retention task has. Per row, an active customer's trail is a rolling three-year window; an erased
customer's pseudonymised rows expire three years after each act. The sweep never touches the admin or
employee tables (ADR-0012 D6 stands; asserted by row count). Q-AUDIT-01 is re-filed under Q-AUD-L1.

**Erasure.** Verdict **`AnonymizedInPlace`** on the roster: the subject handle is already
pseudonymous (the `User` row keeps its id); the three request-metadata columns are personal data and
are blanked by `customerActionAuditRepository.PseudonymiseForSubjectAsync(userId)` — a **tracked
load** through `GetQueryableIgnoringTenant()` (defence in depth like the sibling walks) followed by
`Pseudonymise()` on each row, **riding the erasure's single commit**. Not `ExecuteUpdateAsync`: that
runs outside the erasure's `SaveChangesAsync` transaction, so a commit failure would leave the trail
blanked while the customer still exists (or the reverse), and no sibling walk is set-based. The payload
survives because Verification #5 proves it holds ids, money, enums and versions only.
`CustomerActionAuditErasureTests` (real Postgres) covers the survival and the commit-throw atomicity.

**What the pseudonymised row still proves, and how it could be re-identified — stated, not hidden.**
`Order.AnonymizeCustomerData()` nulls `Order.UserId`, `PromoCodeId`, `MembershipPlanIdAtPurchase` and
`RecurringTemplateId`: the platform deliberately severs the order's link to the subject on erasure and
again at the two-year order-PII sweep. The audit row **keeps `UserId` and `ResourceId`** — after erasure
it is the only link from the erased id to its orders, and that is the point: without it a chargeback on
an erased customer's order cannot be tied to that customer's acts. The id resolves to a `User` row whose
email is `deleted_{Id}@anonymized.local`; the only route from the id back to a natural person is
**outside the platform**, through Stripe's own records via the order's payment ids, which is the
platform's existing position for the financial record (ADR-0007 D4). **Q-AUD-L1 ruling: the link is
kept.**

**Export (Art. 15).** `GdprExportService.BuildAsync` gained a `customerActions` section
(`GdprExportCustomerActionDto`: action, occurredOn, resourceType, resourceId, success, errorCode,
payloadJson, ipAddress, deviceLabel) — every row of the subject, IP and device null after an erasure,
the payload intact. Both callers get it — the customer's own `ExportUserData` and the admin's
`AdminExportUserData`. A pre-existing gap — the consent section omits IP/UA — is **reported, not
absorbed**.

### D6 — The admin read surface: a per-customer timeline, a searchable list, a detail view, and the existing subject export made accountable

- **`GetActionTimeline` (admin host)** — one paged, `OccurredOn DESC` union over the **three audit
  tables**, keyed either by `UserId` (customer rows of the user ∪ admin rows whose resource is the
  user or one of the user's orders/disputes/memberships ∪ employee rows on the user's orders) or by
  `(ResourceType, ResourceId)`. Common `TimelineEntryDto(Source: Customer|Admin|Employee, Id,
  OccurredOn, ActorId, Action, ResourceType, ResourceId, Success, ErrorCode)`; employee rows map their
  enum to `employee.order.cover_requested` / `employee.order.dropped` so one column reads the same
  whatever the source (no fallback arm — a new enum member must be named or it throws). Order status
  tracks, refunds and payments are **not** a fourth source — they live on the order detail the
  timeline links to. The user's resource-id set for the admin/employee arms is bounded (the 1 000 most
  recent orders/disputes/memberships, tenant-filtered) so the `IN (...)` list cannot grow without
  limit; `Limit ≤ 100`. Each source contributes its own top `offset + limit` rows and the page is cut
  from their in-memory union, so the merge never needs a row that was not fetched. Reads are not
  audited (ADR-0012 D7 stands). Guest acts (`UserId IS NULL`) are reachable **only** by resource,
  never by user — a guest who later registers with the same email does not inherit them.
  **Shape, as shipped:** the request is a `DataRangeRequest` that is an `IQuery<PagedData<T>>` — i.e.
  it answers `BusinessResult<PagedData<TimelineEntryDto>>` — because the "exactly one key" rule must
  answer `400 audit.timeline.filter_required`, and the validation pipeline runs only for a
  `BusinessResult` response. That is a declared A2 deviation from the paged-query convention
  (`agents/cleanup/consistency-baseline.md`); the inherited `Sort` member is accepted and ignored (the
  order is fixed newest-first). `EmployeeActionAudits` gained the `(OrderId, CreatedOn DESC)` index the
  employee arm reads by.
- **`GetPagedCustomerActionAudits` / `GetCustomerActionAuditById`** — the `GetPagedAdminActionAudits`
  shape: `DataRangeRequest`, filter (`UserId, Action, ResourceType, ResourceId, OccurredFrom,
  OccurredTo, Success, ClientAudience`), spec, `CustomerActionAuditSort { OccurredOn, Action, UserId }`,
  a list DTO **without** `payloadJson`/`ipAddress`/`deviceLabel`/`deviceId`, a detail DTO with them and
  without `tenantId`; the by-id validator's existence check is paired with a null guard in the handler.
- **Routes** (`Cleansia.Web.Admin/Controllers/CustomerAuditController.cs`, all `CanViewAuditLog`):
  `GET api/CustomerAudit/get-paged`, `GET api/CustomerAudit/get-by-id/{auditId}`,
  `GET api/CustomerAudit/timeline`. One new error key, `audit.timeline.filter_required`, in the five
  admin locales under `api.*`.
- **The "incident file" of the first version is the admin subject export that already exists.**
  `AdminExportUserData` (`CanAdminExportUserData`) already dumped the subject: profile, address, orders,
  invoices, consents, payout block. With the `customerActions` section (D5) it carries the trail with
  payloads, IP and device. The author's first draft added `ExportCustomerIncidentFile.Command` + an
  assembler + an `IncidentFileDto` with seven sub-DTOs + a new policy — **cut**: it guessed the lawyer's
  file shape before the lawyer's list exists (Q-AUD-L6), and the platform would have carried two
  whole-subject exports. What the first version needs is that the existing export **leaves a record**,
  and it left none: `AdminExportUserData` was a `Query` that `Add`ed a `GdprRequest("Export")` row
  `UnitOfWorkPipelineBehavior` never commits (non-`Command` name; no `CommitAsync` in the handler or in
  `GdprExportService`), and the ADR-0012 gate skipped it for the same reason — so an admin dumping
  another person's whole record was unrecorded anywhere. **It is now `AdminExportUserData.Command` with
  `[AuditAction("gdpr.user.export", Sensitive = true, ResourceType = "User")]`** — the
  `order.access_instructions.reveal` precedent: a read that is itself recorded because it is a PII
  egress — so the `GdprRequest` row commits and an `AdminActionAudit` row is written by the shipped
  pipeline with a PII-free `GdprExportSnapshot(SubjectUserId, Scope, OrderCount, CustomerActionCount)`.
  The verb changed with the shape: `POST api/v1/AdminGdpr/export/{userId}`. **Q-AUD-O3 ruling: the
  customer's own export is fixed in the same ticket** — `ExportUserData.Command` on
  `POST api/v1/Gdpr/export`, no marker (a self-export is not an admin act), its `GdprRequest` now
  committed. **JSON, not PDF** (Q-AUD-L6 ruling: JSON, unsigned, with the subject's identity as of
  export time); the dispute file a lawyer asks for is composed from this export plus the order/dispute
  detail screens until the lawyer says what it must contain.
- **Permissions (Q-AUD-O1 ruling: no support role).** The three reads reuse **`Policy.CanViewAuditLog`**
  (AdminOnly) — it *is* the audit log, and one gate keeps one nav item; a separate customer-trail policy
  would be a policy with no second consumer today. The export keeps its existing
  **`CanAdminExportUserData`**; no new policy (the first draft's `CanExportCustomerIncidentFile` went
  with the command it gated).
- **Admin web (`audit-log` lib + `loyalty-user-detail`).** `/audit-log` gained a segment switch
  *Admin actions | Customer actions*; `/audit-log/customers` lists the customer trail with the
  feature's filter idiom (customer id, action from a catalogue pinned to the backend roster by
  `customer-audit-actions.spec.ts`, client, outcome, date range); `/audit-log/customers/entry/:auditId`
  renders the header (when / who / client / IP / device / outcome) and the payload as a key/value table
  with a raw-JSON toggle (nested `before`/`after` as two columns; the diff renderer stays for admin
  entries; `deviceLabel` and payload values are interpolated, never `innerHTML`);
  `/audit-log/resource/:type/:id` now calls the timeline and shows Customer / Admin / Employee source
  badges (customer and admin rows click through to their entry; employee rows have no detail).
  `/customers/:userId` gained a **Timeline** section (the paged lazy `cleansia-table` idiom, 20 rows)
  and an **Export subject data** button that calls the admin GDPR export and downloads the JSON
  (rendered only with `CanAdminExportUserData`). The order and dispute detail screens carry the
  **View audit history** link to the resource timeline (`CanViewAuditLog`). Five locales (fifteen action
  labels under `pages.audit_log.actions.customer.*` + the page strings); error keys under `api.*`.
- **Request-log hygiene.** The admin middleware suppresses the bodies of every path containing
  `/customeraudit/` (the `gdpr/` shape) — which covers all three routes, `api/CustomerAudit/timeline`
  included — so `payloadJson`, `ipAddress` and `deviceLabel` never reach a log line
  (`RequestLogCustomerAuditPathSuppressionTests`). The S6 surface guards point at the suppression
  rather than at per-member exceptions.

### D7 — Tenant scoping (ADR-0061)

`CustomerActionAudit` is `ITenantEntity` and its column is **NOT NULL** like every stamped table
(ADR-0061 D8; `TenantIdRequiredModelTests` walks it). `DbContextAuditWriter` and
`OutOfBandAuditFailureSink` stamp `TenantId ??= tenantProvider.GetCurrentTenantId()` exactly as they do
for the admin row — **the ambient tenant at write time**. For an authenticated customer that is the
`tenant_id` claim; for an anonymous act it is the market's operator that `OperatorTenantScopeBehavior`
set before validation ran (ADR-0061 D3), so the audit row and the `User`/`Order` row it describes are
stamped from the same source in the same request and agree by construction. The one row that cannot be
stamped — an anonymous refusal raised *by* the scope behaviour, before any operator exists — is skipped
with a warning (D1). This ADR derives no tenant of its own. Admin reads see their own tenant through
the global filter; the erasure's pseudonymisation and the retention sweep read with
`GetQueryableIgnoringTenant()` like every other sweep.

### D8 — What stays out

No request/response body logging; no card data of any kind (not even last4 — Stripe ids only, and
only where the domain row already holds them); no name/email/phone/address/instructions/floor/door;
no free text the customer typed; no JWT/refresh/confirmation tokens (the PII guard refuses the
live-secret names `ConfirmationCode`, `ResetCode`, `VerificationCode` and `AccessCode` by name — S6's
own named residual — while a catalogue code such as `PlanCode` passes); no blob paths; no rows for reads; no rows for cleaner or system acts (their
tables exist and the timeline reads them); no hash chain; no PDF; no second whole-subject export
(`ExportCustomerIncidentFile` was cut — D6); no `AgreementVersion` tables; no backfill; no rows for
social sign-in (`GoogleAuth`/`AppleAuth` unmarked — D3); no client-asserted money figure on any row
(D3); no gating of registration/checkout on the terms flag; no login/session history (Q-AUD-L5
ruling: no — `RefreshToken`'s 90 days stand); no change to `AdminActionAudit` or `EmployeeActionAudit`
columns (the employee table gained an index, not a column).

## Consequences

- The customer hosts write rows on sixteen commands; the admin host reads three tables. No host
  couples to another: the gate, factory, writer and sink live in Core/Infra/Config as before.
- `AdminExportUserData` and `ExportUserData` are `Command`s; the admin export is audited; both export
  calls changed from GET to POST (NSwag regen of the admin and customer clients). Admin failure rows
  carry the error key instead of the field name from T-AUD-1 on (Q-AUD-O2).
- `Initial` was regenerated once for the new table, `UserConsents.DocumentVersion` and the
  `EmployeeActionAudits (OrderId, CreatedOn DESC)` index — the shipped id is **`20260913174821`**; **the
  DEV drop is owed at the DEV deploy** (memory: timed with the deploy, never on the branch), and it is
  the same one drop ADR-0061 D13 already owes, now belonging to this id.
- Two DTO surfaces changed: admin client (three new endpoints + the export verb) and customer client
  (`Register` and `CreateOrder` gained an optional field; the export verb; mobile spec re-dump). Old
  mobile clients keep working.
- The roster gained one row; `CustomerAuditPayloadPiiGuardTests` is the standing proof the erasure
  verdict relies on. A future evidence record with a contact-shaped, free-text-shaped or code-shaped
  member fails the build naming the record and the member.
- `T-0686` closes as absorbed. `Q-AUDIT-01` is re-filed as `Q-AUD-L1`.
- `docs/architecture/security-rules.md` S2 carries the customer paragraph; `docs/domain/model.md`,
  `/product/features`, `/product/business-rules` (§*What is recorded about a customer*), the booking,
  cancellation/dispute, identity and GDPR flow pages and two role cards are updated by the docs ticket.

**As shipped — where the tree differs from the draft, and why each is fine (2026-09-13):**

- **`CreateOrder.Command.TermsAccepted` is server-side only today.** The regenerated customer client
  and the mobile spec carry `termsAccepted` on `Register`, `GoogleAuth` and `AppleAuth`, but

  clients are regenerated (the orchestrator's batched `generate-admin-client` +
  `generate-customer-client` after the phase; HostTests pin the `POST` verbs server-side). Named so a
  reviewer does not read the button as broken by design.
- The entity has **private setters and a factory**, not `init` (stricter than the draft).
- `AuditErrorCode.Resolve` falls back to `Error.Code` when `Message` is blank (a defensive arm the
  draft did not name).
- The marker gained **`ResourceIdProperty`**, read by `ResolveExact`, so the three schedule acts' failure
  rows carry the probed template id (five lines across attribute / descriptor / resolver / factory —
  the alternative was renaming `TemplateId` on the wire across three client trees).
- `ConsentEvidence` is a **top-level record** shared by `GrantConsent` and `WithdrawConsent`; the PII
  guard walks `ICustomerAuditPayload` implementations by reflection, not by nested-type position.
- **Enums by name** on all three tables (D1), not on the customer table alone; the admin int-pinning
  tests moved to names. No production data existed to migrate.
- `CreateOrder.Validator` gained the **`LanguageValidator`** so `language` on the booking row is one of
  the five seeded codes — a behaviour change at checkout (an unknown code is refused); no shipped
  client sends one outside the five.
- `expressWaiverReleased` records the consumer's **answer** (a slot was released), not the asking.
- `GetActionTimeline` is a **validated paged query** (`BusinessResult<PagedData<T>>`), declared as an A2
  deviation in `agents/cleanup/consistency-baseline.md`; `Sort` is accepted and ignored.
- The retention task **refuses a window at or below zero** and keeps the default with a warning.
- `AuditContext` records the device the **session was minted for** on a signed-in row (the claim), not
  the header the request carried; the header only on an anonymous row.
- The two consent-type refusals on `GrantConsent`/`WithdrawConsent` carry the `invalid_enum_value` key
  rather than an English sentence with the submitted integer (found on the way; the failure row
  carries the key).
- Verification #12's "customer link from order and dispute detail to `/customers/:userId`" did **not**
  ship — those screens carry the **View audit history** link (resource timeline) only; the customer
  page is reached from the admin user list and by URL. Reported by the docs lane, not absorbed.

## Open questions (owner / lawyer) — the rulings recorded, each with the default now in force

Every question below was answered on 2026-09-13 by taking the recommended default; the lawyer's
review can narrow or widen any of them by editing a descriptor, a payload record or a setting — never
the table or the pipeline. They are filed in `agents/backlog/questions/open.md` so the review has a
list to work from.

- **Q-AUD-L1 (lawyer)** — retention window and legal basis for customer-conduct evidence, incl. IP
  address; and whether keeping the pseudonymous `UserId → OrderId` link after erasure (D5) is
  acceptable under Art. 17(3)(e). **Ruling:** legitimate interest / defence of claims (Art. 6(1)(f),
  Art. 17(3)(e)); **three years from each act, per row**; IP/device blanked on erasure, deleted with
  the row; **the link is kept**. (Re-files ADR-0012's Q-AUDIT-01.)
- **Q-AUD-L2 (lawyer)** — what identifies a terms version, and what happens to customers who accepted
  before versioning. **Ruling:** a dated version string in code, `"2026-09-draft"` now; legacy rows
  `null` = "version unknown"; **no re-prompt**, no backfill.
- **Q-AUD-L3 (lawyer)** — must the customer's free text (dispute description, cancellation reason)
  survive erasure for defence? **Ruling: no** — the existing verdicts stand (`Dispute.Description`
  blanked, `Order.CancellationReason` kept); the audit row references by id and records length only.
- **Q-AUD-L4 (lawyer + owner)** — must registration and guest checkout be *refused* without an
  explicit terms tick, and from which client versions? **Ruling: record only, refuse nothing** until
  the legal texts are final; then a validator rule per path, web first.
- **Q-AUD-L5 (lawyer)** — must login/session history (IP, device, failed attempts, password resets) be
  kept beyond the 90-day `RefreshToken` window? **Ruling: no**; no login rows in the customer table.
- **Q-AUD-L6 (lawyer)** — export format and content: is JSON acceptable, must it carry the customer's
  identity, must it be signed? **Ruling: JSON, unsigned, with identity** — the existing export, now
  audited and re-generatable from the database; a purpose-built incident file is built once, after
  the lawyer's list.
- **Q-AUD-O1 (owner)** — does support get a role distinct from Administrator? **Ruling: no** for now —
  `AdminOnly` on every read; the export keeps `CanAdminExportUserData`.
- **Q-AUD-O2 (owner)** — should the admin table's failure rows also switch from the field name to the
  error key? **Ruling: yes** — one helper, both arms, from T-AUD-1 on; no rewrite of existing rows.
- **Q-AUD-O3 (owner)** — fix the customer-host `ExportUserData`'s uncommitted `GdprRequest("Export")`
  in the same ticket as the admin export, or file it separately? **Ruling: both in T-AUD-5** — the
  admin one gets the `gdpr.user.export` marker, the customer one does not; both commit.
