# ADR-0065 — Administrators are told: an in-app feed and an e-mail per event

- **Status:** `proposed` — panel-accepted draft 2026-09-19 (challenge B1–B11 resolved below). Implements the
  owner ruling of 2026-09-19 on **D5** (*"both in-app and email"*). The orchestrator's defaults are carried
  in and named as defaults the owner may overrule (O-1..O-6). Builds as **T-0768** (the notifier, the feed
  audience, the admin feed routes, the first event), **T-0769** (the admin web bell and list), **T-0774**
  (the e-mail channel, the template, the mailbox key) and **T-0775** (the seven remaining events); the ninth
  event rides **T-0770** (ADR-0067). Accepted when those ship; where the tree departs from this text the
  departure will be recorded in a *§What shipped* block, as ADR-0064 did.
- **Date:** 2026-09-19
- **Supersedes:** nothing. **Amends by reference:** the `RetryFailedUserDeletions.Response` doc comment
  (*"until admin notifications exist the Error log line per row is how anyone hears about it"*,
  `src/Cleansia.Core.AppServices/Features/Gdpr/RetryFailedUserDeletions.cs:28-32`) — that day is this ADR.
- **Composes with:** ADR-0002 (the outbox → drainer → queue → consumer shape; every e-mail here rides it),
  ADR-0025 (the push/feed catalogue and its "args are never PII" rule — kept, reused for the feed rows),
  ADR-0061 (tenancy: **every** read the notifier makes is a function of the company argument, never of the
  ambient tenant — D2, D3), ADR-0062 (audit labels: the two admin writes this ADR adds carry them), ADR-0064
  (the wind-down milestones it announces; the `TenantSettingCatalog` it extends by one key; the account
  surface that lets the archive event ride a frozen company's commit — D4), the T-0759 catalogue
  (`TenantSettingCatalog` / `SetTenantSetting` / the company settings page), ADR-0067 (the ninth event),
  and — when it lands — ADR-0066 (roles: the recipient set narrows by the entry's **audience**; the column
  is placed here, read for nothing until then).
- **Applies to:** `Cleansia.Core.Domain` (one enum value, one feed audience, **one event-key catalogue**),
  `Cleansia.Core.AppServices` (one notifier service, one event table, one `EmailType`, one `IEmailService`
  method, one `TenantSettingCatalog` key with a new value type, one repository read on the feed, nine call
  sites), `Cleansia.Core.Queue.Abstractions` (one message shape, one key builder), `Cleansia.Functions.Core`
  (one `switch` arm in `SendEmailHandler`), `Cleansia.Infra.Database` (two repository reads; **no new
  table**), `Cleansia.Web.Admin` (one controller), the admin web app (a bell, a list page, one settings
  editor branch), `email-templates/` (one template).
- **Owner ruling this ADR implements (2026-09-19, verbatim):** *"both in-app and email"*.
- **Orchestrator defaults carried in (overrulable):**
  - **O-1** in-app feed to **every Administrator of the order's company** — kept; ADR-0066 narrows it by
    the entry's audience.
  - **O-2** e-mail to a **`TenantConfiguration` key** (the admin notification address), **falling back to
    every administrator's e-mail when unset** — kept (D3). The volume this implies is put to the owner as
    **O-5** (challenge B3).
  - **O-3** the events: new order, dispute filed, failed erasure, payment failure, chargeback, wind-down
    milestones, and the D2 event *"an order lost its last cleaner"* — kept, with **"new order" refined to "an
    order the company now has to serve"** (D4), **"payment failure" refined to "once per order"** (D4, put to
    the owner as **O-6**), and **"wind-down run" refined to "a run that did something"** (D4).
  - **O-4** *"never PII beyond what the admin panel shows anyway"* — **narrowed** to the feed catalogue's
    existing rule: **no PII at all** in args or e-mail bodies (D4). The panel shows the customer's name behind
    the link.

> **One decision:** *administrators learn about the things the platform can already prove happened —
> through the feed row and the e-mail queue the platform already has, from one writer, without a new
> table, without push, without a digest, without preferences.* An event site calls `IAdminNotifier` once;
> the notifier writes one `UserNotification` row per administrator of the **named** company and enqueues one
> e-mail per recipient address through the outbox, inside the caller's unit of work, so the rows exist iff
> the event committed and a failing e-mail can never fail the command. The admin app grows a bell, a list
> and a mark-read; the company settings page grows one field.

## Context (every citation opened at `2b9cd268`, committed files only; re-checked at `def6c7b3` (2026-09-19) — every cited line holds)

### What exists

**A feed row type, written by one producer, read by two audiences.** `UserNotification : TenantAuditable`
— `UserId`, `EventKey`, `ArgsJson`, `ReadOn`; `Create(userId, eventKey, argsJson, tenantId)`,
`MarkRead(readOn)` idempotent, `RefreshDigest` for the two collapsing keys
(`src/Cleansia.Core.Domain/Notifications/UserNotification.cs:15-55`). Its doc comment states the rule this
ADR reuses: *"the feed records business truth, so the row exists iff the event the user reads about
committed"* and *"`ArgsJson` is exactly the push `Args` dictionary (loc-args, never PII, never rendered text)"*
(`:6-13`). **It has no subject column** — the resource an event is about lives inside `ArgsJson`.
`NotificationProducer.NotifyAsync` (`src/Cleansia.Core.AppServices/Services/NotificationProducer.cs:18-47`)
resolves the recipient's company from the persisted user (`:27`), writes the feed row when the key is a feed
key (`:34-37`) and **unconditionally enqueues a push** (`:39-46`). The feed is read per audience:
`NotificationFeedAudience { Customer = 0, Partner = 1 }` and the two keysets are **`Cleansia.Core.Domain`**
(`src/Cleansia.Core.Domain/Notifications/NotificationFeedEventKeys.cs:11-15, 27-57`); the host controller
sets the audience server-side (`GetPagedUserNotifications.Request.Audience`,
`src/Cleansia.Core.AppServices/Features/Notifications/GetPagedUserNotifications.cs:29-30`); the query scopes by
`(userId, keyset)` newest-first (`:57-64`); `GetUnreadNotificationCount`, `MarkNotificationRead`,
`MarkAllNotificationsRead` sit beside it — **none of the three carries `[AuditAction]`**, so the admin arm of
`AuditGate` (`AuditGate.cs:45-55`: any `*Command` run by an Administrator) records an administrator's
mark-read on the partner app's feed as an admin act today. **A key belongs in a keyset only once the
audience's clients render it** (`NotificationFeedEventKeys.cs:20-23`). Rows are swept after
`retention.notifications.days` (default 90 — `RetentionDefaults.cs:11,21`). The repository exposes a
per-user unread lookup and the count/mark-all reads (`IUserNotificationRepository.cs:12-26`); nothing reads
by event key across users.

**E-mail is a queue, not a call.** `SendEmailMessage(EmailType, Email, UserName, Code, LanguageCode, UserId,
TenantId)` (`src/Cleansia.Core.Queue.Abstractions/Messages/SendEmailMessage.cs:16-23`) on `QueueNames.SendEmail`,
enqueued through `IPendingDispatch` (`EmailDispatch.cs:27-34`, `RequestPromoCode.cs:96-108`) or straight
through `IQueueClient` for a paged fan-out (`CompanyWindDownService.cs:180-193`). `IPendingDispatch` is the
outbox: `OutboxPendingDispatch.Enqueue` writes an `OutboxMessage` row in the scoped context the pipeline
commits — *"a message row exists if and only if the business state committed … `Enqueue` stays infallible
and non-network"* (`src/Cleansia.Infra.Database/OutboxPendingDispatch.cs:7-13`), collapsing a double-enqueue
on `(queue, key)` **in-request only** (`:23-32`). **Across requests the collapse is a `23505`:** the unique
index `IX_OutboxMessages_QueueName_MessageKey` is unfiltered (`OutboxMessageEntityConfiguration.cs:43-45`)
and dispatched rows live until `PruneOutbox` removes them after `DispatchedRetentionDays = 14`
(`OutboxRetentionConfig.cs:14`) — a second request enqueuing a key that already exists **fails the business
commit**, and for a Stripe webhook that failure also un-stamps the `ProcessedStripeEvent`, so the redelivery
fails the same way forever. `OutboxDrainerService` sends the rows (`ServiceExtensions.cs:223-225`). The
consumer `SendEmailHandler` (`src/Cleansia.Functions.Core/Handlers/SendEmailHandler.cs`) **already dual-reads a
second message shape off the same queue** by a `messageType` discriminator —
`SendGuestOrderCancellationEmailMessage`, `:42-64` — before the frozen `SendEmailMessage` shape; it is
idempotent act-then-claim on a deterministic key (`:103-146`), acks permanent discards, throws on transport
faults so the runtime retries and dead-letters (`:13-26`). Each `EmailType` maps to one embedded template
(`EmailService.TemplateFileFor`, `EmailService.cs:1004-1016`); the newer kinds layer **in-code default copy
per locale** under admin `EmailTemplateTranslation` rows (`SendCompanyWindDownNoticeAsync`, `:775-825`).
`EmailType` holds nine values (`EmailType.cs:6-23`) and is on the wire to the admin template page.
`MessageKeys.HashCode` is SHA-256 (`MessageKeys.cs:93-94`) — an e-mail key built from it is deterministic.

**Per-company settings are a catalogue with two value types, read for the AMBIENT company.**
`TenantSettingCatalog.All` — ten definitions, `IntTenantSetting` and `BoolTenantSetting`
(`TenantSettingCatalog.cs:29-71`); `Find(key)` gates the writer (`SetTenantSetting.Validator`,
`SetTenantSetting.cs:27-40`, which also refuses an empty value at `:34-37`);
`IAppConfigurationProvider.GetAsync(definition)` resolves stored-or-default (`TenantSettingReader.cs:11-18`)
**through `GetTenantSettingAsync(key)`**, whose implementation is a filtered `FirstOrDefault(c => c.Key == key)`
(`src/Cleansia.Infra.Database/AppConfigurationProvider.cs:8-15`) — the company is whatever the tenant provider
says it is. `TenantSettingValueType { Int = 1, Bool = 2 }` crosses the wire as an integer (*"a member may be
added but never reordered"*, `TenantSettingValueType.cs:5-14`). The settings page renders a checkbox for
`Bool` and a **number input for everything else** (`company-settings.component.html:46-60`).

**Administrators are `User` rows with `Profile == Administrator`, stamped with their company.** Created by
`CreateAdminUser` (`CreateAdminUser.cs:90-98`, e-mail pre-confirmed) or the DEV seed
(`sql-scripts/insert_seed_data.sql:1983-1997`); `IsActive` is the deactivation flag (`DeactivateAdminUser.cs:36-40`).
The tenant filter scopes every `GetAll()` read to the ambient company; a webhook or sweep sets the override
before reading (`HandlePaymentNotification.cs:214-217, 439-442`).

**A frozen company admits only account-surface writes.** `ArchivedCompanyWriteGuard.AccountSurface` lists
`UserNotification` and `OutboxMessage` (`src/Cleansia.Infra.Database/ArchivedCompanyWriteGuard.cs:36, 48`);
everything else stamped is books and throws `CompanyArchivedException` at commit once
`ArchiveRequestedOn` is set (ADR-0064 D3).

### What does not exist, and what compensates

Nothing tells an administrator anything. Five places say so in the tree:

| Site | What happens today | Line |
|---|---|---|
| Failed erasure retry | `LogError` per row, *"until admin notifications exist"* | `RetryFailedUserDeletions.cs:28-32, 87-103` |
| Card payment failed | `LogWarning`, order stays `Pending` for a client retry — **fires per attempt** | `HandlePaymentNotification.cs:237-249` |
| Chargeback | a `Dispute` with `DisputeReason.Chargeback` is added, escalated, and nobody is told | `HandlePaymentNotification.cs:452-475` |
| Wind-down run | `LogError` with the run summary — *"a company closing is a thing a person must see"*; the run is re-run on purpose (`MessageKeys.cs:72-75`) | `CompanyWindDownService.cs:104-114` |
| Order lost its crew | nothing; the seat is re-advertised to cleaners only | `DropOrder.cs:128-132`, `RejectEmployee.cs:119-148` |

A customer dispute (`CreateDispute.cs:168-195`) writes audit evidence and nothing else; a new order tells
the preferred cleaner (`OrderFactory.cs:314-315`) and, once paid, the customer
(`HandlePaymentNotification.cs:293-306`) — never the operator.

### What the ruling fixes as fact

- **Both channels, every event.** The owner did not split events by channel. No per-event channel matrix is
  designed; the pressure valve for volume is the shared-mailbox key (D3), and O-5 asks whether the default
  should be feed-only for the noisiest event.
- "Administrator" is `UserProfile.Administrator` of the event's company. Until ADR-0066 there is one role,
  so every administrator is the recipient set (O-1).

## Decision

> **Contract principle.** *One writer, no new table, no new channel, no ambient read.* An event site names
> the event, the company and the resource; the notifier turns that into the feed rows and the e-mails using
> the two mechanisms the platform already trusts — `UserNotification` and the `send-email` outbox — inside
> the caller's unit of work, reading everything it needs by the company **argument**.

### D1 — The row: `UserNotification`, one per administrator, under a third feed audience

**The admin feed reuses `UserNotification`.** One row per **(administrator, event)**, written with
`UserNotification.Create(adminUserId, eventKey, argsJson, tenantId)` exactly as `NotificationProducer`
writes a partner or customer row (`NotificationProducer.cs:69`). A third audience and keyset — **in
`Cleansia.Core.Domain`, like the two it joins** (challenge B2: Domain cannot reference AppServices, so the
keys cannot be "built from" an AppServices table):

```csharp
// Cleansia.Core.Domain/Notifications/AdminNotificationEventCatalog.cs — the keys and nothing else
public static class AdminNotificationEventCatalog
{
    public const string OrderNew                = "admin.order.new";
    public const string OrderCrewLost           = "admin.order.crew_lost";
    public const string DisputeFiled            = "admin.dispute.filed";
    public const string DisputeChargeback       = "admin.dispute.chargeback";
    public const string PaymentFailed           = "admin.payment.failed";
    public const string ErasureFailed           = "admin.erasure.failed";
    public const string CompanyWindDownRequested = "admin.company.wind_down_requested";
    public const string CompanyWindDownRun      = "admin.company.wind_down_run";
    public const string CompanyArchived         = "admin.company.archived";
    public static readonly IReadOnlyList<string> All = [ … the nine … ];
}

public enum NotificationFeedAudience { Customer = 0, Partner = 1, Admin = 2 }
NotificationFeedEventKeys.Admin = AdminNotificationEventCatalog.All;   NotificationFeedEventKeys.For(Admin) => Admin
```

The AppServices side — `AdminEventCatalog` (`Core.AppServices/Features/AdminNotifications/AdminEventCatalog.cs`)
— is a table **keyed by those constants**: per entry `Audience` (D4) and `EmailArgOrder` (D2). A guard test
asserts the two key lists are equal, disjoint from the customer and partner keysets, and every key starts
with `admin.`.

The admin host routes the three existing queries with the audience server-enriched to `Admin`, the same
way the two mobile hosts do (`GetPagedUserNotifications.cs:29-30`): a new `AdminNotificationController` with
`GET get-paged`, `GET unread-count`, `POST {id}/mark-read`, `POST mark-all-read`, all under one new policy
`Policy.CanViewAdminNotifications` → `PhysicalPolicy.AdminOnly` (ADR-0066 keeps it "any role").
`MarkNotificationRead` already refuses a row that is not the caller's.

**What the admin feed must show, and how the row shows it.**

| Need | Where it is on the row |
|---|---|
| the event | `EventKey` — the web renders title/body from its own locale bundle (ADR-0025) |
| the company | `TenantId` — the row is the admin's own company's by the global filter |
| the resource link | `ArgsJson` carries the id(s) the web deep-links from (`orderId`, `disputeId`, `requestId`) |
| read state | `ReadOn` — per administrator, because the row is per administrator |
| when | `CreatedOn` — the feed is newest-first (`GetPagedUserNotifications.cs:38-46`) |

**Why not a new `AdminNotification` table.** A per-event row needs a per-admin read state beside it — a
second table or a `ReadBy` list — plus its own paged query, unread count, mark-read commands, retention
window, entity configuration, and a third place the "never PII in args" rule is restated. Every one of those
exists for `UserNotification` and is tested. CLAUDE.md §4: *"a new type is paid by every future reader,
forever"*. The only cost of reuse is fan-out — N rows for N administrators — and N is single digits.
**And the reuse is load-bearing for one event** (challenge B7): `admin.company.archived` is written at
`CompanyArchiveService.MarkArchived` (`:172-173`) on a company that is already *frozen*; the rows ride that
commit only because `UserNotification` and `OutboxMessage` are on `ArchivedCompanyWriteGuard.AccountSurface`
(`:36, 48`). A new stamped table would have thrown `CompanyArchivedException` there, or needed sorting onto
the account surface with an argument for why a company's notifications are a person's.

**Why one row per administrator and not one shared row.** A shared read state means the first admin who
glances at the bell silences it for everyone — which is how a chargeback goes unhandled.

**Retention.** Admin rows fall under `retention.notifications.days`. The feed is a bell, not a ledger: the
record of a chargeback is the `Dispute` row; of a failed erasure the `GdprRequest` row; of a wind-down run the
`Tenant` stamps and the admin audit trail (ADR-0064).

**No collapsing.** No admin key joins `NotificationEventCatalog.CollapsingDigestKeys` (`:269-270`). Every
admin event is new information about a distinct resource; a failed erasure retried daily is *meant* to repeat.

### D2 — The writer: `IAdminNotifier`, feed rows plus outbox e-mails, never push, never a commit, never ambient

```csharp
namespace Cleansia.Core.AppServices.Services.Interfaces;

/// One call per event site. Writes one UserNotification per administrator of the NAMED company and
/// enqueues one e-mail per recipient address through the outbox — inside the CALLER's unit of work; it
/// never commits, never touches the network, never enqueues a push, and reads nothing for the ambient tenant.
public interface IAdminNotifier
{
    Task NotifyAsync(AdminEvent adminEvent, CancellationToken cancellationToken);
}

/// <param name="Key">An AdminNotificationEventCatalog key.</param>
/// <param name="TenantId">The company whose administrators are told — an ARGUMENT, never the ambient tenant.</param>
/// <param name="Subject">The dedup subject: the resource id the event is about, plus a discriminator where one resource can raise the event more than once. MUST be unique per logical event ACROSS requests (see "Idempotency").</param>
/// <param name="Args">Loc-args for the feed row and the e-mail body. Never PII. Always carries the id(s) the web deep-links from.</param>
public sealed record AdminEvent(string Key, string TenantId, string Subject, IReadOnlyDictionary<string, string> Args);
```

`AdminNotifier` (`Core.AppServices/Services/AdminNotifier.cs`) — collaborators: `IUserRepository`,
`IUserNotificationRepository`, `IAppConfigurationProvider`, `IPendingDispatch`, `ILogger` — five. Steps:

1. **Recipients.** `IUserRepository.GetActiveAdministratorsAsync(tenantId, ct)` — a tenant-**ignoring** read
   with an explicit `TenantId == tenantId` predicate, returning `(Id, Email, FirstName, LastName,
   PreferredLanguageCode)` for `Profile == Administrator && IsActive && IsEmailConfirmed
   && !Email.EndsWith("@anonymized.local")` — the eligibility the wind-down notice applies
   (`CompanyWindDownService.cs:144-152`). An empty set logs a warning and returns; it is not an error. Once
   ADR-0066 lands the projection gains `AdminRole` and the set is filtered by the entry's `Audience` (D4)
   through `AdminRoleSets.For(audience)`.
2. **The mailbox key — read BY ARGUMENT** (challenge B1, accepted). The first draft read
   `IAppConfigurationProvider.GetAsync(TenantSettingCatalog.AdminNotificationEmail)`, which resolves for the
   **ambient** company (`TenantSettingReader.cs:16` → `AppConfigurationProvider.cs:10-12`). Under a wrong ambient
   tenant the feed rows would have gone to A's administrators (step 1 is explicit) and the e-mail — order
   number, amount, dispute id — to **B's mailbox**. Every listed site sets the override today
   (`CreateOrder.cs:993-994`, `ConfirmRecurringOrder.cs:143`, `CreateDispute.cs:128-130`,
   `HandlePaymentNotification.cs:214-217, 439-442`), which is why it is a defect of the contract and not of
   the tree — and a contract that leans on nine call sites remembering is the failure ADR-0061 exists to
   prevent. So: `IAppConfigurationProvider` gains an overload `GetTenantSettingAsync(string tenantId, string
   key, ct)` implemented as `IgnoreQueryFilters().Where(c => c.TenantId == tenantId && c.Key == key)`, and
   `TenantSettingReader.GetAsync(provider, tenantId, definition, ct)` beside the ambient one. The notifier
   uses only the explicit overload. The CRC's *"does NOT know: the ambient tenant"* is then true.
3. **Feed rows.** One `UserNotification.Create(admin.Id, key, argsJson, tenantId)` per recipient, through
   `IUserNotificationRepository.Add`. No push: `INotificationProducer` is **not** called — its `NotifyAsync`
   enqueues a `SendPushNotificationMessage` unconditionally (`NotificationProducer.cs:39-46`), an
   administrator may hold a partner-app device row (`TokenService.Admits`, `TokenService.cs:90-96`), and a push
   would reach an app that cannot render an `admin.*` key.
4. **E-mail.** The recipient **addresses** are resolved by D3. For each address, one message on
   `QueueNames.SendEmail` through `IPendingDispatch.Enqueue`:

   ```csharp
   // Cleansia.Core.Queue.Abstractions/Messages/SendAdminNotificationEmailMessage.cs
   public sealed record SendAdminNotificationEmailMessage(
       string MessageType,            // "admin-notification" — the discriminator SendEmailHandler dual-reads (SendEmailHandler.cs:50-52)
       string EventKey,
       IReadOnlyDictionary<string, string> Args,
       string Email,
       string LanguageCode,
       string TenantId);

   MessageKeys.AdminNotificationEmail(eventKey, subject, email) => $"admin-email:{eventKey}:{subject}:{HashCode(email)}";
   ```

   Enqueued in a `QueueEnvelope<…>(key, tenantId, message)`; the outbox row's tenant is read back from the
   envelope (`OutboxPendingDispatch.cs:35-39`). *Why a second message shape rather than `SendEmailMessage`
   with the event stuffed into `Code`.* The frozen shape's one payload slot is hashed into the idempotency
   key and treated as a secret (`SendEmailHandler.cs:74`); the promo and wind-down kinds keep the shape by
   re-reading *rows* the command wrote (`:191-199`), and a shared-mailbox send has no per-recipient row to
   re-read. The guest cancellation set the precedent at `:42-64`.
5. **No commit.** The caller's pipeline (`UnitOfWorkPipelineBehavior` on a `*Command`) or the job's own
   `CommitAsync` inside its loop lands the feed rows and the outbox rows with the business state. **A
   failing e-mail cannot fail the command** because the command never sends one — it writes a row.

**Idempotency and duplicates — the rule, stated** (challenge B4, accepted). *A `Subject` must be unique per
logical event across requests.* In-request the outbox collapses `(queue, key)` (`OutboxPendingDispatch.cs:23-32`);
**across requests the unique index is a hard failure of the business commit, not a collapse** — and for a
webhook it un-stamps the Stripe event so the redelivery fails the same way. Feed rows carry no dedup: a row
is written iff the event committed, and an event that commits twice is two events. The audit of every
subject in D4 against this rule is in the table's last column. A Stripe redelivery never reaches a site
(`ProcessedStripeEvents` short-circuits first, `HandlePaymentNotification.cs:148-171`).

**The e-mail body.** One `EmailType.AdminNotification = 10`, one template
`email-templates/admin-notification.html`, one `IEmailService.SendAdminNotificationEmailAsync(email,
eventKey, args, languageCode, ct)`. The template is the chrome (greeting, an "open the console" button to
`{ClientDomainUrl}/notifications`, closing, footer); the **subject and the one-paragraph body are per event**,
from in-code defaults in the five locales keyed `"{eventKey}.Subject"` / `"{eventKey}.Body"` with `{0}`..
placeholders filled from `Args` in a fixed per-event order (`AdminEventCatalog.Entry.EmailArgOrder`), layered
under `EmailTemplateTranslation` rows for `EmailType.AdminNotification` exactly as the wind-down copy is
(`EmailService.cs:788-803`). The language is the recipient's `PreferredLanguageCode` through the
wind-down's `ResolveLocale` rule (`CompanyWindDownService.cs:493-496`, hoisted — a second caller); for the
shared mailbox (D3) it is **English**.

*Why one `EmailType` and not one per event.* `EmailType` is on the wire to the admin template page, where
every value is a row an admin can retitle in five locales. Nine events as nine types is nine rows, nine
templates and forty-five default dictionaries for e-mails that differ by two sentences.

### D3 — The recipient rule and the `TenantConfiguration` key

```csharp
// TenantSettingCatalog
public const string NotificationsCategory = "notifications";
public const string AdminNotificationEmailKey = "notifications.admin_email";
public static readonly EmailTenantSetting AdminNotificationEmail = new(AdminNotificationEmailKey, NotificationsCategory, @default: string.Empty);
```

`EmailTenantSetting : TenantSettingDefinition<string>` — `ValueType = TenantSettingValueType.Email = 3`
(appended, per `TenantSettingValueType.cs:5-8`), `TryParse` = trim, lowercase, `MailAddress.TryCreate`
succeeds, length ≤ 150, and **the empty string is invalid** — `SetTenantSetting` refuses it (it already
refuses empty at `:34-37`) and **"unset" is `ResetTenantSetting`**, which deletes the row; `Resolve(null)`
answers `""`. The category `notifications` is new; the page renders any category through its translation
key (`company-settings.models.ts:24-26`).

**The rule.** `AdminNotifier` reads the key by the event's `TenantId` (D2 step 2).

| `notifications.admin_email` | E-mail goes to | Language |
|---|---|---|
| set | **exactly that one address**, one message | English |
| unset (default) | **every recipient of D2 step 1**, one message each | each administrator's preferred language |

The feed rows are written in both cases — the key changes the *e-mail* fan-out only. *Why an address and
not a list.* A company that wants three mailboxes has a distribution list on its own mail server. *Why the
fallback is every administrator and not none.* "Nobody is e-mailed until somebody configures it" is the
state the platform is in today; the ruling is that administrators are told. **The volume this implies is a
product decision** (challenge B3): fifty offerable orders a day and three administrators is 150
`admin.order.new` e-mails a day until the key is set. Put to the owner as **O-5**; the default stands until
overruled, and if the answer is "feed-only for new orders until a mailbox is set" the change is a
`Channels` flag on that one catalogue entry.

**The company settings page.** The row appears with the catalogue; the editor gains a third branch —
`Email` → `<cleansia-text-input dataType="email">` — beside the checkbox and the number input
(`company-settings.component.html:46-60`); `formatSettingValue` shows the address or the translated *"every
administrator"* for the empty default; the reset action exists. The write is audited as
`tenant_setting.set` / `tenant_setting.reset` (`SetTenantSetting.cs:16`) — no new label.

### D4 — The events: keys, sites, payloads, subjects, audience, and the dedup audit

**"New order" is the offerable transition, not creation (O-3 refined).** An unpaid card order is an
abandoned checkout `CleanupStalePendingOrders` cancels an hour later (`HandlePaymentNotification.cs:309-311`);
announcing it at creation hands the operator a job that vanishes — the reasoning that moved the preferred
cleaner's offer off the creation site (`PreferredOfferNotifier.cs:11-14`). The notifier call sits beside the
existing `PreferredOfferNotifier` call at each site, guarded by the same `OrderAvailability.IsOfferable`
read. **At `OrderFactory.cs:314` `order.TenantId` is `string?`** (set at `:162` from
`input.OperatorTenantId`; challenge B9): the site skips the call with a warning when it is null — a
market with no operator is a seed defect, not a reason to fail an order.

**"Payment failure" is once per order (O-3 refined; challenge B5, accepted; put to the owner as O-6).**
`payment_intent.payment_failed` fires **per attempt** on PaymentSheet; the order stays retryable
(`HandlePaymentNotification.cs:237-249`) and, unpaid, is cancelled by the stale sweep an hour later. Five
declines would be five feed rows and five e-mails per administrator for a state the platform resolves
itself. The subject is therefore `order.Id`, and — because a repeated subject is a `23505` at commit (D2),
never a collapse — the **site** guards before calling: `IUserNotificationRepository.AnyForEventAsync(tenantId,
eventKey, argName, argValue)`, a tenant-ignoring read with an explicit `TenantId == tenantId` predicate
matching `EventKey == key && ArgsJson.Contains("\"orderId\":\"<id>\"")` — a `LIKE` on a text column, bounded
by one company's rows of one key inside the 90-day retention window, and honest about being that. The
notifier controls `ArgsJson` serialisation, so the fragment it matches is the fragment it wrote; a unit test
pins the two. *Why not a stamp on `Order`.* A `PaymentFailedAt` column is a schema change for a notification
cadence nobody reads elsewhere. *Why not the stale sweep's cancel as the moment.* An abandoned checkout with
zero attempts is not a payment failure, and the sweep cannot tell the two apart without the same stamp.

**Payloads are never PII.** No customer name, e-mail, phone or address; no cleaner name; no dispute prose.
The `ArgsJson` rule of `UserNotification.cs:11-12` is inherited; the existing `PushLocKeyCatalogTests` shape
gains an admin-catalogue case that fails on any arg named like contact identity.

**The audience column.** Each `AdminEventCatalog.Entry` carries `Audience` — one of the five
administrator-set names (`PhysicalPolicy.AdminOnly` today, the sets ADR-0066 D2 introduces). **This ADR
reads it for nothing**; it is placed so ADR-0066 D8 narrows the recipient set with one filter in D2 step 1
and no second design. The first draft carried a `Policy.*` constant and resolved it through
`PolicyBuilder`; the panel (challenge C6, C7) found that shape wrong for a `User`-row filter and unable to
say "Support and Accountant both" — a chargeback is exactly that, and the set name says it directly.

### D5 — What the admin web shows

- **A bell** in the admin app's top bar beside the language switcher (`app.component.ts:27-31`): unread
  count from `GET unread-count`, polled every 60 s while the tab is visible — no push channel, no SignalR.
- **A list page** `/notifications` (route + sidebar item `sidebar.notifications`, permission
  `Policy.CanViewAdminNotifications`): newest first, 20 a page (`GetPagedUserNotifications.cs:19-20`), each row
  rendering `pages.notifications.events.<eventKey>.title` / `.body` from the args (five locales; the key is the
  translation path, as the settings page nests dotted keys, `company-settings.models.ts:18-22`), unread rows
  emphasised, **mark read** on click that also navigates to the resource (order detail, dispute detail, the
  data-protection requests page, the company lifecycle page), and **mark all read**.
- **The settings field** on the company settings page (D3).
- The `POLICY_MAP` mirror gains `CanViewAdminNotifications: AdminOnly` (`policy.ts:207-371`).

## What is NOT built (and why)

- **No push to administrators.** The admin console is a browser; the partner app is the wrong app (D2 step 3).
- **No digest, no throttling.** Every event is one row and one e-mail per recipient. Volume is O-5's; the
  first follow-up if the owner asks is a per-*event* `Channels` flag on the catalogue entry, not a digest.
- **No per-admin preferences.** `UserNotificationPreferences` is a customer/partner mute table keyed by
  `NotificationCategory`; admin events map to no category (`GetCategoryFor` returns null for every `admin.*`
  key — non-mutable). An administrator who does not want order e-mails is a company that sets the mailbox.
- **No holding-wide feed.** The row is stamped with the company.
- **No reason free text anywhere** (ADR-0045 D13).
- **No admin audit rows for reads — one mechanism** (challenge B10): `MarkNotificationRead.Command` and
  `MarkAllNotificationsRead.Command` are marked `[AuditAction(Audited = false)]` (`AuditActionAttribute.cs:34`).
  A bell click is not a ledger entry. This **also switches off the accidental admin audit rows written
  today** when an administrator marks read in the partner app's feed (`AuditGate.cs:50-55` fires on the
  profile for any unmarked `*Command`) — a tidy-up the ADR takes deliberately because the mechanism is one
  attribute. The two writes that *are* admin acts — setting and resetting the mailbox key — carry the
  existing `tenant_setting.*` labels.
- **No notifier-side dedup.** The subject rule (D2) is the caller's; the one site that needs a cross-request
  guard (`admin.payment.failed`) reads the feed before calling.

## Residuals (accepted, named)

- **Volume.** N administrators × M offerable orders a day → N×M `admin.order.new` e-mails until the mailbox
  key is set (O-5).
- **The shared mailbox is English.** A second key for its language is the "do nothing" answer until asked.
- **Sixty seconds of stale badge** between polls; the list page refreshes on open.
- **Two silent ends on the e-mail path** (challenge B8). A mistyped mailbox that bounces dead-letters every
  admin e-mail after `maxDequeueCount`, and the fallback never engages — the platform cannot tell a bounce
  from an outage; a SendGrid outage dead-letters likewise, and a `DeadLetter` row tells nobody (itself a
  candidate admin event, not this ADR's). **The feed is the surviving channel** in both cases, which is
  why "both channels" is the right ruling and not a redundancy.
- **An administrator created without a confirmed e-mail** (impossible through `CreateAdminUser`, `:98`)
  receives feed rows and no e-mail.
- **A chargeback linked to an existing open dispute** (`HandlePaymentNotification.cs:447`) raises
  `admin.dispute.chargeback` with the *existing* dispute's id — the panel opens the dispute the money is
  now attached to.
- **`admin.payment.failed` after a retention sweep** — a decline more than 90 days after the first on the
  same still-unpaid order would re-alarm; impossible, the stale sweep cancels the order after an hour.

through `INotificationProducer` and never through `IEmailService` directly from a handler; an `AdminEvent`
subject is unique per logical event across requests, because the outbox index fails the commit."*

**CRC — `AdminNotifier`.** *Responsibility:* turn one admin event into the feed rows and the e-mail intents of
one **named** company's administrators, inside the caller's unit of work. *Collaborators:* `IUserRepository`
(who), `IUserNotificationRepository` (the rows), `IAppConfigurationProvider` (the mailbox key, by company),
`IPendingDispatch` (the e-mail intent). *Does NOT know:* the ambient tenant, how e-mail is rendered or sent,
what a push is, whether the caller will commit, what any event *means*, whether an event repeats.

## Verification (what a reviewer checks)

1. `AdminNotifier` calls neither `INotificationProducer` nor `IEmailService` nor `IQueueClient` nor any
   `CommitAsync`, and never the ambient `GetTenantSettingAsync(key)`; a unit test with a throwing
   `IPendingDispatch` stub is the only way it can fail, and the test asserts it writes the feed rows before
   enqueuing.
2. The recipients read and the mailbox read are both `IgnoreQueryFilters()` with `TenantId == tenantId` in
   the predicate; a Testcontainers test seeds two companies' administrators **and a mailbox on B**, raises an
   event for A under an override set to B, and asserts the feed rows are A's administrators' **and the outbox
   row's `Email` is A's fallback address, never B's mailbox**.
3. The e-mail fan-out test: key set → exactly one outbox row to that address with `LanguageCode = "en"`;
   key unset → one row per eligible administrator in their own language; a deactivated, unconfirmed or
   anonymised administrator gets neither row nor e-mail.
4. `SendEmailHandler` renders `admin-notification.html` for the new discriminator and throws on a transport
   fault (the shape of `:124-131`); a malformed body acks.
5. `AdminNotificationEventCatalog.All` equals `AdminEventCatalog`'s key set, equals `NotificationFeedEventKeys.Admin`,
   is disjoint from the customer and partner keysets, every key starts with `admin.`, maps to `null` in
   `GetCategoryFor`, and has title/body keys in all five admin locales (the locale-parity spec shape).
6. Each site in D4 calls the notifier **once** inside the same unit of work as the business write; the
   `HandlePaymentNotification` tests assert a redelivered Stripe event produces no second outbox row; the
   `RetryFailedUserDeletions` test asserts a request failing on two consecutive days produces two rows and
   two outbox rows with distinct keys, and that one day's retry twice produces one **because the second run
   selects no candidate**; the `payment_intent.payment_failed` test asserts two declines on one order produce
   one row per administrator and one outbox row per address.
7. `admin.order.new` fires from the three offerable sites and **not** from an unpaid card creation: an
   integration test creates a card order and asserts zero admin rows until the completed-session webhook; a
   creation with a null `OperatorTenantId` logs a warning and writes nothing.
8. `admin.company.wind_down_run` is not raised for a 0/0/0/0 run; `admin.company.archived` is written on a
   frozen company without `CompanyArchivedException` (the account-surface test).
9. HostTests: the four admin-host notification routes answer 401 anonymous, 403 to an Employee token, 200 to
   an administrator; `mark-read` on another administrator's row is refused; a mark-read by an administrator
   writes **no** `AdminActionAudits` row.
10. The company settings page renders the `Email` type as an e-mail input, refuses a malformed address
    client-side with the server's `tenant_setting.invalid_value` key, and shows *"every administrator"* for
    the default.
11. No arg value in any site is a name, e-mail, phone or free text — the catalogue guard.

## Alternatives considered

- **A new `AdminNotification` table** — rejected (D1): re-implements four query paths and a retention window,
  and would have thrown on the frozen company's archive commit.
- **Reuse `INotificationProducer` with an admin keyset** — rejected (D2): it enqueues a push per call.
- **`SendEmailMessage` with the event encoded in `Code`** — rejected (D2 step 4): the slot is a secret by
  contract and a shared-mailbox send has no row to re-read.
- **One `EmailType` per event** — rejected (D2): nine template-page rows for two sentences each.
- **Read the mailbox key for the ambient company** (the first draft) — rejected (D2 step 2, challenge B1):
  a contract that depends on nine call sites remembering an override.
- **Build `NotificationFeedEventKeys.Admin` from an AppServices catalogue** (the first draft) — rejected
  (D1, challenge B2): Domain cannot reference AppServices; the keys are Domain constants.
- **Carry a `Policy.*` constant on the entry and resolve it through `PolicyBuilder`** (the first draft) —
  replaced by the audience set name (D4, challenges C6/C7).
- **`admin.payment.failed` per Stripe attempt** (the first draft) — rejected (D4, challenge B5): an alarm per
  fumbled card entry. **A `PaymentFailedAt` stamp on `Order`** — rejected: schema for a cadence. **The
  stale sweep's cancel as the moment** — rejected: cannot tell an abandonment from a decline.
- **`admin.company.wind_down_run` on every run** (the first draft) — rejected (D4, challenge B6).
- **A per-event channel matrix now** — deferred: the ruling is both channels; O-5 decides whether the first
  flag is needed.
- **Announce at order creation** — rejected (D4): abandoned checkouts.
- **A descriptor-level opt-out for the mark-read audit** — dropped (challenge B10): one attribute does it.

## Open questions for the owner

- **O-1** (default applied: every administrator of the company is told; ADR-0066 narrows by audience).
- **O-2** (default applied: one shared address in English, or every administrator in their language).
- **O-3** (default applied, refined: "new order" = became offerable; "wind-down run" = a run that did something).
- **O-4** (narrowed: no PII at all in the notification; the panel shows it behind the link).
- **O-5** — *`admin.order.new` by e-mail, by default.* Fifty orders a day × three administrators = 150
  e-mails a day until a mailbox is set. Default kept: e-mail every administrator (the ruling says both
  channels). Overrule: feed-only for `admin.order.new` until a mailbox is set (a `Channels` flag on one entry).
- **O-6** — *Payment failure cadence.* Stripe fires a decline per attempt; the platform retries or cancels
  the order itself within the hour. Default: **once per order** (the first decline). Overrule: per attempt,
  or not at all.

## Challenge

B1 (High, tenancy) the mailbox read was ambient while the recipients read was explicit; Verification #2
would have passed while the e-mail went to the wrong company · B2 (Medium, layering) Domain keys "built
from" an AppServices catalogue · B3 (Medium) the default e-mail volume of `admin.order.new` is a product
decision taken silently · B4 (Medium) outbox keys collapse in-request only; a repeated subject fails the
commit · B5 (Medium) `admin.payment.failed` per Stripe event is an alarm per fumbled card entry · B6
(Medium) `admin.company.wind_down_run` fires on every re-run · B7 (Low) `admin.company.archived` works
only because of the account surface · B8 (Low) two silent ends on the e-mail path · B9 (Low)
`OrderFactory.cs:314` has a nullable tenant · B10 (Low) one mechanism for the mark-read opt-out · B11
(Low) T-0768 is not one commit's worth · C6/C7 (from ADR-0066) the `Policy`-on-entry seam is the wrong
shape and cannot express a chargeback's audience.

## Defense

B1 conceded and fixed (explicit-tenant overload; the CRC is now true; Verification #2 asserts the outbox
`Email`). B2 conceded (the keys are Domain constants; the AppServices table is keyed by them). B3 conceded
as a question, not a change: O-5 with the numbers, default kept. B4 conceded: the subject rule is stated and
every subject audited in D4. B5 conceded: once per order, with the feed read as the guard and the two
alternatives argued; O-6. B6 conceded. B7, B8, B9, B10 accepted and written in. B11 accepted (the tickets
file splits T-0768 into T-0768 / T-0774 / T-0775). C6/C7 accepted: the entry carries an audience set name.

## Verdict

**Consensus.** All findings resolved by change or by a named residual; two are owner questions (O-5, O-6)
whose defaults do not block the build. ADR-0065 is accepted for build as T-0768, T-0774, T-0775 (backend)
and T-0769 (web).
