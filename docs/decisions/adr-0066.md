# ADR-0066 — Four administrator roles: Administrator, Manager, Support, Accountant

- **Status:** `accepted` — **2026-09-19, shipped as T-0748 (backend `56fa5aa2`, with the fix `45462202`) and
  T-0773 (admin web `14c833bf` + `bef0838e`; the create form's default role and the two refusal keys in
  five locales ride `45462202`).** Where the tree departs from the text below the departure is recorded in
  *§What shipped* at the foot, as ADR-0064 did; the decision itself is unchanged. Panel-accepted draft
  2026-09-19 (challenge C1–C8 resolved below). Implements the owner ruling of 2026-09-19 on **D8 / T-0748**
  (*"let's do those 3 for now"*: Support, Accountant, Manager beside Administrator). The orchestrator's
  default matrix is the starting table; every row that departs from it says why in one line (D3) and is
  listed for the owner one per line (O-R1..O-R10) — every one of the ten shipped as its default. Built as
  **T-0748** (backend, last in the batch — it changed the recipient filter ADR-0065 ships and the admin-host
  policies every earlier ticket routes on) and **T-0773** (admin web).
- **Date:** 2026-09-19
- **Supersedes:** ADR-0001 **D2's table** (the frozen `Policy.* → PhysicalPolicy.*` map) for every row that
  reads `AdminOnly` today and for **eight shared reads routed on the admin host** (D3) — those rows are
  re-mapped or split; ADR-0001 D1 (fail-closed completeness), D3 (`OwnerOrElevated`), D4 (one shared
  registration) and D5 (audiences) stand. `FrozenPermissionMapTests`' header names this: *"a semantic change
  to an existing row requires a superseding ADR before this test is touched"*
  (`src/Cleansia.Tests/Authentication/FrozenPermissionMapTests.cs:10-11`).
- **Amends by reference:** ADR-0062 D1 (the admin audit row gains the actor's role); ADR-0064 §D1 (*"when
  T-0748 lands, a one-line ruling moves administrators into the constant"* — **not taken**: Q-LC-01 is kept
  as ruled, D7); ADR-0065 D2 step 1 / D4 (the recipient set of an admin event narrows by the entry's
  **audience**); the atomic guard in `DeactivateAdminUser` (D4: it is made atomic).
- **Composes with:** ADR-0001 (the seam is reused: `Policy` constants, `PolicyBuilder.Map`, `AssertComplete`,
  `PermissionAttribute`, the startup filter), ADR-0061 D5 (administrators are stamped with their company;
  the role is per company by construction), ADR-0062 (audit), ADR-0024/ADR-0026 (token lifetimes bound the
  residual of a role change).
- **Applies to:** `Cleansia.Core.Domain` (one enum, one column on `User`, one column on `AdminActionAudit`),
  `Cleansia.Core.AppServices` (four physical-policy constants, the map, one claim, one command, two DTO
  members, **eleven** new `Policy` constants), `Cleansia.Config` (four registrations, the startup semantics),
  `Cleansia.Infra.Database` (one regenerated `Initial`, one check constraint, two guarded repository writes),
  `Cleansia.Web.Admin` (one controller action; sixteen attribute edits across six controllers — fourteen
  shared reads plus the two legal-document routes),
  `Cleansia.Tests` (the policy matrix), `Cleansia.HostTests` (the reflection test and four behavioural
  classes), `sql-scripts/` (the seed and `set-admin-role.sql`), the admin web app (role picker,
  `PermissionService`, guards, sidebar), `docs/`.
- **Owner ruling this ADR implements (2026-09-19, verbatim):** *"let's do those 3 for now"* — Support /
  Accountant / Manager beside Administrator.
- **Orchestrator default matrix, carried in:** Administrator = all; Manager = all but company lifecycle,
  company settings, legal documents, role assignment; Support = customers, cleaners (approve/reject,
  documents), orders (reassign, cancel, override), disputes, refunds within the policy, audit +
  data-protection reads, export + incident file, notifications; Accountant = reports, receipts, payout
  invoices, pay periods, fiscal counters, company info, refund reads, employee payout details (masked).
  Q-LC-01 (administrators of a deactivated company stay admitted) **kept as ruled (D7)**.

> **One decision:** *an administrator's role is a second axis on the account — not a new profile — carried
> as one claim, gating every admin permission through the seam that already exists.* `UserProfile.Administrator`
> stays the profile (so the token mint, the customer-exclusion policy, the audit gate and twenty-five
> handler-level audience checks are untouched); `AdminRole` is a column on `User`, meaningful only for that
> profile, minted into the JWT as `admin_role`, and `PolicyBuilder.Map` re-maps every admin-host row to one
> of five administrator sets — `AdministratorOnly`, `ManagerOrAbove`, `SupportOrAbove`, `AccountantOrAbove`,
> or `AdminOnly` (any). **Shared reads the admin host routes get admin-host constants so the partner hosts
> stay byte-identical while the role gates PII on the admin host.** A role is assigned by an Administrator
> through one audited command that can never demote the last Administrator of a company — under a company
> lock, because the conditional `UPDATE` alone is not atomic; the seeded administrator is an Administrator;
> the admin web hides what the role lacks while **the server remains the gate**; and a policy matrix
> evaluates every map row × role in milliseconds so a new policy without a row cannot ship.

### What the ruling fixes as fact

- **Three roles now; "etc." later.** Four members, no fifth designed.
- **Administrator keeps everything.** The seeded administrator is an Administrator.
- **Q-LC-01 stays as ruled (D7).**
- **The matrix is a lattice** — Administrator ⊇ Manager ⊇ (Support ∪ Accountant) — with one named
  exception the ruling itself creates: a chargeback is Support's *and* the Accountant's (D8).

## Decision

> **Contract principle.** *The profile answers "which audience is this account?"; the role answers "which
> administrator is this?". One claim each. Every admin-host permission resolves through the existing map to a
> set of roles; the server is the gate, the web is a hint, the audit row records both; the partner hosts
> never read the role.*

### D1 — The model: `AdminRole` is a second axis on the account, not a new profile

```csharp
// Cleansia.Core.Domain/Enums/AdminRole.cs
[SwaggerEnumAsInt]
public enum AdminRole
{
    Administrator = 1,   // everything, including the four Administrator-only areas (D3)
    Manager = 2,         // everything but company lifecycle, company settings, legal documents, admin accounts and roles
    Support = 3,         // customers, cleaners, orders, disputes, refunds, audit and data-protection reads, exports, notifications
    Accountant = 4,      // reports, payouts, pay periods, fiscal, company info, money reads, masked payout details
}

// User.cs — beside Profile (:52)
/// The administrator's role. NOT NULL iff Profile == Administrator (DB check constraint); meaningless and
/// null for a customer or a cleaner. Set at creation and by SetAdminRole only.
public AdminRole? AdminRole { get; private set; }

public static User CreateWithPassword(…, UserProfile profile = UserProfile.Customer, string? languageCode = null,
                                      AdminRole? adminRole = null)
    // profile == Administrator requires a role; any other profile requires none — the invariant the
    // constraint enforces, refused here first as an InvalidOperationException (a programming error, not input).

public User SetAdminRole(AdminRole role)
{
    if (Profile != UserProfile.Administrator) throw new InvalidOperationException("Only an administrator holds a role.");
    AdminRole = role;
    return this;
}
```

**Schema.** `Users.AdminRole integer NULL` + `CK_Users_AdminRole_Profile CHECK (("Profile" = 100) = ("AdminRole"
IS NOT NULL))`; `AdminActionAudits.ActorAdminRole integer NULL` (D5). One regenerated `Initial`; the DEV drop
is owed once, at deploy time. The seed (`insert_seed_data.sql:1983-1997`) gains `"AdminRole" = 1`;
`set-admin-role.sql` sets both columns. `DomainSeed.Admin` and `CreateAdminUser` pass the role.

**Why a column and a claim, not new `UserProfile` members** (T-0748's own sketch, `agents/backlog/tickets/T-0748-roles-beyond-administrator.md:44-47`).
Four profiles for staff would touch every place the profile is read as *"is this staff?"*: the twenty-five
handler checks, `Admits` at the mint (`TokenService.cs:90-96`), `CustomerOnly` (`ServiceExtensions.cs:53-60`),
`OwnerOrElevated` (`:75-89`), `AuditGate` (`:52`), `AdminLogin`'s profile gate (`AdminLogin.cs:71`), the partner
logins' (`PartnerLogin.cs:61`, `MobilePartnerLogin.cs:74`), the three GDPR admin validators, the admin-user
queries (`GetPagedAdminUsers.cs:28`), the frontend `Role` enum, and the integer on the wire to three generated
clients and two mobile specs. All would enumerate four values forever. The role is orthogonal to the audience
question every one of those asks.

**Why nullable and constrained, not a default for everyone.** A `Customer` with `AdminRole = Support` is a
row that lies. **A row that violates the constraint cannot be written** — fail-closed at the database,
the ADR-0061 D8 discipline. **The fixtures this breaks are listed, not called "unchanged"** (challenge C4):
every `CreateWithPassword(…, UserProfile.Administrator)` in the three test projects (§Context) gains
`adminRole: AdminRole.Administrator`; T-0748 carries the list. *Why the throw and not a silent default to
`Administrator`.* A silent default to the most privileged role is fail-open in a domain factory; the nine
edits are one line each. **Any path that changes `Profile`** must keep the constraint true:
`RegisterEmployeeProfileUpgrade` moves `Customer → Employee` with `AdminRole` null on both sides — true by
construction; the only writer of `→ Administrator` is `set-admin-role.sql`, which sets both columns.

**The claim.** `SetClaims` yields `new Claim("admin_role", user.AdminRole.ToString())` when
`Profile == Administrator` (beside `tenant_id`, `AuthExtensions.cs:28-31`). `JwtTokenResponse` gains
`string? AdminRole = null` (additive, positional, after `Role`); the admin web stores it (D6).
`TestJwtFactory.Mint` gains `AdminRole? adminRole = null`, defaulting to `Administrator` when
`profile == Administrator` so every existing HostTests **token** keeps its meaning. `RefreshToken` re-mints
through `GenerateTokenAsync`, so a changed role reaches the token — **and the web's stored hint, because
`refreshSession` calls `setSession` on the refresh response** (`admin-auth.service.ts:70-71`; challenge C5)
— at the next refresh (≤ 15 minutes on the admin host, ADR-0064 §D1). **No bulk session revocation on a
role change** (ADR-0064's reasoning for deactivation applies: fifteen minutes of a role that was just
narrowed, every act of which is audited with the role it ran under, is *"an unlikely path fails ugly"*).

### D2 — Five administrator sets, registered once, resolved through the existing map

```csharp
// PhysicalPolicy.cs — appended; AdminOnly keeps its name and meaning: ANY administrator
public const string AdminOnly          = "AdminOnly";           // Profile == Administrator, any role (unchanged constant)
public const string AdministratorOnly  = "AdministratorOnly";   // { Administrator }
public const string ManagerOrAbove     = "ManagerOrAbove";      // { Administrator, Manager }
public const string SupportOrAbove     = "SupportOrAbove";      // { Administrator, Manager, Support }
public const string AccountantOrAbove  = "AccountantOrAbove";   // { Administrator, Manager, Accountant }

// Cleansia.Core.AppServices/Authentication/AdminRoleSets.cs — the one place a set is spelled
public static class AdminRoleSets
{
    public const string ClaimType = "admin_role";
    public static readonly IReadOnlySet<AdminRole> AdministratorOnly = …;   // and the other three
    public static readonly IReadOnlySet<AdminRole> Any = all four members;

    /// The set a physical-policy NAME denotes; AdminOnly → Any; anything else → throws (a programming error).
    /// The one mapping ADR-0065's notifier and the authorization handlers both use (challenge C6).
    public static IReadOnlySet<AdminRole> For(string physicalPolicy) => …;

    /// Fail-closed: not an administrator, no claim, an unparseable claim, or a role outside the set → false.
    public static bool Admits(ClaimsPrincipal user, IReadOnlySet<AdminRole> set) =>
        user.IsInRole(UserProfile.Administrator.ToString())
        && Enum.TryParse<AdminRole>(user.FindFirst(ClaimType)?.Value, out var role)
        && set.Contains(role);
}

// ServiceExtensions.AddCleansiaAuthorization — four registrations beside AdminOnly (:65-66)
.AddPolicy(PhysicalPolicy.AdministratorOnly, p => p.RequireAssertion(ctx => AdminRoleSets.Admits(ctx.User, AdminRoleSets.AdministratorOnly)))
… ManagerOrAbove, SupportOrAbove, AccountantOrAbove likewise
```

*Why "or above" sets and not one set per role.* The matrix is a lattice: every permission is "the least
role that has it, and everyone above" — four sets plus "any". A per-role bitmask is more general and general
is what is not wanted. The one event that is Support's *and* the Accountant's — a chargeback — is exactly
the union of the two branches, which is "any administrator" = `AdminOnly` (D8); the lattice expresses it.

*Why `AdminOnly` keeps its name.* Referenced from the startup filter (`:44-50, 75-82`), the frozen snapshot,
the frontend mirror and every partner-host row that stays "any administrator". Its doc comment gains *"any
administrator role"*.

*The registration and the startup semantics.* `AssertAllRegistered` lists the four new names
(`AuthorizationCompletenessStartupFilter.cs:42-50`); `AssertSemantics` (`:67-82`) gains: a principal with
`Role = Administrator, admin_role = Support` passes `SupportOrAbove` and `AdminOnly` and fails
`ManagerOrAbove`, `AccountantOrAbove`, `AdministratorOnly`; one with `Role = Administrator` and **no**
`admin_role` claim passes `AdminOnly` and fails all four sets; an Employee fails all five. **`AdminOnly` does
not require the claim** — it is what keeps a token minted before this deploys usable on the any-admin
routes until its refresh.

### D3 — The map: every policy the admin host routes, by area

The default matrix is the row unless the last column says otherwise. **Every policy not in this table
keeps its current physical policy.** **Shared reads routed on the admin host get an admin-host constant**
(challenge C1, accepted): the lattice cannot narrow a physical policy the partner hosts share, and leaving
those rows "unchanged" would have handed every Accountant every customer's phone and address and every
cleaner's identity document through the order detail and the document download — the ruling's matrix not
implemented on exactly the PII reads, while T-0773 hid the pages. The `CanViewDisputeAdmin` precedent is
followed: eight constants, the admin controllers re-routed onto them, the partner hosts byte-identical.
`CanCalculateOrderPay` — `AdminOnly`, routed on the partner host only — stays `AdminOnly`; an administrator
of any role passes it there, as every partner-host row.

### D4 — Assignment: one command, Administrator-only, never the last Administrator — under a company lock

```csharp
[AuditAction("admin.user.set_role", ResourceType = "AdminUser")]
public class SetAdminRole
{
    public record Command(string UserId, AdminRole Role) : ICommand<Response>;
    public record Response(string Id, AdminRole Role);
    public record RoleSnapshot(string UserId, AdminRole? Role);   // before/after through IAuditContext.RecordChange — no PII
}
```

Route: `POST api/AdminUser/{userId}/role` on `AdminUserController`, `[Permission(Policy.CanSetAdminRole)]`,
`[EnableRateLimiting("auth")]` like its siblings (`:54, 70, 91, 107`). Validator, `Cascade.Stop`: `UserId`
required; the target exists with `Profile == Administrator` (`admin_user.not_found`, `BusinessErrorMessage.cs:419`);
not the caller (`admin_user.cannot_change_own_role` — mirrors `CannotDeactivateSelf`, `:421`); `Role` `IsInEnum`.

**The guard, made atomic** (challenge C2, accepted). The `DeactivateAdminUser.cs:57-87` shape — one
conditional `UPDATE` whose `WHERE` carries the other-administrator predicate — is not atomic against a
second such statement on a different row (§Context: write skew under READ COMMITTED). Both guards therefore
run **inside one transaction that first takes a per-company advisory lock**, so two demotions or
deactivations of the last two Administrators serialise and the second one's predicate reads the first's
committed result:

```csharp
// IUserRepository — the two guarded writes live in the repository because they need the transaction and
// the lock statement; the handlers ask and read rows == 0.
Task<int> DemoteAdministratorIfAnotherRemainsAsync(string tenantId, string userId, AdminRole role, CancellationToken ct);
Task<int> DeactivateAdministratorIfAnotherRemainsAsync(string tenantId, string userId, string actorId, DateTimeOffset now, CancellationToken ct);

// UserRepository (Infra.Database) — the shape of both
await using var tx = await Context.BeginTransactionAsync(ct);                       // IUnitOfWork.BeginTransactionAsync exists (IUnitOfWork.cs:9)
await Context.Database.ExecuteSqlAsync($"SELECT pg_advisory_xact_lock(hashtext({tenantId}))", ct);   // released at commit/rollback
var rows = await GetDbSet().IgnoreQueryFilters()
    .Where(u => u.TenantId == tenantId && u.Id == userId && u.Profile == UserProfile.Administrator
        && (role == AdminRole.Administrator
            || GetDbSet().IgnoreQueryFilters().Any(other =>
                other.TenantId == tenantId && other.Id != userId && other.Profile == UserProfile.Administrator
                && other.IsActive && other.AdminRole == AdminRole.Administrator)))
    .ExecuteUpdateAsync(s => s.SetProperty(u => u.AdminRole, role), ct);
await tx.CommitAsync(ct);
return rows;
```

`rows == 0` → `admin_user.cannot_demote_last_administrator` (a new constant beside `CannotDeactivateLastAdmin`,
`BusinessErrorMessage.cs:424`). The tenant is passed explicitly (the actor's `tenant_id` claim through
`IUserSessionProvider`), so the lock key and the predicate name the same company. A sanctioned self-commit,
as the deactivate guard already is (`:62-66`), and the transaction is its own — the UnitOfWork pipeline
commits nothing for it. **`DeactivateAdminUser` moves onto the second method**: the same lock, and its
predicate narrows to *"another active Administrator-**role** administrator"* (`:36-40, 68-75` gain
`&& AdminRole == Administrator` on the *other*), or a company could deactivate its only Administrator while
a Support remains and lock the console. The Testcontainers race test (T-0748 AC5) is now **deterministic**:
with the lock, exactly one of two concurrent demotions of the last two Administrators succeeds, every time.

`CreateAdminUser.Command` gains `AdminRole Role` (required, `IsInEnum`); `AdminUserListItem` and
`AdminUserDetailDto` gain `AdminRole? AdminRole`.

*Why not fold the role into `UpdateAdminUser`.* That command edits name, phone, birth date and language
(`UpdateAdminUser.cs:15-22`); a role change is a privilege act with its own guard, label and refusal keys.
*Why an advisory lock and not `SELECT … FOR UPDATE`.* Both are raw SQL; the lock is one statement keyed by
the company, holds only for the transaction, and does not depend on which rows the predicate happens to
touch.

## What is NOT built (and why)

- **No holding role.** The role is per company by construction. A holding view is ADR-0061 D14's open item.
- **No per-market scoping inside a company.** A Support of a two-market company sees both markets.
- **No invitations, no self-service.** Administrators are created as today (`CreateAdminUser.cs:90-98`).
- **No fifth role.** A new member is one enum value, one set, one column of the matrix and one frontend case.
- **No policy splits beyond the eleven.** The document-requirement CRUD sharing `CanAdminUpdateEmployee` and
  the admin-user read `{userId}` sharing `CanViewOrderCustomer` are reported as findings.
- **No re-write of the twenty-five handler checks.** They ask the audience question and stay.
- **No change to the partner or customer hosts, apps or clients.** The `admin_role` claim rides the partner
  audience token an administrator holds and is read by nothing there; the eight shared read policies keep
  their partner-host meaning.
- **No HTTP walk of every route** (D9).
