# ADR-0067 — `Confirmed → New` when the last assigned cleaner leaves; the company's administrators are told

- **Status:** `accepted` — **2026-09-19**, on the day **T-0770** shipped in `c30e2580` + `667de9f7`
  (closing T-0693: AC1 yes, AC2 = D7, AC3 = D8 kept-argued, AC4 n/a). Panel-accepted draft the same day
  (challenge A1–A8 resolved below). Implements the owner ruling of 2026-09-19 on **D2** (verbatim): *"I
  want that it could go back to New since 'Confirmed' means that cleaner(s) are assigned. Also I want admin
  know about it as well."* The panel's verdict on the vehicle (challenge A4): the change adds a domain
  writer, a lifecycle edge, an override rule and a hold-ending — that is a decision, not a dated amendment
  block on ADR-0057, and an `accepted` ADR is not edited; ADR-0057 carries a one-line pointer here. Where
  the tree departs from this text the departure is recorded in **§What shipped** below, as ADR-0064 did.
- **Date:** 2026-09-19
- **Supersedes:** ADR-0057's **open consequence only** (`adr-0057.md:78-83`, *"`Confirmed` can still be true
  with zero assignees … a separate decision and is deliberately left open"*). ADR-0057's status ruling —
  *Confirmed means a cleaner took the job* — stands; this ADR makes the word stay true after the cleaner
  leaves. ADR-0037's offerability rule and its two evaluation forms are untouched.
- **Composes with:** ADR-0065 (the admin event rides `IAdminNotifier`), ADR-0045 (the preferred hold),
  ADR-0062 (the audit rows already written by both writers are the reason no status row carries a reason).
- **Applies to:** `Cleansia.Core.Domain.Orders.Order`, `Features/Orders/DropOrder`,
  `Features/Employees/RejectEmployee`, `Features/Orders/AdminOverrideOrderStatus`,
  `Infra.Database/Repositories/OrderRepository`, the four "do not trust `Confirmed`" comments, the docs
  in §Consequences. Ticket **T-0770**.

> **One decision:** *a release that empties the crew returns the order to `New` when the order is
> `Confirmed`, through one domain writer; every release that empties the crew — whatever the status —
> tells the company's administrators; the override may not set `Confirmed` on an order with nobody on it;
> the sweeps keep reading the crew, because the status is a summary and the crew is the fact.*

## Context (every citation at `2b9cd268`, committed files only; re-checked at `def6c7b3` (2026-09-19) — every backend citation holds; the one drift is noted in place)

### The tree today

**The crew is a collection with one remover.** `Order.UnassignEmployee(employeeId)` hard-removes the
assignment row and nothing else (`src/Cleansia.Core.Domain/Orders/Order.cs:789-798`); `AddAssignedEmployee`
seats by the smallest free ordinal (`:765-782`). **`CurrentStatus` has one writer**, `Order.AddOrderStatus`,
which assigns the strictly-increasing `Sequence` and recomputes `CurrentStatus` from the loaded history
(`:655-669`) — which is why every caller must `Include(o => o.OrderStatusHistory)` (the warning at
`DropOrder.cs:77-78` and `RequestCover.cs:78-80`).

**Four callers remove a crew row. Two of them can empty the crew.**

| Caller | Removes | Then | Can the crew reach zero? |
|---|---|---|---|
| `DropOrder.Handler` | the caller's own assignment (`DropOrder.cs:116`) — admitted in **any** offerable status, `New`/`Confirmed`/`OnTheWay`/`InProgress` (`:99-103`, `OrderAvailability.cs:53-54`) | ends the caller's own hold (`:123-126`), re-appends a **same-value** track so the digest re-advertises (`:128-132`), audits `OrderDropped` (`:134-135`), wakes cleaners (`:139-145`) | **yes** — a single-seat job, at any of the four statuses |
| `RejectEmployee.Handler.ReleaseFutureSeatsAsync` | every future **`Confirmed`** assignment of the rejected cleaner (`RejectEmployee.cs:119-148`; query `OrderRepository.cs:37-47`) | tells the cleaner per assignment (`:142-146`); appends **no** status row | **yes** — every single-seat job they held |
| `AdminReassignOrder.Handler` | `FromEmployeeId` (`AdminReassignOrder.cs:106`) | **always adds `ToEmployeeId`** (`:118-119`; `NotEmpty`, `:42-44`) | **no** — a swap |
| `TakeOrder.Handler` (cover swap) | the oldest cover-requesting holder (`TakeOrder.cs:299-308`) | **adds the taker** (`:311-312`) | **no** — a displacement |

**A cover request removes nobody.** `RequestCover` stamps `CoverRequestedAt` and the cleaner *stays
assigned* (`RequestCover.cs:14-22`; `Order.CoverSeatsOpen`, `Order.cs:131-136`). The premise in ADR-0057's
consequence, `order-lifecycle.md:67-71`, T-0693's context and CLAUDE.md landmine 4 — *"a drop, a cover
request or an admin rejection removes the assignment"* — is one third wrong. The writers that can leave an
order with nobody on it are exactly two.

**Erasure never unassigns** (`GdprDeletionService.HasBlockingAssignedOrderAsync`, `GdprDeletionService.cs:240-242`).

**The admin override forbids backward moves** by rank over a total `Lifecycle` array
(`AdminOverrideOrderStatus.cs:59-67, 110-123`), refuses `Pending` (`:103-108`), and loads the history only
(`:72-75`) — it does not read the crew, so it **can force `Confirmed` onto an order with nobody on it**.

**The customer is e-mailed "Confirmed" only on a status change.** `TakeOrder` writes `Confirmed` only from
`New` (`TakeOrder.cs:314-320`) and sends `SendOrderStatusUpdateEmailAsync(…, "Confirmed", …)` only when
`statusChanged` (`:382-394`); the `order.cleaner_assigned` push goes out per assignment regardless
(`:376-377`, `OrderCleanerAssignedNotifier.cs:34-44`).

**Six places conjoin the status with the crew**, and what each term is *for* decides whether it may go:

| # | Site | Predicate | The crew term is… |
|---|---|---|---|
| 1 | `SendPreCleaningReminders.cs:66-73` | `Confirmed && AssignedEmployees.Any() && …` | the promise: *"your cleaner is coming"* is about the crew |
| 2 | `SendCleanerJobReminders.cs:94-101` | `Confirmed && Any() && (…)` | implied by the inner `Any`s — inert |
| 3 | `SendTomorrowJobDigest.cs:247-255` | `Confirmed` then `SelectMany(AssignedEmployees)` | none — it iterates assignments |
| 4 | `NotifyOnTheWay.Validator` `:77-89, 91-102` | `Confirmed` **and** the caller is assigned | authorisation of the caller |
| 5 | `StartOrder.Validator` `:90-102, 104-115` | `Confirmed\|OnTheWay` **and** the caller is assigned | authorisation of the caller |
| 6 | `OrderRepository.GetFutureConfirmedOrdersForEmployeeAsync` `:37-47` | `Confirmed && future && Any(ae => ae.EmployeeId == id)` | selection of *this* cleaner's jobs |

And the sweep that closes the loop: `CancelUnfilledOrders` selects `NeverStarted = {New, Confirmed}` **and**
`!AssignedEmployees.Any()` (`CancelUnfilledOrders.cs:81, 122-128`); its comment at `:24-28` says every other
sweep *requires* an assignment. **Three comments exist only to say the status cannot be trusted:**
`CancellationAssessor.cs:49-55`, `BookingPolicy.cs:286-287`, `AdminReassignOrder.cs:121-135`.

**Concurrency.** `Orders.CurrentStatus` is the only concurrency token (`OrderEntityConfiguration.cs:200-202`).
Two cleaners dropping a two-seat job in the same window each load two assignees (`DropOrder.cs:79-83`),
remove their own row, see one remaining, and neither changes `CurrentStatus` — the commits do not conflict,
both DELETEs land, and the row reads `Confirmed` with nobody on it. A drop racing `RejectEmployee` is the
same shape.

**The customer's screens key on the crew, not the word.** The mobile timelines key their assignment step on
`cleanerAssigned` (ADR-0057 §Consequences); the customer web timeline reads both — the assignment row is
driven by `assignedEmployees`, `Confirmed` is the step behind it
(`libs/cleansia-customer-features/orders/src/lib/order-detail/order-detail.component.ts:178-207`; the draft
cited `:176-181` at `2b9cd268` — the batch-5 cancel-set work moved the timeline down, the reading is the same).

### What the ruling fixes as fact

- `Confirmed` with no crew is a state the platform should **not leave standing**: the order goes back to
  `New`. The ruling says `New`; a new member is not on the table (ADR-0057 rejected it, `adr-0057.md:104-106`:
  `New + Paid` already expresses "paid, unassigned").
- The administrators are told. The channel is ADR-0065's.

## Decision

### D1 — One writer for the walk-back: `Order.ReturnToBoardIfUnstaffed()`

```csharp
/// The ONLY writer of Confirmed → New. Called by a release that may have emptied the crew. A no-op when
/// somebody is still on the job or the order is not Confirmed: a New order has nothing to walk back
/// from; an OnTheWay/InProgress order is a cleaner in a home and is never walked back — that is the
/// administrator's to resolve (RejectEmployee already says so at :111-113) and they are told (D4).
/// Requires OrderStatusHistory to be loaded, like every AddOrderStatus caller.
public bool ReturnToBoardIfUnstaffed()
{
    if (_assignedEmployees.Count > 0 || CurrentStatus != OrderStatus.Confirmed)
    {
        return false;
    }

    AddOrderStatus(OrderStatusTrack.Create(OrderStatus.New, this));
    return true;
}
```

*Why a separate method and not inside `UnassignEmployee`.* Two of the four removers are swaps
(`AdminReassignOrder`, the cover swap in `TakeOrder`): remove-then-add, with a transient empty crew between
the two lines that the ordering comment at `TakeOrder.cs:286-291` makes load-bearing. A walk-back inside
`UnassignEmployee` would append `New` between them and `AdminReassignOrder.cs:132-135` would append
`Confirmed` again — two rows for a swap that changes nothing about whether the job is staffed. The rule
belongs to the *release*; it is a method the two release callers invoke after their remove and the two swap
callers never do. It is still one place: `OrderStatusTrack.Create(OrderStatus.New, …)` reaches
`AddOrderStatus` from `OrderFactory.cs:304` (creation) and here, nowhere else.

*Why `New` and not a new member.* The ruling says `New`; `New + Paid` is precisely "an order the company has
to serve with nobody on it yet" — the state a paid card order rests in before its first take. A walked-back
order is that state again. No wire change, no mobile spec re-dump.

### D2 — Two facts, two tests: the walk-back and the alarm are not the same event (challenge A1, accepted)

The first draft raised the admin event only when the walk-back happened. That misses the most urgent case:
`DropOrder` admits a drop at `OnTheWay` and `InProgress` (`DropOrder.cs:99-103`), the walk-back is
`Confirmed`-only by design, and no sweep catches an unstaffed `OnTheWay` order — `CancelUnfilledOrders`
selects `NeverStarted = {New, Confirmed}` (`CancelUnfilledOrders.cs:81`). A customer waiting or a clean
half-done with nobody on it would have told no one. So:

- **`crewEmptied = order.AssignedEmployees.Count == 0`** after the unassign → `admin.order.crew_lost` is
  raised on **every** non-terminal status, with `statusAtLoss` in the args so the sentence can say *"during
  the clean"*.
- **`ReturnToBoardIfUnstaffed()`** walks back on `Confirmed` only.

### D3 — The writers

**`DropOrder.Handler`** (`DropOrder.cs:116-145`), one new collaborator (`IAdminNotifier`; six in total):

```csharp
order.UnassignEmployee(employeeId);
if (heldByCaller) order.EndPreferredHold(nowUtc);

var crewEmptied  = order.AssignedEmployees.Count == 0;
var statusAtLoss = order.CurrentStatus;                       // read BEFORE the walk-back
if (!order.ReturnToBoardIfUnstaffed())
{
    // Somebody is still on it, or the order is past Confirmed: re-advertise the freed seat with the
    // same-value track the digest's freshness test needs (unchanged behaviour).
    order.AddOrderStatus(OrderStatusTrack.Create(order.CurrentStatus, order));
}

employeeActionAuditRepository.Add(EmployeeActionAudit.Create(employeeId, order.Id, EmployeeAuditAction.OrderDropped));
await SeatOpenedNotifier.NotifySeatOpenAsync(…);              // unchanged

if (crewEmptied && order.TenantId is not null)
{
    await adminNotifier.NotifyAsync(new AdminEvent(
        AdminNotificationEventCatalog.OrderCrewLost, order.TenantId,
        Subject: $"{order.Id}:{releasedAssignmentId}",
        Args: { orderId, orderNumber, cause = "dropped", statusAtLoss = statusAtLoss.ToString(), cleaningDateTime = ISO-8601 UTC }), ct);
}
```

The walk-back *is* a fresh status row, so the digest's `OrderStatusHistory.Any(s => s.CreatedOn > since)`
freshness test (`DropOrder.cs:128-131`) is satisfied by it; the same-value append survives for the
multi-seat and past-`Confirmed` cases.

**`RejectEmployee.Handler.ReleaseFutureSeatsAsync`** (`RejectEmployee.cs:119-148`), per order after
`UnassignEmployee`:

```csharp
order.UnassignEmployee(employeeId);
if (order.PreferredEmployeeId == employeeId)
{
    // The rejected cleaner may hold this order's exclusive reservation; leaving it live would hide the
    // seat from every other cleaner for up to twelve hours on behalf of someone who can no longer work.
    order.EndPreferredHold(now);
}

if (!order.ReturnToBoardIfUnstaffed())
{
    // A crew remains: re-advertise the freed seat exactly as a drop does (challenge A6 — the two
    // release writers stay symmetrical; before this the reject path left the seat invisible to the digest).
    order.AddOrderStatus(OrderStatusTrack.Create(order.CurrentStatus, order));
}
else
{
    await adminNotifier.NotifyAsync(new AdminEvent(AdminNotificationEventCatalog.OrderCrewLost, order.TenantId!,
        $"{order.Id}:{assignmentId}", args /* cause = "rejected", statusAtLoss = "Confirmed" */), ct);
}
```

The query selects `Confirmed` only, so for this writer "crew emptied" and "walked back" coincide.
**`GetFutureConfirmedOrdersForEmployeeAsync`** (`OrderRepository.cs:40-46`) gains
`.Include(o => o.OrderStatusHistory)` **and `.AsSplitQuery()`** (challenge A5 — two collection includes
beside `.ThenInclude(Employee)` are a cartesian product; the siblings at `:33` and `:70` already split).
*The hold end is new behaviour and in scope*: an order returned to the board must be *on* the board, and a
live hold for a rejected cleaner keeps it off. A hold for a *different* cleaner is not the rejection's to end.

**The rejecting administrator receives their own consequence** (challenge A7, accepted): N released orders →
N `admin.order.crew_lost` rows and e-mails, one of each to the admin who clicked Reject. Excluding the actor
is a parameter on the notifier for one caller; not worth it. The e-mail says what they did.

**`AdminReassignOrder`, `TakeOrder`, `RequestCover`** — unchanged. Neither of the first two can empty a
crew; the third removes nobody.

### D4 — The admin event: `admin.order.crew_lost` (ADR-0065 D4)

Raised iff `crewEmptied` (D2). Args: `orderId`, `orderNumber`, `cause` (`dropped`/`rejected`),
`statusAtLoss` (`Confirmed`/`OnTheWay`/`InProgress`/`New`), `cleaningDateTime` (ISO-8601 UTC). Subject
`{orderId}:{releasedAssignmentId}` — unique per assignment, so a re-take-and-re-drop is a second event and
the outbox unique index (ADR-0065 D2) is never hit twice by one logical event. Channels per ADR-0065 (feed +
e-mail). The e-mail sentence names the order, the time and — when `statusAtLoss` is past `Confirmed` — that
the clean was under way; it does not name the cleaner. The recipient audience is `SupportOrAbove` once
ADR-0066 lands (orders are Support's); until then every administrator.

### D5 — The preferred-cleaner hold

- **The board.** Nothing changes for offerability: `Confirmed` and `New` are both in
  `OrderAvailability.OfferableStatuses` and the rule reads no seats (`OrderAvailability.cs:33-37, 53-54`).
  A walked-back order was already offerable at `Confirmed` with a free seat; it stays offerable at `New`.
- **The offer window.** `PreferredOfferExit.IsOpen` conjoins `AssignedEmployees.Count == 0`, no live
  reservation, the round cap and the lead time (`PreferredOfferExit.cs:40-49`) — status-blind; unchanged.
- **The lapse sweep.** `NotifyLapsedPreferredOffers.cs:74` selects `!AssignedEmployees.Any()`; unchanged.
- **A hold whose beneficiary was the dropper** — already ended (`DropOrder.cs:123-126`). **A hold whose
  beneficiary was the rejected cleaner** — ended by D3, new. **A hold for a third cleaner** on a multi-seat
  job — untouched.

### D6 — The history row carries no reason

The `New` row is an `OrderStatusTrack` like every other (`OrderStatusTrack.cs:6-28`). The reason is already
recorded next door by the writer that caused it: `EmployeeActionAudit.OrderDropped` (`DropOrder.cs:134-135`)
and the admin audit label of `RejectEmployee` (`employee.reject`, `RejectEmployee.cs:89-93`). A `Reason` column
would be a schema addition duplicating two audit rows — CLAUDE.md §4's first target. The admin-facing reason
rides the notification as `cause`; the customer-facing timeline needs none (it renders the search step
current again).

### D7 — The override guard, and what it still allows

`AdminOverrideOrderStatus` keeps its forward-only rank rule untouched (`:110-123`) — the walk-back is a
domain consequence of a release, not a generic backward move an administrator may make. One rule is
**added**: `TargetStatus == Confirmed` on an order with `AssignedEmployees.Count == 0` is refused with
`order.status.confirmed_needs_crew` (a new `BusinessErrorMessage` constant under the existing
`order.status.*` category; five admin locales under `api.*`). *Why.* Under ADR-0057 `Confirmed` means a
cleaner took the job; an administrator who wants a cleaner on it uses `AdminReassignOrder`, which writes
`Confirmed` itself (`AdminReassignOrder.cs:132-135`). The handler's query gains `.Include(o => o.AssignedEmployees)`.

**What the override still allows, said plainly** (challenge A8): `New → OnTheWay / InProgress / Completed`
on an **unstaffed** order stays allowed. Those are the *"the cleaner is there but never tapped"* repairs the
override exists for, they are about the work, not the crew — and they can manufacture exactly the state D2
alarms on (`OnTheWay` with nobody assigned) by an administrator's hand. Accepted: it is the administrator's
own act, audited as `order.status.override` (`AdminOverrideOrderStatus.cs:15`), and no sweep will cancel
it out from under them.

**Reconciliation with T-0693 AC2** — the override gains no backward move; the domain gains a release
consequence. Two writers, two rules; the `Lifecycle` array is untouched.

### D8 — No invariant is claimed; the sweeps stay load-bearing (challenge A2, accepted)

The first draft claimed *"`Confirmed` ⇒ crew ≥ 1 for every row written after this date"*. It is not true
under concurrency (§Context): two same-window drops on a two-seat job, or a drop racing a rejection, leave
`Confirmed` with nobody on it and no walk-back, because `CurrentStatus` is the only concurrency token and
it did not change. A DB-evaluated conditional walk-back would close it but splits the one writer of
`CurrentStatus` — not worth it pre-prod. So:

- **The crew terms in the six sites are kept and are load-bearing** — not belts, not compensation. Four
  of them were never compensation (#3 has none; #4, #5 authorise the caller; #6 selects this cleaner's
  rows); #2 is inert; #1 states the promise a reminder makes.
- **`CancelUnfilledOrders` keeps `Confirmed` in `NeverStarted`** and `!AssignedEmployees.Any()` as its
  predicate — for the race above and for DEV rows written before this ADR, not only for legacy.
- **The override refusal (D7) is the one hard rule**: it closes the one door an administrator could open
  with a click.
- The four comments are rewritten to say: *the crew is read because it is the fact; the status is its
  summary, and a release walks the summary back when it can prove the crew is empty.* T-0693 AC3 ("drop the
  now-redundant term") is answered **no**, on this argument. The rewritten comments carry **no ticket ids**
  (challenge F4).

**Legacy rows.** DEV rows may hold `Confirmed` with no crew. No data migration: the sweeps' crew terms make
them harmless and the DEV database is dropped at the next deploy.

### D9 — The customer: what changes, and what is deliberately not sent (challenge A3, accepted)

**Nothing new is sent on the walk-back.** Two rulings already decide it: a drop moves no money and cancels
nothing — *"the customer has lost a cleaner, not their clean"* (`DropOrder.cs:24-28`) — and the slot-time
sweep is the **one** place the customer learns nobody came (`CancelUnfilledOrders.cs:36-39`); the customer is
never told a *named* person walked (`NotificationEventCatalog.cs:47-57, 113-115`).

**But the customer's sequence does change, and the first draft said it did not.** After the walk-back,
the next take is a `New → Confirmed` transition again, so `TakeOrder` sends a **second "your order is
confirmed" e-mail** (`TakeOrder.cs:382-394`) on top of the `order.cleaner_assigned` push it already sends per
assignment. Today a re-take after a drop sends no second e-mail (status unchanged). The customer therefore
sees: *Confirmed (e-mail + push) → silence → Confirmed again (e-mail + push)* — with the timeline's search
step having been current again in between, and no message saying why.

**Default taken: accept it** — a new cleaner *is* a new confirmation, and the e-mail is true when it is sent.
The alternative (suppress the e-mail when the history already carries a `Confirmed` row) hides a true fact
to avoid explaining an earlier one. **Escalated as O-D2-1** with the full sequence above, paired with the
product question it exposes: *should the customer be told "your cleaner left, we are looking for another"?*
That message is copy in five locales on three clients and a question the owner has not ruled on (does the
customer want to know hours before, when the platform may still fill the seat?). Default: nothing sent.

## What is NOT built (and why)

- **No `Reason` column on `OrderStatusTrack`** (D6). **No customer message** (D9, O-D2-1). **No change to
  `UnassignEmployee`, `AdminReassignOrder`, `TakeOrder`, `RequestCover`.** **No removal of any
  `AssignedEmployees.Any()` term** (D8). **No data migration.** **No DB-evaluated walk-back** (D8).
- **No exclusion of the acting administrator** from `admin.order.crew_lost` (D3).

## Residuals (accepted, named)

- **Concurrent releases can leave `Confirmed` with no crew** (D8); the sweeps catch it at slot time, the
  override cannot re-create it, and the next drop/reject on the row walks it back.
- **The customer receives a second "Confirmed" e-mail on a re-take** (D9, O-D2-1).
- **The override can produce `OnTheWay`/`InProgress` with no crew** by an administrator's hand (D7).
- **The rejecting administrator is e-mailed about their own rejection** (D3).
