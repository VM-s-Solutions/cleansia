# ADR-0071 — An order's two lifecycle axes, fulfilment and payment, are its concurrency tokens, and a status the refund settle derives is read again on a conflict

- **Status:** `accepted` — **2026-10-12**, in the commit that ships D1 (finding BE-11). D2 shipped first on the
  same branch, in `ff30c87d5`, which said this record would be written whole with D1. Argued by an author →
  challenger → lead panel; the trail is in §Challenge, §Defense and §Verdict, and where the tree departs from the
  panel's text the departure is recorded in §What shipped.
- **Date:** 2026-10-12
- **Supersedes:** nothing. It changes a **premise** of ADR-0067 D8 (*"`CurrentStatus` is the only concurrency
  token"*, `adr-0067.md:89`, `:281-287`) while D8's conclusion stands (§Consequences). ADR-0067 is not edited.
- **Composes with:** ADR-0073 (the credit an order gives back when it ends commits with the commit that ends it —
  so a commit this record refuses hands no credit back), ADR-0072 (one scope per job item and per timer command —
  so a unit this record refuses costs no other), ADR-0006 (confirm-then-record refunds), ADR-0067 D8.
- **Lands after:** ADR-0073 and D2, in that order. Landed before either, a refused commit would hand credit back
  on an order that stays paid, and a refund's settle would fail after Stripe has paid.
- **Applies to:** `OrderEntityConfiguration` (D1) and `RefundService.SettleAsync` (D2). Every other tracked writer
  of `Orders` takes D1 with no code of its own.

> **Two decisions:** *both of an order's lifecycle axes — fulfilment (`CurrentStatus`) and payment
> (`PaymentStatus`) — are its EF concurrency tokens, so a tracked write of the order is refused at commit when
> either axis has moved since the writer read it (D1); and a value the platform derives from the ledger rather
> than decides — the payment status a refund's settle saves — is read and saved again on such a refusal, instead
> of failing after money has moved (D2). The tokens refuse decisions made on a stale read; they do not refuse
> arithmetic.*

## Context (citations at `b405e9cc5`, with this change's own lines where it moved them)

### The defect (BE-11)

`CurrentStatus` was the order's only concurrency token (`OrderEntityConfiguration.cs:252-254`); `PaymentStatus`
was only indexed (`:245`). A tracked UPDATE therefore compared the fulfilment axis and nothing else, and any writer
that decided on a payment status it had read earlier overwrote a `Paid` committed since:

- **The stale-checkout sweep** read the company's unpaid card checkouts (`CleanupStalePendingOrders.cs:89-99`),
  wrote `Failed`, a `Cancelled` track and the cancellation (`:137-149`) and committed per company (`:167`). The
  webhook's payment writes `PaymentStatus` alone (`HandlePaymentNotification.cs:389`), so the sweep's
  `UPDATE … WHERE "CurrentStatus" = New` still matched.
- **The recurring auto-cancel** read its occurrences (`AutoCancelStaleRecurringOrders.cs:74-81`) and committed each
  cancellation (`:146`) the same way.
- **The request-path cancels** decided on the payment status they loaded: the customer's
  (`CustomerOrderCancellation.cs:45`, `:97-99`) and the platform's (`PlatformOrderCancellation.cs:46-53`,
  `:68-78`).

The order ended cancelled — `Failed`, or still `Paid` — with the money kept and nothing refunded. The webhook
escalates a payment that lands on a cancelled order only when it reads `Cancelled` itself
(`HandlePaymentNotification.cs:365-375`), and each payment raises one order-moving event, so nothing escalated
later. The reverse order was already handled: a webhook that commits second conflicts on `CurrentStatus`, Stripe
retries it, and the retry escalates.

### The settle (challenge O1)

`RefundService.SettleAsync` saves the order's payment status after Stripe has refunded (`RefundService.cs:345-352`,
then `:367-381`), computed from what the order has given back. With a payment-axis token, a second settle of the
same order that commits inside that window refuses the first one's save. The refund then stays pending although
Stripe paid it, and a cancellation that owned it loses everything it does after its refund: the claim commit had
already committed the cancel (`:150`), and the callers catch only Stripe transport faults
(`CustomerOrderCancellation.cs:180`, `PlatformOrderCancellation.cs:115`, `CleanerNoShowCancellation.cs:110`).

## Decision

### D1 — Both lifecycle axes are the order's concurrency tokens

`builder.Property(o => o.PaymentStatus).IsConcurrencyToken()`, beside `CurrentStatus`, with a comment naming the
two axes (`OrderEntityConfiguration.cs:256-260` at this change). Every tracked UPDATE of an order now compares both,
for every writer today and every writer added later, on both providers.

- **No code change** to the webhook, the request-path cancels, `TakeOrder` or `MarkCashCollected`: the change
  tracker compares the tokens for them.
- **No `Orders` lock** and no new repository method.
- **No DDL.** `Initial` is regenerated as `20261012190449`: the migration body is byte-identical to
  `20261005201452`, and the Designer and the snapshot each gain the one `IsConcurrencyToken()` line on
  `PaymentStatus`.
- **The tokens hold only because `Orders` is written only through the change tracker.** No `ExecuteUpdate` or
  `ExecuteDelete` and no raw `UPDATE` or `DELETE` targets the table in production code; the only raw SQL naming
  it is a `SELECT … FOR UPDATE` (`EmployeeActionAuditRepository.cs:21-25`). `OrderConcurrencyTokenTests` now
  fails the build on one (challenge O5).

### D2 — A derived write reads again; the tokens refuse decisions

`SettleAsync` keeps `refund.MarkSucceeded` before a loop of at most three passes (`RefundService.cs:367-402`). Each
pass reads the confirmed card refunds again, leaving out this refund's own key and adding the refund once, returns
the credit leg on its key, sets the payment status from the fresh totals and commits. It reloads the order and
runs the pass again only when the refused save (`:423-445`):

- names this order alone;
- has nothing but `PaymentStatus`, `UpdatedOn` and `UpdatedBy` staged on it — a reload discards what is staged,
  and a decision staged on the order (a cancel replayed on a claim still pending on its key) must stay refused;
- and finds the order still on the fulfilment status it was read with (`:434-439`), checked against the committed
  row before anything is applied. A reload replaces the baseline that every later commit of this unit of work is
  compared against, so a reload past a cancel or a cleaner's start committed meanwhile would let a decision the
  caller stages after its refund returns commit over that change instead of being refused by it; a guest's cancel
  is staged only then (`CustomerOrderCancellation.cs:92-97`). *(Shipped ahead of this text and ratified on
  2026-10-13; §Verdict.)*

Anything else is rethrown as before. The whole post-Stripe block runs again, not just the save: a refused commit
has rolled the lock transaction back (`CleansiaDbContext.cs:115-118`), so a re-save alone would land without the
credit leg the raw SQL wrote inside it. The leg moves exactly once either way, because `TryReturnAsync` re-checks
its key under the owner lock.

**The guard's comparison follows the token set.** A reload is admitted only when the payment axis, the one this
pass derives, is the only token that can have refused the save; every other token must still read as this unit of
work last saw it. Today that is `CurrentStatus` alone. A token added to `Orders` later, such as the row version kept
as the escalation path (§Residuals), joins this comparison in the same change. The model check in
`OrderConcurrencyTokenTests` fails on such a token and links here; nothing checks the comparison itself.

## Consequences

- **A payment that lands while an order is being cancelled is kept.** Whichever commits second is refused. A sweep
  rolls back whole, credit included (ADR-0073), and the order stays paid and booked; a refused webhook is retried
  by Stripe and escalates as before; a customer's or administrator's cancel gets one error, and a retry reads the
  paid order.
- **New refusals, by design.** A writer whose read-to-commit window contains a payment-axis write now fails instead
  of overwriting it:
  - a request path returns one unmapped 500, and a retry reads the new state;
  - `TakeOrder` answers `order.no_available_spots` when a take races a refund's settle
    (`TakeOrder.cs:425-437`);
  - `MarkCashCollected`'s repair commit after Stripe has settled (`MarkCashCollected.cs:235-246`) can return one
    500;
  - a refused company ends that run of the stale-checkout sweep and later companies wait one tick, while ADR-0072
    D1 keeps the timer's other commands running; a refused occurrence of the auto-cancel is counted as failed.
- **`SendRecurringOrderReminders` gains a trigger.** It commits per order inside a catch in one shared scope
  (`SendRecurringOrderReminders.cs:62-92`), so a payment landing during its run of a few seconds at 02:30 UTC
  (`main.bicep:531`) now fails every later reminder of that run. It is the first item of ADR-0072's
  canonicalization ticket, T-0841.
- **ADR-0067 D8: the premise changes, the conclusion stands.** No release commit — a drop, a rejection — changes
  either token, so two releases racing on one order can still leave `Confirmed` with nobody on it, and the crew
  stays the fact the sweeps read.
- **`has-pending-model-changes` cannot see this change.** It reported no pending change before the regeneration as
  well as after: a token on an ordinary column changes no table, column or index, which is what that comparison
  reads. The gate for a change like this one is the snapshot diff.

## Residuals (accepted, named)

- **`CustomerConfirmedAt` is not a token**, and need not be at the shipped settings: a confirm is refused within two
  hours of the slot (`ConfirmRecurringOrder.cs:190-194`; `BookingPolicy.cs:28`, `:304-307`) and the auto-cancel acts
  only within the last hour (`AutoCancelStaleRecurringOrders.cs:32`, `:66`). It reopens only if the grace is set to
  two hours or more; the validator allows 0 to 24 (`:46`).
- **Every other column stays last-writer-wins.** A row version (`xmin`) remains the escalation path if a lost update
  on another column ever matters.
- **A settle refused on the fulfilment axis, or three times, still fails after Stripe has paid** (security finding 4).
  The refund itself is safe: a cancellation's own refund is re-driven hourly, and any other raises an alert to the
  company's administrators (`RedrivePendingRefunds.cs:111-117`). But what the caller does after its refund — the
  crew's notices and fee share, the waiver release, the loyalty revoke, a no-show's apology credit — is not done
  again. The class is older than this record; D2 removes the payment-axis trigger the token would have added.
- **The source guard does not see everything.** An `ExecuteUpdate` on a query held in a variable from an earlier
  statement, or SQL assembled at runtime, passes it; the S8 grep (`security-rules.md:591`) still finds
  both.
- **Two branches that regenerate `Initial` merge one after the other**, and the second regenerates again; one DEV
  drop covers both.

## Verification (what to check)

1. `OrderEntityConfiguration.cs` marks both `CurrentStatus` and `PaymentStatus` with `IsConcurrencyToken()`, and so
   do the snapshot and the Designer of `20261012190449_Initial`; the migration body is byte-identical to
   `20261005201452`'s.
2. `src/Cleansia.Tests/Infrastructure/OrderConcurrencyTokenTests.cs`: the production model's order tokens are exactly
   the two axes; a cancel decided on an unpaid order whose payment committed meanwhile is refused (SQLite, two
   contexts); and the source guard — no raw `UPDATE`/`DELETE` of `Orders` and no `ExecuteUpdate`/`ExecuteDelete`
   chained from the orders set in production code, anchored on `OrderRepository.cs` and
   `EmployeeActionAuditRepository.cs`, with known-bad and known-good samples.
3. On Postgres, each on two connections: a payment that lands while the stale-checkout sweep cancels its company
   (`CleanupStalePendingOrdersTwoOperatorsTests.A_Payment_Landing_While_Its_Company_Is_Swept_Is_Kept_And_Nothing_Is_Cancelled`),
   while the auto-cancel cancels its occurrence
   (`RecurringAutoCancelCreditAtomicityTests.A_Payment_Landing_While_The_Occurrence_Is_Cancelled_Is_Kept_And_Nothing_Is_Cancelled`)
   and while a customer cancels (`CustomerCancelRacingPaymentTests`): the order stays paid and open, nothing is
   cancelled and no credit is returned. Two refunds settling at once are both recorded and the order ends
   `Refunded` (`ConcurrentRefundSettleTests`, now on the production model). All of these failed before D1.
4. The same refund settled twice at once — during the first one's Stripe call or at its save — is counted once:

5. D2's guard refuses the two reloads it must: one that would discard a decision staged on the order
   (`ConcurrentRefundSettleTests.A_Settle_That_Carries_A_Cancel_Staged_On_The_Order_Is_Refused_Rather_Than_Read_Again`),
   and one past a fulfilment change, so a guest's cancel stays refused by a cleaner's start
   (`GuestOrderCancellationTests.Cleaner_start_during_refund_or_before_final_commit_cannot_be_overwritten`, whose
   `duringStripe: True` variant fails without the third condition).

## Alternatives considered

- **A row lock per sweep group** (`SELECT … FOR UPDATE` of the group's orders inside a transaction). Opt-in: it
  covers only the sweeps that adopt it and leaves the request-path cancels racing; it needs a new Npgsql-only lock
  that no SQLite suite can see; and it locks `Orders` before the customer's `Users` row, the reverse of every credit
  path, which holds `Users` until the commit that updates `Orders` — a deadlock shape.
- **SERIALIZABLE units.** Whole-transaction isolation for a two-column invariant: serialization failures on unrelated
  reads, Npgsql-only, and retry plumbing at every unit.
- **`xmin` on `Orders`.** It would refuse every concurrent write to the platform's busiest row, including writes to
  unrelated columns — reminder stamps, notes, lapse stamps — and `TakeOrder` maps any conflict to
  `order.no_available_spots`, so a reminder stamp racing a take would refuse a cleaner a free seat. The two axis
  tokens encode exactly the invariant at risk: a decision about the order is made on its committed state.
- **A conditional `ExecuteUpdate` in the sweep** (`… WHERE "PaymentStatus" = Pending`). Forbidden for a sweep
  (`security-rules.md:691-692`): it commits outside the caller's unit of work and breaks the job's atomicity, and it
  would cover that one sweep.
- **A host-level 409 for `DbUpdateConcurrencyException`.** Not built: the race is rare, a retry reads the new state,
  and the 500 is paid once.
- **Doing nothing.** A payment that lands while its order is being cancelled is kept with no refund and no
  escalation.
- **D2 — re-save the status only.** Unsafe: the refused commit rolled the lock transaction back, so the save would
  land without the credit leg written inside it.
- **D2 — the challenger's literal remedy**, a reload of the database values and a second save in the manner of the
  loyalty replay (`CleansiaDbContext.cs:181-206`). Refined rather than taken: that replay runs inside the commit,
  under its savepoint, while a retry in `SettleAsync` runs after `CommitAsync` has rolled the lock transaction back;
  so the whole post-Stripe pass runs again.

## Challenge

- **Author's draft.** Option (a), the token, not (b) and not `xmin`; *"no code change to … `RefundService` …:
  every tracked Order UPDATE compares both tokens"*; the token to wait for a transaction in each sweep unit (since
  replaced by ADR-0073); the tracker-only rule enforced *"by `OrderConcurrencyTokenTests` plus tests B to D —
  `T1-CI`"*.
- **O1** (must fix) — the token refuses `SettleAsync`'s derived write after Stripe has refunded, and three
  cancellation callers then lose follow-ups that nothing retries: the crew's fee share and notices, the waiver
  release, the loyalty revoke, a no-show's apology credit.
- **O5** (must fix) — *"Orders are written only through the tracker"* was labelled `T1-CI`, but none of the named
  tests fails on a future `ExecuteUpdate` or raw `UPDATE` of `Orders`.
- **O7** (precision) — the `CustomerConfirmedAt` residual cannot occur at the shipped settings; the business rules'
  passage on a drop checked at commit also names only the `CurrentStatus` token; and the catalog's
  `CurrentStatus` section is about reads, the wrong home for a rule about writes.
- **O2, O3** — the deadlock partner and the credit seam; answered in ADR-0073.
- **Security findings 3, 4 and 5** — a customer's cancel racing their own payment would hand credit back on an order
  that stays paid; a refused settle drops its caller's later effects; the tracker-only rule had no enforcer.
- **Implementation review, item 7** (2026-10-13, after acceptance and before merge) — D2's guard has a third
  condition the panel did not rule: the order must still be on the fulfilment status it was read with. §What
  shipped records it, and nobody has ratified it. It is load-bearing: removed,
  `GuestOrderCancellationTests.Cleaner_start_during_refund_or_before_final_commit_cannot_be_overwritten(duringStripe: True)`
  fails. Ratify it or amend it.

## Defense

- **O1 adopted, and fixed rather than priced:** D2. The challenger's literal remedy was refined (§Alternatives).
- **O5 adopted:** a source guard in `OrderConcurrencyTokenTests` makes `T1-CI` true, and the catalog entry states
  its scope. Security finding 5 is answered the same way.
- **O7 adopted:** the residual states the guard that rules it out, both business-rules passages name the two
  tokens, and the catalog entry is a section of its own after the read discipline.
- **Security finding 3** is closed by ADR-0073: the refused commit rolls the credit return back with it.
- **Security finding 4** is a named residual, narrowed by D2 to a refusal on the fulfilment axis or three in a row.
- **Item 7 — the implementation's case.** As the panel wrote it, the guard reloaded the order past a cleaner's
  start committed during the Stripe call, and the guest's cancel, staged only after its refund returns
  (`CustomerOrderCancellation.cs:92-97`), was then compared against the start and committed over it: the test
  failed with *no exception was thrown*. The third condition refuses that reload, and the test pins it.

## Verdict

**Consensus.** Every challenge was adopted or answered above, and none blocks. The order of landing is the guard:
ADR-0072 D1, ADR-0073, ADR-0072 D2, then D2 of this record (`ff30c87d5`), then D1 with the regenerated `Initial`.
Accepted on 2026-10-12, in the commit that ships D1.

**Item 7 — ratified without amendment, 2026-10-13.** The third condition is D2's own rule (the tokens refuse
decisions, not arithmetic) applied to the whole unit of work rather than to the one save. A reload rewrites the
baseline that every later commit of the unit is compared against. Past a payment-axis change that is the purpose:
the status is arithmetic, and the pass recomputes it from the ledger. Past a fulfilment-axis change it would let a
decision the caller has yet to stage be compared against a state it never read, which is the lost update D1
refuses. `RefundService` cannot tell a caller that still decides on the order after its refund from one that does
not without knowing its callers' rules, which it must not, so it refuses that reload for every caller.

- **Provenance, re-read in the tree:** the condition at `RefundService.cs:434-439`, inside the guard at `:423-445`;
  the guest's refund ahead of its cancel at `CustomerOrderCancellation.cs:92-97`; the test at
  `GuestOrderCancellationTests.cs:642-692`. The failure without the condition was produced twice, by the
  implementation and by its review.
- **Alternatives answered.** Re-basing `PaymentStatus` alone leaves `CurrentStatus` refusing every remaining pass,
  each re-running the credit leg only to roll it back, and ends in the same exception: no better. A settle in a
  scope of its own would record the refund, but its status write would then race the order the caller still
  tracks: a guest's cancel would be refused by its own refund's status every time, and a caller that reads the
  status the settle saved (`AdminRefundOrder.cs:114-115`) would read the old one.
- **The cost, stated exactly.** A settle refused on the fulfilment axis fails as it did before this record
  (§Residuals). The hourly job re-drives only a cancellation's own refund, and only on a cancelled order, so it
  does not re-drive this one. Once the row reaches its alert age, the job tells the company's administrators:
  `RefundWithoutCancel` for a guest's cancel that did not commit, `RefundNeedsRetry` for any other refund
  (`RedrivePendingRefunds.cs:102-117`, `:186-203`). That is what §What shipped's *"the hourly job takes the pending
  refund"* means.
- **D2 now states the condition, its reason and the token set it compares, and §Verification item 5 names its
  tests.**

## What shipped (where the tree departs from the panel's text)

- **D2's guard has a third condition**: the order must still be on the fulfilment status it was read with. Without
  it, a guest's settle refused by a cleaner's start during the Stripe call reloaded the order past the start, and
  the guest's cancel was then compared against the start instead of refused by it
  (`GuestOrderCancellationTests.Cleaner_start_during_refund_or_before_final_commit_cannot_be_overwritten(duringStripe: True)`
  failed). So the panel's expectation that D2 also repairs a settle refused by a cancel's or a start's status change
  did not hold: that settle fails as it did before, and the hourly job takes the pending refund. *Ratified on
  2026-10-13 (§Verdict, which also states exactly what the hourly job does with that refund).*
- **The model check pins the exact set**: the order's tokens are the two axes and nothing else, so a row version
  added to `Orders` later fails it as well.
- **`ConcurrentRefundSettleTests` ran on a model of its own** carrying the payment-axis token until D1 shipped; it
  now runs on the production model.
- **D2's count leaves out the settle's own key** (security review of the implementation, finding F1). The panel's
  pass re-read every confirmed card refund and added this one. Two settles of one key — an administrator's partial
  refund or a dispute's resolution sent twice at once, or an administrator's retry of a pending refund beside the
  hourly re-drive — share one row: the one that commits second read that row as already succeeded and counted it
  twice, and D2's retry did so whichever committed first, so 600 back on a paid 1 000 ended `Refunded`, and every
  later cancellation, which refunds only an order still `Paid` or `PartiallyRefunded`, gave none of the other 400
  back. Without the token the same double count already happened when the later settle read after the earlier
  one's commit. The pass now sums the confirmed refunds without this key
  (`IRefundRepository.GetSucceededRefundTotalForOrderAsync(orderId, exceptRefundKey, …)`), so the refund is counted
  once in every order of events; Stripe pays it once on its key.
