# ADR-0072 — A system job gives each item, and each command on a shared timer, a DI scope of its own

- **Status:** `accepted` — **2026-10-12**, in the commit that ships D2 (finding BE-13). D1 (finding BE-14)
  shipped first on the same branch, in `56324e91c`, which said this record would be written whole with D2.
  The design review is recorded in §Challenge, §Defense and §Verdict.
- **Date:** 2026-10-12
- **Decided by:** the design review — 2026-10-12. Mike's direction, "Go with recommended long-term
  fix" (2026-10-12, T-0844), approved the fix without choosing between its offered mechanisms.
- **Supersedes:** nothing.
- **Composes with:** ADR-0002 D1 (an outbox row commits with the change it describes), ADR-0038 §D8 (fail-soft
  is admissible only over an operation that normally succeeds), ADR-0061 (a system job sets the tenant per row
  or per company and commits inside the loop), ADR-0073 (the order-ending credit return joins the commit that
  ends the order, which is what makes a caught commit in a shared scope lose credit).
- **Applies to:** the two timers that carry several commands (`CleanupStalePendingOrdersHandler`,
  `AutoCancelStaleRecurringOrdersHandler`), and `AutoCancelStaleRecurringOrders`, which now sends
  `AutoCancelRecurringOccurrence` once per occurrence. D2's rule reaches every system job; the jobs that break
  it today are listed in `agents/knowledge/consistency.md` and wait for T-0841, the canonicalization ticket.

> **Record wording — owner decision of 2026-10-13:** Mike's answer 6 was
> "If rules improve the workflow in a better way then yes"; the approved default was
> "Go with defaults (recommended)". This correction records the decider without contributor role
> credits and preserves the dated acceptance and deliberation trail.

> **Two decisions:** *a timer that carries several commands sends each from a DI scope of its own and fails the
> invocation only after the last (D1); a job whose items must fail independently gives each item a DI scope of
> its own, and no loop continues past a failed commit, or past staging that a later commit in the same scope
> will save, with or without `Rollback()` (D2).*

## Context

### D1 — two timers that said each command fails alone (citations at `db2272a5d`, before `56324e91c`)

`CleanupStalePendingOrdersHandler` said its commands were *"sent separately so a failure in one does not
suppress the others"*, and `AutoCancelStaleRecurringOrdersHandler` said the same of its two. Neither was true.
The three sends (`CleanupStalePendingOrdersHandler.cs:28`, `:46-47`, `:66`) and the two
(`AutoCancelStaleRecurringOrdersHandler.cs:28`, `:45`) shared the handler's own scope
(`FunctionsProcessingRegistration.cs:53-54`) with no `try`, and every pipeline behaviour rethrows
(`UnitOfWorkPipelineBehavior.cs:35-39`). A throw in the first command therefore ended the tick:
`CancelUnfilledOrders`, the only sweep that refunds paid orders nobody took, waited 15 minutes, and
`RedrivePendingRefunds`, which moves money, waited an hour. The shared scope also carried one command's change
tracker and never-cleared tenant override into the next. The host's own rule is to log and rethrow, never
swallow, so that a timer still reports failure (`FunctionInvocationErrorMiddleware.cs:14-15`).

### D2 — the recurring auto-cancel's catch (citations at `9c806d84e`, the parent of this change)

`AutoCancelStaleRecurringOrders` loaded every candidate occurrence (`AutoCancelStaleRecurringOrders.cs:74-81`)
and, for each, cancelled it, returned its credit, staged its notice and committed (`:113-146`) inside a `try`
whose `catch` only logged at Warning (`:149-154`). It neither rolled back nor detached anything. A failed
`CommitAsync` leaves every tracked entry as it was (`CleansiaDbContext.cs:84-120`), so the failed occurrence's
modified order, its `Cancelled` track and its feed and outbox rows rode the next occurrence's commit, or the
pipeline's commit after the sweep (`UnitOfWorkPipelineBehavior.cs:28-29`):

- **A transient failure** saved the occurrence later anyway; a failure inside the notice saved the
  cancellation without its notice.
- **A deterministic failure** (an outbox key collision, a concurrency conflict) failed every later commit in
  the run, so nothing more was cancelled, every hour, and the pipeline's commit then threw out of the timer.
- **Since ADR-0073 it lost credit.** A refused commit rolls back the credit the occurrence returned, and its
  leftovers then commit without it. Measured on Postgres at `9c806d84e`, through the sweep's real
  unit-of-work pipeline: an occurrence with 300 of credit applied whose commit was refused once ended
  `Cancelled` with no credit returned, and no later run returned it, because a cancelled occurrence is skipped.

`MaterializeRecurringBookingTemplate.cs:26-40` already explains why catch-and-continue in a shared scope is
unsafe with or without `Rollback()`, and `MaterializeRecurringBookings` gives each template a scope of its own
(`MaterializeRecurringBookings.cs:86-130`), as `RetryFailedUserDeletions` does for each request
(`RetryFailedUserDeletions.cs:73-111`).

## Decision

### D1 — A timer that carries several commands sends each from its own scope, then rethrows

Both timer handlers take an `IServiceScopeFactory` instead of an `IMediator`, and send each command through a
mediator resolved from `scopeFactory.CreateAsyncScope()` (`CleanupStalePendingOrdersHandler.cs:110-129`,
`AutoCancelStaleRecurringOrdersHandler.cs:85-104`).

- An `OperationCanceledException` while the host is stopping is rethrown at once.
- Any other exception is logged at Warning, naming the command, and the next command still runs.
- After the last command, one failure is rethrown as itself and several as an `AggregateException`, so the
  invocation still fails and `FunctionInvocationErrorMiddleware` logs it once, at Error. The exception is a lone
  `OperationCanceledException` the host did not ask for, such as a call's timeout: the middleware passes every
  cancellation on unlogged, so the command's Warning is its only line; before this change it left none. *(Added
  2026-10-13, before merge.)*
- A failure result is unchanged: logged at Error, never thrown.
- No shared type: a private helper in each handler. Only these two handlers send more than one command, and a
  source guard keeps any third one honest (§Verification).

### D2 — A job whose items must fail independently gives each item its own scope

> **The rule.** A job whose items must fail independently gives each item its own DI scope. A loop must never
> continue past a failed commit, or past staging that a later commit in the same scope will save, with or
> without `Rollback()`.

Applied to the recurring auto-cancel, in the `MaterializeRecurringBookings` shape:

- **`AutoCancelStaleRecurringOrders` is a dispatcher.** One clock and one cutoff; an ids-only read, today's
  predicate plus a status term (not `Cancelled`, not `Completed`), ordered by `CleaningDateTime`, then `Id`
  (`AutoCancelStaleRecurringOrders.cs:67-84`). For each id it checks for cancellation, opens
  `await using var scope = serviceScopeFactory.CreateAsyncScope()` and sends
  `AutoCancelRecurringOccurrence.Command(orderId, cutoff)`. An `OperationCanceledException` while cancelled is
  rethrown; any other exception, and any failure result, is logged at Error and counted
  (`:89-126`). It returns `Response(Cancelled, Considered, Failed)`.
- **`AutoCancelRecurringOccurrence` is the unit.** It reads its order again past the tenant filter and checks
  again that it still awaits confirmation, that its slot is at or before the cutoff and that it has a customer;
  otherwise it returns `Cancelled = false` and changes nothing (`AutoCancelRecurringOccurrence.cs:51-62`). It
  sets the tenant override from the order, then cancels it with its credit return and its notice, as the loop
  did (`:64-97`). **It neither commits nor catches.** The unit-of-work pipeline commits it inside its own scope,
  where the same tenant override and the same credit-lock transaction live, so the unit needs no transaction of
  its own and no `CommitAsync`, and a failure leaves with its scope.
- **Its validator caps the cutoff at 24 hours ahead** (`:33-34`), the sweep's own bound, because the unit
  cancels whatever order its caller names, past the tenant filter.
- **The status term is `Order.AwaitsCustomerConfirmation`'s own.** This sweep never writes `PaymentStatus`, so
  every occurrence it ever cancelled stayed `Pending`, was loaded every hour and was skipped in memory. Now
  it is not read at all. The term is the one offerability already negates, so what a cleaner is offered does
  not change.
- No registration changes: MediatR finds the new handler, and the timer handler keeps its two scopes.

## Consequences

- **An occurrence that fails stays exactly as it was** — no cancellation, no notice, its credit still spent —
  and is counted in `Failed`, logged at Error and tried again an hour later. The others go ahead on the same
  run.
- **`Considered` counts only the occurrences still awaiting confirmation**, so the number in the timer's log
  drops by the old cancellations it used to count. The timer's log line now reports `Failed` as well.
- **One scope and one `DbContext` per occurrence.** With the status term in SQL, that is one per occurrence
  actually being retracted.
- **The rule puts shipped jobs in violation.** They are listed in `consistency.md` §"A loop that continues past
  a failed commit in a shared scope", with the search that found them; converting them is T-0841, a
  canonicalization ticket for the owner to schedule, `SendRecurringOrderReminders` first, because ADR-0071's
  token on the order's payment status will give its catch a new trigger.

## Residuals (accepted, named)

- **A poison occurrence is retried and logged at Error every hour, with no attempt cap.** That does not meet
  `runtime-readiness.md`'s *"a max attempt count"*; the visible places are Sentry and `Response.Failed`. It is
  recorded here as a deviation, not as compliance, and accepted as it is for `MaterializeRecurringBookings`: a
  cap needs persisted state for a failure nobody has yet seen.
- **The listed jobs keep their shared-scope catches** until T-0841, the canonicalization ticket, is scheduled.
  `RedrivePendingRefunds` is one of them, and it moves money.
- **The unit trusts the id it is sent.** No HTTP route sends it; its only sender reads the ids itself, and the
  validator bounds the cutoff.
- **A failure followed by the host stopping raises no Sentry event.** When one command on a shared timer throws
  and a later command on the same tick meets the host stopping, the stop is rethrown at once, and the host's error
  middleware passes a cancellation on without logging it, so the earlier failure keeps only its Warning line, a
  breadcrumb rather than an event. Each command picks its work by state, so the next tick runs it again, and a
  failure that repeats is reported then.

### Mechanism update — 2026-10-13

Mike's answer 8, "Analyze and Fix those", and default choice, "Go with defaults (recommended)",
authorize T-0841's twelve-child conversion. The remaining-jobs change follows T-0856's merged reminder
scope with refund command scopes; existing-service cleaner, receipt and employee scopes; company/task
retention scopes with child-local legal gates; and no-catch membership/company staging boundaries.
The exact temporary catalog rows retire with their child changes. The persistent rule still forbids
continuation with a failed scope; its named tests are a closed roster, not a universal detector.

Payroll employee commits keep the parent durably Open until its post-email close, but prior invoice
records can survive and a crash before close can repeat email. Fiscal claim-before-send retains its
crash-after-claim loss tradeoff and does not broaden the existing retry selector. Batch retries still
require their original windows; a permanently refused item or an expired window remains a residual.
The unfilled-order fresh read keeps an explicit read-to-claim race. Per-child Work records distinguish
actual RED assertions from baseline-passing characterization and retain failed harness attempts.
Separate final review, combined suites, exact-head CI and merge evidence belong to those records.
This dated mechanism note does not claim a deploy; the later wording sweep is a separate phase.

## Alternatives considered

- **D1 — swallow a thrown command** (the draft). Withdrawn: it breaks the host's rule
  (`FunctionInvocationErrorMiddleware.cs:14-15`), and a timer would no longer report failure.
- **D1 — a shared helper type.** Not built: two handlers, one private method each.
- **D2 — drop the catch.** Correct, but then one bad occurrence stops every occurrence after it, every hour.
- **D2 — catch and `Rollback()`.** `Rollback()` turns an `Added` row into an `Unchanged` phantom that the next
  commit drags along, and leaves stale values to identity resolution (`MaterializeRecurringBookingTemplate.cs:26-40`).
- **D2 — a `ChangeTracker.Clear()` seam.** Every catch site must remember it, and it leaves the pending-dispatch
  buffer's keys behind (`OutboxPendingDispatch.cs:25-32`): the scope still believes the cleared outbox rows are
  staged, and skips any later enqueue of the same key.
- **D2 — the unit opens its own transaction, or commits itself** (the draft). Withdrawn: ADR-0073
  already makes the credit return join the commit, and a handler does not call `CommitAsync`. In its own scope
  the pipeline's commit sees the same override and the same lock transaction.
- **D2 — one scope per order for `CleanupStalePendingOrders` too.** Rejected: its one commit per company is
  pinned (`CleanupStalePendingOrdersTwoOperatorsTests`, the recipients read once per company and the batch
  committed once per company), and it is the named reference for the row-driven shape. It has no catch: a
  refused company ends the run, and the next run takes it again.

## Challenge

- **O4** (must fix) — read literally, *"never catch-and-continue in a shared scope"* puts shipped code in
  violation, including the reference shape for the per-company jobs (`DataRetentionBackgroundService`), and the
  draft labelled its enforcement `T1-CI`, which nothing could fail. ADR-0071's token will also give
  `SendRecurringOrderReminders`, which has this exact shape, a new trigger.
- **O6** (not blocking) — swallowing a thrown command breaks the host's log-and-rethrow rule.
- **O7** (precision) — the draft claimed the dead-end rule was met; it is not, because nothing caps the retries.
- **Security finding 1** — a catch inside a unit's own transaction would commit every credit return of a group
  without its cancellations. **Security finding 6** — the unit cancels the order its caller names, past the
  tenant filter; bound its cutoff.

## Defense

- O4 adopted. The rule is stated precisely (D2), the shipped deviations are listed by name in `consistency.md`
  with the search behind the list, the tier is `T3-HUMAN` for every job but the two dispatchers whose isolation
  tests are `T1-CI`, and a canonicalization ticket is owed (T-0841), `SendRecurringOrderReminders` first.
- O6 adopted: each command runs in its own scope and the handler rethrows once, after the last (D1).
- O7 adopted: the missing attempt cap is a named residual, not a claim of compliance.
- Security finding 1 is moot as stated, because no unit opens a transaction; its intent is kept as D2's
  sentence: no catch around a commit in a shared scope. Security finding 6 adopted: the validator caps the
  cutoff at 24 hours ahead.

## Verdict

**Consensus.** Every challenge was adopted or answered above, and none blocks. D1 shipped in `56324e91c`; D2
ships with this record, accepted on 2026-10-12.
