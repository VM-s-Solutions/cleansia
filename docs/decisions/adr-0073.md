# ADR-0073 — The credit an order gives back when it ends unpaid commits with the commit that ends it

- **Status:** `accepted` — **2026-10-12**, in the commit that ships it (finding BE-12). Argued by an
  author → challenger → lead panel: the challenger's O3 proposed the seam, the lead adopted it and withdrew
  the author's draft (a transaction opened in each unit). The trail is in §Challenge, §Defense and §Verdict.
- **Date:** 2026-10-12
- **Supersedes:** nothing.
- **Composes with:** ADR-0038 (a self-committing write inside a handler rides the pipeline's commit; this
  record brings the order-ending return in line with it), ADR-0061 (a system job sets the tenant per group
  and commits inside the loop), ADR-0064 D3 (a return onto a company frozen for archive is still skipped).
- **Lands before:** [ADR-0071](./adr-0071), which makes the order's payment status a concurrency token. Under that token a
  refused commit would otherwise hand credit back on an order that stays paid and booked.
- **Applies to:** `CreditUnwind.ReturnUnpaidOrderCreditAsync` and `CleanupStalePendingOrders`. The other six
  callers of the return take the change with no code of their own.

> **One decision:** *the credit an order gives back because it ended without a card refund of its own
> (`order-ended-unpaid:{orderId}`) commits with the commit that ends the order, or not at all; and a unit
> that holds several customers' credit locks until its commit takes them in ordinal user-id order.*

---

## Context (citations at `56324e91c`, with this change's own lines where it moved them)

### The defect

`CreditAccountRepository.TryReturnAsync` opens and commits a transaction of its own when none is open on the
context, and joins the open one otherwise (`CreditAccountRepository.cs:107-110`, `:154-155`;
`ICreditAccountRepository.cs:94-97` says so). The order-ending return
(`CreditUnwind.ReturnUnpaidOrderCreditAsync`) opened nothing first, so it committed on its own, before the
commit that ends the order.

In `CleanupStalePendingOrders` the return ran inside a company's loop and the company committed after it. A
throw at that commit — a concurrency conflict from a concurrent cancel or the expired-session webhook, or a
database fault — left the credit returned on an order that was still `Pending` until the next 15-minute tick.
In that window the customer could still pay, and the booking would go ahead with its credit already handed
back. The same shape sat at the other six callers: the recurring auto-cancel, the customer's and the
platform's cancellations, the no-show cancellation, the expired-session webhook and the lockout cancellation
(whose return is in a cash-only branch, `AdminCancelOrderAsLockout.cs:112-114`, while credit is card-only,
`CreateOrder.cs:1233`, `ConfirmRecurringOrder.cs:304`, so nothing moves there today). The Postgres suite
pinned only a failure before any credit moved.

### The seam that was already there

- `ICreditAccountRepository.LockForUserAsync` → `CleansiaDbContext.LockCreditOwnerAsync` opens the context's
  lock transaction when no transaction and no ambient `TransactionScope` is current, then takes the
  customer's `Users` row `FOR NO KEY UPDATE` (`CleansiaDbContext.cs:295-305`). It is Npgsql-only
  (`:297-298`).
- `CommitAsync` commits that transaction after the save (`:108-113`) and rolls it back whole when the save
  fails (`:115-119`). `Rollback()` rolls it back too (`:359-367`), and the pipeline calls it for every command
  that fails or throws (`UnitOfWorkPipelineBehavior.cs:29-38`).

A return that takes the owner lock first therefore joins whichever commit ends the order.

---

## Decision

### D1 — The return takes the customer's owner lock first, and so joins the commit that ends the order

`ReturnUnpaidOrderCreditAsync` returns early for an order with no credit applied or no customer account, and
otherwise calls `LockForUserAsync(order.UserId)` before it reads what is still owed
(`CreditUnwind.cs:140-145`). The lock opens the lock transaction when none is open; `TryReturnAsync` finds it
and joins it; the commit that ends the order commits both, or rolls both back.

- **One change covers all seven callers**, with no interface change and no transaction opened in any
  handler: `CleanupStalePendingOrders.cs:161`, `AutoCancelStaleRecurringOrders.cs:119`,
  `CustomerOrderCancellation.cs:116`, `PlatformOrderCancellation.cs:73`, `CleanerNoShowCancellation.cs:78`,
  `HandlePaymentNotification.cs:459`, `AdminCancelOrderAsLockout.cs:114`.
- **What is still owed is read under the lock**, so a return another unit committed meanwhile is counted, and
  the key check inside `TryReturnAsync` (`CreditAccountRepository.cs:120-127`) still runs after the lock, on
  the same connection. A concurrent unit waits on the lock.
- **Unchanged:** `ReturnCreditAsync` and `ReturnPendingRefundCreditLegAsync`. `CreateOrder`'s compensation
  calls `ReturnCreditAsync` directly and stays self-committing (`CreateOrder.cs:1181-1186`): it has to
  survive a request that is about to return a failure.
- **No lock is held across a network call.** Between each caller's return and its commit there are only
  database reads, tracked staging and outbox rows, and every refund call comes before the return.
- It brings the code in line with `agents/knowledge/consistency.md:410-416` (§Post-commit ordering (a)): a
  self-committing write inside a handler must ride the pipeline's commit, and the order-ending return now
  does.

### D2 — A unit that holds several customers' credit locks takes them in ordinal user-id order

A company's group in `CleanupStalePendingOrders` now holds, until one commit, the credit lock of every customer in
its batch whose checkout spent credit. *(Amended 2026-10-13, before merge: this said the group was the first unit
to hold several customers' locks; the referral grant and its reversal already hold their two parties'.)* It now
processes each company's orders by `UserId` (ordinal), then by `Id` (`CleanupStalePendingOrders.cs:132-136`). Which orders a run takes is unchanged: the batch read is the same,
oldest first.

The order is the one the referral grant and its reversal already use (`ReferralService.cs:306-311`,
`ReverseReferral.cs:99-104`), so a group cannot wait in a cycle with either. `ExpireStaleCredit` keeps
holding one customer's lock at a time (`ExpireStaleCredit.cs:86`, `:112-114`).

---

## Consequences

- **A refused commit that would have ended an order leaves the order and its credit as they were.** The retry
  — the sweep's next tick, Stripe's redelivery, the customer's or administrator's retried cancel — returns
  the credit once, on the same key.
- **The owner lock is held from the return until the ending commit:** milliseconds on a request path, seconds
  for a company's group of up to 500 orders. Meanwhile these wait for the same customer: a checkout that
  spends credit, `CompleteOrder`'s loyalty lock, the `EnsureForUserAsync` callers (`IssueCustomerCredit.cs:162`,
  `ResolveDispute.cs:283`, `CleanerNoShowCancellation.cs:163`) and the erasure (`GdprDeletionService.cs:254`).
- **A loop that catches a refused commit and goes on in the same scope now loses credit.** The failed order's
  staged changes stay tracked and ride the next commit, without the return the refused commit rolled back.
  `CleanupStalePendingOrders` has no such catch and says so at its commit. `AutoCancelStaleRecurringOrders`
  keeps one around each occurrence's commit until [ADR-0072](./adr-0072) gives each occurrence its own scope.
- **SQLite cannot show any of this.** The lock is Npgsql-only, so the join is proven on Postgres only.

## Residuals (accepted, named)

- **A deadlock between a company's group and `CompleteOrder`.** `CompleteOrder` locks the customer first
  (`LoyaltyService.cs:56`, through `CompleteOrder.cs:311`) and then the referrer (through `CompleteOrder.cs:313`
  and `ReferralService.cs:335`), whatever their ordinal order. A cycle needs all of: a referrer and the
  customer they referred both with abandoned checkouts carrying credit in the same company's group, the
  referrer sorting first, and the referred customer's first job completing in that second. Postgres aborts
  one side (40P01) and both roll back whole; the sweep retries on its next tick and the cleaner retries the
  completion.
- **A future caller that ends an order and gives its credit back some other way loses the atomicity.** The
  guard is `CreditUnwind`'s rule that every order end returns credit through it (`CreditUnwind.cs:7-20`).

## Verification (what to check)

1. `ReturnUnpaidOrderCreditAsync` takes the lock before its reads and before `TryReturnAsync`, and only for
   an order with credit applied and a customer account — `ReturnUnpaidOrderCreditTests`.
2. On Postgres: a company's refused commit leaves no `order-ended-unpaid` row and the rerun writes exactly
   one (`CleanupStalePendingOrdersTwoOperatorsTests.A_Refused_Company_Commit_Rolls_Back_The_Credit_Its_Orders_Returned`);
   a refused administrator cancel returns nothing and its retry returns the credit once
   (`PlatformCancellationCreditReturnAtomicityTests`); a company takes its customers' locks in ordinal
   user-id order (`CleanupStalePendingOrdersTwoOperatorsTests.A_Company_Takes_Its_Customers_Credit_Locks_In_Ordinal_User_Order`).
3. No `BeginTransactionAsync` was added in a handler.

## Alternatives considered

- **A transaction opened in each unit** (the author's draft, withdrawn). Every caller has to remember it, the
  request-path cancels need it as much as the sweeps, and `IUnitOfWork.BeginTransactionAsync` is not guarded
  against an ambient `TransactionScope` (`CleansiaDbContext.cs:354-357`) where the lock is (`:299`), so the
  tests that run inside one would have to change shape.
- **The two sweeps only.** It needs a second method, and the request-path cancels keep the defect.
- **An outbox-keyed return.** The balance moves later, and it needs a new consumer.
- **A return hook inside the context's commit.** A new seam for what the owner lock already gives.
- **Doing nothing.** The credit keeps coming back ahead of the commit, and under [ADR-0071](./adr-0071)'s token a refused
  commit would hand credit back on an order that stays paid.

## Challenge

- **O3** (should fix) — the request-path returns stay self-committing ahead of a commit the token can refuse,
  and a transaction in each unit relies on every caller remembering it, when the owner lock already opens a
  transaction that `CommitAsync` commits or rolls back for all seven callers.
- **O2** (must fix) — a company's group becomes the first unit to hold several customers' locks until its
  commit; the draft named the wrong deadlock partner (`ExpireStaleCredit` holds one lock per commit), and
  `CompleteOrder`'s customer-then-referrer order can form a cycle.
- **Security finding 1** — a catch inside a unit's own transaction would commit every credit return of the
  group with none of its cancellations. **Security finding 2** — as O2. **Security finding 3** — under the
  token, a customer's cancel that races its own payment would hand credit back on an order that stays paid.

## Defense

- O3 adopted as this record, and the per-unit transaction withdrawn. Security finding 1 is moot as stated,
  because no unit opens a transaction; its intent is kept: no catch around a commit in a shared scope.
- O2 adopted: the deadlock text is corrected, a company's group takes its locks in ordinal user-id order (D2),
  and the `CompleteOrder` cycle is a named residual. Security finding 2 is answered the same way.
- Security finding 3 is closed by D1: the refused commit rolls the return back with it.

## Verdict

**Consensus.** Every challenge was adopted or answered above, and none blocks. Accepted on 2026-10-12, in the
commit that ships it.
