# ADR-0075 — The mobile contract states a query sort the way the server binds it

- **Status:** `accepted` — **2026-10-12**, by consensus of the panel that ruled on **T-0832**: the
  author's decision stands, challenges 1a, 1b and 1d were conceded and 1c in part, all folded in, and
  the lead added amendments A and B (§*Challenge, defense and verdict*).
- **Date:** 2026-10-12
- **Supersedes:** nothing.
- **Superseded by:** —
- **Composes with:** [ADR-0048](./adr-0048) (the response side of the mobile wire contract; this is
  the request side), [ADR-0019](./adr-0019) (the iOS generated client authenticates through the Core
  spine, which this leaves alone) and [ADR-0031](./adr-0031) (the web NSwag regeneration, which this
  does not touch).
- **Applies to:** `src/Cleansia.Config/Swagger/IndexedSortOperationFilter.cs`, the `AddSwagger` of
  `Cleansia.Web.Mobile.Partner` and `Cleansia.Web.Mobile.Customer`, the two committed mobile specs
  under `src/cleansia_android/openapi/`, and the six native call sites that send a sort. Ticket
  **T-0832**.
- **Living doc:** `agents/architecture/decisions/mobile-wire-contract.md`, §*The request side: the
  query sort*.

> **One decision:** *the two mobile hosts describe `DataRangeRequest.Sort` as the two scalar query
> parameters ASP.NET already binds, `Sort[0].Field` and `Sort[0].Direction`, so every generator reading
> the committed specs emits a form the server binds. The server's runtime, the web clients and every
> model binder are unchanged.*

## Context (every citation at `6952149a1` unless marked)

**The request type.** Every paged GET binds `DataRangeRequest` from the query, and its sort is a
collection of objects: `public IEnumerable<SortDefinition>? Sort`
(`src/Cleansia.Core.AppServices/Shared/DTOs/RequestModels/DataRangeRequest.cs:13`), each element a
`Field` string and a `Direction` (`SortDirection`, an int enum carrying `[SwaggerEnumAsInt]`,
`src/Cleansia.Core.Domain/Sorting/Common/SortDirection.cs:5-10`). Nothing in `src/` adds a model binder,
a type converter or a value provider for it.

**What the mobile specs said.** Swashbuckle described the sort as one query parameter, `"name": "Sort"`,
an array whose items are `$ref SortDefinition` — four times in each mobile spec
(`partner-mobile-api.json:1093`, `:3433`, `:4219`, `:4655`; `customer-mobile-api.json:1549`, `:3090`,
`:4274`, `:4542`, before this change). **OpenAPI 3.0 defines no query serialization for an array of
objects**, so each generator sent its own fallback:

- **Kotlin** (`jvm-retrofit2`) declared `@Query("Sort") sort: List<SortDefinition>?`. Retrofit has no
  string converter for it — the only converter is the kotlinx JSON one (partner
  `core/network/NetworkModule.kt`, `provideAuthRetrofit`) — so it fell back to the data class's
  `toString`: `Sort=SortDefinition(field=cleaningDateTime, direction=0)`.
- **Swift** (`swift5`, `urlsession`) JSON-encoded each element, pretty-printed, and sent it base64:
  `Sort=ewog…`.

**What the server binds.** A probe on ASP.NET Core 10.0.301 with the same request shape bound **both
native strings to an empty list, with ModelState valid**. `Sort%5B0%5D.Field=x&Sort%5B0%5D.Direction=0`
bound one entry, and so did the raw-bracket form the web client sends. `Sort[1]` on its own bound an
empty list (an index must start at 0), `Sort.Field` bound nothing, and a direction of `7` was refused
with a 400 on `Sort[0].Direction`.

**What that cost.** Every native sorted list took its endpoint's default. The orders page is newest
created first, then `Id` (`src/Cleansia.Core.AppServices/Mappers/SortMapper.cs:22-38`), so the Orders
sort choice did nothing on either app and the dashboard's upcoming page was the ten most recently
created orders from today rather than the ten soonest. The invoice lists had **no `ORDER BY` at all**:
an empty sort reaches `GetPagedSort` (`Features/EmployeePayroll/GetPagedInvoices.cs:58-63`), which
loops over zero definitions (`src/Cleansia.Infra.Database/BaseRepository.cs:88-96`).

## Decision

### D1 — The two mobile hosts register `IndexedSortOperationFilter`

A Swashbuckle `IOperationFilter`. For each parameter of an operation that ASP.NET binds from the query
as a collection of `SortDefinition`, it replaces the `Sort` parameter in place with:

- `Sort[0].Field` — `string`, nullable;
- `Sort[0].Direction` — the existing `$ref SortDirection`, taken from the schema generator, so it stays
  the integer enum the rest of the spec uses.

Only index 0 is described: every native caller sends one key, and the orders page adds its `Id`
tie-break on the server (`SortMapper.cs:31-38`). A second key would be one more index in the filter.

Only `Cleansia.Web.Mobile.Partner` and `Cleansia.Web.Mobile.Customer` register it, beside their schema
filters in `AddSwagger`. **The web hosts do not**: their NSwag clients are generated from `:5000`,
`:5001` and `:5003` (`src/Cleansia.App/nswag-*.json:5`) and already send the indexed form.

### D2 — One shared class in `Cleansia.Config`, registered per host (amendment A)

Every Swagger filter before this one is a per-host copy — `EnumSchemaFilter` exists five times, once in
each host's `SwaggerSchemaFilters/`. This one is a single class in `src/Cleansia.Config/Swagger/`,
because two hosts need the identical change today (CLAUDE.md §4: extract when a second caller exists
today) and `Cleansia.Config` already references Swashbuckle (`src/Cleansia.Config/Cleansia.Config.csproj:18`).
The registration point is the house seam, each host's own `AddSwagger`.

Do not "fix" it either way. A copy per host would be two copies of one rule; registering it from shared
startup would reach the web hosts and change their contracts.

### D3 — The specs are re-dumped, never hand-edited, and drift lands first (amendment B)

A hand-trimmed dump is forbidden, because the next dump overwrites it
(`docs/mobile-app/api-integration.md`, *never hand-edit generated output*). So the change follows four
steps:

1. Dump both specs once **before** the filter is registered.
2. If that dump differs from the committed specs, it lands first, as its own drift-only commit, with
   both apps compiling and their suites green.
3. The filter's commit may then change only the eight `Sort` parameters listed in §*Context*.
4. Drift that needs any hand-written code stops the work and is reported: that is new scope.

**What happened on 2026-10-12.** Both mobile hosts were booted in Development against a throwaway
Postgres and their `/swagger/v1/swagger.json` was written through
`src/cleansia_ios/scripts/refresh-mobile-spec.sh`. Before the filter, both dumps were **byte-identical**
to the committed specs, so there was no drift commit. After it, undoing exactly the eight replacements
gives back the earlier document, so nothing else moved. The `SortDefinition` schema stays in
`components` with nothing referencing it, which is harmless.

### D4 — The clients send the generated scalars

At the pinned openapi-generator **7.10.0**, both platforms emit two scalar parameters (probed
2026-10-12):

- Kotlin: `@Query("Sort[0].Field") sort0Field: kotlin.String? = null` and
  `@Query("Sort[0].Direction") sort0Direction: SortDirection? = null`;
- Swift: `"Sort[0].Field": (wrappedValue: sort0Field?.encodeToJSON(), isExplode: true)` and the same
  for `sort0Direction`.

Both send the direction as `0` or `1`. The six partner call sites pass today's field and direction
through them: Android `OrdersRepository.kt`, `DashboardRepository.kt` and `InvoicesRepository.kt`; iOS
`PartnerOrderClient.swift`, `PartnerDashboardClient.swift` and `PartnerPayrollClient.swift`. The customer
apps pass only `offset` and `limit`, by name, so they need no change.

## Alternatives considered

**(a) Generator configuration.** It cannot do this. 7.10.0's Kotlin `jvm-retrofit2`
`queryParam.mustache` and Swift `_param.mustache` emit one key per parameter, `deepObject` included. Only
a forked `templateDir` could change that, and the iOS spine depends on those generated internals.

**(b) A query seam in each app.** Rejected. Android has no single Retrofit seam: it would need an OkHttp
interceptor on the authenticated chain plus a string converter, or code that parses a `toString`. iOS
would decode base64 pretty-printed JSON inside the auth spine, which couples hand-written code to
generated internals and widens ADR-0019's auth seam into query rewriting. The Android wire tests build
their own Retrofit, so such a seam would go untested; the customer apps would need copies; and the spec
would go on describing the wrong shape.

**(c) A server binder that accepts the native forms.** Rejected. It makes two generators' fallbacks part
of the server contract, adds parsing of untrusted input to every paged request, helps nothing until it
is deployed, and must then be kept forever. No native client has shipped to production, so there is no
installed base to keep reading.

**(d) Reshaping `DataRangeRequest` into scalars.** Rejected. All five hosts share the type, so the web
NSwag contracts would change, and T-0832's NOT list protects them.

**(e) Hand-editing the committed spec.** Rejected. The next dump overwrites it.

**Why the spec is the right place.** The root cause is the description, not either client. When the
spec describes the shape the server binds, every generator, today's and the next version, emits a
defined form. There is no deploy coupling: the running server already binds the indexed names, so a
rebuilt app sorts correctly against DEV today and an old build keeps the default order. It fixes the
customer apps' four sort parameters at the same time, and it couples no hosts, because the web hosts do
not register the filter.

## Consequences

- **The Orders sort choices start working** on both partner apps. The pay sorts still reorder only
  within a page (`Features/Orders/GetPagedOrders.cs`, the in-memory pay re-sort).
- **The dashboard's upcoming page becomes the ten soonest orders from the start of today.**
- **The invoice lists go from no `ORDER BY` to newest generated first.** `createdOn` is not an
  `EmployeeInvoiceSort` field, so it falls back to `GeneratedAt`
  (`src/Cleansia.Core.Domain/Sorting/EmployeeInvoiceSort.cs:10`, `:42`).
- **A Swashbuckle or Microsoft.OpenApi upgrade** that changes how a complex query parameter is expanded
  would make the filter miss its target. The host tests below fail on that upgrade.
- **`backend-ci` ignores `src/cleansia_android/**`**, so a spec-only commit runs no server test.
  Compilation covers it instead: a re-dump without the filter brings back `sort: List<SortDefinition>`
  and breaks the six call sites on android-ci and ios-ci.

## Challenge, defense and verdict

The panel ruled on the author's draft, which proposed this decision. **Defense:** the decision stands;
each challenge below was conceded, 1c in part, and folded into this record.

- **1a — iOS before 17.** The generated builder rebuilds the request with `URL(string:)` after setting
  `URLComponents.queryItems`, and `URL(string:)` is stricter before iOS 17. **Conceded:** the extended
  and new iOS wire tests also run green on the iOS 16.4 simulator, recorded on the ticket as Gate 8.5
  evidence. A URL with raw brackets would fail there as *no request was sent*, so the existing test
  shape catches it.
- **1b — Findability.** **Conceded:** the record gets a row in the decisions index and a sidebar entry.
- **1c — The living doc said the re-dump was owner-only.** **Conceded in part:** the four places where
  `mobile-wire-contract.md` says so in its own voice change in the same edit, because its new section
  runs that very step (CLAUDE.md, owner ruling of 2026-09-07). Its quotation of
  `generated-client-contract.md` stays verbatim; that page's stale lines are reported, not absorbed.
- **1d — Name the real enforcer.** **Conceded:** the mobile catalog entry's enforcer is
  `MobileSpecSortParameterTests`, which keeps the spec flat and so leaves a generated operation no other
  way to send a sort. The native wire tests cover only the six existing call sites, a closed roster.
- **Amendment A** — the shared class and its reason (D2).
- **Amendment B** — the drift rule (D3). Without it, *"report the drift, do not ride it in"* left no
  allowed move if the committed specs lagged the hosts.

**Verdict:** consensus, `accepted`.

## How a reviewer verifies compliance

1. **`MobileSpecSortParameterTests`** (`src/Cleansia.HostTests/Tests/`, backend-ci) is green. It boots
   both mobile hosts and reads `ISwaggerProvider.GetSwagger("v1")`:
   - no query parameter in either mobile spec is a collection of objects;
   - every operation that binds a query sort carries `Sort[0].Field` (`string`) and `Sort[0].Direction`
     (`$ref SortDirection`), and no `Sort`, with at least one such operation per host;
   - on the partner mobile host, `GET /api/Order/GetPaged` with the two parameter names read out of the
     document comes back by ascending cleaning date, where the server's default would list the same
     orders the other way round.
2. `rg -n '"name": "Sort",' src/cleansia_android/openapi` returns nothing.
3. T-0832's native half: the wire tests pin the six call sites — `DashboardWireTest`, `InvoicesWireTest`
   and `OrdersWireTest` on Android, `UpcomingOrdersWireTests` and two new siblings on iOS — and the iOS
   ones also run green on the iOS 16.4 simulator (1a).
