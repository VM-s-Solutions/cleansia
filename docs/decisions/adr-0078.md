# ADR-0078 — Each Live Activity token carries its APNs environment

- **Status:** accepted
- **Date:** 2026-10-28
- **Decided by:** the design review, 2026-10-28
- **Changes:** ADR-0029's environment-selection premise only. Its token ownership, lifecycle, delivery taxonomy, payload and claim-before-send behavior remain in force.

## Context

The customer TestFlight build can use DEV APIs while carrying a production APNs signing entitlement. `deploy/bicep/main.bicep` selects sandbox for DEV, and the old `ApnsLiveActivityClient` used that global setting for every token. API deployment environment therefore cannot choose the correct APNs endpoint for mixed Xcode/TestFlight installs.

`LiveActivityToken` already owns per-user/device/order operational addressing. Its raw token has a 512-character column limit; its upsert key is `(UserId, DeviceId, OrderId)`. Token rotation, terminal cleanup, device retirement/revocation, logout and GDPR deletion already operate through that entity and key. These contracts stay unchanged.

## Decision

1. Add nullable `UseSandbox` to the token and optional nullable `useSandbox` to the authenticated registration command. New clients state the supported signing configuration; a rotated registration replaces token and environment together. Omitted metadata deliberately clears a previous override and returns a legacy client to the existing global default.
2. The dispatch consumer passes each recipient's environment to the APNs adapter. `true` selects Apple's fixed sandbox endpoint; `false` selects Apple's fixed production endpoint; null uses `APNS:UseSandbox`. No arbitrary URL or topic comes from the client. Raw token bytes/string and device identity are preserved.
3. New customer builds bind their public environment marker to supported signing configuration. Artifact verification compares it with the actual signed `aps-environment`; an ambiguous custom signing configuration fails verification. Do not infer APNs environment from the API URL or use private entitlement APIs.
4. Never probe the other endpoint after `BadDeviceToken`. Apple's [APNs response guidance](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns?language=_4) treats that error as nonretryable. Token pruning, the existing provider-token remint behavior and priority 10 remain unchanged. Production APNs is an Apple transport selection for an approved DEV-backed TestFlight build; it does not authorize access to Cleansia PRO resources.
5. Keep all registration ownership/status/tenant gates and lifecycle deletion predicates. The new metadata changes neither who may register nor which token is retired.

## Alternatives

- **One DEV global flip:** rejected because it trades TestFlight failure for Xcode sandbox failure.
- **Try the other endpoint after a definitive rejection:** rejected. A rejected first send avoids two successful deliveries, but still retries an error Apple tells providers not to retry, repeatedly guesses the environment and adds avoidable invalid-token traffic.
- **Encode environment inside the existing Token string:** rejected after comparing the no-schema benefit with its costs: a new versioned storage protocol, parsing/validation, reduced raw-token capacity and diagnostic ambiguity. Repurposing DeviceId is also rejected because retirement and shared-device protections join on that identity.
- **Typed nullable column:** selected. It represents an actual property of the recipient address, preserves raw-token semantics and makes legacy behavior explicit. Its deployment cost is real and is recorded below.

## Deployment consequence

This is a source schema change under the repository's single-Initial policy. Regenerate Initial using the normal EF commands and verify the emitted model with local real-Postgres integration tests. A future DEV deployment requires an explicitly approved DEV database reset/reseed because the Initial migration identifier changes. This decision authorizes no reset, deployment, environment edit, upload or PRO access. Existing client versions omit metadata and keep the prior global-default behavior; new routing support requires the new backend schema and app contract together.

## Verification

`RegisterLiveActivityTokenTests` pins explicit sandbox/production/null registration, rotation, legacy clearing and the existing caller ownership/status rules. `ApnsLiveActivityClientTests` pins explicit overrides, both legacy defaults and a single terminal BadDeviceToken send. `SendLiveActivityUpdateHandlerTests` pins recipients with mixed environments in one order without changing the shared payload. Existing erasure, shared-device retirement and terminal cleanup tests remain part of verification. `LiveActivityTokenModelMetadataTests` pins nullable metadata and the unchanged raw-token limit.

Mock transport acceptance is not physical-device delivery proof. Key support for both Apple environments and actual device receipt are separate rollout evidence. No timer reduction or instantaneous-delivery promise follows from this decision.

## Challenge

- **F2-A:** a source column imposes a future DEV reset cost and may exceed the current no-reset boundary.
- **F4:** a typed column preserves the existing raw-token contract more faithfully than an encoded Token envelope, but its deployment cost must be disclosed.
- **F5:** foreground recovery can recreate a dismissed card unless suppression is session/order-scoped and retired correctly.

## Defense

- **F2-A/F4:** the agreed functional scope includes necessary backend/API repairs; the no-reset boundary forbids executing that operation now. The design review explicitly weighed the future reset against a new token storage protocol and selected the column. The user did not select this mechanism; future reset approval remains outstanding.
- **F5:** the functional story requires dismissal suppression for local and server-adopted cards, scoped to session/order and cleared on terminal state/session wipe. Routing does not relax those lifecycle rules.

## Verdict

The design review selected typed nullable recipient metadata on 2026-10-28. Two independent rechecks found no surviving technical blocker after concrete retry, session, late-card-callback and dismissal boundaries were specified in `agents/analysts/mobile-functional-repairs.md`. Endpoint guessing and opaque-token storage are rejected. All external operations retain their existing approval boundaries.
