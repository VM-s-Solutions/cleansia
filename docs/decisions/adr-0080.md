# ADR-0080 — The order-status tint table lives in Core, keyed by the wire value

- **Status:** `proposed` — decided 2026-11-02. It moves to `accepted` when T-0910 ships the move, with a
  *What shipped* note wherever the tree departs from this record.
- **Date:** 2026-11-02
- **Owner:** Michael Chaban
- **Decided by:** Mike's approval of the partner Orders mock v2, 2026-11-02: *"OK, I like the designs and
  you can go with recommended"*. The approved design moves the status pill's table into Core. The
  keying, by the backend's integer rather than by a type, is the design review's of the same day.
- **Supersedes:** no record. **Changes** one documented rule, the doc comment on `OrderStatusTone`
  (quoted under Context).
- **Applies to:** CleansiaCore `OrderStatusMarks.swift`; the customer iOS `OrderStatusPresentation`; the
  partner iOS order pill; Android `:core` `orderStatusInk` / `orderStatusColor` / `OrderStatusPill` and
  their callers in both apps.
- **Ticket:** T-0910.

## Context

Both iOS apps draw an order's status with Core's `OrderStatusBadge(label:tint:tone:)`. Only the customer
app has the table that picks its tint and tone: `OrderStatusPresentation.color(_:)` / `.tone(_:)`
(`CleansiaCustomer/Sources/Features/Orders/OrderStatusPresentation.swift:25-46`), a switch on the
customer's generated `OrderStatus`. The partner app has had no pill since T-0907. Mock v2 restores one
with the **same** tints. The rule that keeps the table out of Core is
`CleansiaCore/Sources/CleansiaCore/Components/OrderStatusMarks.swift:5-7`:

> The two apps generate their own `OrderStatus` from their own API contract, so — exactly as
> `OrderTrackerRule` does — the mapping stays in each app and only the GROUP crosses into
> `CleansiaCore`.

Under that rule, the partner app writes a second seven-case copy of the customer's table, and nothing
compares the two copies. No checker reads a tint or ink table.
`agents/tools/check-available-status-parity.mjs` checks only the offerability literals of
[ADR-0037](./adr-0037). The rule's premise is also narrower than it reads. Both generated enums are
identity maps of the backend's integers: `case _0 = 0 … case _6 = 6` in
`CleansiaPartnerApi/Models/OrderStatus.swift:13-21` and `CleansiaCustomerApi/Models/OrderStatus.swift:13-21`
([ADR-0042](./adr-0042) §V.6). So the two apps already share one type, the integer.

Precedents:

- Core already keys a rule on that integer: `DisputeMessagePolicy.allowsMessages(statusValue: Int?)`
  (`CleansiaCore/…/Validation/DisputeMessagePolicy.swift:10`).
- Android already keys this same table on it: `orderStatusInk(statusValue: Int?, scheme)`
  (`customer-app/…/ui/format/OrderFormatters.kt:43-52`).

## Decision

1. **The iOS tint and tone table moves into CleansiaCore**, next to `OrderStatusBadge`, as
   `OrderStatusStyle.tint(wireValue: Int?) -> Color` and `OrderStatusStyle.tone(wireValue: Int?) ->
   OrderStatusTone`. It holds the customer's table verbatim:

   | Wire value | Tint | Tone |
   |---|---|---|
   | 0, 1 | `warningStar` | `.live` |
   | 2 | `primary` | `.live` |
   | 3, 4 | `secondary` | `.live` |
   | 5 | `successText` | `.done` |
   | 6 | `error` | `.failed` |
   | any other value, or nil | `outlineVariant` | `.unknown` |

2. **The rule, restated.** When both apps map an order status the same way, the mapping crosses into
   Core keyed by the backend's wire integer, never by a generated type. A mapping that differs between
   the apps stays in each app. Two such mappings are unchanged by this record:
   - the status-to-art mapping (`agents/knowledge/patterns-mobile.md:566-569`);
   - the tracker's step index (`OrderTrackerBar.swift:19-21`).
3. **An app passes the integer through its one mapper.** It hands over its typed status's `rawValue`
   (`code?.toOrderStatus()?.rawValue`) and never reads `Code.value` inline. The following rules stand
   unchanged:
   - the catalog's *"no raw-`Int` `.value` compares, no second mapper"*
     (`patterns-mobile.md:1564-1566`, `:1945-1948`);
   - the partner app's *"read it everywhere instead of inspecting `.value` inline"*
     (`CleansiaPartner/Sources/Data/OrderStatus+Code.swift:4-8`).
4. **Each app keeps its labels and decides which status to show.** Examples are the customer's
   `OrderStatusPresentation.label` and the partner's rule that a job she has not taken reads *New*.
   Core answers only one question: which tint and tone a status takes.
5. **Android:** `orderStatusInk(statusValue: Int?, scheme)`, `@Composable orderStatusColor` and the
   customer's 16 % `StatusPill` move to `:core` verbatim, the pill as `OrderStatusPill(label, ink)`.
   The eight inks are copied exactly. Customer call sites change only an import, and the partner app
   uses the `:core` pill. The table is already keyed by the integer, so Android needs no new rule.
6. **There is one table per platform, not one for both platforms.** The two platforms keep the
   difference they have today: iOS puts a tint behind an `onSurface` label with a mark, and Android puts
   a light or dark ink on the label itself
   ([mobile patterns](/mobile-app/patterns#brand-text-ink)). This record does not unify them.

## Consequences

- **The customer's pixels do not change.** `OrderStatusPresentation.color` and `.tone` delegate to Core
  and return the same value for every input:
  - values 0–6 map as before;
  - nil and an unknown status both reach Core's last row, just as both reached the old `nil` arm.

  The proof is customer captures of the order-detail header and timeline, taken before and after, light
  and dark.
- **The partner's pill reads Core** on both platforms. There is no partner copy left to drift.
- **A new backend status (wire 7) draws the neutral pill with no mark** in both apps until Core's table
  names it. That is one edit per platform, not two.
- **Core's table is a hand-written mirror of part of `OrderStatus.cs`**, as `DisputeMessagePolicy` is.
  A Core test over every value covers it, and no checker does. Nothing is added to a checker here.

## Alternatives considered

- **Keep a table in each app**, as the old rule says. The partner app gains a copy of the customer's
  table, which gives two copies on each platform of one fact that nothing compares. That is the drift
  that *"Put shared code in `:core`, never duplicate it across the two apps"*
  (`patterns-mobile.md:30`) exists to prevent. Rejected.
- **A partner style parameter on the shared pill**, so that each app passes its own look. That puts two
  looks inside Core, and the two apps' tints are identical anyway. Rejected.
- **A Core enum mirroring the seven statuses**, the shape of `SignupConsentType: Int`, which each app
  maps onto. It is a new type for one table and a second hand-written copy of the enum's members. The
  generated raw values already are the wire integers, and `Int?` matches Android's signature. Rejected.

## Verification

- `rg -n "enum OrderStatusStyle" src/cleansia_ios` prints one hit, under `CleansiaCore/`.
- `rg -n "fun orderStatusInk|fun OrderStatusPill" src/cleansia_android` prints one hit for each, under
  `core/`.
- In the customer app, `OrderStatusPresentation.color` and `.tone` are one-line delegations to Core. No
  partner file declares a switch from status to tint or tone.
- A CleansiaCore test pins every row of the table: 0–6, nil and 7, each against its tint and tone.
- On Android, the customer's `OrderStatusInkTest` runs against the `:core` function. A twin test in the
  partner app checks the same 4.5:1 floor over the partner app's schemes.
- The comment at `OrderStatusMarks.swift:5-7` states the new rule and points to `/decisions/adr-0080`.
