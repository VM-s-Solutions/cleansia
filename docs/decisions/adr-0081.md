# ADR-0081 — The profile says when an Apple account's stored name is the placeholder, read from the stored name on every request

- **Status:** `proposed` — decided 2026-11-08. It moves to `accepted` when the pull request that carries it
  leaves draft with T-0920's iOS half, with a *What shipped* note wherever the tree departs from this record.
- **Date:** 2026-11-08
- **Owner:** Michael Chaban
- **Decided by:** Mike's ruling of 2026-11-08, *"go"*, on the recommended pick *"Apple account with a hidden
  name: yes, show the name step"* (the what), and the design review of 2026-11-08 (the how).
- **Supersedes:** no record. It makes **one named exception** to [ADR-0048](./adr-0048) D1 rule 2, for this
  member alone (D5).
- **Applies to:** `User`, `MyProfileDto`, `UserMappers`, `AppleAuth`, both mobile specs and both NSwag clients;
  the iOS and Android profile mappers when they read the member.
- **Ticket:** T-0920.

> **One decision:** *the current-user profile carries `isNamePlaceholder`, `true` while an Apple account's
> stored name still carries a placeholder word the server wrote. It is computed from the stored row on every
> read. An app treats such a name as no name, gates nothing on it, and reads an absent member as `false`.*

---

## Context (citations at `b7c7e4237`)

**Apple sends the name once.** It arrives on the first authorisation only, and the person may clear either
part in Apple's sheet. The command carries the two parts as optional strings.

**The server never stores a blank part.** `UpdateCurrentUser` needs both names (`UpdateCurrentUser.cs:40-42`)
and `CreateOrder` a customer name of at least two characters (`CreateOrder.cs:143`), so a blank part would
leave the customer unable to save a profile or book. Each missing part comes from the verified e-mail's
local part or, when that gives none, from the placeholder pair `Cleansia` / `Customer`. An Apple relay
address (`privaterelay.appleid.com`) always gives none. The rule is `AppleAuth`'s `ResolveDisplayName` and
`DeriveNameFromEmail`, and the two words are `User.PlaceholderFirstName` and `User.PlaceholderLastName`.
→ [An Apple account's name](/flows/auth-and-identity#apple-account-name)

**Nothing records where a name came from.** `User` has no provenance column, provisioning declines its audit
row, and the profile save writes none. Its command cannot tell a typed name from a replayed one, and the
clients replay both names on every profile save, the session-start language update included.

**So the apps could not tell.** The iOS onboarding asks for a name only when a stored part is blank
(`ProfileViewModel.swift:147-150`), which provisioning never leaves, and the Android onboarding has no name
step. Both greet an Apple customer who hid her name with *Welcome aboard, Cleansia!*. Mike's pick of
2026-11-08 is that she is asked.

---

## Decision

1. **The member.** `MyProfileDto` gains `bool IsNamePlaceholder`, JSON `isNamePlaceholder`, appended last.
   It is served by `GET api/User/GetCurrent` on the four hosts that return the DTO: Customer web and mobile,
   Partner web and mobile. The admin host has no current-user read. `true` means the stored name is a
   stand-in the server wrote, not a name the person gave, so a client treats the **whole** stored name as no
   name. `false` means the stored name counts as given.
2. **Today's rule.** `true` when the account's `AuthenticationType` is `Apple` and its stored first name is
   `Cleansia` or its stored last name is `Customer`, compared by the identification rule that
   `ReplaceSystemGeneratedName` already uses: trimmed, ignoring case, and a blank part counts. It lives in one
   place, `User.IsNamePlaceholder()`, the second caller of that rule's private comparison. It is a method,
   not a property, so EF, serializers and reflection sweeps never see it. Google and password accounts are
   always `false`, so a password account named *Test Customer* is never asked.
3. **Computed on every read, stored nowhere.** `UserMappers.MapToMyProfileDto` calls the method, and the
   handler passes nothing in, so no caller can send a defaulted `false`.
   - A save of a name that carries neither word ends it on every device at once.
   - A save that replays the placeholder keeps it.
   - Apple's real name, arriving at a later sign-in, replaces the placeholder parts and ends it.
4. **A name built from the e-mail counts as given**, unless a placeholder word sits beside it.
   `jana.novakova@seznam.cz` stored as *Jana Novakova* reads `false`. `info@firma.cz` stored as
   *Info Customer* reads `true` for the whole name, so *Info* is never offered back as her first name.
5. **Absent reads as `false`, and a mobile mapper never refuses the profile over it.** This is the one
   exception to ADR-0048 D1 rule 2, *"Booleans follow the money rule"*, that this record makes, and it is
   for this member alone.
   - Only a server older than the member omits it, and `false` is exactly what every app did before it
     existed: no name step for a non-blank name, and the stored first name in the greeting.
   - Refusing would fail every profile read of a new app against an older server: a TestFlight build
     against a DEV that has not deployed the change, or a rollback.
   - The iOS mapper writes `?? false` and the Android one `?: false`. Each carries a comment that gives this
     reason and cites this record, the way `hasReview` does (`CustomerOrderSummary.swift:62-64`,
     `OrderApi.kt:185-187`). `isEmailConfirmed` and the names keep refusing.
6. **Only the customer apps' onboarding reads it**, to pick the step it opens on, to leave the name fields
   empty and to greet without a name. Nothing gates on it: whether the onboarding shows, booking, Edit
   profile and every web and partner screen do not read it. No app compares a name with `Cleansia` or
   `Customer` itself.

---

## Consequences

- **The placeholder words are read-side evidence too.** Changing `User.PlaceholderFirstName` or
  `User.PlaceholderLastName` makes every row written with the old word read as a real name, to the sign-in
  repair and to this member alike, so a change needs a data fix-up. The warning sits on the constants.
- **The partner hosts always send `false`.** They serve the same DTO, and no Apple account can sign in there.
- **The accepted limit.** A hidden-name Apple account whose e-mail gives two name-shaped pieces keeps the
  guess and is not asked. Usually the guess is her name without diacritics; sometimes it is not. How often
  this happens is unknown.
- **A customer who finished the old onboarding is not asked.** She has a phone, so the onboarding does not
  show again. Production does not exist, so this reaches DEV accounts only.
- **The upgrade path needs no client change.** The whole-name rule under Alternatives, or a stored marker,
  would change only what the server computes.
- **No schema change:** no column, no migration and no DEV database step.
- **Three mappers already default a boolean that a newer server added**, each with only an in-code reason:
  iOS and Android `hasReview`, and Android `trialEligible` (`MembershipApi.kt:131`). This record sanctions
  `isNamePlaceholder` alone and rules on none of them. A general carve-out from ADR-0048 D1 rule 2 is a
  separate decision.

---

## Alternatives considered

- **A stored marker, one column or two, set at provisioning.** Cleared on any save, it is wiped before she is
  ever asked, by the session-start language update and by a phone-only profile edit. Cleared on change, it
  does not loop and it would catch e-mail guesses. Its price is a regenerated `Initial` migration, a DEV
  database drop at the next deploy, the seed script's column list
  (`sql-scripts/insert_local_dev_admin.sql`), a backfill, and three writers kept in step: provisioning, the
  sign-in repair and the profile save. That is more than the agreed half day, for one gain this member can
  add later with no client change. Rejected for now.
- **Re-derive each part from the e-mail and compare.** It flags Apple's real name when one part equals an
  e-mail piece: Apple sends *Jana Nováková* for `jana.novakova@seznam.cz`, *Jana* equals the derived *Jana*,
  and she is asked for a name she gave. Rejected.
- **The whole name equals the two-piece guess, or a part is a placeholder word.** Apple sends *Petr Svoboda*
  for `petr.svoboda@gmail.com`, and he is asked for a name Apple gave. It also needs the derivation at read
  time. Rejected, and kept as the upgrade path: one server line, no client change.
- **Two booleans, one per part.** They would offer the guess *Info* back as a first name, where T-0920 wants
  both fields empty, to spare a person who gave half a name one retype. Rejected.
- **Each app compares the name with `Cleansia` and `Customer`.** It copies the server's identification words
  into every shipped build with no Apple guard, so every *Test Customer* password account is asked, and a
  rule change takes three releases. Rejected.
- **Blank names on the wire, or no placeholder stored.** Older iOS builds refuse a blank name and fail the
  whole profile (`UserProfileClient.swift:116-117`), and `CreateOrder` needs at least two characters.
  Rejected.
- **`bool?`, to fit ADR-0048 rule 5.** The server never sends null, and a nullable that is never null
  misleads every reader. Rejected.
- **Refuse an absent member, as ADR-0048 D1 rule 2 is written.** A new build against an older server would
  fail every profile read for every customer. Rejected; D5 is the exception instead.
- **The flag in the onboarding gate.** A customer who keeps the placeholder on purpose and has saved a phone
  would see the onboarding again on every new device or reinstall. Rejected; when the onboarding shows does
  not change.

## Challenge, defense and verdict

The design review wrote two drafts and tried each against the other. The first changed as little as
possible: no record, and the onboarding gate untouched. The second walked every sign-up path and every
person the rule reaches. Each challenge names a concrete case. *Stands* means it changed this record;
*rebutted* means it did not.

**Challenges to the first draft**

- **P1 — the absent default had no sanction.** Its client rule wrote `?? false`, which ADR-0048 D1 rule 2
  forbids, and it recorded a finding instead of an exception, so the iOS mapper would fail against the
  catalog when it is checked. **Stands:** this record makes the one-member exception (D5).
- **P2 — the Android pin's comment.** The captured payload is stated to carry every member non-default
  (`ProfileWireTest.kt:186`); updating only the property set would make that false. **Stands:** each payload
  gains `"isNamePlaceholder": true`.
- **P3 — a typed "customer".** She hid her name, types *Jana* and *customer* in Edit profile, and has no
  phone. On a new device the onboarding opens the name step empty, because the rule ignores case.
  **Rebutted:** asking once does no harm, and Skip ends it. Ignoring case is the identification rule's
  pinned property, and two comparisons for one piece of evidence could disagree on a drifted row.
- **P4 — no sequence test.** Nothing pins that a replayed save keeps the flag or a typed name ends it.
  **Rebutted:** the rule is a pure function of the stored row, and a replay leaves the same row. The theory
  pins every row shape, and the handler assertions pin the mapper's wiring.
- **P5 — a customer who finished the old onboarding.** She has a phone, so she is never asked. **Accepted as
  a limit:** this is DEV accounts only, and a fresh hidden-name account is asked (Consequences).

**Challenges to the second draft**

- **L1 — the flag in the onboarding gate.** It reopens the onboarding on every new device or reinstall for a
  customer who keeps the placeholder on purpose and has saved a phone. It also contradicts the draft's own
  "only onboarding reads it", and it changes a gate nobody asked to change. **Stands:** the gate is
  unchanged.
- **L2 — a property on an EF entity.** EF skips a get-only property, but a serializer or a reflection sweep
  over `User` sees it. **Stands:** it is a method.
- **L3 — an ordinal comparison.** It adds a second comparison for evidence the sign-in repair already
  compares trimmed and ignoring case, so the two could disagree on a drifted row. **Stands:** the method
  reuses `IsSystemGenerated`.
- **L4 — implementation details as decisions.** Moving the constants and appending the member last are code,
  not decisions. **Stands:** this record holds one decision, the contract and its exception; the details live
  in code and tests.
- **L5 — Skip saves a typed name.** That is a second, partial save. It goes against *Skip for now*, which
  already discards a typed phone, and against Save and continue waiting for a name and a valid phone.
  **Stands:** rejected, and Skip saves nothing, as today. Whether a name typed before Skip should survive is
  Mike's call, not this record's.
- **L6 — a sequence fact.** It restated the theory through `Update`. **Stands:** dropped; see P4.
- **L7 — a catalog edit.** Carving an exception out of the mobile catalog's boolean rule narrows a catalog
  law, which needs a named enforcer, and a test on one site cannot enforce a general carve-out.
  **Stands:** no catalog edit; this record sanctions this member alone.

**Both drafts.** Neither loops when her real name equals her e-mail guess and she types exactly that: the
flag never reads the derivation, and the step's done state is local to the screen. The stored marker was
tried again as *clear on change, never a gate*. It does not loop either, and it still loses on cost
(Alternatives).

**Verdict:** the decision above, `proposed`, grafted from both drafts. From the first: the domain method on
the existing comparison, the unchanged onboarding gate, the two provisioning assertions and the docs
section. From the second: this record with its one named exception, the Android payload line, the walk of
every sign-up path and the anchor name.
