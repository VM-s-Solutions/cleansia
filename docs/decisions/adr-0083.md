# ADR-0083 — An issued invoice or receipt PDF is never overwritten: every render is a new numbered file, the row points at the newest, and the earlier files stay as issued

- **Status:** `accepted` 2026-11-19
- **Date:** 2026-11-19
- **Owner:** Michael Chaban
- **Decided by:** Mike's ruling of 2026-11-19 on the phase-2 E2E report (`e2e/runs/2026-11-18/findings.md`,
  F-075): *a re-rendered invoice or receipt PDF keeps every version: each render writes a new file, the row
  points at the newest, older files stay as issued, nothing is overwritten.*
- **Supersedes:** no record.
- **Applies to:** backend (`DocumentVersions`, `RegenerateInvoicePdf`, the night run's invoice render,
  `ReceiptService`, the receipt retention sweep).
- **Tickets:** T-0937.

> **One decision:** *a payout invoice or a receipt is rendered under a stable first name and every later render
> of the same document is a new file numbered after it, `INV-2026-000017.pdf`, then `INV-2026-000017-2.pdf`,
> `-3` and so on. A render is created only under a name no file holds, the document's row points at the newest
> render in the same commit, and no render ever replaces or deletes an earlier one.*

---

## Context

**A second render of one document failed.** The blob client's `UploadAsync` is the storage SDK's create-only
upload, so a second write under one name is refused with 409 `BlobAlreadyExists`. Two paths render a document
more than once under a fixed name: `RegenerateInvoicePdf`, reached by Regenerate PDF, by the re-render after
Adjust amounts and by the repair of a night render whose stamp was lost; and the receipt's fiscal retry, which
renders the receipt again with its fiscal code. On DEV the first made `INV-2026-000017` read
`pdfGenerationFailed` (F-075). The second would leave a receipt stamped with a fiscal code whose PDF does not
print it.

**Overwriting was the other way to make the write succeed, and it was rejected.** A cleaner files the invoice
PDF they downloaded; a customer keeps the receipt they were e-mailed. Replacing either under the same address
changes a document somebody already holds.

---

## Decision

1. **Every render is a new file.** The first render takes the document's first name; each later one takes the
   first free name of `{name}-2.pdf`, `{name}-3.pdf` and so on (`DocumentVersions.UploadNewVersionAsync`).
2. **The store arbitrates each name.** A name is written with create-if-absent; when a file already holds it,
   the render moves to the next number. Two renders at once never land on one file, and a repair after a lost
   stamp finds the night's file taken and writes beside it.
3. **The row points at the newest render, in the same commit.** An invoice's `PdfBlobUrl` and a receipt's
   `BlobName` move to the new file; a download serves what the row names.
4. **Nothing deletes an earlier render.** The one deletion is the end of a receipt's retention period, and it
   removes every render of that receipt, newest first, so a sweep that stops half way leaves the earlier
   renders contiguous for the next run.
5. **`UploadAsync` stays create-only**, for blobs written once under a fresh name (photos, evidence,
   employee documents). A document rendered more than once under a stable name uses
   `UploadNewVersionAsync`.

---

## Consequences

- **The container holds every version.** An invoice adjusted twice has three files. They are small, and the
  count is bounded by how often an administrator re-renders; `UploadNewVersionAsync` refuses a render once a
  hundred versions exist rather than looping.
- **A render whose commit failed leaves an orphan file** that no row names. The next render takes the number
  after it, so the orphan is never overwritten and is removed with the receipt at retention.
- **The company archive copies the current render** of each invoice and receipt, the one its row names.
- **No schema change.** The rows already held the document's address.

---

## Alternatives considered

- **Overwrite on re-render.** Rejected by the ruling: it changes a document a cleaner or a customer already
  holds.
- **Azure blob versioning on the storage account.** It would keep every overwritten blob, but also every
  deleted photo and document, against erasure and retention. Rejected (T-0937 *Not doing*).
- **A timestamp or GUID in each render's name.** Unique without arbitration, but not readable and not ordered
  by the name. Rejected for the numbered name.

---

## Verification

- `InvoicePdfVersionsTests` renders an invoice twice, repairs a lost stamp, adjusts its amounts and downloads
  it, against a container that refuses a second write to one name as Azure does.
- `ReceiptPdfVersionsTests` retries a receipt's fiscal registration and downloads it the same way, and
  `ReceiptBlobRetentionSweepTests` removes every render at the end of retention.
