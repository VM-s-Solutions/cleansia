## Rules that make it compact — "bez vody"

- **The explanation of a fact lives in PROVOZ; a row anywhere states the fact itself** in ≤ 20 words with its citation and may add `→ PROVOZ §x` for the mechanism. A row whose fact cell is only a pointer fails review. Numbers are stated once, in A1; elsewhere the row cites A1.
- **Tables before prose.** Anything with more than two of the same shape (parties, tiers, windows, gaps, scenarios, decisions, events) is a table. A paragraph that only restates a table is deleted.
- **A cell is ≤ 40 words and ≤ 2 citations** (a claim that holds on several stacks cites each stack once, in one cell — that is the exception). A fact that needs more is two rows. No bold narrative, no parenthesis carrying a second claim. The checker fails any row over 40 words per cell.
- **No tense but the audited tree.** No date of when the code changed, anywhere in the four documents; „od 20. 9.", „nově", „dosud", „změněno", „trvá" are forbidden words. Change lives only in the AUDIT-LOG delta table.
- **No reading instructions beyond five lines**, no „tento dokument popisuje", no „jak bylo uvedeno", no history of the document itself.
- **One summary per document** (≤ 250 words) — the decisions and the numbers, not an abstract; in TECHNICKE the ten-row table is the summary.
- **Numbers, not adjectives.** „72 hodin před začátkem, 50 %" — never „krátce před, podstatná část".
- **Nothing about what the platform *should* do**, except inside a decision (`→ Rn`), phrased as a choice.
- If a budget cannot be met, the document is not done — cut, do not summarise.

## Rules that make it true

- **Ground truth is the tree at the audited commit**, read with Grep/Read/`git show <SHA>:<path>` — never `docs/`, never the old analysis, never a ticket. `docs/` is a secondary source to *find* code (`/decisions/` for why, `/domain/roles/` for the contracts, `/product/business-rules` for the numbers); the citation is the code line, never the page.
- **Citation form — one shape, a change from the 09-16 set, and the checker parses only it:** `[File.cs:123](../../src/…/File.cs#L123)` — label is the file name and line (or `:120-131`), the href is the repo-relative path with the `#L123` (or `#L120-L131`) anchor; the same shape for `sql-scripts/`, `deploy/`, `.github/`, `docs/` paths. Never the 09-16 `–[:39]` continuation form. A legal-draft claim: `[VOP P028](../analyza-2026-09-11/podklady/Cleansia_VOP.txt)` — the draft's abbreviation and the three-digit `Pxxx` (`P001`–`P241`; ranges `P156–P166`) in the label.
- **A negative claim** („no code writes `OrderStatus.Pending`") cites the declaration it is about and states the search in the same cell: `grep -rn "OrderStatus.Pending" src/ → 0 zápisů mimo deklaraci`. **A seed or placeholder fact** cites `sql-scripts/insert_seed_data.sql:<line>` (the `REPLACE WITH ACTUAL` comments beside the `CompanyInfo` IČO / DIČ values are there) or `src/Cleansia.Infra.Database/Seed/Legal/<path>:<line>`; DEV-only figures cite the seed or the configuration line.
- **A contradiction is a draft paragraph against a code line**, both quoted in the row. If you cannot find the paragraph, it is not a contradiction; if you cannot find the line, it is not a fact — and if a draft is silent, it is a §2 row.
- **State what has no producer or no reader** when a draft assumes it (an enum member no code writes, an endpoint no client calls) — that is a finding, cited per the negative-claim rule.
- **The citation checker** — `lawyers-docs/check-citations.py <folder> <SHA>`, written by you, committed in the PR — parses every link of the two shapes in the five documents. Scope of a citation = the table cell it sits in or, in prose, the sentence it closes; identifiers = backticked tokens and numeric literals in that scope. Checks: (1) the path exists at the SHA (`git show <SHA>:<path>`); (2) the line ≤ the file's length; (3) if the scope has at least one identifier, one of them occurs within lines L−3…L+3 — a scope with none passes on (1)+(2) and is counted separately as `bez identifikátoru`; (4) a P-link's file exists and contains a line starting `[Pxxx]`; (5) no cell over 40 words; (6) none of the forbidden tense words. Summary line: `N citací · M bez identifikátoru · 0 nevyřešených`. No document ships otherwise; the line goes into `AUDIT-LOG.md`.
- Nothing in these documents names the repository's rule files or any AI tool; the rule set is „projektová pravidla repozitáře". The owner is the author of record.

## Method — lanes, adversarially, with the hand-offs written down

Do not read the whole tree from one context. Run every lane with the `Agent` tool (`analyst` for readers, writers and the lawyer-reader challenger; `reviewer` for the claim-vs-code challenger); if a workflow harness is present, use it the same way. **A lane cannot spawn a lane** — every hand-off is a file. Notes live in the scratchpad at `notes/<domain>.md`: one file per reader, H2 = claim group, body lines of the shape `- <tvrzení> — [File.cs:123](…)` only, no prose. The skeleton and the decision register live at `notes/00-skeleton.md`.

1. **Inventory** (one lane): the counts for `AUDIT-LOG.md`, pinned at the SHA.
2. **Readers** (parallel, one per domain, notes only): identity, consent, GDPR and the seeded legal texts · booking, pricing, markets and currencies · payments, receipts, fiscalisation, refunds, disputes, chargebacks · cleaners: onboarding, documents, offerability, taking, pay periods, invoices, cash · memberships, loyalty, referrals, notifications (the §10 events) · tenancy, admin roles, archive, retention, background jobs and Functions · the ten legal drafts (paragraph-numbered claims the code must answer, from the 09-11 extracts) · the delta `7acea58b..<SHA>` from `git log`, verified in the tree · **decision carry-forward** — reads ONLY the decision lists of the 09-16 set (ROZPORY §3 R1–R11, OBCHODNI §9, the Q-WC questions) and returns each with its status verified in the tree: open / ruled (ADR, commit) / moot (why).
3. **Skeleton** (you, from the notes): the numbered H2/H3 outline of PROVOZ and the decision register `R1…Rn` (id + title + one line), written to `notes/00-skeleton.md` before any writer starts. Writers point at those ids only.
4. **Writers** (parallel, one per document, from the notes and the skeleton, with their 09-16 counterpart for shape only): to budget, cited. A writer that needs a fact the notes lack does not guess: it ends its output with a `## Chybí` list (claim + which reader owns it). You spawn that reader for the listed facts, append the answers to the notes file, re-run the writer. A claim still missing after the second pass is dropped and reported.
5. **Challengers** (two per document, parallel, read-only, code open): *claim-vs-code* tries to refute every cited claim by reading the cited lines at the SHA; *lawyer-reader* asks what is not a fact, a paragraph, a citation or a decision, what is said twice, what number is missing, what cell is over 40 words, what is over budget. Serious findings → one fixer per document → the checker → render.
6. **You** run the checker and the render, read the five PDFs (the Read tool renders them page by page), and report: the word counts against budgets, the checker's summary line, what the challengers found and what was cut, and every finding about the code the audit surfaced and that you did **not** fix — this is a documentation task; no code, migration, seed or setting changes, whatever you find. Findings go on `agents/OWNER-PLATE.md` under a new heading `### Findings from the lawyer audit <date>`, the existing four columns, ids continuing from the last `F` on the page, in the same PR.
